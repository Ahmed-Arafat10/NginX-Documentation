# 1. Why Was NGINX Developed?

NGINX was developed by **Igor Sysoev**, a Russian developer.

According to the lecture, the primary motivation behind NGINX was to solve the **10K concurrent problem**.

At the time, Igor Sysoev was working with **Apache** and encountered difficulties handling a very large number of concurrent requests.

This led to the development of a new application designed to efficiently handle large numbers of simultaneous connections.

---

# 2. Understanding the 10K Concurrent Problem

The **10K concurrent problem** refers to a situation where a web server receives approximately **10,000 concurrent requests at the same time**.

Consider a normal website request:

1. A user opens a website.
2. The user accesses a URL.
3. The URL request is sent to a web server.
4. The web server processes the request.
5. The web server returns the response.

Now imagine that **10,000 users access the same URL simultaneously**.

Conceptually:

```text
10,000 users
     |
     | 10,000 concurrent requests
     v
+----------------+
|   Web Server   |
+----------------+
```

The server must process a very large number of requests concurrently.

The lecture describes this as the **10K concurrent problem**.

According to the lecture, Apache was unable to efficiently handle this large number of concurrent requests in the situation being discussed. This became one of the motivations for developing NGINX.

# 8. NGINX as a Reverse Proxy

NGINX is commonly used as a **reverse proxy**.

A reverse proxy sits between clients and backend or upstream servers.

For example:

```text
Client
  |
  v
+----------------+
|     NGINX      |
| Reverse Proxy  |
+----------------+
       |
       +----------> Upstream Server 1
       |
       +----------> Upstream Server 2
       |
       +----------> Upstream Server 3
```

The lecture explains that NGINX can connect to upstream servers and distribute incoming traffic among them.

The upstream servers can exist:

- On the same machine.
- On different machines.

The course will later demonstrate how NGINX connects to upstream servers and distributes the load between them.

# 9. NGINX as a Software Load Balancer

NGINX can operate as a **software-based load balancer**.

This provides an alternative to dedicated hardware load-balancing solutions.

## Hardware vs. Software Load Balancing

The lecture explains that hardware load balancers can be expensive.

With NGINX, the load balancer can be implemented in software.

The basic process is:

1. Install NGINX.
2. Configure NGINX.
3. Tune the configuration according to requirements.
4. Use NGINX to serve and distribute traffic.

Conceptually:

```text
                 Clients
                    |
                    v
              +-----------+
              |   NGINX   |
              |   Load    |
              |  Balancer |
              +-----------+
                 /  |  \
                /   |   \
               v    v    v
             App1  App2  App3
```

The lecture emphasizes that because NGINX is software-based, it can be highly configurable.

# 13. Docker-Friendly Technology

Another advantage highlighted in the lecture is that NGINX is **Docker-friendly**.

NGINX can be deployed directly inside a Docker container.

The lecture explains that an official NGINX image is available through **Docker Hub**.

A basic conceptual workflow is:

```text
Docker Hub
    |
    v
NGINX Image
    |
    v
Download Image
    |
    v
Run Docker Container
    |
    v
Configure NGINX
```

The NGINX image can also be used as a **base image** for creating a customized Docker image.

For example:

```dockerfile
FROM nginx

# Add custom NGINX configuration
# Add application-specific files
# Configure required settings
```

The lecture's main point is that the Dockerized version of NGINX can be used as a stable and reliable component in containerized environments.

# Key Concepts

### 10K Concurrent Problem

The challenge of handling approximately 10,000 simultaneous requests against a server.

### Reverse Proxy

An intermediary server that receives client requests and forwards them to backend/upstream servers.

### Upstream Server

A backend server to which NGINX forwards client requests.

### Load Balancer

A component that distributes incoming traffic among multiple backend servers.

### Software Load Balancer

A load balancer implemented in software rather than dedicated hardware. NGINX can fulfill this role.

### NGINX Plus

The commercial version of NGINX, as distinguished from the open-source NGINX version in the lecture.

### Dockerized NGINX

NGINX deployed inside a Docker container, typically using an NGINX image as the starting point for the deployment.
