# 39. Enable Secure Connection with HTTPS

## Overview

This lecture explains how to enable **SSL/TLS-based HTTPS** on an NGINX web server and switch a website from an unsecured HTTP connection to a secure HTTPS connection.

The lecture covers:

- What SSL is and why it is needed.
- How SSL and HTTP combine to provide HTTPS.
- How the SSL handshake establishes a secure connection.
- The roles of the **public key, private key, and session key**.
- How to generate a self-signed SSL certificate using OpenSSL.
- How to configure the NGINX server to use the certificate.
- Why HTTPS uses **port 443** instead of HTTP's port 80.
- How to test HTTPS in a browser.
- Why self-signed certificates generate browser security warnings.

# Key Concepts

## 1. What Is SSL?

**SSL (Secure Sockets Layer)** is described in the lecture as a standard security technology for establishing an encrypted link between a client and a server.

Examples of client/server communication include:

- A web browser communicating with a web server.
- A mail client communicating with a mail server.
- An application communicating with an application server.

In the NGINX client-server model, SSL provides a mechanism for establishing **secure communication between the client and server**.

SSL allows sensitive information such as:

- Credit card numbers
- Social security numbers
- Login credentials

to be transmitted securely.

### Why Encryption Is Necessary

Without encryption, data transmitted between a browser and a web server may be sent as **plain text**.

If an attacker intercepts this traffic, they may be able to read the information being transmitted.

SSL protects the communication by encrypting the transmitted data.

---

# 2. SSL as a Security Protocol

SSL is a security protocol that defines how encryption algorithms are used to protect communication between the client and server.

It determines the encryption mechanisms used for:

- The communication link.
- The data transmitted over that link.

In other words, data transmitted using SSL is encrypted so that unauthorized parties cannot simply read the intercepted information.

---

# 3. HTTP + SSL = HTTPS

SSL can be combined with HTTP to create **HTTPS**.

Conceptually:

```text
HTTP + SSL = HTTPS
```

HTTPS is a secure protocol that uses SSL-based encryption to protect data exchanged between the browser and server.

Therefore, when a URL uses:

```text
https://
```

instead of:

```text
http://
```

the connection is intended to be secured using SSL/TLS.

> **Note:** The lecture uses the term SSL throughout. Modern HTTPS deployments generally use **TLS (Transport Layer Security)**, which is the successor to SSL.

---

# 4. Browser and Server SSL Support

Modern web browsers support secure communication with web servers using SSL/TLS.

The lecture notes that HTTPS has become the standard for websites.

When a website continues to use plain HTTP, modern browsers may display a warning indicating that the connection is **not secure**.

To establish a secure connection, both the browser and server need to participate in the SSL/TLS process, with the server configured with an appropriate certificate and private key.

---

# How the SSL Handshake Works

When a browser accesses a website secured with SSL, the browser and server establish a secure connection through a process called the **SSL handshake**.

The handshake happens automatically and is generally invisible to the user.

The lecture describes three important keys involved in establishing the connection:

1. **Public key**
2. **Private key**
3. **Symmetric session key**

---

## Public and Private Keys

The public and private keys form a key pair.

The lecture explains the relationship as:

- Data encrypted with the public key can be decrypted with the corresponding private key.
- The public/private key combination is used during the secure connection establishment process.

However, asymmetric encryption using public/private keys requires significant processing power.

Therefore, these keys are primarily used during the handshake to establish a **symmetric session key**.

---

## Symmetric Session Key

After the secure connection is established, the session key is used to encrypt the actual transmitted data.

This is more efficient than using public/private-key encryption for every piece of application data.

The overall concept is:

```text
Public/Private Key
        │
        ▼
SSL Handshake
        │
        ▼
Symmetric Session Key
        │
        ▼
Encrypted Data Transfer
```

---

# SSL Handshake — Step by Step

The lecture describes the process using a sequence of requests and responses.

## Step 1 — Browser Connects to the Server

The browser attempts to connect to a website secured with SSL.

The browser requests that the server identify itself.

---

## Step 2 — Server Sends Its Certificate

The server sends a copy of its SSL certificate to the browser.

The certificate includes the server's public key.

Conceptually:

```text
Browser
   │
   │ Request server identity
   ▼
Server
   │
   │ SSL Certificate + Public Key
   ▼
Browser
```

---

## Step 3 — Browser Validates the Certificate

The browser checks the server certificate.

Among other things, the browser checks whether the certificate is:

- Valid.
- Unexpired.
- Not revoked.

If the certificate passes validation, the browser creates a symmetric session key.

The browser then sends the session key encrypted using the server's public key.

---

## Step 4 — Server Decrypts the Session Key

The server uses its private key to decrypt the symmetric session key.

The server then sends an acknowledgement encrypted using the session key.

This indicates that the encrypted session can begin.

---

## Step 5 — Secure Session Is Established

A symmetric encrypted session is now established between the browser and server.

From this point onward, the session key is used to protect the transmitted data.

The complete simplified flow is:

```text
Browser
   │
   │ 1. Request server identity
   ▼
Server
   │
   │ 2. Certificate + Public Key
   ▼
Browser
   │
   │ 3. Validate certificate
   │    Create session key
   │    Encrypt session key with public key
   ▼
Server
   │
   │ 4. Decrypt session key with private key
   │    Send encrypted acknowledgement
   ▼
Browser
   │
   │ 5. Secure session established
   ▼
Encrypted communication
```

# Lab: Enable HTTPS on NGINX

# Step 3 — Create an SSL Directory

Create a directory for the SSL certificate and key.

The lecture uses a directory named `ssl`:

```bash
mkdir -p ssl
```

The exact directory name is not mandatory. The instructor chooses `ssl` for simplicity.

The resulting directory is:

```text
/etc/nginx/ssl
```

---

# Step 4 — Generate the SSL Certificate

The lecture uses **OpenSSL** to generate the SSL certificate and key.

The command uses:

- `req` — certificate request functionality.
- `-x509` — generate an X.509 certificate.
- An expiration period of **100 days**.
- A new RSA key.
- A **2048-bit** key size.
- `-keyout` — specify where the private key should be saved.
- `-out` — specify where the certificate should be saved.

The intended command is:

```bash
openssl req -x509 -days 100 -newkey rsa:2048 \
  -keyout /etc/nginx/ssl/self.key \
  -out /etc/nginx/ssl/self.cert
```

The generated files are:

```text
/etc/nginx/ssl/self.key
/etc/nginx/ssl/self.cert
```

### Important

The lecture refers to the generated certificate as a **self-created/self-signed certificate** for testing purposes.

This is suitable for a lab environment, but it is not equivalent to a certificate issued by a trusted public Certificate Authority (CA).

# Step 7 — Configure NGINX for HTTPS

Next, modify the NGINX configuration.

Open:

```text
/etc/nginx/nginx.conf
```

The instructor simplifies the configuration for the demonstration by removing previously configured CGI processes and unnecessary `location` blocks.

This simplification is only for teaching purposes. You **do not need to remove existing configuration from your own NGINX configuration** if those settings are required by your application.

---

# Step 8 — Change the Listening Port

HTTP normally listens on:

```text
80
```

HTTPS normally listens on:

```text
443
```

Therefore, change the NGINX `listen` directive from port `80` to port `443`.

For example:

```nginx
server {
    listen 443 ssl;

    ...
}
```

The `ssl` parameter indicates that this server block handles SSL/TLS traffic.

---

# Step 9 — Configure the SSL Certificate

NGINX needs to know the location of the certificate.

Use:

```nginx
ssl_certificate /etc/nginx/ssl/self.cert;
```

The certificate path must match the location where the certificate was created.

---

# Step 10 — Configure the Private Key

NGINX also needs access to the corresponding private key.

Use:

```nginx
ssl_certificate_key /etc/nginx/ssl/self.key;
```

The basic HTTPS server configuration therefore looks like:

```nginx
server {
    listen 443 ssl;

    ssl_certificate /etc/nginx/ssl/self.cert;
    ssl_certificate_key /etc/nginx/ssl/self.key;

    # Other server configuration...
}
```

### Configuration Paths

The paths shown above are examples from the lecture.

In your own environment:

- The certificate location may be different.
- The key location may be different.
- The certificate filename may be different.
- The key filename may be different.

Therefore, configure these directives according to the actual files you generated.

# Complete NGINX HTTPS Configuration

A simplified configuration based on the lecture is:

```nginx
server {
    listen 443 ssl;

    ssl_certificate /etc/nginx/ssl/self.cert;
    ssl_certificate_key /etc/nginx/ssl/self.key;

    # Website configuration
}
```

The important directives are:

| Directive | Purpose |
|---|---|
| `listen 443 ssl;` | Makes the server listen for HTTPS traffic on port 443 |
| `ssl_certificate` | Specifies the SSL certificate |
| `ssl_certificate_key` | Specifies the corresponding private key |

# Practical Notes / Best Practices

### 1. HTTPS uses port 443

The lecture distinguishes the default ports:

```text
HTTP  → 80
HTTPS → 443
```

If NGINX is configured only for port `443`, requests sent to port `80` will not reach that HTTPS server block.

### 2. Self-signed certificates are mainly useful for testing

The certificate generated in this lab is a custom/self-signed certificate.

Therefore, browsers do not automatically trust it.

For a production website, use a certificate issued by a trusted Certificate Authority.

### 3. Certificate and key paths must match

Make sure the paths configured in NGINX correspond to the actual generated files:

```nginx
ssl_certificate /path/to/certificate;
ssl_certificate_key /path/to/private-key;
```

### 4. Do not confuse the private key with the certificate

The two files serve different purposes:

```text
self.cert → Certificate
self.key  → Private key
```

The private key should be protected and should not be publicly exposed.

# Common Mistakes / Warnings

## HTTP URL Still Being Used

If you continue accessing:

```text
http://example.com
```

you are still attempting to use HTTP.

After configuring the server for HTTPS, use:

```text
https://example.com
```

---

## Browser Says "Connection Is Not Private"

This is expected when using the self-signed certificate generated in the lab.

It does **not necessarily mean the NGINX SSL configuration failed**.

The certificate is simply not trusted by the browser.

---

## HTTPS Works but Browser Shows a Warning

There are two separate concepts:

1. **Encryption is working.**
2. **The certificate is trusted.**

A self-signed certificate can establish an encrypted connection while still producing a browser trust warning.

For production use, a trusted CA-issued certificate should be used.

---

## Wrong Certificate or Key Path

If these directives point to incorrect files:

```nginx
ssl_certificate /etc/nginx/ssl/self.cert;
ssl_certificate_key /etc/nginx/ssl/self.key;
```

NGINX will not be able to correctly establish the SSL configuration.

Verify that the files exist and that NGINX can access them.
