# 1. HTTP Protocol History

HTTP was originally designed by **Tim Berners-Lee**, the pioneer of the World Wide Web, with simplicity in mind for
performing high-level data communication between web clients and servers.

The lecture describes the evolution of HTTP as follows:

| Version  | Year | Description                                                   |
|----------|-----:|---------------------------------------------------------------|
| HTTP/0.9 | 1991 | First documented version                                      |
| HTTP/1.0 | 1996 | Official introduction of HTTP                                 |
| HTTP/1.1 | 1997 | Became the dominant HTTP version                              |
| HTTP/2   | 2015 | Second major version developed by the IETF HTTP working group |

HTTP/1.1 received relatively few iterative improvements after its introduction in 1997.

In February 2015, the **Internet Engineering Task Force (IETF)** HTTP working group developed HTTP/2 as the next major
version of the protocol.

---

# 2. Why HTTP/2?

The primary motivation for HTTP/2 is to overcome important limitations of HTTP/1.1.

## HTTP/1.1 and Multiple TCP Connections

The lecture describes HTTP/1.1 as being limited to processing one outstanding request per TCP connection.

As a result, when a browser needs many resources from a website, it may establish multiple TCP connections so that
resources can be requested simultaneously.

For example, suppose a website requires:

- 1 HTML file
- 1 CSS file
- 1 PNG image
- 2 JavaScript files

That is five resources.

With the HTTP/1.1 model described in the lecture, the browser sends multiple requests:

```text
Browser
   │
   ├── Request → HTML
   ├── Request → CSS
   ├── Request → PNG
   ├── Request → JS
   └── Request → JS
```

The server then sends the corresponding resources back.

---

# 3. Problems with Multiple TCP Connections

Using many TCP connections in parallel introduces several problems.

## Network Resource Consumption

Multiple connections can lead to **TCP congestion** and greater utilization of network resources.

Browsers using multiple connections can consume a larger share of available network resources, potentially reducing
network performance for other users.

The lecture identifies drawbacks from both:

- The **network side**.
- The **server/application side**.

---

## Data Duplication and Transmission Overhead

Multiple requests and responses can introduce additional transmission overhead.

The lecture explains that this led the industry to develop techniques intended to work around HTTP/1.1's limitations,
including:

- Domain sharding.
- Concatenation.
- Data inlining.
- Spriting.

These techniques attempted to reduce the number of separate resources and connections required by a web application.

---

# 4. Poor Resource Prioritization

The inefficient use of TCP connections in HTTP/1.1 can also lead to poor resource prioritization.

As web applications become more complex and include more functionality and resources, these limitations can cause
increasingly poor performance.

Modern websites may require large numbers of:

- HTML resources.
- CSS files.
- JavaScript files.
- Images.
- Other application resources.

Therefore, a protocol that can handle multiple resources more efficiently is beneficial.

---

# HTTP/1.1 Example

Consider a website containing **100 resources**.

The browser may need to issue 100 requests, and the server needs to provide 100 responses.

Conceptually:

```text
Browser
   │
   ├── Request 1  → Resource 1
   ├── Request 2  → Resource 2
   ├── Request 3  → Resource 3
   ├── ...
   └── Request 100 → Resource 100
                       │
                       ▼
                    Server
```

Each response carries the corresponding resource.

This becomes inefficient as the number of resources increases.

---

# 5. HTTP/2 Multiplexed Streams

One of the major features of HTTP/2 is **multiplexing**.

HTTP/2 creates multiplexed streams that allow multiple streams of data to be exchanged over a single TCP connection.

The lecture describes a stream as a bidirectional sequence of frames exchanged between the client and server.

Instead of requiring a separate TCP connection for each resource, HTTP/2 can use:

```text
                  Single TCP Connection
                         │
        ┌────────────────┼────────────────┐
        │                │                │
     Stream 1          Stream 2         Stream 3
        │                │                │
      Data             Data             Data
```

This is one of the fundamental differences between the HTTP/1.1 approach discussed in the lecture and HTTP/2.

---

# 6. HTTP/2 Frames

HTTP/2 does not simply send a complete large HTTP payload as one unit.

Instead, the server can break the payload into smaller, independent and manageable **frames**.

These frames can then be interleaved across multiple streams.

Conceptually:

```text
Stream A → Frame A1
Stream B → Frame B1
Stream A → Frame A2
Stream C → Frame C1
Stream B → Frame B2
Stream A → Frame A3
```

The frames are transmitted over the same TCP connection and are reassembled at the receiving side.

This allows multiple streams to make progress concurrently.

---

# 7. Binary Protocol

Another important HTTP/2 feature is its use of a **binary framing layer**.

HTTP/1.1 uses textual commands and textual representations for its protocol communication.

HTTP/2 instead uses binary frames.

```text
HTTP/1.1
Text-based protocol communication

HTTP/2
Binary protocol communication
```

The binary format allows HTTP/2 to create and transmit multiple small frames efficiently.

At the client side, the received binary frames are processed and reconstructed into the required application-level
content.

---

# 8. Multiplexing Over a Single TCP Connection

The lecture emphasizes that HTTP/2 can transmit multiple streams through a single TCP connection.

Instead of:

```text
HTTP/1.1

TCP Connection 1 → Resource 1
TCP Connection 2 → Resource 2
TCP Connection 3 → Resource 3
TCP Connection 4 → Resource 4
```

HTTP/2 uses:

```text
HTTP/2

                 One TCP Connection
                        │
          ┌─────────────┼─────────────┐
          │             │             │
       Stream 1      Stream 2      Stream 3
          │             │             │
       Frames         Frames        Frames
```

The frames from the different streams can be interleaved and then reassembled by the client.

This reduces the need for many parallel TCP connections.

---

# 9. HTTP/2 Server Push

Another feature discussed in the lecture is **HTTP/2 Server Push**.

Server Push allows a server to send additional cacheable resources to the client even though those resources have not
explicitly been requested yet.

The idea is that the server can anticipate what the client will need next.

---

## Server Push Example

Suppose the browser requests:

```text
index.html
```

The HTML document references:

```text
style.css
image.png
```

Normally, the browser would first request the HTML and then discover the CSS and image references before requesting
those resources.

With HTTP/2 Server Push, the server can anticipate that these resources will be required.

Conceptually:

```text
Browser → Server:
    Request index.html

Server → Browser:
    index.html
    style.css
    image.png
```

The browser did not explicitly request the CSS or image yet.

The server sends them because they are referenced by the HTML and are anticipated to be needed.

---

# 10. Benefit of Server Push

Server Push can reduce the number of request/response round trips.

Instead of:

```text
Request HTML
     ↓
Receive HTML
     ↓
Discover CSS
     ↓
Request CSS
     ↓
Receive CSS
     ↓
Discover Image
     ↓
Request Image
```

the server can proactively provide related resources.

This can reduce **network latency** and improve page-loading performance.

The lecture describes this ability to prioritize and push resources as an important performance differentiator between
HTTP/2 and HTTP/1.

---

# 11. Binary Data and Network Efficiency

Because HTTP/2 uses binary frames, it can divide data into smaller chunks and transmit those chunks through multiple
streams over the same TCP connection.

The lecture highlights the network-efficiency benefits of this approach:

- Smaller data chunks can be transmitted.
- Multiple streams can operate concurrently.
- Multiple streams share one TCP connection.
- The client reassembles the received frames.

This can make better use of the underlying network.

---

# 12. Security Considerations Mentioned in the Lecture

The lecture also associates HTTP/2's binary framing approach with eliminating certain security concerns associated with
textual HTTP/1.x processing, mentioning **response splitting attacks** as an example.

The lecture's explanation is that when complete textual responses are transmitted, manipulation of response data can
create security concerns. HTTP/2's binary framing changes how protocol data is represented and transmitted.

> **Important:** This should not be interpreted as HTTP/2 automatically making an application secure. Application
> security still depends on proper HTTPS/TLS configuration, input handling, authentication, authorization, and other
> security controls.

# 13. Stateful Header Compression

Another major HTTP/2 feature covered in the lecture is **header compression**.

The lecture refers to the **HPACK** specification.

> The transcript repeatedly transcribes this as "HPEC"; the intended HTTP/2 header compression mechanism is **HPACK**.

HTTP is fundamentally stateless. Each request needs to contain the information required by the server to process that
request.

As a result, successive requests can contain many repetitive headers.

For example, a browser may repeatedly send similar header information across many requests.

Sending these redundant headers increases:

- Network traffic.
- Request size.
- Bandwidth consumption.
- Latency.

HTTP/2 addresses this through HPACK header compression.

---

# 14. How HPACK Header Compression Works

The lecture explains that both the client and server maintain information about previously transmitted header values.

Instead of repeatedly transmitting the complete header information, subsequent requests can reference information that
has already been transmitted.

Conceptually:

```text
First request:

Client → Server
Full Header Information
        │
        ▼
Header information stored/indexed
```

A later request can then use compressed/reference information:

```text
Later request:

Client → Server
Compressed Header Reference
        │
        ▼
Server looks up previous header information
        │
        ▼
Full Header reconstructed
```

The basic idea is:

1. Header values are compressed.
2. Previously transmitted header information is maintained.
3. Subsequent requests can reference existing header information.
4. The receiving side reconstructs the complete headers.

This reduces repetitive data transmitted over the network.

# 15. Web Performance

The lecture presents HTTP/2 as a significant improvement for web performance.

HTTP/2 can improve performance through several mechanisms:

- Multiplexed streams.
- A single TCP connection for multiple streams.
- Binary framing.
- Server Push.
- Header compression.
- Reduced redundant data transmission.
- Better network utilization.

The instructor specifically recommends considering HTTP/2 for **high-traffic websites** because of its performance
benefits.

# 16. Mobile Web Performance

The lecture also highlights mobile web performance.

Mobile devices may have more limited:

- RAM.
- Processing resources.
- Network resources.

At the same time, users expect websites to load quickly.

HTTP/2 can help improve the efficiency of web communication, which can contribute to better mobile web performance.

# 17. Bandwidth and Internet Cost

The lecture associates HTTP/2's more efficient data transmission with reduced bandwidth consumption.

By:

- Compressing headers.
- Avoiding unnecessary repeated header data.
- Multiplexing streams.
- Efficiently transmitting frames.

HTTP/2 can make more efficient use of network bandwidth.

The lecture therefore connects HTTP/2 with the potential for more economical use of Internet connections.

# 18. Media-Rich Web Experiences

Modern websites can contain substantial amounts of:

- Images.
- JavaScript.
- CSS.
- Other media.
- Dynamic application resources.

HTTP/2's multiplexing and efficient binary framing can help applications deliver these resources more efficiently.

The lecture describes this as particularly useful for **media-rich experiences** and increasingly complex web
applications.

# 19. Improved Technology Utilization

The combined HTTP/2 features can improve utilization of the underlying network and processing infrastructure.

Instead of establishing many connections and repeatedly transmitting redundant information, HTTP/2 can use:

```text
One TCP connection
        │
        ├── Stream 1
        ├── Stream 2
        ├── Stream 3
        ├── Stream 4
        └── Stream N
```

with each stream carrying frames of application data.

# HTTP/1.1 vs HTTP/2

| Area                    | HTTP/1.1                                | HTTP/2                                      |
|-------------------------|-----------------------------------------|---------------------------------------------|
| Protocol representation | Text-based                              | Binary framing                              |
| Multiple resources      | Often requires multiple connections     | Multiplexed streams over one TCP connection |
| Streams                 | Limited compared with HTTP/2            | Multiple concurrent streams                 |
| Data transmission       | Textual HTTP messages                   | Binary frames                               |
| Header handling         | Repetitive headers                      | HPACK compression                           |
| Server Push             | Not available as described              | Supported                                   |
| Resource delivery       | More request/response overhead          | Can multiplex resources                     |
| Network utilization     | Less efficient for resource-heavy sites | More efficient                              |
| Performance             | Can degrade as resource count increases | Designed to improve performance             |

# Key Takeaways

1. **HTTP/1.1 has limitations when handling websites containing many resources.**
2. HTTP/1.1 can require browsers to use multiple TCP connections to process multiple resources concurrently.
3. HTTP/2 introduces **multiplexed streams**.
4. Multiple streams can share a **single TCP connection**.
5. HTTP/2 breaks data into smaller **binary frames**.
6. These frames can be interleaved and reconstructed at the receiving side.
7. **Server Push** allows the server to proactively send anticipated resources.
8. **HPACK** reduces redundant HTTP header transmission.
9. HTTP/2 can improve web and mobile performance and network efficiency.
10. HTTP/2 is particularly useful for complex, resource-heavy, and high-traffic websites.
