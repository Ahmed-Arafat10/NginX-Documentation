# 42. Prevent DoS Attack or Limit the Service

## Overview

This lecture explains how to use the **NGINX rate-limiting feature** to control the number of HTTP requests a client can
make during a specified period.

Rate limiting can help protect an NGINX server from:

- Excessive request traffic.
- Denial-of-Service (DoS) attacks.
- Brute-force password-guessing attempts.
- Malicious clients generating very large numbers of requests.
- Resource exhaustion that can cause server degradation or downtime.

---

# 1. What Is Rate Limiting?

**Rate limiting** in NGINX restricts the number of HTTP requests a client can make within a particular period.

For example, suppose a resource should not be accessed more than **10 times within a specified period** by a particular
client.

A rate limit can be configured so that requests exceeding the allowed rate are rejected or queued according to the
configured behavior.

Conceptually:

```text
Allowed rate:
1 request / second

Incoming requests:
1 → Allowed
2 → Limited
3 → Limited
4 → Limited
...
```

Rate limiting is one of NGINX's useful mechanisms for controlling request traffic.

---

# 2. Rate Limiting and DoS Attacks

A malicious user can send a very large number of requests to an NGINX server.

For example:

```text
Malicious Client
       │
       ├── Request
       ├── Request
       ├── Request
       ├── Request
       ├── ...
       └── Millions of requests
                │
                ▼
             NGINX
```

If rate limiting is not applied, excessive requests can consume server resources.

Potential consequences include:

- High CPU utilization.
- Increased memory consumption.
- Server slowdown.
- Requests taking longer to complete.
- Server becoming unresponsive.
- Production downtime.

The lecture therefore presents rate limiting as one mechanism that can help protect production servers from excessive
request traffic.

> **Important:** NGINX rate limiting is a mitigation mechanism; it does not by itself provide complete protection
> against large-scale distributed DDoS attacks.

---

# 3. Rate Limiting for Brute-Force Protection

Rate limiting can also be used to slow down **brute-force password-guessing attacks**.

For example, if a login endpoint normally allows unlimited requests, an attacker could repeatedly submit password
attempts.

A rate limit can restrict how frequently that resource can be accessed.

Conceptually:

```text
Without rate limiting:

Password attempt 1
Password attempt 2
Password attempt 3
...
Password attempt 10,000
```

With rate limiting:

```text
Attempt 1 → Allowed
Attempt 2 → Rate limited
Attempt 3 → Rate limited
...
```

This makes automated password guessing substantially less effective.

---

# 4. Identifying What Should Be Rate Limited

The lecture recommends identifying the URLs or resources that are being targeted.

Rate limiting can be applied based on different entities, including:

- The server/host.
- The client IP address.
- The request URI.

The choice is important because applying a limit at the wrong level can unintentionally restrict legitimate users.

---

# 5. Leaky Bucket Algorithm

NGINX rate limiting uses the **leaky bucket algorithm**.

The leaky bucket algorithm is widely used in telecommunications and packet-switched networks for dealing with burst
traffic and limited bandwidth.

The lecture uses a simple bucket analogy.

Imagine a bucket:

```text
        Incoming requests
              ↓ ↓ ↓
        ┌─────────────┐
        │             │
        │   BUCKET    │
        │   (QUEUE)   │
        │             │
        └──────┬──────┘
               │
               ↓
       Processed requests
```

Water represents incoming requests.

The bucket represents the queue where requests wait for processing.

The leakage represents requests leaving the queue and being processed by the server.

---

# 6. How the Leaky Bucket Works

## Normal Traffic

If the incoming request rate is equal to the processing rate:

```text
Incoming rate = Processing rate
```

requests can be processed without overflowing the bucket.

---

## Excessive Traffic

If requests arrive faster than they can be processed:

```text
Incoming rate > Processing rate
```

the queue begins to fill.

When the queue reaches its capacity, additional requests are rejected.

The lecture describes this as the **overflow**.

---

# 7. FIFO Processing

Requests waiting in the bucket are processed using a **FIFO (First In, First Out)** approach.

That means:

```text
First request in
       ↓
First request processed
```

The queue therefore processes waiting requests in their arrival order.

# Configure NGINX Rate Limiting

## 14. Define the Rate Limit Zone

Open the NGINX configuration:

```bash
vi /etc/nginx/nginx.conf
```

The rate-limit zone is defined in the **HTTP context**.

The primary directive is:

```nginx
limit_req_zone
```

Its general structure is:

```nginx
limit_req_zone <key> zone=<zone_name>:<size> rate=<rate>;
```

---

# 15. Choose the Rate-Limiting Key

The first important decision is what entity should be used to identify requests.

The lecture discusses three possibilities.

## Server Name

The rate limit can be based on the server name.

Conceptually:

```nginx
limit_req_zone $server_name zone=test_zone:10m rate=1r/s;
```

This applies the limit based on the server/host being accessed.

The instructor notes that this is generally **not a good choice** for the demonstrated use case because all clients
accessing that server can effectively share the same limit.

---

## Client IP Address

A more common approach is to rate-limit based on the client's IP address.

The lecture refers to:

```nginx
$binary_remote_addr
```

Example:

```nginx
limit_req_zone $binary_remote_addr zone=test_zone:10m rate=1r/s;
```

This means NGINX identifies the client by IP address and applies the rate limit separately to each client IP.

This is described in the lecture as the **most common approach**.

---

## Request URI

The rate limit can also be based on the requested URI.

The lecture refers to:

```nginx
$request_uri
```

Example:

```nginx
limit_req_zone $request_uri zone=test_zone:10m rate=1r/s;
```

This applies the rate-limit key based on the requested URI.

> **Important:** Choosing `$request_uri` means clients requesting the same URI can share the same rate-limit bucket.
> This can behave very differently from limiting per client IP.

---

# 16. Define the Shared Memory Zone

After selecting the key, define a shared memory zone.

The lecture uses:

```text
test_zone
```

with a size of:

```text
10 MB
```

For example:

```nginx
limit_req_zone $request_uri zone=test_zone:10m rate=1r/s;
```

Here:

```text
$request_uri → Rate-limit key
test_zone    → Zone name
10m          → Zone size
1r/s         → Allowed rate
```

```nginx

```

### 60 requests per hour

### One request per second

# 18. Apply the Zone to a Location

After defining the rate-limit zone in the HTTP context, apply it inside the desired `location` block.

Use:

```nginx
limit_req zone=test_zone;
```

For example:

```nginx
http {
    limit_req_zone $request_uri zone=test_zone:10m rate=1r/s;

    server {
        listen 443 ssl http2;

        location / {
            limit_req zone=test_zone;

            # Other configuration...
        }
    }
}
```

The exact server configuration depends on the existing NGINX setup.

# The Problem with Strict Rate Limiting

Strict rate limiting creates another potential problem.

Imagine a website with millions of legitimate users.

If the rate is too restrictive, legitimate requests may also be rejected.

For example:

```text
Configured:
1 request / second

Legitimate client:
Several requests arrive quickly

Result:
Some legitimate requests → rejected
```

Therefore, the rate limit needs to balance:

- Security.
- Performance.
- Legitimate application traffic.

---

# 24. The `burst` Parameter

NGINX provides the `burst` parameter to handle short periods of increased request activity.

The lecture adds:

```nginx
burst=5
```

to the rate-limit configuration.

For example:

```nginx
limit_req zone=test_zone burst=5;
```

The `burst` parameter allows a client to temporarily exceed the normal configured rate.

---

# 25. What Does `burst=5` Mean?

If the base rate is:

```text
1 request / second
```

and the configuration uses:

```text
burst=5
```

the client can temporarily have additional requests accommodated by the burst queue.

The lecture describes this as allowing up to six requests to be handled within the broader burst scenario:

```text
1 normal request
+
5 burst requests
```

The key concept is that the burst parameter provides additional queue capacity rather than simply rejecting every
request that arrives above the normal rate.

---

# 26. Burst as a Queue

The burst requests are held in a queue.

The lecture describes:

```text
burst=5
```

as allowing up to five requests to wait in the queue.

Conceptually:

```text
Incoming requests
       │
       ▼
┌─────────────────┐
│ Rate Limit Queue │
│                 │
│ Request 1       │
│ Request 2       │
│ Request 3       │
│ Request 4       │
│ Request 5       │
└────────┬────────┘
         │
         ▼
      NGINX
```

Instead of immediately rejecting all excess requests, NGINX can process them according to the configured rate.

---

# 27. Effect of `burst` Without `nodelay`

After adding the burst configuration, the lecture runs the test again.

The requests are now processed instead of being immediately rejected.

However, there is a new problem:

**The requests are delayed.**

The lecture observes that the complete test can take several seconds—in the demonstrated example, approximately **9
seconds**.

This happens because the requests are being processed according to the configured rate rather than all being forwarded
immediately.

Therefore:

```text
burst
   ↓
Fewer immediate rejections
   ↓
More requests accepted
   ↓
Requests wait in queue
   ↓
Higher response time
```

---

# 28. The `nodelay` Parameter

To avoid the additional delay, the lecture adds:

```nginx
nodelay
```

The resulting configuration conceptually becomes:

```nginx
limit_req zone=test_zone burst=5 nodelay;
```

---

# 29. How `nodelay` Works

With `nodelay`, NGINX still respects the burst capacity but does not intentionally space the burst requests out
according to the normal rate.

In other words:

- The rate limit remains in effect.
- The burst capacity remains available.
- Requests within the permitted burst are processed without waiting for the rate interval to elapse.
- Requests beyond the allowed burst capacity are rejected.

The lecture describes this as allowing the additional burst requests to be processed in the same queue/time slot without
extending the queue's processing delay

---

# 30. Final Configuration Used in the Lab

The key configuration demonstrated by the lecture is conceptually:

```nginx
http {
    limit_req_zone $request_uri zone=test_zone:10m rate=1r/s;

    server {
        location / {
            limit_req zone=test_zone burst=5 nodelay;
        }
    }
}
```

### Breakdown

```text
$request_uri
    ↓
Identifies the rate-limit key

test_zone
    ↓
Shared memory zone

10m
    ↓
Zone size

1r/s
    ↓
Base rate

burst=5
    ↓
Allow up to five additional queued requests

nodelay
    ↓
Process permitted burst requests without intentional delay
```

# `burst` vs `burst nodelay`

| Configuration                      | Behavior                                                                                    |
|------------------------------------|---------------------------------------------------------------------------------------------|
| No burst                           | Requests exceeding the rate are rejected                                                    |
| `burst=5`                          | Additional requests can wait in a queue                                                     |
| `burst=5 nodelay`                  | Additional requests within the burst are processed immediately, without intentional spacing |
| Requests beyond the burst capacity | Rejected                                                                                    |

### 5. Setting the rate too aggressively

A rate limit that is too restrictive can reject legitimate users.

This is why the lecture introduces:

```text
burst
```

and:

```text
nodelay
```

to provide more flexible handling of short request bursts.

### Important

Exactly. It is fundamentally different from a cache.
While an Nginx cache (proxy_cache_path) uses a shared memory zone only to store keys and metadata while dumping the
actual content onto the hard disk, limit_req_zone keeps 100% of its data in RAM.
Here is a direct comparison of how they behave in memory:

| Feature             | limit_req_zone (Rate Limiting)                                            | proxy_cache_path (Caching)                                           |
|---------------------|---------------------------------------------------------------------------|----------------------------------------------------------------------|
| What the RAM holds  | The entire state: the key ($request_uri), request counts, and timestamps. | Only the cache keys (hashes) and metadata pointing to the disk.      |
| What the Disk holds | Nothing.                                                                  | The actual cached response bodies (HTML, images, JSON, etc.).        |
| Primary Purpose     | High-speed tracking to block or delay requests in real time.              | Saving RAM by offloading heavy response payloads to cheaper storage. |

## Summary

With your rate limit rule, Nginx doesn't have a "payload" or a file to offload. The key and the counter are the data.
Because it needs to read and update this counter on every single network packet, it must happen instantly in RAM.
