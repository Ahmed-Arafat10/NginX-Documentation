# Section 09 — NGINX Access Control and Traffic Management

# Lecture 53: Limit Access to Resources in NGINX

## 1. Overview

NGINX can limit the rate at which clients download resources from a web server. This is particularly useful for websites
that provide large downloads, video files, music, reports, software packages, or other bandwidth-intensive resources.

Without download-rate limits, clients with fast network connections may consume a disproportionate amount of the
server's available bandwidth. This can reduce the resources available to other users, especially those with slower
connections.

NGINX provides the `limit_rate` directive to control the rate at which response data is transmitted to a client. It also
provides the `limit_rate_after` directive, which allows an initial portion of a response to be transmitted before the
rate limit is applied.

This lecture covers:

- Why download-rate limiting is useful.
- How to configure `limit_rate`.
- How to test download speeds using `wget`.
- How to change the configured rate and observe the results.
- How to use `limit_rate_after` to allow an initial portion of a download at an unrestricted rate.
- How download-rate limiting can support different service tiers.

| Concept            | Description                                                                                                         |
|--------------------|---------------------------------------------------------------------------------------------------------------------|

## 3. Why Download-Rate Limiting Is Important

Consider a web server that allows users to download files.

Examples include:

- Websites that provide movies or music.
- Video-streaming platforms.
- Software and operating-system download sites.
- Applications that provide medical or pharmaceutical reports.
- Websites that distribute large documents or data files.

Suppose the server has a limited amount of available outbound bandwidth.

Several clients are downloading files simultaneously:

| Client      | Example connection speed |
|-------------|-------------------------:|
| User 1      |                 100 Mbps |
| User 2      |                 100 Mbps |
| User 3      |                  20 Mbps |
| User 4      |                  20 Mbps |
| Other users |                   Varies |

The lecture uses a hypothetical server bandwidth of 10 Mbps to illustrate the problem.

If the server does not control download rates, users' transfers may compete for the available network capacity. A client
downloading a large file may consume a substantial share of that capacity, leaving less available for other requests.

This can result in:

- Uneven download performance.
- Slow responses for other users.
- Reduced service quality during periods of high demand.
- Increased difficulty maintaining predictable download speeds.

**Important:** A fast client does not automatically receive all of the server's bandwidth. Actual transfer rates depend
on TCP congestion control, competing connections, server capacity, network conditions, and other factors. Rate limiting
provides a way to control response transmission independently of those factors.

## 4. NGINX Rate-Limiting Directives

NGINX provides two directives central to this lecture:

- `limit_rate`
- `limit_rate_after`

They can be used to control how quickly a client receives response data.

### 4.1 The `limit_rate` directive

The `limit_rate` directive limits the rate at which NGINX transmits response data to a client.

Example:

```nginx
location /downloads/ {
    limit_rate 100k;
}
```

In this example, NGINX limits the response transmission rate for matching requests to approximately 100 kilobytes per
second.

The `k` suffix represents kilobytes per second, not kilobits per second.

Common examples include:

```nginx
limit_rate 50k;
limit_rate 100k;
limit_rate 500k;
limit_rate 1m;
```

These values configure different maximum response transmission rates.

### 4.2 The `limit_rate` directive applies to a response

The directive controls the rate of response transmission for an individual request. It is not a guarantee of a fixed
speed for every user, nor does it reserve a specified amount of bandwidth for each client across the entire server.

For example:

```nginx
location /assets/images/downloads/ {
    limit_rate 100k;
}
```

Requests matching this location are subject to the configured response-rate limit.

Actual throughput may be lower because of network congestion, client limitations, or server performance.

### 4.3 The `limit_rate_after` directive

The `limit_rate_after` directive specifies how much response data can be transmitted before `limit_rate` takes effect.

Example:

```nginx
location /downloads/ {
    limit_rate_after 30m;
    limit_rate 500k;
}
```

Conceptually, this configuration allows the first 30 MB of the response to be transmitted without this rate limit. After
that amount has been sent, NGINX applies the configured rate of 500 kilobytes per second.

This can be useful when an application wants to provide a faster initial download while limiting the transfer rate for
the remainder of a large file.

**Important:** The threshold applies to the amount of response data transmitted for a request. It does not mean that 30%
of the file is downloaded without a limit. The threshold is a data size, not a percentage.

## 8. Apply a Download-Rate Limit

Now configure NGINX to restrict the response rate for the download resource.

### 8.1 Step 1: Open the NGINX configuration

Open the configuration file that contains the relevant website `server` block.

For example:

```bash
sudo nano /etc/nginx/nginx.conf
```

Alternatively, edit the appropriate virtual-host file under `/etc/nginx/sites-available/` or `/etc/nginx/conf.d/`,
depending on the installation.

Locate the `location` block responsible for serving the test file.

### 8.2 Step 2: Configure a 100 KB/s rate limit

Add the following directive to the appropriate location:

```nginx
location /assets/images/downloads/ {
    limit_rate 100k;
}
```

This example assumes the URL path maps to the stated directory. Adapt the location to match the website's actual routing
configuration.

The `limit_rate 100k;` directive limits the response transmission rate to approximately 100 KB/s.

If the application already has a matching `location` block, add the directive to that block where appropriate rather
than creating a conflicting location.

### 8.3 Step 3: Validate the configuration

Run:

```bash
sudo nginx -t
```

Do not apply the changes until the configuration test succeeds.

### 8.4 Step 4: Reload NGINX

Apply the updated configuration:

```bash
sudo systemctl reload nginx
```

A reload allows NGINX to load the new configuration without requiring a full service restart.

### 8.5 Step 5: Test the download again

Return to the second machine and download the file again:

```bash
wget http://SERVER_IP/assets/images/downloads/100mb.test
```

The lecture observes a transfer rate close to 100 KB/s after the limit is applied.

This demonstrates the effect of the `limit_rate` directive.

## 10. Allow an Initial Portion of the File at a Higher Speed

The lecture then introduces a more flexible configuration: allow the initial portion of a download to transfer at the
available network speed before applying the configured limit.

This pattern can be used when an application wants to provide a faster initial download while controlling the rate for
the rest of the response.

### 10.1 Configure `limit_rate_after`

The lecture uses a threshold of 30 MB and a subsequent rate limit of 500 KB/s.

```nginx
location /assets/images/downloads/ {
    limit_rate_after 30m;
    limit_rate 500k;
}
```

Explanation:

- `limit_rate_after 30m;` allows the first 30 MB of response data to be transmitted before this rate limit takes effect.
- `limit_rate 500k;` limits the subsequent response transmission rate to approximately 500 KB/s.

### 10.2 Validate and reload

Check the configuration:

```bash
sudo nginx -t
```

Reload NGINX:

```bash
sudo systemctl reload nginx
```

### 10.3 Test the result

From the second machine, run:

```bash
wget http://SERVER_IP/assets/images/downloads/100mb.test
```

The lecture observes that the download initially transfers at a higher rate and then slows to approximately 500 KB/s
after the threshold is reached.

The expected behavior is:

```text
Response data transmitted
          |
          v
 First 30 MB
          |
          | No limit from this limit_rate
          | directive has taken effect yet
          v
 Remaining response data
          |
          v
 Approximately 500 KB/s maximum
```

The actual speed during the initial portion depends on the available network capacity and other constraints.

**Important:** The lecture refers to the initial portion as “30%” in its explanation, but the configured value is `30m`.
For a 100 MB file, 30 MB is approximately 30% of the file. The directive itself specifies an absolute data size, not a
percentage.

## 11. Practical Applications

The lecture relates rate limiting to websites that provide different levels of service.

For example, a website may provide free users with a limited download rate while offering premium users a higher rate.

A possible conceptual design is:

| User category   | Example policy                                                                |
|-----------------|-------------------------------------------------------------------------------|
| Free users      | Apply a lower download-rate limit.                                            |
| Premium users   | Apply a higher download-rate limit or a different policy.                     |
| Large downloads | Allow an initial portion at a higher rate, then limit the remaining transfer. |

The directives shown in this lecture provide the rate-limiting mechanism. They do not automatically identify premium
users or implement subscription logic.

To apply different limits by membership, the application or NGINX configuration must separately determine which policy
applies to each request. That may involve authentication, trusted variables, or different locations, depending on the
architecture.

## 12. Important Notes and Common Mistakes

### 12.1 Kilobytes are not kilobits

The values `100k` and `500k` represent approximately 100 and 500 kilobytes per second, respectively.

Network connection speeds are often advertised in megabits per second (Mbps), while download tools may report megabytes
per second (MB/s).

These units are different:

- 1 byte = 8 bits.
- 1 MB/s is approximately 8 Mbps, ignoring unit-convention differences and protocol overhead.

Be careful when comparing the `wget` output with the NGINX rate-limit configuration.

### 12.2 A rate limit is a maximum, not a guaranteed speed

Setting:

```nginx
limit_rate 500k;
```

does not guarantee that the client will download at exactly 500 KB/s.

The actual speed can be lower because of network congestion, server load, or client limitations.

### 12.3 Apply the directive to the correct location

A rate limit only affects requests handled by a configuration context where the directive applies.

If the download is served by a different location or proxied to another system, verify which location handles the
request and whether the directive is effective there.

### 12.4 Avoid duplicate or conflicting location blocks

Before creating a new `location`, inspect the existing server configuration. An existing location may already handle the
relevant resource path.

Combining the directive with the appropriate existing location is often safer than introducing another block without
understanding NGINX's location-matching rules.

### 12.5 Validate before reloading

Always run:

```bash
sudo nginx -t
```

before reloading NGINX. This helps catch syntax errors before they affect the active configuration.

### 12.6 Rate limiting is not the same as limiting concurrent connections

The `limit_rate` directive controls response transmission speed. It does not limit how many simultaneous connections a
client can establish.

Connection limiting uses separate functionality, such as `limit_conn` with a configured shared-memory zone.

This lecture explains how NGINX controls the rate at which clients download resources.

The main takeaways are:

1. Download-rate limiting helps manage server bandwidth and improve fairness between clients.
2. The `limit_rate` directive sets a maximum response transmission rate for matching requests.
3. The lecture demonstrates rate limits of 100 KB/s and 500 KB/s.
4. The `limit_rate_after` directive allows an initial amount of response data to be transmitted before the configured
   rate limit applies.
5. A configuration such as `limit_rate_after 30m;` uses an absolute data-size threshold, not a percentage.
6. `wget` can be used to test download behavior from a separate client machine.
7. Configuration changes should be validated with `sudo nginx -t` and applied with `sudo systemctl reload nginx`.
8. Different rate limits can support different service policies, but user identification and policy selection require
   additional configuration or application logic.

These techniques help administrators control download performance and manage bandwidth-intensive resources served
through NGINX.
