# Section 09 — NGINX Access Control

# Lecture 52: Allow and Restrict IP Addresses in NGINX

## 1. Overview

NGINX provides built-in access-control directives that allow administrators to permit or deny requests based on the
client's IP address.

IP-based access control is useful when a website or application contains resources that should not be accessible to
everyone. For example, an administrator may want to restrict access to an administration panel, internal authentication
service, or specific static files.

NGINX provides two primary directives for this purpose:

- `allow` — permits requests from a specified IP address or network.
- `deny` — denies requests from a specified IP address or network.

These directives can be configured within contexts such as `http`, `server`, and `location`, allowing access
restrictions to apply to an entire website or to selected resources.

This lecture covers:

- Why IP-based access control is useful.
- How to allow a specific IP address and deny other clients.
- How to restrict access to PNG images.
- How to test access restrictions using browser developer tools and an online proxy.
- How to manage multiple allowed IP addresses using an included configuration file.
- How to troubleshoot configuration errors and HTTP `403 Forbidden` responses.

## 2. Key Concepts

| Concept              | Description                                                                            |
|----------------------|----------------------------------------------------------------------------------------|
| IP whitelisting      | Allowing requests only from specified IP addresses or networks.                        |
| IP restriction       | Limiting access to a resource based on the client's IP address.                        |
| `allow`              | Permits access from a specified IP address or CIDR network.                            |
| `deny`               | Rejects access from a specified IP address or CIDR network.                            |
| `location` block     | Defines how NGINX handles requests matching a particular URI.                          |
| CIDR notation        | Represents an IP network using an address and prefix length, such as `192.10.10.0/24`. |
| `include`            | Loads directives from another configuration file.                                      |
| HTTP `403 Forbidden` | Indicates that the server understood the request but refuses to authorize access.      |
| NGINX access log     | Records HTTP requests and their results, including status codes.                       |

## 3. Why IP-Based Access Control Is Needed

Consider a web application accessed by multiple users.

```text
User 1 ──┐
         │
User 2 ──┼────> NGINX Web Server ────> Application
         │
User 3 ──┘
```

Normally, all users can access the same publicly available resources.

However, some resources should be accessible only to trusted clients.

Examples include:

- Administration panels.
- Internal authentication services.
- Internal APIs.
- Restricted application endpoints.
- Specific files or directories.
- Resources intended only for an organization's internal network.

For example, an authentication service may be used by several internal application services. If it is not intended for
public access, the administrator can restrict access to known internal IP addresses or networks.

NGINX can enforce these restrictions before the request reaches the protected resource.

### 3.1 Example IP addresses

Suppose three clients have the following addresses:

| Client   | Example IP address |
|----------|--------------------|
| Client 1 | `10.3.10.45`       |
| Client 2 | `127.12.30.88`     |
| Client 3 | `35.90.87.0`       |

These are illustrative addresses from the lecture. In a real configuration, use the actual trusted client addresses and
networks.

The goal is to allow authorized clients to access a protected resource while denying unauthorized clients.

## 4. Understanding the `allow` and `deny` Directives

NGINX provides the following directives for IP-based access control.

### 4.1 The `allow` directive

The `allow` directive permits access from a specified IP address or network.

Example:

```nginx
allow 190.99.0.71;
```

This permits requests from the specified IPv4 address, subject to other applicable access rules.

An entire network can also be allowed using CIDR notation:

```nginx
allow 192.10.10.0/24;
```

### 4.2 The `deny` directive

The `deny` directive blocks access from a specified IP address or network.

Example:

```nginx
deny 203.0.113.10;
```

To deny all other addresses after allowing a trusted client, use:

```nginx
allow 190.99.0.71;
deny all;
```

This configuration allows the specified IP address and denies other clients that do not match an earlier applicable
rule.

### 4.3 Restricting access to a specific location

Suppose an application has an administration endpoint at `/admin/`. Only one trusted IP address should be able to access
it.

```nginx
server {
    listen 80;
    server_name app.example.com;

    location /admin/ {
        allow 190.99.0.71;
        deny all;

        # Application handling directives go here.
    }
}
```

In this example:

- Requests from `190.99.0.71` are permitted by the access-control rules.
- Requests from other IP addresses are denied.
- Unauthorized requests typically receive an HTTP `403 Forbidden` response.

**Important:** Access control should be placed in the appropriate configuration context. A restriction inside
`location /admin/` applies to that location, not automatically to every resource on the website.

## 5. Practical Lab: Restrict Access to PNG Files

The lecture demonstrates how to restrict access to PNG files on the Brownie website.

The objective is to allow access from the instructor's public IP address while denying requests from other IP addresses.

### 5.1 Step 1: Open the NGINX configuration

Open the configuration file used by the existing website.

For example, the main configuration file is commonly located at:

```bash
sudo nano /etc/nginx/nginx.conf
```

Depending on the installation, the website configuration may instead be in a file under:

```text
/etc/nginx/conf.d/
/etc/nginx/sites-available/
/etc/nginx/sites-enabled/
```

Locate the relevant `server` block and the existing `location` block used for cache-control settings.

The lecture updates that existing configuration block to apply IP restrictions to PNG resources.

### 5.2 Step 2: Add the IP restriction

The lecture's intended configuration is:

```nginx
location ~* \.png$ {
    allow YOUR_PUBLIC_IP;
    deny all;
}
```

Replace `YOUR_PUBLIC_IP` with the actual public IP address that should be allowed.

For example, using a documentation-only address:

```nginx
location ~* \.png$ {
    allow 192.0.2.10;
    deny all;
}
```

The address `192.0.2.10` is only an example and must not be treated as the instructor's real IP address.

Explanation:

- `location ~* \.png$` matches URI paths ending in `.png`, without distinguishing uppercase and lowercase letters.
- `allow YOUR_PUBLIC_IP;` permits the configured address.
- `deny all;` denies other clients.

The lecture initially modifies an existing cache-control block. If you follow that approach, review the original
directives carefully so that the new location does not unintentionally remove required caching behavior.

**Configuration note:** NGINX location matching, regular-expression precedence, and nested configuration can affect
which block handles a request. If an existing location already matches PNG resources, adapt that block rather than
blindly adding a competing one.

### 5.3 Step 3: Validate the configuration

Before reloading NGINX, test the configuration:

```bash
sudo nginx -t
```

A successful test typically reports that the syntax is valid and the configuration test has succeeded.

Do not reload NGINX if the configuration test fails. Correct the reported errors first.

### 5.4 Step 4: Check the website before applying the restriction

Before reloading the configuration, refresh the Brownie website in the browser.

The lecture confirms that the website continues to load and that PNG images are accessible.

At this point, the new configuration has not yet been applied, so the existing behavior remains in effect.

### 5.5 Step 5: Monitor the access log

Open a terminal and follow the NGINX access log:

```bash
sudo tail -f /var/log/nginx/access.log
```

The log helps identify:

- Client IP addresses.
- Requested resource paths.
- HTTP response status codes.

The exact log format depends on the NGINX `log_format` configuration.

### 5.6 Step 6: Identify the allowed public IP

From the browser or terminal on the machine that should be authorized, determine its public IP address.

Update the configuration with that address:

```nginx
location ~* \.png$ {
    allow YOUR_PUBLIC_IP;
    deny all;
}
```

Replace the placeholder with the actual IP address, then save the configuration.

**Security note:** An online “what is my IP” service reports the public IP visible to that service. If the client uses a
VPN, proxy, corporate gateway, or NAT, this may differ from its local network address.

### 5.7 Step 7: Reload NGINX

Validate the configuration again:

```bash
sudo nginx -t
```

If validation succeeds, reload NGINX:

```bash
sudo systemctl reload nginx
```

The lecture uses a reload so that NGINX applies the updated access-control rules without requiring a full service
restart.

### 5.8 Step 8: Test from the authorized client

Refresh the Brownie website from the machine whose public IP is allowed.

In Firefox:

1. Press **F12** to open Developer Tools.
2. Select the **Network** tab.
3. Refresh the website.
4. Inspect requests for PNG images.

The lecture observes that the allowed client can continue retrieving PNG files successfully, with HTTP `200` responses
for the relevant requests.

Example:

```text
GET /assets/images/banner.png 200
GET /assets/images/profile.png 200
```

The paths above are illustrative examples.

### 5.9 Step 9: Test from a different public IP

To test the restriction, the lecture uses an online web proxy to access the same website from a different public IP
address.

The proxy makes requests to the website, allowing the administrator to compare the results against requests from the
authorized client.

After applying the restriction, the lecture observes `403` responses for PNG requests made through the proxy.

Example:

```text
GET /assets/images/banner.png 403
GET /assets/images/profile.png 403
```

This indicates that the requests reached the access-control rule but were not permitted.

**Caution:** Public online proxies are not reliable or appropriate for every environment. Use a controlled test client,
a separate network, or an authorized external testing system whenever possible. Do not submit sensitive URLs or
credentials to an untrusted proxy.

### 5.10 Expected results

| Test client         | IP status         | Expected PNG access               |
|---------------------|-------------------|-----------------------------------|
| Authorized client   | IP is allowed     | Permitted, typically `200 OK`     |
| Unauthorized client | IP is not allowed | Denied, typically `403 Forbidden` |

Other resources may behave differently if the access restriction matches only PNG files.

## 6. Allowing Multiple IP Addresses

A common requirement is to permit several trusted clients rather than a single IP address.

NGINX allows multiple `allow` directives in the same configuration context.

### 6.1 Method 1: Define multiple IP addresses directly

Example:

```nginx
location ~* \.png$ {
    allow 192.0.2.10;
    allow 198.51.100.25;
    allow 203.0.113.0/24;

    deny all;
}
```

This example allows two individual addresses and one IP network before denying all other clients.

The addresses and network above are documentation-only examples. Replace them with the real trusted addresses.

This method is straightforward for a small list of IP addresses.

### 6.2 Method 2: Store the access rules in a separate file

For larger lists, the lecture demonstrates using an external file and including it in the main configuration.

Create a separate file:

```bash
sudo nano /etc/nginx/whitelist-ip.conf
```

Add the access-control directives:

```nginx
allow 127.0.0.1;
allow 192.10.10.0/24;
deny all;
```

Explanation:

- `allow 127.0.0.1;` permits requests from the loopback address.
- `allow 192.10.10.0/24;` permits addresses in that network.
- `deny all;` denies other clients.

The `/24` prefix represents a network mask of `255.255.255.0` for IPv4, corresponding to 256 total addresses, including
the network and broadcast addresses in a conventional IPv4 subnet.

**Important:** `127.0.0.1` is the loopback address. It is not the public IP of the browser's computer when connecting to
a remote web server. It usually matches requests originating from the same host, subject to the actual connection path.

The network `192.10.10.0/24` is retained from the lecture's example. Confirm that you intend to permit this specific
network before using it.

### 6.3 Step 3: Include the file in the NGINX configuration

Inside the appropriate `location` block, replace the individual access directives with an `include` directive:

```nginx
location ~* \.png$ {
    include /etc/nginx/whitelist-ip.conf;
}
```

NGINX reads the directives in the included file as part of the configuration.

The included file must contain valid NGINX directives, and each directive must end with a semicolon.

The path must match the actual file location on the server.

### 6.4 Step 4: Validate the included configuration

Run:

```bash
sudo nginx -t
```

If the test fails, inspect the reported file path and line number.

The lecture demonstrates two configuration errors:

1. An incorrect filename or include path.
2. A missing semicolon after an `allow` directive.

For example, this is invalid:

```nginx
allow 127.0.0.1
allow 192.10.10.0/24;
deny all;
```

The first directive is missing its terminating semicolon.

The corrected configuration is:

```nginx
allow 127.0.0.1;
allow 192.10.10.0/24;
deny all;
```

### 6.5 Step 5: Reload NGINX

Once the configuration test succeeds, reload NGINX:

```bash
sudo systemctl reload nginx
```

The included access rules are now part of the active configuration.

### 6.6 Step 6: Verify access when the local client is not allowed

In the lecture, the instructor removes the local client's public IP from the whitelist and reloads NGINX.

After refreshing the website, the browser shows `403 Forbidden` for PNG resources.

This confirms that the access-control configuration is being enforced.

When testing a specific image, use its direct URL or inspect the request in Firefox Developer Tools. A private or
incognito window can help avoid some existing browser-cache effects, but it does not change the client's public IP
address.

## 7. Understanding HTTP `403 Forbidden`

The lecture emphasizes that a `403 Forbidden` response does not mean that the requested resource is missing.

Instead, it means that the server refuses to authorize access to the requested resource.

For example:

```http
HTTP/1.1 403 Forbidden
```

In the context of this lab:

- The PNG file may exist on the server.
- The client requests the file.
- The request does not satisfy the configured IP access rules.
- NGINX denies access and returns `403 Forbidden`.

Compare the two common outcomes:

| Status code     | Meaning                                                                                                    |
|-----------------|------------------------------------------------------------------------------------------------------------|
| `200 OK`        | The request succeeded and the resource was returned.                                                       |
| `403 Forbidden` | The server refuses access to the requested resource.                                                       |
| `404 Not Found` | The server could not find the requested resource, or is configured to respond as though it does not exist. |

A `403` can also be caused by other authorization rules or filesystem permissions, so inspect the NGINX configuration
and logs if the reason is unclear.

## 8. Troubleshooting Checklist

When IP restrictions do not behave as expected, verify the following:

- [ ] The `allow` directive contains the correct client IP or CIDR network.
- [ ] The `deny all;` directive is in the intended configuration context.
- [ ] The relevant request matches the expected `location` block.
- [ ] The include file exists at the specified path.
- [ ] The filename in the `include` directive is spelled correctly.
- [ ] Every directive ends with a semicolon.
- [ ] `sudo nginx -t` succeeds.
- [ ] NGINX has been reloaded after the configuration change.
- [ ] The access log shows the expected client address and response status.
- [ ] Browser caching is not obscuring the result of the latest request.
- [ ] A proxy or VPN is not changing the apparent source IP address.

### Useful commands

Check the configuration:

```bash
sudo nginx -t
```

Reload NGINX:

```bash
sudo systemctl reload nginx
```

Follow the access log:

```bash
sudo tail -f /var/log/nginx/access.log
```

Display the active configuration, including included files:

```bash
sudo nginx -T
```

The `nginx -T` command prints the configuration NGINX loads, which can help identify unexpected or conflicting location
blocks.

## 9. Best Practices

1. **Use the narrowest practical scope.** Apply IP restrictions to the specific protected location or resource instead
   of blocking the entire website unnecessarily.

2. **Prefer trusted network ranges where appropriate.** If several internal services require access, a carefully
   selected CIDR range may be easier to maintain than many individual addresses.

3. **Keep access rules organized.** An included file can make larger allowlists easier to manage.

4. **Validate before reloading.** Always run `nginx -t` before applying configuration changes.

5. **Check the actual client IP.** Reverse proxies, VPNs, and NAT can affect which address NGINX sees. If NGINX sits
   behind another proxy, configure trusted real-IP handling carefully rather than trusting arbitrary forwarded headers.

6. **Do not rely on IP restrictions as the only security control for sensitive applications.** Use authentication,
   authorization, TLS, and other appropriate security measures alongside IP filtering.

7. **Review access logs after changes.** Confirm that authorized clients receive successful responses and unauthorized
   clients are denied.

## 10. Summary

This lecture explains how to use NGINX's `allow` and `deny` directives to restrict access by IP address.

The main takeaways are:

1. IP-based access control can protect administration panels, internal services, and selected website resources.
2. `allow` permits specified IP addresses or networks.
3. `deny` blocks specified IP addresses or networks; `deny all;` can be used to deny other clients after the permitted
   entries.
4. Restrictions can be applied within an appropriate `location` block, such as one matching PNG files.
5. Multiple IP addresses can be listed directly or stored in a separate configuration file loaded with `include`.
6. `sudo nginx -t` validates the configuration before a reload.
7. Browser Developer Tools and access logs help verify whether requests succeed or return `403 Forbidden`.
8. HTTP `403 Forbidden` indicates denied access, not necessarily a missing resource.

With these techniques, administrators can control which clients are permitted to access specific resources served by
NGINX.
