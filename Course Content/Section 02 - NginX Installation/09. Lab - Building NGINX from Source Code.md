# 09. Lab — Building NGINX from Source Code

Pasted text

## Overview

In the previous lectures, NGINX was installed using operating-system package managers. In this lab, the installation
method is different: **NGINX is built directly from its source code**.

Building NGINX from source is important when you need more control over the NGINX build, particularly when you want to
include:

- Custom modules
- Third-party modules
- Additional libraries
- Specific build-time configuration options

The lab demonstrates the complete process on both:

- **Ubuntu**
- **CentOS**

The instructor performs the installation on both operating systems in parallel to show that the overall NGINX build
process is the same, while package-management commands and some OS-specific utilities differ.

---

# 1. Why Build NGINX from Source?

When NGINX is installed using a package manager, the available build is determined by the package provided by the
operating system or repository.

The instructor highlights an important limitation:

> When installing NGINX through a package manager, custom or third-party modules cannot simply be added to the NGINX
> build.

Building NGINX from source solves this problem.

With a source-code installation, you can configure the NGINX build and include the modules and libraries you require.

The general workflow is:

```text
Download NGINX Source Code
          ↓
Install Compilation Dependencies
          ↓
Configure the NGINX Build
          ↓
Compile the Source Code
          ↓
Install the Compiled NGINX
          ↓
Start NGINX
```

# 19. Why Configure NGINX at Build Time?

When an option is supplied to `./configure`, the resulting NGINX build is created with that configuration.

In other words:

```text
./configure options
        ↓
NGINX Build Configuration
        ↓
make
        ↓
Compiled NGINX
        ↓
make install
```

The resulting NGINX installation reflects the choices made during the configuration stage.

This is one of the major reasons to build NGINX from source: **you can control the features, modules, paths, and
libraries included in the build.**

# 20. Example Custom `configure` Command

The instructor demonstrates a custom configuration containing options for the binary path, configuration file, logs,
PCRE, PID file, and OpenSSL.

The command is conceptually:

```bash
./configure \
    --sbin-path=/usr/bin/nginx \
    --conf-path=/etc/nginx/nginx.conf \
    --error-log-path=/var/log/nginx/error.log \
    --http-log-path=/var/log/nginx/access.log \
    --with-pcre \
    --pid-path=/var/run/nginx.pid \
    --with-http_ssl_module
```

### Important Configuration Options

#### Binary path

```text
--sbin-path=/usr/bin/nginx
```

Specifies where the NGINX executable will be installed.

#### Configuration path

```text
--conf-path=/etc/nginx/nginx.conf
```

Specifies the location of the main NGINX configuration file.

#### Error log

```text
--error-log-path=/var/log/nginx/error.log
```

Specifies the NGINX error log location.

#### HTTP access log

```text
--http-log-path=/var/log/nginx/access.log
```

Specifies the HTTP access log location.

#### PCRE

```text
--with-pcre
```

Enables PCRE support.

#### PID file

```text
--pid-path=/var/run/nginx.pid
```

Specifies the location of the NGINX PID file.

#### SSL

```text
--with-http_ssl_module
```

Builds NGINX with the HTTP SSL module, enabling support for secure HTTP connections.

# 29. Package Manager vs. Source Installation

The lab demonstrates two fundamentally different approaches to installing NGINX.

| Aspect                      | Package Manager                               | Source Code                                  |
|-----------------------------|-----------------------------------------------|----------------------------------------------|
| Installation method         | OS package manager                            | Compile source manually                      |
| Custom modules              | Limited by packaged build                     | Can be included during configuration         |
| Third-party modules         | Not directly included in the existing package | Can be incorporated into the build           |
| Dependencies                | Package manager handles them                  | Developer must install required dependencies |
| Configuration at build time | Determined by package                         | Controlled with `./configure`                |
| Compilation required        | No                                            | Yes                                          |
| `make` required             | No                                            | Yes                                          |
| `make install` required     | No                                            | Yes                                          |

The source-code approach provides significantly more control over the resulting NGINX build.

# Practical Notes / Best Practices

- Building from source is useful when the standard package does not provide the modules or build configuration you need.
- Always install the required compiler and development libraries before attempting to compile NGINX.
- If `./configure` reports a missing library, install the corresponding development package and run `./configure` again.
- Ubuntu and CentOS use different package names and package-management commands, even though they build the same NGINX
  source code.
- Use `./configure --help` to inspect the available build-time configuration options.
- Build-time options determine important paths and modules in the resulting NGINX installation.
- `make` **compiles** the configured source code.
- `make install` **installs** the compiled NGINX.
- Always verify the resulting installation with:
  ```bash
  nginx -v
  ```
- Verify that the master and worker processes are running after starting NGINX.
