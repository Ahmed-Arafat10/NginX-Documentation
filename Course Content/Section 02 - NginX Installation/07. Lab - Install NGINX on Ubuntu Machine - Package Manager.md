# 07. Lab — Install NGINX on Ubuntu Machine Using the Package Manager

## Overview

In the previous lecture, an Ubuntu cloud machine was created. This lab demonstrates how to:

- Connect to the Ubuntu cloud machine using SSH.
- Update Ubuntu's APT package manager.
- Install NGINX using APT.
- Verify that NGINX processes are running.
- Explore the default NGINX configuration.
- Locate and inspect NGINX log files.
- Access the default NGINX page from a browser.
- Observe access logs generated by HTTP requests.
- Understand the `200` and `304 Not Modified` response codes in the context of the default NGINX page.

Ubuntu provides the **APT package manager**, which is used in this lab to install NGINX and its required dependencies.

---

## 1. Connect to the Ubuntu Machine

Open a terminal and connect to the Ubuntu cloud machine created in the previous lecture using SSH and the machine's IP
address.

The general SSH command is:

```bash
ssh root@<IP_ADDRESS>
```

Replace `<IP_ADDRESS>` with the IP address of the Ubuntu machine.

After executing the command, provide the password when prompted.

Once authentication succeeds, you are logged into the Ubuntu machine.

You can clear the terminal with:

```bash
clear
```

---

## 2. Update the APT Package Manager

Before installing NGINX, update the APT package manager:

```bash
sudo apt-get update
```

This updates the package information and dependencies used by the APT package manager.

The lecture emphasizes performing this update before installing NGINX.

---

## 3. Install NGINX

After updating APT, install NGINX with:

```bash
apt install nginx
```

APT installs NGINX along with the packages it requires as dependencies.

During installation, Ubuntu may ask for confirmation. The installation output also shows the additional packages that
will be installed alongside NGINX.

Confirm the installation by entering:

```text
Y
```

and pressing **Enter**.

After the installation completes, NGINX is installed on the Ubuntu machine.

---

## 4. Verify That NGINX Is Running

After installation, the lecture verifies the NGINX processes using a process-listing command combined with `grep`.

The command shown in the lecture is intended to list running processes and filter the results for NGINX:

```bash
ps aux | grep nginx
```

The output shows NGINX processes running on the machine.

The lecture observes two actual NGINX processes:

1. **NGINX master process**
    - Runs under the `root` user.
    - This is the main/master process responsible for managing NGINX.

2. **NGINX worker process**
    - Runs under the `www-data` user.
    - This is the worker process that handles NGINX work.

There is also a third line corresponding to the `grep nginx` command itself; this is not an NGINX process.

### NGINX Process Model

By default, the installation shown in the lecture creates:

```text
NGINX
├── Master Process
│   └── runs as root
│
└── Worker Process
    └── runs as www-data
```

The master process and worker process have different responsibilities. The lecture identifies the first process as the
master process and the second as the worker process.

# 5. Explore the NGINX Configuration

NGINX configuration files are located under:

```text
/etc/nginx
```

List the contents of this directory:

```bash
ls -l /etc/nginx
```

The directory contains the configuration required by NGINX, including:

- `conf.d`
- Other NGINX configuration files
- `nginx.conf`

The main NGINX configuration file is:

```text
/etc/nginx/nginx.conf
```

You can open it with:

```bash
/etc/nginx/nginx.conf
```

The lecture then examines the contents of the configuration file.

---

## 6. Important Parts of `nginx.conf`

The configuration file contains several important settings.

### User

The configuration specifies:

```nginx
user www-data;
```

This indicates the user associated with NGINX worker processes.

### Worker Processes

The configuration contains:

```nginx
worker_processes auto;
```

The lecture points out that the worker process setting is configured as `auto`.

### PID

NGINX also has a PID configuration, which identifies the process ID file used by NGINX.

### Included Modules

The configuration includes files from:

```text
/etc/nginx/modules-enabled
```

The lecture explains that the modules provided by the default NGINX installation are available through this location.

### HTTP Configuration

The configuration then contains the HTTP section, including settings such as:

```nginx
http {
    ...
}
```

The lecture mentions settings such as:

- `sendfile`
- TCP-related configuration
- Other HTTP configuration directives

At this stage, the complete meaning of these directives is not explained in detail.

> **Note:** The instructor indicates that the configuration file will become much easier to understand later in the
> course, particularly after learning NGINX configuration, load balancing, and custom NGINX configurations.

# 7. NGINX Log Files

The NGINX configuration also specifies locations for its logs.

The two important log files are:

```text
access.log
error.log
```

They are located under:

```text
/var/log/nginx
```

Navigate to the directory:

```bash
cd /var/log/nginx
```

Then list its contents:

```bash
ls
```

You should see the NGINX log files, including:

```text
access.log
error.log
```

### Access Log

The access log records HTTP requests processed by NGINX.

### Error Log

The error log records NGINX errors and related diagnostic information.

---

# 8. Monitor the NGINX Logs

The lecture uses `tail` to monitor the log files:

```bash
tail -f access.log error.log
```

The `-f` option follows the files, allowing new log entries to appear in the terminal as they are generated.

Initially, both log files are empty because no requests have been made to the newly installed NGINX server.

---

# 9. Find the Machine's IP Address

To access NGINX from a browser, determine the IP address of the Ubuntu machine.

The lecture uses:

```bash
ifconfig
```

The command displays the machine's network configuration, including its IP address.

The same IP address was previously used to connect to the machine through SSH.

---

# 10. Access the NGINX Default Page

Copy the machine's IP address and enter it into a web browser.

For example:

```text
http://<IP_ADDRESS>
```

Press **Enter**.

You should see the default NGINX welcome page.

The default page is being served because NGINX is already running and listening on **port 80**.

Therefore, a request to:

```text
http://<IP_ADDRESS>
```

is handled by NGINX.

---

# 11. Observe the Access Log

Return to the terminal where the NGINX logs are being followed:

```bash
tail -f access.log error.log
```

After opening the NGINX page in the browser, an entry appears in the access log.

This demonstrates that the browser's HTTP request reached NGINX and was processed successfully.

The lecture describes this as a `GET` request for the NGINX HTML page.

---

# 12. Refresh the Browser and Observe Additional Requests

Refresh the NGINX page several times.

For example:

```text
Refresh → Refresh → Refresh
```

Each browser request produces another entry in the NGINX access log.

This provides a practical demonstration of the relationship between:

```text
Browser Request
       ↓
     NGINX
       ↓
 Access Log Entry
```

# 13. Understanding HTTP Status Codes: `200` vs `304`

An important observation in the lab is that the first request and subsequent requests may have different HTTP response
codes.

### First Request — `200`

The first time the browser requests the NGINX HTML page, the response is:

```text
200
```

`200 OK` indicates that the request was successfully processed and the requested resource was returned.

### Subsequent Requests — `304`

After refreshing the same page, the lecture observes responses such as:

```text
304
304
304
```

The lecture explains `304 Not Modified` as indicating that the requested resource has not changed and that the browser
can use its cached version rather than receiving the resource again.

In the lecture's explanation, the first request causes NGINX to read the HTML resource, after which subsequent requests
can result in `304` responses when the resource has not changed.

---

## 14. Request and Cache Flow

The behavior demonstrated in the lab can be represented as:

### First Request

```text
Browser
   │
   │ GET /
   ▼
 NGINX
   │
   │ Reads requested HTML resource
   ▼
 HTML Resource
   │
   │
   ▼
 Browser
   │
   └── HTTP 200
```

### Subsequent Request

```text
Browser
   │
   │ GET / + cache validation
   ▼
 NGINX
   │
   │ Resource has not changed
   ▼
 HTTP 304 Not Modified
   │
   ▼
Browser uses cached resource
```

This is why the access log can contain a sequence such as:

```text
200
304
304
304
```

The exact log entries depend on the browser's request and caching behavior.
