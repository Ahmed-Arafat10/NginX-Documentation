# Lab: Add NGINX as a Service in the Operating System

## Lecture Title

**Add NGINX as a systemd Service to Make the Web Server Resilient**

## Overview

Running NGINX as a manually started process is not sufficient for a production environment. If the server reboots, the
NGINX process stops and must be started manually again.

In this lab, NGINX is configured as a **systemd service** so that the operating system can manage the NGINX process.

Using systemd allows you to:

- Start and stop NGINX using `systemctl`.
- Restart NGINX easily.
- Check the current NGINX service status.
- Manage NGINX as an operating-system service.
- Configure NGINX to start automatically after a system reboot.
- Reduce manual intervention after crashes, reboots, or maintenance.

The lab demonstrates this process on Ubuntu. The general approach also applies to other Linux distributions that use
systemd.

---

# 1. Why Add NGINX as a Service?

NGINX is commonly used as the front-end web server for an application.

A typical request flow is:

```text
User
  |
  v
NGINX
  |
  v
Web Application / Backend
```

If NGINX stops running, the front end can no longer accept incoming requests.

Therefore, in a production environment, it is important to minimize the amount of time that NGINX remains unavailable.

### Without systemd

If NGINX is started manually:

1. NGINX is started manually.
2. The machine reboots.
3. The NGINX process is terminated.
4. Someone must connect to the server.
5. NGINX must be started manually again.
6. Until this happens, the front end remains unavailable.

This increases potential production downtime.

### With systemd

When NGINX is configured as a systemd service:

```text
NGINX Process
      |
      v
systemd Service
      |
      +---- Start
      |
      +---- Stop
      |
      +---- Restart
      |
      +---- Status
      |
      +---- Automatic Startup After Boot
```

The operating system can then manage NGINX as a service.

---

# 2. What Is systemd?

**systemd** is the service-management system used by modern Linux distributions.

It allows processes such as NGINX to be managed as operating-system services.

In this context, systemd makes NGINX more **resilient** by allowing it to be managed consistently across events such as:

- Process termination
- Process crashes
- Operating-system reboots
- Machine shutdown and startup

The main focus of this lab is automatic startup after a reboot and easier management of NGINX in a production
environment.

---

# 3. Demonstrating the Problem

Before configuring systemd, consider what happens when NGINX is only running as a manually started process.

Initially:

```text
NGINX running
      |
      v
Server is accessible
```

After the machine is rebooted:

```text
Server reboot
      |
      v
NGINX process terminates
      |
      v
NGINX is no longer running
```

The browser can no longer access the NGINX web server.

The NGINX process must then be started manually again.

This demonstrates why manually running NGINX is not sufficient for a production server.

# 4. Create the NGINX systemd Service

NGINX provides documentation containing examples for different service-management systems.

The relevant example for this lab is the **systemd** configuration.

The service definition is stored as:

```text
/lib/systemd/system/nginx.service
```

> **Important:** The exact service-file location should match the approach used in your environment.

The general process is:

1. Create the `nginx.service` file.
2. Add the NGINX systemd configuration.
3. Adjust the NGINX paths to match the actual installation.
4. Use `systemctl` to manage the service.

---

# 5. NGINX Service Definition

A typical service definition contains the following:

```ini
[Unit]
Description = The NGINX HTTP and reverse proxy server
After = syslog.target network-online.target remote-fs.target nss-lookup.target
Wants = network-online.target

[Service]
Type = forking
PIDFile = /run/nginx.pid
ExecStartPre = /usr/bin/nginx -t
ExecStart = /usr/bin/nginx
ExecReload = /usr/bin/nginx -s reload
ExecStop = /bin/kill -s QUIT $MAINPID
PrivateTmp = true

[Install]
WantedBy = multi-user.target
```

### Important

The paths in this service file must match the actual NGINX installation.

In the environment used in this lab, NGINX was installed at:

```text
/usr/bin/nginx
```

Therefore, the service definition must use:

```text
/usr/bin/nginx
```

rather than:

```text
/usr/sbin/nginx
```

This distinction is particularly important when NGINX has been **built and installed from source** with a custom
`--sbin-path`.

---

# 6. Important Service Configuration

## 6.1 PID File

The service needs to know where NGINX stores the master process ID.

For example:

```ini
PIDFile = /run/nginx.pid
```

The PID file location must match the location configured for the actual NGINX installation.

If your NGINX configuration uses:

```text
/var/run/nginx.pid
```

then the service definition must use the corresponding path.

---

## 6.2 Test the NGINX Configuration Before Starting

The service uses:

```bash
nginx -t
```

The `-t` option tests the NGINX configuration.

It verifies that the configuration is valid before NGINX is started.

Therefore, the service definition can use:

```ini
ExecStartPre = /usr/bin/nginx -t
```

This means that systemd performs a configuration test before attempting to start NGINX.

---

## 6.3 NGINX Binary Location

The service must point to the actual NGINX executable.

In this environment:

```text
/usr/bin/nginx
```

Therefore:

```ini
ExecStart = /usr/bin/nginx
```

and:

```ini
ExecReload = /usr/bin/nginx -s reload
```

must use `/usr/bin/nginx`.

Do not blindly copy a service file that references:

```text
/usr/sbin/nginx
```

if your NGINX binary is actually located at:

```text
/usr/bin/nginx
```

You can verify the location with:

```bash
which nginx
```

or:

```bash
type -a nginx
```

# 7. Reload systemd After Creating or Modifying the Service

After creating or changing a systemd service definition, reload systemd so that it recognizes the service configuration:

```bash
systemctl daemon-reload
```

Then the NGINX service can be managed using `systemctl`.

Start the NGINX service:

```bash
systemctl start nginx
```

This starts NGINX immediately.

Verify that it is running:

```bash
systemctl status nginx
```

```bash
systemctl stop nginx
```

You can verify its state with:

```bash
systemctl status nginx
```

# 10. Restart NGINX

To restart NGINX:

```bash

```

After restarting, check the service:

```bash

```

# 11. Check NGINX Service Status

Use:

```bash
systemctl status nginx
```

This provides information about the current state of the NGINX service.

The output can include:

- Whether the service is running
- The main process ID
- Child-process information
- The service description
- Recent service activity
- Whether the service started successfully

For example:

```text
● nginx.service - The NGINX HTTP and reverse proxy server
   Active: active (running)
```

The status output is particularly useful when troubleshooting a failed NGINX startup.

# 12. NGINX Signals

NGINX also provides its own signal mechanism.

Display the available command options with:

```bash
nginx -h
```

The `-s` option allows a signal to be sent to the NGINX master process.

Common signals include:

```text
stop
quit
reopen
reload
```

## Stop NGINX

```bash
nginx -s stop
```

This sends a stop signal to the NGINX master process.

## Reload NGINX

```bash
nginx -s reload
```

This reloads the NGINX configuration.

When you modify the NGINX configuration file, the running NGINX process does not automatically use the new
configuration. You need to reload NGINX for the changes to be applied.

The practical use of configuration reloads will become more important when working with NGINX configuration later in the
course.

---

# 13. Start vs. Enable

One of the most important concepts in this lab is the difference between:

```bash
systemctl start nginx
```

and:

```bash
systemctl enable nginx
```

They perform two different operations.

### `systemctl start nginx`

```text
Start NGINX now
```

It starts the service immediately, but it does **not** necessarily configure the service to start after future reboots.

### `systemctl enable nginx`

```text
Configure NGINX to start automatically during boot
```

It configures systemd so that NGINX will be started automatically when the appropriate boot target is reached.

Therefore:

```text
start  → Run the service now
enable → Start the service automatically on future boots
```

For a production server, these are separate but complementary operations.

---

# 14. Enable NGINX at Boot

Enable the service:

```bash
systemctl enable nginx
```

This creates the required systemd symbolic link under the appropriate boot target.

For example:

```text
/etc/systemd/system/multi-user.target.wants/nginx.service
```

This connects the NGINX service to the `multi-user.target` boot target.

As a result, systemd will automatically start NGINX during the normal boot process.

---

# 15. Verify Automatic Startup

After enabling the service, reboot the server:

```bash
reboot
```

Reconnect to the machine after it becomes available.

Then check:

```bash
systemctl status nginx
```

NGINX should already be running.

This confirms that NGINX has been configured to start automatically after an operating-system reboot.

# Practical Notes / Best Practices

- Running NGINX manually is not sufficient for production environments.
- Add NGINX to systemd so the operating system can manage the process.
- **Creating a service file does not automatically enable startup at boot.**
- Use `systemctl start nginx` to start NGINX immediately.
- Use `systemctl enable nginx` to configure automatic startup after reboot.
- Use `systemctl status nginx` when verifying or troubleshooting the service.
- Always make sure the paths in `nginx.service` match your actual NGINX installation.
- Pay particular attention to the NGINX binary path when NGINX was installed from source.
- The PID file path in the service definition must match the PID file generated by NGINX.
- Run `nginx -t` before starting or reloading NGINX to verify the configuration.
- Use `nginx -s reload` when configuration changes need to be applied to an already-running NGINX process.

## Key Takeaway

The goal of this lab is to move NGINX from a **manually managed process** to an **OS-managed systemd service**.

The most important distinction to remember is:

```text
systemctl start nginx
        ↓
Start NGINX now
```

versus:

```text
systemctl enable nginx
        ↓
Configure NGINX to start automatically on future boots
```

For a resilient production setup, you typically need both.
