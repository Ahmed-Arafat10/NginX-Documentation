# Lab: Add NGINX as a Service in the Operating System

## Lecture Title

**Add NGINX Process in systemd Services to Make the Web Server Resilient**

## Overview

NGINX can be added to the operating system as a **systemd service** so that the web server becomes more resilient and
easier to manage in a production environment.

The main benefits are:

- NGINX can be started and stopped using `systemctl`.
- NGINX can be restarted easily.
- The operating system can monitor and manage the NGINX service.
- NGINX can be configured to start automatically after a system reboot.
- Manual intervention is reduced after crashes, reboots, or scheduled maintenance.

The lecture demonstrates the process on **Ubuntu**, while explaining that the general procedure is similar on Ubuntu and
CentOS-based systems that support systemd. The instructor specifically mentions Ubuntu 15.4+ and CentOS 7.0+ as
supporting systemd. Pasted text

# 1. Why Add NGINX as a Service?

NGINX is commonly used as the **front-end web server** for an application.

A typical request flow is:

```text
User
  |
  v
NGINX
  |
  v
Web Application / Backend
```

If the NGINX process stops, the front end can no longer accept incoming user requests. Therefore, a production
environment should minimize the amount of time NGINX remains unavailable.

### Without a Service

If NGINX is running as a manually started process:

1. NGINX is started manually.
2. The machine reboots.
3. The NGINX process is terminated.
4. Someone must manually connect to the machine.
5. NGINX must be started again.
6. Until this happens, the front end remains unavailable.

This can increase production downtime. Pasted text

### With systemd

When NGINX is configured as a systemd service:

```text
NGINX process
     |
     v
systemd service
     |
     +---- Start / Stop / Restart
     |
     +---- Service status
     |
     +---- Automatic startup after boot
```

The operating system can manage the process as a service.

# 2. What Is systemd?

**systemd** is the service-management system used by modern Linux distributions.

A process managed through systemd can be treated as an operating-system service.

The instructor describes this as making the process more **resilient**.

In this context, resilience means that the service can be managed automatically when:

- The process exits.
- The process crashes.
- The operating system reboots.
- The machine is powered off and powered on again.

The lecture's main focus is automatic startup after reboot and making NGINX easier to manage as a production service.

# 10. Enable NGINX to Start Automatically at Boot

To configure NGINX to start automatically when the operating system boots, execute:

```bash
systemctl enable nginx
```

This creates the required symbolic link for the service under the systemd target structure.

The instructor observes a symlink being created under the systemd multi-user target:

```text
/etc/systemd/system/multi-user.target.wants/nginx.service
```

This connects the NGINX service to the appropriate boot target. Pasted text

### Important Concept

There is a difference between:

```bash
systemctl start nginx
```

and:

```bash
systemctl enable nginx
```

`start`:

```text
Start NGINX now
```

`enable`:

```text
Configure NGINX to start automatically during boot
```

Therefore, for a production server, both concepts are important.

# Practical Notes / Best Practices

- **Running NGINX manually is not sufficient for production resilience.** A reboot can terminate the manually running
  process.
- **Adding a systemd service and enabling the service are separate operations.**
- Use `systemctl start nginx` to start the service immediately.
- Use `systemctl enable nginx` to configure automatic startup during boot.
- Use `systemctl status nginx` to troubleshoot and verify the service state.
- Make sure the paths in the service file match the actual NGINX installation.
- The PID-file location must match the PID file generated by NGINX.
- Use `nginx -t` to validate the configuration before starting or reloading NGINX.
- `nginx -s reload` is used when configuration changes need to be applied to the running NGINX process.
- Automatic service startup helps reduce production downtime following reboots or planned maintenance.

## Key Takeaway

The main objective of this lab is to move NGINX from a **manually managed process** to an **OS-managed systemd
service**.

The important distinction is:

```text
systemctl start nginx
        ↓
Start NGINX now

systemctl enable nginx
        ↓
Start NGINX automatically on future boots
```

Together, these capabilities make NGINX more resilient and improve availability in a production environment. The
instructor emphasizes that these are basic concepts, but they are particularly useful for production systems where
availability and minimizing manual intervention are important. Pasted text
