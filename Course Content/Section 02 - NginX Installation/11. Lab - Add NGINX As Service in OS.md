# 11. Lab — Add NGINX as a Service in the Operating System

## Lecture Title

**Add NGINX Process to systemd Services to Make the Web Server Resilient**

## Overview

When NGINX is installed from source and started manually, it runs as a normal process. This means that if the server is rebooted, the NGINX process stops and must be started manually again.

To make NGINX easier to manage and more resilient, we can register it as a **systemd service**.

Once NGINX is configured as a systemd service, the operating system can:

- Start NGINX.
- Stop NGINX.
- Restart NGINX.
- Monitor the NGINX service status.
- Start NGINX automatically after a system reboot.
- Reduce manual intervention after reboots or maintenance.

The main goal of this lab is to move NGINX from a manually managed process to an **OS-managed systemd service**.

---

# 1. Why Add NGINX as a Service?

NGINX is commonly used as the front-end web server for an application.

A typical request flow is:

```text
User
  |
  v
NGINX
  |
  v
Web Application / Backend
```

If NGINX stops, the front end can no longer accept incoming requests.

Therefore, in a production environment, NGINX should be managed by the operating system so that it can be started automatically and controlled reliably.

---

## Without systemd

If NGINX is started manually:

```text
1. Start NGINX manually
        ↓
2. Server reboots
        ↓
3. NGINX process terminates
        ↓
4. Connect to the server manually
        ↓
5. Start NGINX again
        ↓
6. Application becomes available
```

During this period, the front end is unavailable.

---

## With systemd

When NGINX is configured as a systemd service:

```text
                 systemd
                    |
        +-----------+-----------+
        |           |           |
      Start       Stop       Restart
        |
      Status
        |
   Auto-start
    after boot
```

The operating system becomes responsible for managing NGINX as a service.

---

# 2. Demonstrate the Problem

Before creating the systemd service, NGINX can be started manually:

```bash
nginx
```

At this point, NGINX is running and the web server can be accessed through the server's IP address.

Now reboot the server:

```bash
reboot
```

After the machine comes back online, reconnect to the server and check the NGINX process.

NGINX will no longer be running because it was started manually rather than as an automatically managed service.

This demonstrates why production NGINX installations should be integrated with systemd.

---

# 3. Create the NGINX systemd Service

Create the following service file:

```text
/etc/systemd/system/nginx.service
```

> **Important:** In this environment, use `/etc/systemd/system/nginx.service`, not `/lib/systemd/system/nginx.service`.

Create or edit the file:

```bash
nano /etc/systemd/system/nginx.service
```

Add the following configuration:

```ini
[Unit]
Description=The NGINX HTTP and reverse proxy server
After=syslog.target network-online.target remote-fs.target nss-lookup.target
Wants=network-online.target

[Service]
Type=forking
PIDFile=/run/nginx.pid
ExecStartPre=/usr/bin/nginx -t
ExecStart=/usr/bin/nginx
ExecReload=/usr/bin/nginx -s reload
ExecStop=/bin/kill -s QUIT $MAINPID
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

### Important

The NGINX binary path in this service file is:

```text
/usr/bin/nginx
```

This is important because NGINX was installed from source in the environment used in the previous lab.

Do **not** blindly copy a service file that uses:

```text
/usr/sbin/nginx
```

if your actual NGINX binary is located at:

```text
/usr/bin/nginx
```

You can verify the actual location with:

```bash
which nginx
```

Expected result:

```text
/usr/bin/nginx
```

# 4. Understand the Service File

## `[Unit]`

The `[Unit]` section describes the service and specifies its dependencies and startup order.

```ini
[Unit]
Description=The NGINX HTTP and reverse proxy server
After=syslog.target network-online.target remote-fs.target nss-lookup.target
Wants=network-online.target
```

### Description

```ini
Description=The NGINX HTTP and reverse proxy server
```

Provides a human-readable description of the service.

### After

```ini
After=syslog.target network-online.target remote-fs.target nss-lookup.target
```

Specifies services/targets that should be available before NGINX is started.

### Wants

```ini
Wants=network-online.target
```

Indicates that the network should be available when NGINX starts.

---

# 5. `[Service]` Configuration

The `[Service]` section defines how systemd starts and manages NGINX.

```ini
[Service]
Type=forking
PIDFile=/run/nginx.pid
ExecStartPre=/usr/bin/nginx -t
ExecStart=/usr/bin/nginx
ExecReload=/usr/bin/nginx -s reload
ExecStop=/bin/kill -s QUIT $MAINPID
PrivateTmp=true
```

---

## Type

```ini
Type=forking
```

NGINX runs as a process that forks into the background, so the service is configured as a `forking` service.

---

## PIDFile

```ini
PIDFile=/run/nginx.pid
```

This tells systemd where the NGINX master process PID file is located.

The PID file location must match the location used by the actual NGINX installation.

You can verify the configured PID path in your NGINX configuration.

---

## ExecStartPre

```ini
ExecStartPre=/usr/bin/nginx -t
```

Before starting NGINX, systemd executes:

```bash
/usr/bin/nginx -t
```

The `-t` option tests the NGINX configuration.

This helps ensure that the configuration is valid before NGINX is started.

---

## ExecStart

```ini
ExecStart=/usr/bin/nginx
```

This is the command systemd uses to start NGINX.

---

## ExecReload

```ini
ExecReload=/usr/bin/nginx -s reload
```

This reloads the NGINX configuration.

When the NGINX configuration is modified, the running NGINX process does not automatically use the new configuration. A reload is required.

```bash
nginx -s reload
```

The reload mechanism will be explored in greater detail when NGINX configuration is covered later.

---

## ExecStop

```ini
ExecStop=/bin/kill -s QUIT $MAINPID
```

This sends the `QUIT` signal to the NGINX master process, allowing NGINX to stop gracefully.

---

## PrivateTmp

```ini
PrivateTmp=true
```

Enables a private temporary directory for the service.

---

# 6. `[Install]` Configuration

The `[Install]` section defines how the service is integrated into systemd targets.

```ini
[Install]
WantedBy=multi-user.target
```

The `multi-user.target` is the target used when the system reaches its normal multi-user operating state.

This configuration allows NGINX to be enabled so that it starts automatically during boot.

---

# 7. Reload systemd Configuration

After creating or modifying a systemd service file, reload systemd's configuration:

```bash
systemctl daemon-reload
```

This tells systemd to re-read the available service definitions.

> **Important:** Creating or modifying `nginx.service` does not automatically cause systemd to reload the file.

---

# 8. Start NGINX Through systemd

Start the service:

```bash
systemctl start nginx
```

This starts NGINX through systemd rather than launching the NGINX binary manually.

---

# 9. Check NGINX Service Status

Check the service:

```bash
systemctl status nginx
```

The status output provides information such as:

- Whether NGINX is running.
- The main process ID.
- Child process information.
- Service description.
- Recent service activity.
- Whether the service started successfully.

A successful status should show that NGINX is active and running.

---

# 10. Stop NGINX

To stop NGINX through systemd:

```bash
systemctl stop nginx
```

This tells systemd to stop the NGINX service.

---

# 11. Restart NGINX

To restart NGINX:

```bash
systemctl restart nginx
```

After restarting, verify the service:

```bash
systemctl status nginx
```

The status should show that NGINX is running again.

---

# 12. Test the NGINX Configuration

Before starting or reloading NGINX, you can validate the configuration:

```bash
nginx -t
```

A successful test confirms that the NGINX configuration syntax is valid.

This command is also automatically executed by the service definition before startup:

```ini
ExecStartPre=/usr/bin/nginx -t
```

# 13. NGINX Signals

NGINX supports several signals that can be sent to the master process.

Display the available options:

```bash
nginx -h
```

The lecture introduces signals including:

```text
stop
quit
reopen
reload
```

Two particularly important signals are `stop` and `reload`.

---

## Stop NGINX

```bash
nginx -s stop
```

This sends the stop signal to NGINX.

---

## Reload NGINX

```bash
nginx -s reload
```

This reloads the NGINX configuration.

For example, after modifying:

```text
/etc/nginx/nginx.conf
```

you can test the configuration:

```bash
nginx -t
```

and then reload NGINX:

```bash
nginx -s reload
```

This allows the running NGINX process to use the updated configuration.

When managing NGINX through systemd, the equivalent operation is:

```bash
systemctl reload nginx
```

provided the service definition includes the appropriate `ExecReload` command.

---

# 14. Enable NGINX to Start Automatically

Starting the service with:

```bash
systemctl start nginx
```

only starts NGINX **right now**.

It does not automatically configure NGINX to start after the next reboot.

To enable automatic startup:

```bash
systemctl enable nginx
```

This creates the required systemd relationship under:

```text
/etc/systemd/system/multi-user.target.wants/nginx.service
```

The service is now associated with the `multi-user.target` boot target.

---

# 15. Start vs. Enable

This distinction is extremely important.

### `systemctl start`

```bash
systemctl start nginx
```

Means:

```text
Start NGINX now.
```

### `systemctl enable`

```bash
systemctl enable nginx
```

Means:

```text
Configure NGINX to start automatically during future boots.
```

Therefore:

```text
start  → affects the current system state
enable → affects future system boots
```

You will commonly use both:

```bash
systemctl start nginx
systemctl enable nginx
```

---

# 16. Reboot and Verify Automatic Startup

After enabling NGINX, reboot the server:

```bash
reboot
```

Wait for the server to come back online, then reconnect through SSH.

Check the NGINX service:

```bash
systemctl status nginx
```

NGINX should already be running.

This confirms that systemd successfully starts NGINX automatically when the operating system boots.

# Practical Notes / Best Practices

- Store the custom service definition in:
  ```text
  /etc/systemd/system/nginx.service
  ```
- Make sure the paths in the service file match your actual NGINX installation.
- In this source-code installation, the NGINX binary is:
  ```text
  /usr/bin/nginx
  ```
- Do not use `/usr/sbin/nginx` unless that is actually where your NGINX binary exists.
- Make sure `PIDFile` matches the PID location configured by NGINX.
- Run:
  ```bash
  nginx -t
  ```
  before starting or reloading NGINX.
- After creating or modifying the service file, run:
  ```bash
  systemctl daemon-reload
  ```
- `systemctl start` starts NGINX immediately but does not enable boot-time startup.
- `systemctl enable` configures NGINX to start automatically during boot.
- Always test automatic startup by rebooting the server and checking:
  ```bash
  systemctl status nginx
  ```

# Key Takeaway

The goal of this lab is to transform NGINX from a manually managed process into an **operating-system-managed systemd service**.

The two most important commands to remember are:

```bash
systemctl start nginx
```

**Start NGINX now.**

and:

```bash
systemctl enable nginx
```

**Start NGINX automatically after future system boots.**

For a source-built NGINX installation, always ensure that the systemd service points to the **actual installed binary**, which in this environment is:

```text
/usr/bin/nginx
```
