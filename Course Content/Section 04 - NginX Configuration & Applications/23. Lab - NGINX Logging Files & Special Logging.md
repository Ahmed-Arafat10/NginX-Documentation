# 23. Lab — NGINX Logging Files & Special Logging

## Overview

NGINX provides logging mechanisms that record information about server activity, requests, and errors.

By default, the NGINX logging configuration includes two important files:

- **`access.log`** — records requests made to the NGINX web server.
- **`error.log`** — records errors and configuration/runtime problems related to NGINX.

This lab demonstrates:

1. The difference between `access.log` and `error.log`.
2. How requests are recorded in the access log.
3. Why a `404` response appears in the access log.
4. How configuration errors appear in the error log.
5. How to create a separate access log for a specific URI.
6. How to disable logging for a specific URI.
7. Why access logs may be distributed while keeping a common error log.

---

# 1. Default NGINX Log Files

The lab starts by examining the NGINX log directory.

```bash
cd /var/log/nginx
```

Listing the directory shows the default log files:

```bash
ls -l
```

Typically, the two files discussed in the lecture are:

```text
access.log
error.log
```

### `access.log`

The access log contains information about requests received by NGINX.

The lecture describes entries containing information such as:

- Request timestamp
- Request URI
- HTTP protocol
- HTTP status code
- Amount of data transferred
- Client information
- Client version/user-agent information

### `error.log`

The error log contains errors and other NGINX-related error information.

For example, it can contain:

- Configuration errors
- Missing resources
- NGINX processing errors
- Other server-side error information

# 3. Monitoring Logs with `tail -f`

To watch new log entries as they are written, the lecture uses:

```bash
tail -f /var/log/nginx/access.log
```

and:

```bash
tail -f /var/log/nginx/error.log
```

The `-f` option keeps the command running and displays new lines as they are appended to the file.

This is particularly useful when troubleshooting NGINX because you can:

1. Keep the logs open in one terminal.
2. Generate a request from a browser or another terminal.
3. Immediately observe the corresponding log entry.

```text
http://SERVER_IP:8081/
```

The access log then receives multiple entries.

```text

```

```text
CSS files
JavaScript files
Images
Other static resources
```

Each request is recorded in the access log.

# 5. Information Recorded in the Access Log

The lecture demonstrates that access-log entries contain multiple pieces of request information.

Conceptually, an entry includes:

```text
Timestamp
Client
Request
Protocol
Status
Transferred data
Client information
```

For example, a request can be represented conceptually as:

```text
GET /some-resource HTTP/1.1
```

along with a status such as:

```text
200
```

The status code indicates how NGINX handled that request.

A successful request in the lab produces a `200` response.

# 6. Understanding `404` in NGINX Logs

The lecture intentionally requests a URI that does not exist.

For example:

```text
/something-that-does-not-exist
```

The browser receives:

```text
404 Not Found
```

The important point demonstrated by the lab is that **the request still appears in `access.log`**.

This is because `404` is an HTTP response status generated for a valid request that could not be fulfilled.

At the same time, NGINX can record a related error message in `error.log`, explaining why the resource could not be
served.



---

# 7. `404` Does Not Mean "Only Error Log"

A common misconception addressed in the lecture is:

> If a request produces `404`, it should only appear in `error.log`.

The lab demonstrates that this is incorrect.

A `404` request is still a request made to NGINX, so it is recorded in the access log.

Conceptually:

```text
Client
  │
  ▼
GET /missing-resource
  │
  ├── access.log
  │      └── GET /missing-resource → 404
  │
  └── error.log
         └── information explaining the missing resource
```

Therefore, when searching for `404` requests, the lecture specifically recommends looking in **`access.log`**.

# 8. Testing a Configuration Error

The lab next introduces an intentionally invalid NGINX configuration.

For example, a syntax element is removed so that the configuration becomes invalid.

When NGINX is reloaded, an error is generated.

The same configuration error can then be observed in:

```text
/var/log/nginx/error.log
```

The lecture demonstrates an error similar to:

```text
unexpected "}" ...
```

along with the relevant configuration line.

This illustrates an important distinction:

- **Request-related information** → primarily observed in `access.log`.
- **NGINX configuration/server errors** → observed in `error.log`.

After correcting the configuration and reloading NGINX, the error disappears and the normal reload-related log entry is
observed.

# 9. Special Logging with `access_log`

NGINX allows access logging to be customized for specific locations.

The lecture demonstrates this using a location named:

```text
/user_data
```

The location returns a simple response:

```nginx
location /user_data {
    return 200 "User data is published";
}
```

The goal is to send requests for this URI to a **separate access log file**.

---

# 10. Creating a Separate Access Log

The `access_log` directive is used to specify where requests should be logged.

Conceptually:

```nginx
location /user_data {
    return 200 "User data is published";

    access_log /var/log/nginx/access_user.log;
}
```

Now requests to:

```text
/user_data
```

are written to:

```text
/var/log/nginx/access_user.log
```

instead of the normal access log demonstrated in the lab.

After reloading NGINX and requesting:

```text
http://SERVER_IP:8081/user_data
```

the response is:

```text
User data is published
```

and a corresponding entry appears in:

```text
access_user.log
```

---

# 11. Verifying the Separate Log

The lecture checks the NGINX log directory:

```bash
ls
```

A new file appears:

```text
access_user.log
```

The file can then be monitored with:

```bash
tail -f /var/log/nginx/access_user.log
```

When the browser requests:

```text
/user_data
```

the new request appears in the dedicated log.

The lecture demonstrates that this request is not being written to the normal `access.log` in this configuration.

# 12. Why Separate Access Logs Are Useful

A website can contain many different URI groups, for example:

```text
/user_data
/user_registration
/forgot_password
/api
/video
```

A separate access log can be configured for a particular URI or group of requests.

This can make it easier to analyze traffic associated with a specific application area.

Conceptually:

```text
                NGINX
                  │
        ┌─────────┴─────────┐
        │                   │
   General traffic      Special URI
        │                   │
        ▼                   ▼
  access.log        access_user.log
```

The lecture presents this as particularly useful for sites with many URIs and significant traffic.

---

# 13. Disabling Logging for a Specific URI

NGINX can also disable access logging for a particular location.

The lecture demonstrates this using:

```nginx
access_log off;
```

For example:

```nginx
location /user_data {
    return 200 "User data is published";

    access_log off;
}
```

With this configuration, requests to `/user_data` are not written to an access log.

After reloading NGINX and repeatedly requesting the URI, the lecture verifies that no new access-log entry is generated
for that request.

---

# 14. When Disabling Logging Can Be Useful

The lecture discusses this in the context of a **high-traffic website**.

If certain requests generate a very large amount of repetitive traffic and the requests do not need to be retained in
the access logs, logging for those requests can be disabled.

Conceptually:

```text
High traffic
     │
     ├── Important requests → Log
     │
     └── Requests not requiring logging → access_log off
```

This can reduce the amount of information written to the access logs.

---

# 15. Distributing Access Logs

The lecture recommends a logging strategy in which:

- A common error log is maintained.
- Access logs can be distributed across different files according to URI or resource.

For example:

```text
/var/log/nginx/
├── access.log
├── access_user.log
├── access_registration.log
├── access_password.log
└── error.log
```

The rationale given in the lecture is that access logs can grow quickly on a heavily trafficked website.

Separating access logs by URI/resource can make it easier to analyze a particular area when a request or resource is
experiencing problems.

# 17. Common Mistakes and Warnings

### Mistake 1: Searching only `error.log` for `404`

A `404` request is still recorded in the access log.

When analyzing which URLs are producing `404` responses, inspect:

```text
access.log
```

### Mistake 2: Confusing request errors with configuration errors

A missing resource and an invalid NGINX configuration are different situations.

- Missing requested resource → can result in a `404` access-log entry and related error information.
- Invalid NGINX configuration → produces configuration errors in `error.log`.

### Mistake 3: Forgetting to reload after changing logging configuration

Changes to the NGINX configuration must be reloaded before they take effect:

```bash
nginx -s reload
```

### Mistake 4: Not checking the correct log file

If a location has:

```nginx
access_log /var/log/nginx/access_user.log;
```

requests for that location should be investigated in the dedicated log.

### Mistake 5: Disabling logs without considering their usefulness

`access_log off;` removes those requests from access logging, so it should be used deliberately when those requests do
not need to be recorded.

---

# 18. Key Takeaways

- NGINX has two primary default log files:
    - `access.log`
    - `error.log`
- `access.log` records requests handled by NGINX.
- `error.log` records NGINX errors and related error information.
- A `404` response appears in the access log because it is still an HTTP request/response.
- Configuration syntax errors are recorded in the error log.
- `tail -f` is useful for watching logs in real time.
- `access_log` can create a separate log file for a specific location.
- `access_log off;` disables access logging for a particular location.
- Separate access logs can help analyze different URI groups.
- The lecture recommends keeping a common error log while distributing access logs when dealing with heavy traffic.
