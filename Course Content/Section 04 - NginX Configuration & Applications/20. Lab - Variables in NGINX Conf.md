# 20. Lab — Variables in NGINX Configuration

## Overview

NGINX configuration supports variables that can be used to store and retrieve values during request processing.

Similar to variables in programming languages, NGINX variables allow configuration to work with dynamic values.

NGINX provides:

- **Built-in variables** that are already available.
- **User-defined variables** that can be created inside the configuration.
- Variables that can be used in conditional statements.

The lecture demonstrates how to:

1. Create a variable with the `set` directive.
2. Use built-in NGINX variables.
3. Display variable values in an HTTP response.
4. Read query-string arguments through variables.
5. Use variables inside an `if` condition.
6. Return different responses based on variable values.

---

# 1. What Is an NGINX Variable?

An NGINX variable is a value that can be accessed from the NGINX configuration.

The lecture compares NGINX variables with variables in programming languages: they are used to store and work with
values.

NGINX variables are generally string-valued.

The lecture specifically presents NGINX variables as simple variables containing string values rather than typed
structures such as:

- Integer
- Float
- Array
- List

---

# 2. User-Defined Variables

NGINX allows you to create your own variables.

The `set` directive is used to assign a value to a variable.

General syntax:

```nginx
set $variable value;
```

For example:

```nginx
set $a "hello world";
```

Here:

- `$a` is the variable.
- `hello world` is its value.
- `set` assigns the value to the variable.

The `$` character identifies the variable.

---

# 3. Built-In NGINX Variables

NGINX also provides built-in variables that can be used directly in configuration.

Some variables are provided by NGINX itself, while others can be inherited from third-party libraries.

The lecture introduces several variables:

| Variable               | Purpose                                                  |
|------------------------|----------------------------------------------------------|
| `$args`                | Contains the query-string arguments from the request URI |
| `$body_bytes_sent`     | Number of bytes sent to the client                       |
| `$body_bytes_received` | Number of bytes received from the client                 |
| `$connection_requests` | Number of requests made through the current connection   |
| `$date_local`          | Current local time                                       |
| `$hostname`            | Hostname of the machine                                  |
| `$nginx_version`       | NGINX version                                            |

The lecture focuses practically on variables such as `$hostname`, `$args`, `$connection_requests`, and `$nginx_version`.

---

# 4. `$args`

The `$args` variable contains the arguments passed in the request URI.

For example:

```text
/find?api_key=1234
```

The query-string portion is:

```text
api_key=1234
```

Therefore, `$args` can be used to access the query-string arguments.

If no arguments are supplied:

```text
/find
```

then `$args` does not contain a query-string value.

---

# 5. `$hostname`

The `$hostname` variable returns the hostname of the machine running NGINX.

For example, the response might contain:

```text
ubuntu-custom-nginx
```

The actual value depends on the hostname configured on the server.

---

# 6. `$connection_requests`

The `$connection_requests` variable represents the current number of requests made through the connection.

The instructor demonstrates this variable by repeatedly refreshing the browser.

For example:

```text
Request 1 → 6
Request 2 → 7
Request 3 → 8
Request 4 → 9
```

The exact numbers depend on the connection/request history.

The important observation is that the displayed request count changes as additional requests are made.

---

# 7. `$nginx_version`

The `$nginx_version` variable returns the version of NGINX running on the server.

For example, the response might contain a value similar to:

```text
1.19.1
```

The exact version depends on the NGINX installation.

---

# 8. Lab: Displaying Variables in an HTTP Response

The instructor creates a custom location called `/find`.

A simplified configuration is:

```nginx
location /find {
    return 200 "$hostname\n$args\n$connection_requests\n$nginx_version";
}
```

The `return` directive sends an HTTP response directly from NGINX.

The response contains:

1. Hostname.
2. Request arguments.
3. Connection request count.
4. NGINX version.

The `\n` sequences are used to separate the values onto different lines.

---


The exact values depend on the server and request.

# 12. Testing `$args`

Initially, the request does not contain query arguments:

```text
/find
```

Therefore:

```text
$args
```

is empty.

Now add a query parameter:

```text
/find?api_key=1234
```

The `$args` value becomes:

```text
api_key=1234
```

This demonstrates that `$args` reflects the query-string arguments supplied by the client.

---

# 13. Multiple Query Arguments

The instructor then adds another argument.

For example:

```text
/find?api_key=1234&name=...
```

The `$args` variable contains the query-string portion of the request.

Conceptually:

```text
Request URI
     ↓
/find?api_key=1234&name=...
     ↓
$args
     ↓
api_key=1234&name=...
```

This is useful when NGINX needs to inspect values supplied as query parameters.

---

# 14. Using Variables in Conditional Statements

NGINX variables can also be used in conditional logic.

The lecture demonstrates an `if` statement that checks a request argument.

The idea is:

```text
Read variable
     ↓
Check its value
     ↓
If it matches
     ↓
Return a specific response
```

For example, the configuration checks an argument named `name`.

The relevant built-in variable is:

```nginx
$arg_name
```

This variable represents the value of the `name` request argument.

For example:

```text
/find?name=Anshul
```

allows NGINX to access the value through:

```nginx
$arg_name
```

---

# 15. The `$arg_<name>` Pattern

The lecture demonstrates the variable:

```nginx
$arg_name
```

This corresponds to the query parameter:

```text
name
```

For example:

```text
?name=Anshul
```

can be accessed as:

```nginx
$arg_name
```

This is different from `$args`.

### `$args`

Contains the complete query-string arguments:

```text
api_key=1234&name=Anshul
```

### `$arg_name`

Accesses the value associated with the specific `name` argument:

```text
Anshul
```

---

# 16. Conditional Example

The instructor creates a condition that checks whether the `name` argument has a specific value.

Conceptually:

```nginx
if ($arg_name = Anshul) {
    return 200 "Yes, I am Anshul";
}
```

The exact response text used in the lecture is:

```text
Yes, I am Anshul
```

The purpose of the example is to demonstrate that NGINX can make a decision based on a variable's value.

---

# 17. Testing the Condition

With a request such as:

```text
/find?name=Tom
```

the condition does not match.

Therefore, the custom successful response is not returned.

When the request is changed to:

```text
/find?name=Anshul
```

the condition matches and NGINX returns:

```text
Yes, I am Anshul
```

The demonstration shows:

```text
/find?name=Tom
        ↓
$arg_name = Tom
        ↓
Condition does not match
        ↓
Custom condition response is not returned
```

Whereas:

```text
/find?name=Anshul
        ↓
$arg_name = Anshul
        ↓
Condition matches
        ↓
HTTP 200 + custom message
```

---

# 18. Conditional Configuration Structure

The general structure demonstrated by the lab is:

```nginx
if ($arg_name = Anshul) {
    return 200 "Yes, I am Anshul";
}
```

The important components are:

- `if` — defines the condition.
- `$arg_name` — reads the `name` query argument.
- `=` — compares the value.
- `Anshul` — expected value.
- `return 200` — returns an HTTP 200 response when the condition is satisfied.

# 20. Working with Variables: Overall Flow

The complete concept demonstrated by the lab is:

```text
Client Request
      │
      ↓
NGINX receives request
      │
      ↓
NGINX evaluates variables
      │
      ├── $hostname
      ├── $args
      ├── $connection_requests
      ├── $nginx_version
      └── $arg_name
      │
      ↓
Configuration can use the values
      │
      ↓
Return response / apply condition
```

This allows NGINX configuration to behave dynamically based on request information and server information.

# 22. Built-In vs. User-Defined Variables

There are two broad categories discussed in the lecture.

### Built-In Variables

Provided by NGINX or an associated library.

Examples:

```nginx
$hostname
$args
$connection_requests
$nginx_version
```

### User-Defined Variables

Created using the `set` directive.

Example:

```nginx
set $a "hello world";
```

Then the variable can be referenced as:

```nginx
$a
```

# 24. Final Lab Example

A simplified version of the concepts demonstrated in the lecture is:

```nginx
http {
    include mime.types;

    server {
        listen 8081;
        server_name SERVER_IP;

        root /root/blogging-template;

        location /find {
            return 200 "$hostname\n$args\n$connection_requests\n$nginx_version";
        }

        if ($arg_name = Anshul) {
            return 200 "Yes, I am Anshul";
        }
    }
}
```

A request such as:

```text
http://SERVER_IP:8081/find?api_key=1234&name=Anshul
```

provides NGINX with request information that can be accessed through variables.

The key idea from this lab is that **NGINX variables allow configuration to work with dynamic request and server values
instead of relying only on static configuration values**.
