# 17. NGINX Configuration Terminology

## Overview

NGINX configuration is a fundamental part of the NGINX web server because the configuration file contains the settings
that determine how NGINX behaves and how it handles requests.

The NGINX configuration file can be considered the **heart of the NGINX web server**. Through configuration, you can:

- Customize the NGINX web server for your requirements.
- Change how NGINX handles connections and requests.
- Configure HTTP and HTTPS behavior.
- Configure virtual hosts.
- Configure load balancing and upstream servers.
- Configure worker processes and connections.
- Control settings that apply globally or to specific parts of the configuration.

Before making practical configuration changes, it is important to understand the terminology and structure used by NGINX
configuration files.

---

# 1. NGINX Configuration File Structure

The NGINX configuration file is organized using a **tree-like structure**.

This structure is defined through curly braces:

```nginx
{
    ...
}
```

A typical configuration contains different blocks, such as:

```nginx
events {
    ...
}

http {
    ...
}
```

Each block can contain directives and, in some cases, other nested blocks.

The configuration therefore follows a parent-child relationship:

```text
Main / Global Context
│
├── events Context
│
└── http Context
    │
    ├── server Context
    │   ├── location Context
    │   └── location Context
    │
    ├── server Context
    │   └── location Context
    │
    └── upstream Context
```

The scope of configuration elements is determined by the curly-brace blocks in which they are defined.

---

# 2. Context

A **context** is a complete block of NGINX configuration defined between curly braces.

For example:

```nginx
server {
    ...
}
```

The section between the `{` and `}` is a context.

Contexts are important because NGINX documentation frequently refers to the **context** in which a directive can be
used.

NGINX can have multiple contexts, and contexts can be layered or nested within one another.

For example:

```nginx
http {
    server {
        location / {
            ...
        }
    }
}
```

Here:

- `http` is a context.
- `server` is a child context of `http`.
- `location` is a child context of `server`.

This creates the tree-based structure used by NGINX.

---

# 3. Directive

A **directive** is a configuration setting defined inside an NGINX configuration context.

Directives are generally written as key-value pairs and normally end with a semicolon:

```nginx
directive value;
```

For example:

```nginx
listen 80;
server_name localhost;
index index.html index.htm;
root /usr/share/nginx/html;
```

In the sample configuration discussed in the lecture:

### Server Context

```nginx
server {
    listen 80;
    server_name localhost;
}
```

- `listen 80;` is a directive for the `server` context.
- `server_name localhost;` is another directive for the `server` context.

### Location Context

```nginx
location / {
    index index.html index.htm;
}
```

- `index index.html index.htm;` is a directive for the `location` context.

Another location can contain:

```nginx
location /something {
    root /usr/share/nginx/html;
}
```

- `root /usr/share/nginx/html;` is a directive for that `location` context.

### Context vs. Directive

The distinction is important:

- **Context** → everything defined between curly braces.
- **Directive** → a configuration setting defined inside a context.

---

# 4. Main / Global Context

The **main context**, also called the **global context**, is the broadest NGINX configuration context.

Unlike other contexts, it is **not contained inside a curly-brace block**.

For example, in a typical `nginx.conf` file, configuration appearing before the `events` context belongs to the
main/global context:

```nginx
user nobody;
worker_processes 1;

error_log /var/log/nginx/error.log;
pid /var/run/nginx.pid;

events {
    ...
}
```

The directives before `events` belong to the global context.

Common settings configured in the main context include:

- User used to execute NGINX processes.
- Group associated with that user.
- Number of worker processes.
- Number of worker connections (depending on the applicable configuration context).
- Location of important NGINX files.
- Location of the NGINX process ID (PID) file.
- Global error logging configuration.

For example:

```nginx
user nobody;
worker_processes 1;
pid /var/run/nginx.pid;
```

The main context represents the **broader environment for NGINX**.

A directive placed in the global context can affect the overall NGINX environment and, where applicable, its child
contexts.

Therefore, if a setting needs to apply globally to the NGINX environment, it belongs in the appropriate global/main
context.

---

# 5. Events Context

The `events` context is a **child of the main/global context**.

It is used to configure global options that affect how NGINX handles connections.

Basic structure:

```nginx
events {
    ...
}
```

NGINX uses an **event-based connection processing model**. Directives inside the `events` context determine how worker
processes handle connections.

One important setting discussed in the lecture is the number of worker connections.

For example:

```nginx
events {
    worker_connections 1024;
}
```

The `events` context is therefore concerned with connection handling at a general level.

The important relationship is:

```text
Main / Global Context
└── events Context
```

The `events` context is not a sibling of the main context; it is contained within the main context.

---

# 6. HTTP Context

The `http` context is one of the most important and typically one of the longest sections of an NGINX configuration
file.

Basic structure:

```nginx
http {
    ...
}
```

The `http` context contains the directives and other contexts required for handling:

- HTTP connections.
- HTTPS connections.

Because handling HTTP and HTTPS traffic is one of the primary responsibilities of the NGINX web server, the `http`
context can contain a large portion of the overall configuration.

A simplified structure can look like:

```nginx
http {
    # HTTP-level directives

    server {
        ...
    }

    server {
        ...
    }

    upstream backend {
        ...
    }
}
```

The `http` context is a **sibling of the `events` context**.

They should therefore be placed at the same level:

```nginx
events {
    ...
}

http {
    ...
}
```

They should **not** be nested inside one another.

---

# 7. Server Context

The `server` context is declared inside the `http` context.

```nginx
http {
    server {
        ...
    }
}
```

You can define multiple `server` blocks as required.

For example:

```nginx
http {
    server {
        ...
    }

    server {
        ...
    }
}
```

Each server block can handle a particular set of connections and is used to define a **virtual host**.

A server context can determine which virtual host should handle a particular type of request and how that request should
be processed.

This becomes particularly important when configuring:

- Multiple websites.
- Virtual hosts.
- Different domains.
- Load-balancing configurations.

The basic relationship is:

```text
http
└── server
```

The lecture identifies the `server` context as an important context that will be explored further when discussing load
balancing and request handling.

---

# 8. Location Context

The `location` context exists inside a `server` context.

Basic structure:

```nginx
server {
    location / {
        ...
    }
}
```

A server can contain multiple `location` contexts:

```nginx
server {
    location / {
        ...
    }

    location /images/ {
        ...
    }

    location /videos/ {
        ...
    }
}
```

Each location can be used to handle a particular subset of incoming traffic.

The location context provides more specific request matching and processing within a server context.

The lecture also explains that `location` contexts can be nested in certain configurations:

```text
server
├── location
│   └── location
└── location
```

This allows progressively more specific processing criteria to be defined.

The key relationship is:

```text
http
└── server
    ├── location
    ├── location
    └── location
```

The exact request-matching behavior and more advanced use of nested locations will be covered in later lectures.

---

# 9. Upstream Context

The `upstream` context is another important NGINX context, particularly when working with **load balancing**.

It is used to define a named pool of upstream servers to which NGINX can proxy requests.

The basic relationship is:

```text
http
├── server
├── server
└── upstream
```

The `upstream` context belongs inside the `http` context but is outside any particular `server` context.

For example:

```nginx
http {
    upstream backend {
        ...
    }

    server {
        ...
    }
}
```

The `upstream` context defines a pool of servers.

Conceptually:

```text
upstream
├── Server 1
├── Server 2
├── Server 3
└── Server 4
```

NGINX can then proxy requests to the servers in that pool.

---

## 9.1 Multiple Upstream Configurations

Multiple upstream contexts can be defined to handle different types of requests.

For example, an application could have different upstream groups for:

- Static content.
- Dynamic content.
- Video streaming.
- JPG content.
- MP4 content.

Conceptually:

```nginx
upstream static_backend {
    ...
}

upstream video_backend {
    ...
}

upstream dynamic_backend {
    ...
}
```

The appropriate upstream can then be used for the corresponding type of request.

For example:

```text
Video request
    ↓
Video upstream
    ↓
Video servers

Static request
    ↓
Static upstream
    ↓
Static servers
```

This allows specific types of traffic to be handled by specific server pools.

---

## 9.2 Active and Passive/Fallback Servers

The lecture also introduces the idea of defining multiple servers within an upstream configuration, including servers
that can be used for normal processing and servers that can provide failover behavior.

The instructor describes this in terms of:

- Active nodes.
- Passive/failover nodes.
- Proxy targets.

The detailed configuration and behavior of upstream servers will be covered later when load balancing is discussed.

# 10. Mail Context

The `mail` context is described as a **rarely used** NGINX context.

It is relevant when NGINX is being used as a **mail proxy server** rather than only as a web server.

Its purpose is to provide a configuration area for a mail proxy solution.

Conceptually:

```nginx
mail {
    ...
}
```

The lecture notes that the mail context can be defined at the global level.

The mail functionality is therefore separate from the primary HTTP configuration discussed throughout this lecture.

---

# 11. NGINX Context Hierarchy

The main contexts discussed in the lecture can be summarized as follows:

```text
Main / Global Context
│
├── events
│
├── http
│   │
│   ├── server
│   │   ├── location
│   │   ├── location
│   │   └── ...
│   │
│   ├── server
│   │   └── location
│   │
│   └── upstream
│       ├── backend server
│       ├── backend server
│       └── ...
│
└── mail
```

Important relationships:

| Context           | Parent      | Primary Purpose                          |
|-------------------|-------------|------------------------------------------|
| **Main / Global** | None        | Global NGINX configuration               |
| **Events**        | Main        | Connection/event processing              |
| **HTTP**          | Main        | HTTP/HTTPS configuration                 |
| **Server**        | HTTP        | Virtual hosts and request handling       |
| **Location**      | Server      | Handling specific subsets of traffic     |
| **Upstream**      | HTTP        | Defining pools of upstream/proxy servers |
| **Mail**          | Global/Main | Mail proxy configuration                 |

---

# 12. Example Configuration Structure

A simplified configuration demonstrating the relationships discussed in the lecture could look like this:

```nginx
# Main / Global Context
user nobody;
worker_processes 1;

error_log /var/log/nginx/error.log;
pid /var/run/nginx.pid;

# Events Context
events {
    worker_connections 1024;
}

# HTTP Context
http {

    # Upstream Context
    upstream backend {
        server 192.168.1.10;
        server 192.168.1.11;
    }

    # Server Context
    server {
        listen 80;
        server_name localhost;

        # Location Context
        location / {
            index index.html index.htm;
        }

        # Another Location Context
        location /static/ {
            root /usr/share/nginx/html;
        }
    }

    # Another Server Context
    server {
        listen 8080;
        server_name example.com;

        location / {
            ...
        }
    }
}
```

This example demonstrates the tree-like structure:

```text
Main
│
├── events
│
└── http
    │
    ├── upstream
    │
    ├── server
    │   ├── location
    │   └── location
    │
    └── server
        └── location
```

### Extra

#### Question: worker_connections  vs worker_processes

The easiest way to remember the difference is:

> **`worker_processes` = How many workers NGINX creates**  
> **`worker_connections` = How many connections each worker can handle**

### 1. `worker_processes`

Configured in the **main/global context**:

```nginx
worker_processes 4;
```

It controls the **number of NGINX worker processes**.

Think:

```text
NGINX
│
├── Worker 1
├── Worker 2
├── Worker 3
└── Worker 4
```

So `worker_processes 4` → NGINX creates 4 worker processes.

Your lecture specifically describes this as a global setting for the number of worker processes. 

---

### 2. `worker_connections`

Configured inside the **`events` context**:

```nginx
events {
    worker_connections 1024;
}
```

It controls the number of **connections that each worker process can handle**.

Think:

```text
Worker 1 → up to 1024 connections
Worker 2 → up to 1024 connections
Worker 3 → up to 1024 connections
Worker 4 → up to 1024 connections
```

So, conceptually:

```text
worker_processes × worker_connections
        4       ×       1024
        = 4096
```

The lecture identifies `worker_connections` as a setting in the `events` context that determines how worker processes handle connections. 

### The key difference

| Setting | Controls | Context |
|---|---|---|
| `worker_processes` | Number of **workers** | Main / Global |
| `worker_connections` | Connections **per worker** | `events` |

### Simple analogy

Imagine NGINX is a restaurant:

- **`worker_processes`** = number of **waiters**
- **`worker_connections`** = number of **customers each waiter can handle**

So:

```text
4 workers × 1024 connections per worker
```

means you have **4 worker processes**, with a configured capacity of **1024 connections per worker**.

**Important:** The multiplication is a useful conceptual capacity calculation, but the actual maximum concurrent connections can be constrained by other factors (such as OS limits and whether connections are being proxied).


#### Question: how to compute it related to CPU/Ram of the used PC or Server

Yes. The important point is that **CPU and RAM influence the choice differently**:

- `worker_processes` → primarily related to **CPU**
- `worker_connections` → primarily related to **concurrency + OS/file-descriptor limits**, not directly to RAM

### 1. Choosing `worker_processes`

A common starting point is:

```nginx
worker_processes auto;
```

This tells NGINX to choose the number of worker processes based on the available CPU cores.

For example:

```text
Server has 8 CPU cores
        ↓
worker_processes auto
        ↓
approximately 8 worker processes
```

You can check CPU information with:

```bash
nproc
```

or:

```bash
lscpu
```

If `nproc` returns:

```text
8
```

you could explicitly use:

```nginx
worker_processes 8;
```

But generally, `auto` is the convenient starting point.

---

### 2. Choosing `worker_connections`

This is where it gets more interesting.

Suppose you have:

```nginx
worker_processes 8;

events {
    worker_connections 1024;
}
```

The **theoretical configuration capacity** is:

```text
8 × 1024 = 8192 connections
```

But **do not think of 8192 as a guaranteed real-world maximum**.

There are additional limits, especially the operating system's file-descriptor limit.

You can inspect it with:

```bash
ulimit -n
```

For example:

```text
65535
```

That means the process has an OS-level limit of 65,535 open file descriptors (subject to how the service is actually configured).

---

## 3. Where does RAM come into this?

RAM doesn't directly tell you:

> "I have 16 GB RAM, therefore I should use `worker_connections 16384`."

That's not how these two settings are normally calculated.

Instead:

```text
CPU → worker_processes
Concurrency / connections → worker_connections
RAM → application + NGINX memory requirements
```

Each active connection consumes some resources, but the exact memory usage depends heavily on what NGINX is doing.

For example, serving a simple static file is very different from:

```text
Client
  ↓
NGINX
  ↓
Application server
  ↓
Database
```

If NGINX is acting as a reverse proxy, connections and buffers can consume additional memory.

---

## 4. A practical starting point

For a server with:

```text
CPU: 8 cores
RAM: 16 GB
```

I'd start with something like:

```nginx
worker_processes auto;

events {
    worker_connections 4096;
}
```

Then monitor the server rather than trying to calculate a perfect number from RAM alone.

For example:

```bash
top
```

or:

```bash
htop
```

and monitor:

- CPU utilization
- RAM utilization
- Number of active connections
- Network traffic
- Response latency
- Error rates

---

## 5. One very important formula

You can use this as a **rough conceptual upper bound**:

```text
Potential connections
    ≈
worker_processes × worker_connections
```

For example:

```text
4 workers × 2048 connections
= 8192
```

But the actual usable number may be lower because of:

- OS file-descriptor limits
- NGINX limits
- Reverse-proxy connection requirements
- Available CPU
- Available memory
- Application/backend capacity
- Network capacity

So don't simply maximize `worker_connections`.

### Mental model

```text
                 NGINX Server
                     │
          ┌──────────┴──────────┐
          │                     │
        CPU                    RAM
          │                     │
          ↓                     ↓
worker_processes        buffers/connections/
                         applications/etc.
          │
          ↓
    Worker processes
          │
          ↓
worker_connections
          │
          ↓
   Concurrent connections
```

**For your course, remember:** `worker_processes` is the **number of workers**, while `worker_connections` is the **connection capacity configured for each worker**. The lecture establishes these roles, but it does **not** provide a CPU/RAM sizing formula; the CPU/RAM guidance above is additional practical context.
