# 22. Lab — `try_files` in NGINX Configuration

## Overview

The **`try_files`** directive in NGINX is used to check whether a specified file or directory exists.

It is particularly useful when serving static resources such as:

- HTML files
- Images
- Videos
- MP4 files
- Other static content

The lecture demonstrates how `try_files` can make a web server more reliable by checking multiple possible resource
paths and falling back to another location when a requested resource cannot be found.

The directive can be defined inside either a **`location`** block or a **`server`** block.

---

# 1. What Is `try_files`?

The `try_files` directive checks a sequence of possible files, directories, or URIs.

Conceptually, NGINX evaluates the configured options in order:

```text
Request
   ↓
First try_files option
   ↓
Does it exist?
   ├── Yes → use it
   └── No
       ↓
Second option
   ↓
Does it exist?
   ├── Yes → use it
   └── No
       ↓
Next option
   ↓
Fallback / final option
```

The lecture describes this as an internal redirect process: NGINX checks whether the requested path exists and then
processes the appropriate matching option.

---

# 2. Basic Lab Configuration

The lab begins with a simplified NGINX configuration.

A location is created for `/video`:

```nginx
location /video {
    return 200 "Enjoy the movie";
}
```

After saving and reloading NGINX, requesting:

```text
http://SERVER_IP:8081/video
```

returns:

```text
Enjoy the movie
```

This establishes the initial behavior before adding `try_files`.

---

# 3. Defining `try_files`

The lecture demonstrates that `try_files` can be defined inside a `location` or `server` block.

The general concept is:

```nginx
try_files <path1> <path2> <path3>;
```

For example:

```nginx
try_files test_object /video;
```

Here, two possible resources are supplied:

1. `test_object`
2. `/video`

NGINX evaluates the available options according to the configuration.

---

# 4. First `try_files` Example

The initial configuration uses:

```nginx
try_files test_object /video;
```

The request is made for:

```text
/test_object
```

Because the first resource does not exist, NGINX proceeds to the next configured option.

The `/video` location is then used, producing:

```text
Enjoy the movie
```

Conceptually:

```text
/test_object
      ↓
Does test_object exist?
      ↓ No
/video
      ↓
return 200 "Enjoy the movie"
```

This demonstrates the fallback behavior of `try_files`.

The lecture navigates through the existing website resources and locates an image under a path similar to:

```text
/assets/images/about/profile_image.jpg
```

The configuration is then changed so that the image becomes one of the possible `try_files` resources.

The important concept is that `try_files` can check an actual resource path on the server.

# 6. Multiple Valid Options

The lecture demonstrates a situation where both configured resources are valid.

For example, conceptually:

```nginx
try_files <valid-path-1> <valid-path-2>;
```

When the first resource matches, NGINX uses the first matching resource.

This produces an important behavior demonstrated in the lab:

> Once a matching resource is found, the remaining `try_files` options are not evaluated for that request.

Therefore, if the first option is valid, requests such as different URI suffixes can still end up being handled by that
first matching resource under the demonstrated configuration.

---

# 7. Using `$uri`

To make the configuration more useful, the lecture introduces the **`$uri`** variable as the first `try_files` option.

Conceptually:

```nginx
try_files $uri <second-option> <third-option>;
```

The purpose is to first check the URI that the client actually requested.

For example:

```text
/index.html
```

causes NGINX to check whether the corresponding requested resource exists.

If it does, NGINX uses that resource.

---

## Example

Suppose the configuration contains:

```nginx
try_files $uri /some-resource /video;
```

A request for:

```text
/index.html
```

is first evaluated using:

```text
$uri = /index.html
```

If that resource exists, NGINX serves it.

Likewise, a request for an existing image such as:

```text
/assets/welcome.png
```

can resolve directly to that resource.

---

# 8. Fallback Behavior

The power of `try_files` comes from its sequential fallback behavior.

Suppose the configuration contains three resource options:

```nginx
try_files $uri /valid/path /video;
```

The processing can be represented as:

```text
Requested URI
     ↓
   $uri
     ↓
Exists?
 ┌───┴───┐
Yes     No
 ↓       ↓
Serve   /valid/path
        ↓
      Exists?
      ┌──┴──┐
     Yes   No
      ↓     ↓
    Serve  /video
```

The lecture demonstrates that this allows NGINX to attempt multiple possible resources before reaching the final
fallback.

---

# 9. Making the Second Option Invalid

The lab intentionally changes the second resource path to one that does not exist.

Conceptually:

```nginx
try_files $uri /images/files_image.jpg /video;
```

The nonexistent path ensures that NGINX continues to the next option when the requested URI is also unavailable.

For example, if the user requests:

```text
/some-invalid-resource
```

NGINX checks:

1. `$uri`
2. `/images/files_image.jpg`
3. `/video`

If the first two do not match, `/video` becomes the fallback.

The lecture demonstrates this by receiving:

```text
Enjoy the movie
```

for an invalid requested resource.

---

# 10. Using a `404` Fallback

The next step is to create a dedicated 404 response.

A final `try_files` option can point to a `/404` location:

```nginx
try_files $uri /invalid/path /video /404;
```

Then define the corresponding location:

```nginx
location /404 {
    return 404 "Sorry, this resource doesn't exist";
}
```

The exact message in the lecture is used to demonstrate a custom response when the requested resource cannot be found.

---

# 11. Complete Request Flow

With a configuration conceptually structured like:

```nginx
try_files $uri /invalid/path /video /404;
```

the request flow becomes:

```text
                  Request
                     │
                     ▼
                   $uri
                     │
              Resource exists?
                /          \
              Yes           No
               │             │
               ▼             ▼
             Serve       /invalid/path
                              │
                       Exists?
                       /      \
                     Yes       No
                      │         │
                      ▼         ▼
                    Serve      /video
                                  │
                             Exists?
                             /      \
                           Yes       No
                            │         │
                            ▼         ▼
                          Serve      /404
                                      │
                                      ▼
                                  HTTP 404
```

This demonstrates how `try_files` can provide a chain of fallback resources.

# 15. Practical Notes

### Use `try_files` for Resource Existence Checks

The lecture focuses on using `try_files` to determine whether requested resources exist on the server.

This is especially useful when serving static resources.

### Order Matters

The options are evaluated sequentially.

Therefore:

```nginx
try_files $uri /first-fallback /second-fallback;
```

means NGINX checks the first option before moving to the next one.

### The Final Option Provides the Fallback

The lecture demonstrates using the final option as a fallback such as:

```text
/video
```

or:

```text
/404
```

This allows the configuration to define what should happen when earlier options do not match.

---

# 16. Common Mistakes and Warnings

### 1. Assuming Every Option Is Evaluated

`try_files` does not continue processing all options after finding a matching resource.

The first matching option determines the result demonstrated in the lab.

### 2. Forgetting the `$uri` Check

Using `$uri` as the first option allows NGINX to first check the actual requested URI.

For example:

```nginx
try_files $uri ...;
```

is used in the lab to allow valid resources such as `index.html` to be served directly.

### 3. Using a Fallback That Actually Exists

If a fallback resource is valid, NGINX can return that resource instead of reaching a later fallback.

This is why the lecture intentionally changes one resource path to an invalid path when demonstrating the 404 behavior.

### 4. Not Reloading NGINX

After changing the configuration, reload NGINX:

```bash
nginx -s reload
```

### 5. Not Testing Both Valid and Invalid URIs

A `try_files` configuration should be tested with:

- A valid existing file.
- A valid existing image/resource.
- An invalid URI.
- The intended fallback resource.
- The final 404 behavior, when configured.

---

# 17. Key Takeaways

- `try_files` checks whether specified files, directories, or URI targets exist.
- It can be defined inside a `location` or `server` block.
- Multiple parameters can be supplied.
- NGINX evaluates the options sequentially.
- The first matching option is used.
- `$uri` can be used to check the URI requested by the client.
- Additional parameters can act as fallback resources.
- A final option can be used to route unmatched requests to a custom 404 location.
- The lab demonstrates both successful resource resolution and fallback behavior.
- NGINX logs and `curl -i` can be used to verify the resulting HTTP status and response.

## Quick Reference

Basic structure:

```nginx
try_files <first-option> <second-option> <fallback>;
```

Check the requested URI first:

```nginx
try_files $uri <fallback>;
```

Use a custom 404 fallback:

```nginx
try_files $uri /404;

location /404 {
    return 404 "Sorry, this resource doesn't exist";
}
```

### Overall Concept

```text
Client Request
      ↓
    $uri
      ↓
Resource exists?
  ├── Yes → Serve resource
  └── No
       ↓
   Next option
       ↓
   Resource exists?
  ├── Yes → Serve resource
  └── No
       ↓
   Next option
       ↓
     Fallback
```

The central idea of this lab is that **`try_files` gives NGINX a sequence of possible resources to try, allowing the
configuration to serve an existing resource when available and provide a controlled fallback when it is not.**
