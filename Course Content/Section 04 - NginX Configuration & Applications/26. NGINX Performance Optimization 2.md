# 26. NGINX Performance Optimization 2

## Overview

This lecture continues NGINX performance optimization beyond `worker_processes` and `worker_connections`. It focuses on several configuration areas that can affect performance:

- Request buffering
- Client request body and header sizes
- Request timeouts
- Keep-alive connections
- Response send timeouts
- Gzip compression
- Static-file caching
- `sendfile`
- `tcp_nopush`

The lecture emphasizes that performance tuning should be based on the actual characteristics of the application, especially the typical sizes of POST requests, headers, and static assets.

---

## Key Concepts

| Area | Relevant directives / features | Purpose |
|---|---|---|
| Request buffering | `client_body_buffer_size` | Controls buffering for client request bodies |
| Client headers | `client_header_buffer_size` | Controls buffering for client request headers |
| Maximum request body | `client_max_body_size` | Limits the maximum size of a client request body |
| Large headers | `large_client_header_buffers` | Handles unusually large client request headers |
| Request timeouts | `client_body_timeout`, `client_header_timeout` | Controls how long NGINX waits for client request data |
| Keep-alive | `keepalive_timeout` | Controls how long an idle keep-alive connection remains open |
| Response timeout | `send_timeout` | Controls how long NGINX waits while sending a response |
| Compression | `gzip`, `gzip_comp_level`, `gzip_min_length`, `gzip_types` | Reduces response size over the network |

| File serving | `sendfile` | Allows NGINX to serve static files directly from disk |
| TCP optimization | `tcp_nopush` | Optimizes packet handling when sending files |

# 1. Request Buffering

NGINX uses buffers to temporarily hold request data in memory while processing client requests.

For example, consider a client sending a POST request:

```text
Client
  │
  │ POST request + body
  ▼
NGINX
  │
  │ Request body buffered in memory
  ▼
RAM
```

If the configured buffer is too small for the request, NGINX may need to use temporary files, resulting in additional disk I/O.

Because disk reads and writes are generally more expensive than memory operations, excessive disk activity can negatively affect NGINX performance.

### Important consideration

Before selecting a buffer size, determine the typical request sizes that your application accepts.

For example:

- HTML form submissions
- JSON REST API requests
- Other POST request bodies

The goal is not simply to make the buffer as large as possible. Instead, size it according to the application's normal workload.

---

# 2. `client_body_buffer_size`

The `client_body_buffer_size` directive controls the buffer used for the body of a client request.

A request body can contain information such as:

- Form-submission data
- JSON request data
- REST API payloads

Example:

```nginx
http {
    client_body_buffer_size 10k;
}
```

With this configuration, request bodies within the configured buffer size can be handled using the buffer.

The appropriate value depends on the application's normal POST request sizes.

For example:

```nginx
client_body_buffer_size 100k;
```

or:

```nginx
client_body_buffer_size 10m;
```

The lecture recommends identifying the typical POST request size before choosing this value.

---

# 3. `client_header_buffer_size`

Client requests contain headers in addition to the request body.

The `client_header_buffer_size` directive controls the buffer used for client request headers.

Headers can become relatively large when requests contain information such as:

- Credentials
- Cookies
- Other request metadata

Example:

```nginx
client_header_buffer_size 1k;
```

If the request header is larger than the available buffer, NGINX may need additional processing involving temporary storage, which can negatively affect performance.

The lecture therefore recommends sizing this buffer according to the headers normally generated by the application.

---

# 4. `client_max_body_size`

`client_max_body_size` defines the maximum size of a client request body accepted by NGINX.

For example:

```nginx
client_max_body_size 8m;
```

If a client sends a request body larger than the configured maximum, NGINX returns:

```text
413 Request Entity Too Large
```

The lecture uses an 8 MB example:

```nginx
client_max_body_size 8m;
```

Therefore:

```text
Request body <= 8 MB  → accepted
Request body > 8 MB   → 413 response
```

This directive is particularly important for applications that accept:

- File uploads
- Large JSON payloads
- Large form submissions
- Other large POST requests

The configured limit should match the application's actual requirements.

---

# 5. `large_client_header_buffers`

Some requests may contain unusually large headers.

NGINX provides:

```nginx
large_client_header_buffers
```

to configure the number and size of buffers available for large client request headers.

The lecture identifies two parameters associated with this directive:

- The number of buffers
- The size of each buffer

This allows NGINX to accommodate requests whose headers are larger than the normal client header buffer.

---

# 6. Request Timeouts

Timeouts prevent NGINX from waiting indefinitely for clients that are slow or stop sending data.

The lecture discusses several timeout directives:

- `client_body_timeout`
- `client_header_timeout`
- `keepalive_timeout`
- `send_timeout`

Timeout configuration is another important part of NGINX performance tuning, particularly for applications handling large or heavy traffic.

---

# 7. `client_body_timeout`

`client_body_timeout` controls how long NGINX waits for the client to send the request body.

Example:

```nginx
client_body_timeout 30s;
```

If the client does not provide the expected request body within the configured timeout, NGINX can terminate the request.

The lecture associates timeout failures with HTTP status:

```text
408 Request Timeout
```

---

# 8. `client_header_timeout`

`client_header_timeout` controls how long NGINX waits for the client to send request headers.

Example:

```nginx
client_header_timeout 30s;
```

If the client does not send the required headers within the configured time, NGINX can terminate the request.

The lecture also associates this situation with:

```text
408 Request Timeout
```

---

# 9. `keepalive_timeout`

`keepalive_timeout` controls how long a keep-alive connection remains available between the client and NGINX.

Example:

```nginx
keepalive_timeout 15s;
```

A keep-alive connection allows the client and server to reuse an existing connection instead of establishing a new connection for every request.

Conceptually:

```text
Client ─────────────── NGINX
       persistent
       connection
```

When the configured keep-alive timeout expires, NGINX closes the connection.

---

# 10. `send_timeout`

`send_timeout` controls the time NGINX waits while sending a response to a client.

Example:

```nginx
send_timeout 30s;
```

The lecture explains that this timeout is not intended to represent the entire response-transfer duration. Instead, it relates to the interval between successive operations while NGINX is sending the response.

If the client stops accepting data for longer than the configured timeout, NGINX can close the connection.

This is useful when handling slow clients and large responses.

# 11. Gzip Compression

NGINX can compress responses before sending them to clients.

Without compression:

```text
NGINX
  │
  │ Large response
  ▼
Network
  │
  ▼
Client
```

With gzip compression:

```text
NGINX
  │
  │ Compress response
  ▼
Smaller response
  │
  ▼
Network
  │
  ▼
Client
```

The main benefit is reduced network traffic.

However, compression requires CPU resources. Setting the compression level too high can cause NGINX to spend excessive CPU cycles compressing responses.

Therefore, gzip compression requires a balance between:

- Network bandwidth
- Response size
- CPU consumption

---

## 11.1 Basic Gzip Configuration

The lecture provides examples of directives such as:

```nginx
gzip on;
gzip_comp_level 2;
gzip_min_length 1000;
```

You can also specify which content types should be compressed:

```nginx
gzip_types text/plain application/javascript text/xml text/css;
```

A configuration may therefore look like:

```nginx
http {
    gzip on;
    gzip_comp_level 2;
    gzip_min_length 1000;

    gzip_types
        text/plain
        application/javascript
        text/xml
        text/css;
}
```

The exact MIME types should be selected according to the content your application serves.

# 12. Static File Caching

NGINX can also improve performance by configuring caching behavior for static files.

Static files that do not change frequently are good candidates for caching, including:

- JPEG images
- PNG images
- GIF images
- ICO files
- CSS files
- JavaScript files

The lecture explains that expiration headers can be configured for these files so that clients can reuse cached copies rather than repeatedly requesting the same resources.

A typical configuration concept is:

```nginx
location ~* \.(jpg|jpeg|png|gif|ico|css|js)$ {
    expires 365d;
}
```

This tells the client that these static resources can be cached for an extended period.

The lecture uses **365 days** as the example expiration period.

### Why static caching improves performance

Without caching:

```text
Client → Request image
NGINX  → Read image
NGINX  → Send image
Client → Request image again
NGINX  → Read image again
```

With caching:

```text
First request:
Client → NGINX → Static file

Subsequent request:
Client → Local cache
```

This can reduce repeated requests and the amount of work required from the NGINX server.

> **Practical consideration:** Long expiration periods are most appropriate for static assets whose contents do not change unexpectedly. When assets change, cache-busting techniques such as versioned filenames are commonly used.

# 16. `sendfile`

Another performance-related directive discussed in the lecture is:

```nginx
sendfile
```

When enabled:

```nginx
sendfile on;
```

NGINX can serve static files directly from the filesystem without buffering the entire static file in the NGINX buffer.

The lecture describes the flow as:

```text
Disk
  │
  │ static file
  ▼
NGINX
  │
  │ send directly
  ▼
Client
```

This is particularly relevant when NGINX is serving static files.

---

# 17. `tcp_nopush`

The lecture also introduces:

```nginx
tcp_nopush
```

This directive works with the static-file sending path and is presented as a way to optimize how packets are sent.

A configuration can therefore include:

```nginx
sendfile on;
tcp_nopush on;
```

The lecture associates this configuration with optimization of the way NGINX sends file data over TCP.

# 19. Performance Optimization Strategy

The lecture presents several areas that can be tuned together:

```text
                    NGINX Performance
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
     Workers            Buffers           Timeouts
        │                  │                  │
 worker_processes   client_body_buffer   client_body_timeout
 worker_connections  client_header_buffer client_header_timeout
                    client_max_body_size  keepalive_timeout
                    large headers         send_timeout
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                 ┌─────────┴─────────┐
                 │                   │
              Gzip              Static caching
                 │                   │
          Reduce network       Reduce repeated
             transfer            requests
                 │                   │
                 └─────────┬─────────┘
                           │
                    Static file serving
                           │
                    sendfile / tcp_nopush
```

Performance optimization is therefore not controlled by a single directive. NGINX provides multiple configuration mechanisms for controlling concurrency, memory buffering, network transfer, connection lifetime, compression, and static content delivery.

## Practical Notes / Best Practices

### 1. Size buffers according to the application

Do not select arbitrary buffer sizes. First determine the typical:

- POST body size
- JSON payload size
- Request header size

Then configure the buffers accordingly.

### 2. Set a meaningful maximum request size

Use `client_max_body_size` to prevent unexpectedly large request bodies from being accepted.

For example:

```nginx
client_max_body_size 8m;
```

The appropriate limit depends on the application.

### 3. Balance gzip compression and CPU usage

Higher compression can reduce network transfer, but compression also consumes CPU.

Therefore, avoid assuming that the highest compression level is always optimal.

### 4. Cache static assets

Frequently requested static files can benefit from long expiration periods when they are not expected to change frequently.

### 5. Use `sendfile` for static-file delivery

The lecture presents `sendfile` as another mechanism for optimizing static-file serving.

### 6. Tune timeouts deliberately

Timeouts affect how long NGINX waits for clients and connections. Values that are too long can keep resources occupied unnecessarily, while values that are too short can interrupt legitimate slow requests.

---

## Common Mistakes / Warnings

### Buffer size too small

If request data cannot fit into the configured buffer, NGINX may need additional temporary storage and disk I/O, potentially reducing performance.

### `client_max_body_size` too small

If the application accepts large requests but the limit is too low, clients can receive:

```text
413 Request Entity Too Large
```

### Excessive gzip compression

Increasing gzip compression too aggressively can consume significant CPU resources.

### Incorrect timeout values

Very short timeout values can cause legitimate slow clients or requests to fail unexpectedly.

### Long static-cache expiration without cache management

If a static asset is cached for a long period and its content changes, clients may continue using an older cached version. Static asset versioning/cache busting should therefore be considered when using long expiration periods.

## Summary

This lecture extends NGINX performance optimization into several additional configuration areas:

1. **Buffers** control how request data is handled in memory.
2. **`client_body_buffer_size`** handles request-body buffering.
3. **`client_header_buffer_size`** handles normal client headers.
4. **`client_max_body_size`** limits request-body size and can produce HTTP `413`.
5. **`large_client_header_buffers`** handles unusually large headers.
6. **Timeout directives** control how long NGINX waits for clients and connections.
7. **`gzip`** reduces network transfer size at the cost of CPU processing.
8. **Static-file caching** reduces repeated requests for unchanged assets.
9. **`sendfile`** optimizes static-file delivery.
10. **`tcp_nopush`** is presented as an additional TCP/file-transfer optimization.

Together with the worker-process and worker-connection settings from the previous lecture, these mechanisms form the next layer of NGINX performance tuning.
