# 19. Lab — Location Block Context in NGINX

## Overview

The `location` context is one of the most important parts of NGINX request processing.

A `location` block:

- Exists inside a `server` block.
- Determines how NGINX processes a request URI.
- Determines which configuration should handle a particular URI.
- Can be defined multiple times within the same `server` context.
- Can be nested inside another `location` context.
- Supports different matching methods through **modifiers**.

This lab focuses on understanding how NGINX selects a `location` block when multiple locations can potentially match the same request.

---

# 1. Location Context and Its Relationship to Server

The `location` context is a **child of the `server` context**.

The basic hierarchy is:

```text
http
└── server
    ├── location
    ├── location
    └── location
```

A basic location block has this structure:

```nginx
location /path {
    ...
}
```

Multiple location blocks can exist within the same server:

```nginx
server {

    location / {
        ...
    }

    location /contactus {
        ...
    }

    location /about {
        ...
    }
}
```

The location context is responsible for determining how NGINX should process requests for particular URI paths.

---

# 2. Location Context Can Be Nested

A location can also contain another location.

Conceptually:

```text
server
└── location
    └── location
        └── location
```

The lecture explains that there is no stated fixed number of nesting levels in the teaching example.

Nested locations allow increasingly specific request-processing rules to be represented within the configuration.

---

# 3. What Is a Request URI?

When a client requests a website, the request contains a URI.

For example:

```text
http://example.com/
```

has the root URI:

```text
/
```

But a client can request a specific path:

```text
http://example.com/contactus
```

The request URI is:

```text
/contactus
```

Another example:

```text
http://example.com/contactus/about
```

The URI contains additional path information.

The `location` context determines which configuration should be used to process these different URIs.

---

# 4. Location Syntax

The general syntax introduced in the lecture is:

```nginx
location [modifier] [location-match] {
    ...
}
```

For example:

```nginx
location /contactus {
    ...
}
```

or:

```nginx
location = /contactus {
    ...
}
```

or:

```nginx
location ~ /contactus {
    ...
}
```

The important components are:

### `location`

The keyword that begins the location block.

### Modifier

An optional symbol that changes how NGINX performs the location match.

The lecture emphasizes that the modifier is optional, although the instructor prefers explicitly understanding and using the appropriate modifier.

### Location Match

The URI/path against which NGINX performs the match.

The location match itself is required.

### Location Body

The configuration inside the curly braces:

```nginx
location /contactus {
    ...
}
```

---

# 5. Location Without a Modifier — Prefix Match

If no modifier is specified:

```nginx
location /contactus {
    ...
}
```

NGINX interprets the location as a **prefix match**.

This means NGINX compares the location against the **beginning of the request URI**.

For example:

```nginx
location /contactus {
    return 200 "Hello, you are inside custom location";
}
```

This can match:

```text
/contactus
/contactus/
/contactus/about
/contactus/profile
/contactus/anything
```

because the request URI begins with:

```text
/contactus
```

The important concept is:

> A location without a modifier matches the beginning/prefix of the request URI.

---

# 6. Lab: Creating a Basic Location

The lab begins with an existing server configuration.

Inside the `server` context, a location is added:

```nginx
location /contactus {
    return 200 "Hello, you are inside custom location";
}
```

The complete structure is conceptually:

```nginx
server {
    ...

    location /contactus {
        return 200 "Hello, you are inside custom location";
    }
}
```

The `return` directive is used to return:

1. An HTTP status code.
2. A custom response message.

In this example:

```nginx
return 200 "Hello, you are inside custom location";
```

means that NGINX returns HTTP status `200` together with the specified text.

---

# 7. Case Sensitivity Matters for the Prefix Match

The instructor demonstrates an important behavior.

The configured location is:

```nginx
location /contactus {
    ...
}
```

If the browser requests:

```text
/contactus
```

the location matches.

But if the browser requests:

```text
/ContactUs
```

with different capitalization, it does not match the same way.

The lecture demonstrates that the location was defined using lowercase characters, and changing the request to match that lowercase URI caused the custom response to appear.

Therefore, in the demonstrated configuration, the URI matching is case-sensitive.

---

# 8. Prefix Matching Ignores What Comes After the Prefix

With:

```nginx
location /contactus {
    return 200 "Hello, you are inside custom location";
}
```

the following request:

```text
/contactus
```

matches.

So does:

```text
/contactus/about
```

And:

```text
/contactus/about/me
```

The reason is that NGINX is matching the beginning of the URI.

Conceptually:

```text
/contactus/about/me
^^^^^^^^^^
   match
```

The configured location:

```text
/contactus
```

is found at the beginning of the URI.

Therefore, the rest of the URI does not prevent this prefix location from matching.

---

# 9. Exact Match Modifier `=`

The `=` modifier changes the behavior to an **exact match**.

Syntax:

```nginx
location = /contactus {
    ...
}
```

This location matches only when the request URI exactly matches:

```text
/contactus
```

For example:

```text
/contactus       → Match
/contactus/      → Not an exact match
/contactus/about → Not an exact match
```

The lecture demonstrates that adding extra URI content causes the exact location to fail and results in a `404` when no other suitable location handles the request.

---

# 10. Lab: Exact Match

The previous location:

```nginx
location /contactus {
    return 200 "Hello, you are inside custom location";
}
```

is changed to:

```nginx
location = /contactus {
    return 200 "Hello, you are inside custom location";
}
```

Now NGINX requires an exact URI match.

Request:

```text
/contactus
```

returns the custom message.

Request:

```text
/contactus/about
```

does not match this exact location.

Therefore, if there is no other suitable location, NGINX returns:

```text
404 Not Found
```

---

# 11. Regular Expression Modifier `~`

The `~` modifier specifies a **case-sensitive regular-expression match**.

Syntax:

```nginx
location ~ /contactus {
    ...
}
```

The lecture explains that NGINX uses the PCRE library for regular-expression functionality.

`PCRE` stands for **Perl Compatible Regular Expressions**.

The `~` modifier therefore tells NGINX to interpret the location expression as a case-sensitive regular expression.

Example:

```nginx
location ~ /contactus {
    return 200 "Regex case sensitive match";
}
```

A lowercase matching request can match the expression, while a request using different capitalization does not match the same case-sensitive expression.

---

# 12. Case-Insensitive Regular Expression Modifier `~*`

The `~*` modifier specifies a **case-insensitive regular-expression match**.

Syntax:

```nginx
location ~* /contactus {
    return 200 "Regex case insensitive match";
}
```

This means capitalization does not matter for the regular-expression match.

For example, depending on the expression:

```text
/contactus
/ContactUs
/CONTACTUS
```

can all match.

The important difference is:

```text
~   → case-sensitive regular expression
~*  → case-insensitive regular expression
```

---

# 13. Preferential Prefix Modifier `^~`

The `^~` modifier specifies a **preferential prefix match**.

Syntax:

```nginx
location ^~ /contactus {
    ...
}
```

The lecture describes this as a best non-regular-expression match.

In other words, when this prefix location is selected, regular-expression matching is not performed against it in the same way.

The important modifier is:

```text
^~
```

It is different from:

```text
~
```

because:

```text
~  → regular expression
^~ → preferential prefix match
```

---

# 14. Location Matching Modifiers

The lecture introduces these location forms:

| Syntax | Meaning |
|---|---|
| `location /path` | Prefix match |
| `location = /path` | Exact match |
| `location ~ /path` | Case-sensitive regex |
| `location ~* /path` | Case-insensitive regex |
| `location ^~ /path` | Preferential prefix match |

These modifiers change how NGINX attempts to select the appropriate location block.

---

# 15. Why Location Priority Matters

A server can contain multiple location blocks.

For example:

```nginx
server {

    location /contactus {
        return 200 "Prefix match";
    }

    location = /contactus {
        return 200 "Exact match";
    }

    location ~ /contactus {
        return 200 "Regex match";
    }
}
```

A request such as:

```text
/contactus
```

could potentially match more than one location.

NGINX therefore needs a process for deciding which location should handle the request.

The modifier affects this selection process.

This is one of the most important concepts in this lab.

---

# 16. Exact Match vs. Prefix Match

The instructor demonstrates two locations with the same URI:

```nginx
location /contactus {
    return 200 "Prefix match";
}

location = /contactus {
    return 200 "Exact match";
}
```

When the request is exactly:

```text
/contactus
```

the exact-match location is selected.

The browser therefore receives:

```text
Exact match
```

When additional content is appended:

```text
/contactus/about
```

the exact match no longer applies.

The prefix location can then handle the request:

```text
Prefix match
```

This demonstrates:

```text
/contactus
    ↓
Exact match

/contactus/about
    ↓
Prefix match
```

---

# 17. Exact Match Has Higher Priority Than a Normal Prefix Match

When the same URI can match both:

```nginx
location /contactus {
    ...
}
```

and:

```nginx
location = /contactus {
    ...
}
```

the exact match takes precedence for the exact URI.

Therefore:

```text
/contactus
    ↓
location = /contactus
```

rather than:

```text
location /contactus
```

---

# 18. Regular Expression vs. Normal Prefix Match

The lab then adds a regular-expression location:

```nginx
location ~ /contactus {
    return 200 "Regex case sensitive match";
}
```

alongside a normal prefix location:

```nginx
location /contactus {
    return 200 "Prefix match";
}
```

The instructor demonstrates that the regular-expression location is selected over the normal prefix location in the demonstrated case.

This shows that the presence of a modifier can significantly affect location selection.

---

# 19. Case-Sensitive vs. Case-Insensitive Regex

The case-sensitive regex:

```nginx
location ~ /contactus {
    ...
}
```

does not match the same capitalization variations as:

```nginx
location ~* /contactus {
    ...
}
```

The latter is case-insensitive.

For example:

```text
~  /contactus
```

matches the appropriate case-sensitive form.

Whereas:

```text
~* /contactus
```

can match different capitalization forms.

The instructor demonstrates this by changing:

```text
/contactus
```

to:

```text
/ContactUs
```

and observing the different matching behavior.

---

# 20. Location Matching Priority

The lecture gives the following priority order for the location modifiers.

From higher priority to lower priority:

```text
1. Exact match
       =
       ↓
2. Preferential prefix match
       ^~
       ↓
3. Regular expression
       ~*
       ↓
4. Regular expression
       ~
       ↓
5. Normal prefix match
       no modifier
```

In notation:

```text
=
^~
~*
~
(no modifier)
```

This priority is the ordering presented in the lecture.

---

# 21. Practical Example of Multiple Locations

Consider:

```nginx
server {

    location /contactus {
        return 200 "Normal prefix";
    }

    location = /contactus {
        return 200 "Exact match";
    }

    location ^~ /contactus {
        return 200 "Preferential prefix";
    }

    location ~ /contactus {
        return 200 "Regex case sensitive";
    }

    location ~* /contactus {
        return 200 "Regex case insensitive";
    }
}
```

When multiple locations could potentially match a URI, NGINX uses its location-selection process to determine the applicable block.

The exact behavior depends on the URI and the matching forms present.

The important lesson from the lecture is that **the location modifier affects the matching process and priority**.

# 24. Reloading After Configuration Changes

After modifying the location configuration, reload NGINX:

```bash
nginx -s reload
```

The lecture repeatedly uses reload after configuration changes.

The general workflow is:

```text
Modify location
      ↓
Save nginx.conf
      ↓
Reload NGINX
      ↓
Send request
      ↓
Observe response
      ↓
Check logs
```
