# 25. Lab — NGINX Performance Optimization

## Overview

This lab focuses on tuning two important NGINX directives:

- **`worker_processes`**
- **`worker_connections`**

These settings determine how NGINX creates worker processes and how many connections each worker can handle.

The lecture first explains the role of the NGINX master and worker processes, then demonstrates how to configure the
number of workers and connections according to the CPU and operating-system capabilities of the machine.

The two directives belong to different configuration contexts:

| Directive            | Context             | Purpose                                                   |
|----------------------|---------------------|-----------------------------------------------------------|
| `worker_processes`   | Global/main context | Controls the number of NGINX worker processes             |
| `worker_connections` | `events` context    | Controls the number of connections handled by each worker |

---

# 1. NGINX Master and Worker Processes

NGINX uses a master process and one or more worker processes.

Conceptually:

```text
NGINX
├── Master Process
└── Worker Process(es)
```

### Master Process

The **NGINX master process** manages the worker processes.

According to the lecture, the master process does not directly serve client requests.

Its responsibilities include managing the worker processes and initializing the configured number of workers.

### Worker Process

The **worker process** is responsible for communicating with clients and handling requests.

The lecture emphasizes that the worker process is the actual process serving client traffic.

This distinction is also relevant to the previous PHP-FPM lab, where the NGINX worker process needed appropriate
permissions to communicate with PHP-FPM.

---

# 2. The `worker_processes` Directive

The number of NGINX worker processes is configured with:

```nginx
worker_processes <number>;
```

For example:

```nginx
worker_processes 4;
```

This tells NGINX to initialize four worker processes.

The directive is placed in the **global/main context**.

---

# 3. Worker Processes and CPU Cores

The lecture recommends a general practice of:

> **One worker process per CPU core.**

For example:

| CPU Cores | Recommended Workers |
|----------:|--------------------:|
|         1 |                   1 |
|         2 |                   2 |
|         4 |                   4 |
|         8 |                   8 |
|        16 |                  16 |

Conceptually:

```text
1 CPU core  → 1 worker
2 CPU cores → 2 workers
4 CPU cores → 4 workers
8 CPU cores → 8 workers
```

The purpose is to align the number of worker processes with the CPU resources available to NGINX.



---

# 4. What Happens if There Are Too Many Workers?

The lecture demonstrates the example of a machine with **2 CPU cores** running **4 NGINX worker processes**.

The four workers have to share the available CPU resources.

Conceptually:

```text
2 CPU cores
     │
     ├── Worker 1
     ├── Worker 2
     ├── Worker 3
     └── Worker 4
```

The lecture describes the CPU load as being distributed among the worker processes rather than each worker receiving a
full CPU core.

Similarly, for a one-core machine:

```text
1 CPU core
     │
     ├── Worker 1 → ~33%
     ├── Worker 2 → ~33%
     └── Worker 3 → ~33%
```

when three workers are configured.

With five workers on one core:

```text
Worker 1 → ~20%
Worker 2 → ~20%
Worker 3 → ~20%
Worker 4 → ~20%
Worker 5 → ~20%
```

The lecture's general recommendation is therefore to avoid unnecessarily configuring more workers than the machine's CPU
capacity.

---

# 5. What Happens if There Are Too Few Workers?

The opposite problem can also occur.

Suppose the machine has:

```text
2 CPU cores
```

but NGINX has:

```nginx
worker_processes 1;
```

The lecture explains that only one worker process is available, leaving another CPU core unused by NGINX.

Conceptually:

```text
2 CPU cores

Core 1 → NGINX worker
Core 2 → unused by NGINX
```

Therefore, worker-process configuration should take the available CPU resources into account.

---

# 6. Automatically Detecting CPU Count

Hard-coding a worker count can become inconvenient when the same configuration is deployed on machines with different
CPU sizes.

For example, a configuration containing:

```nginx
worker_processes 4;
```

may be used on:

- A 2-core machine
- A 4-core machine
- An 8-core machine
- A 16-core machine

The lecture introduces the `auto` option to avoid this problem:

```nginx
worker_processes auto;
```

With `auto`, NGINX determines the number of available CPUs and automatically configures the worker-process count
accordingly.

This allows the same configuration to be used across machines with different CPU sizes.



---

# 7. Finding the CPU Count

The lab demonstrates several commands that can be used to identify the CPU resources available on the machine.

## `lscpu`

```bash
lscpu
```

This produces detailed CPU information, including the number of CPUs available.

## `nproc`

A simpler command is:

```bash
nproc
```

It returns the number of processing units available to the system.

## `top`

The lecture also mentions the `top` command as another way to inspect CPU information.

These commands are useful when determining an appropriate worker-process configuration.

---

# 8. Lab: Inspect the Existing NGINX Processes

The lecture begins the practical demonstration by checking the running NGINX processes.

A process-tree command is used:

```bash
ps -aux --forest | grep nginx
```

The `--forest` option helps visualize the parent-child relationship.

The initial output shows:

```text
NGINX master process
        │
        └── NGINX worker process
```

This corresponds to the default one-worker configuration demonstrated in the lab.

---

# 9. Lab: Configure Four Worker Processes

The configuration is changed to:

```nginx
worker_processes 4;
```

After saving the configuration, NGINX is reloaded.

The processes are checked again:

```bash
ps -aux --forest | grep nginx
```

The output now shows:

```text
NGINX master process
├── Worker 1
├── Worker 2
├── Worker 3
└── Worker 4
```

This confirms that NGINX initialized four worker processes according to the configured value.

---

# 10. Verify the Machine CPU Size

The lab then checks the machine's CPU count.

Using:

```bash
lscpu
```

or:

```bash
nproc
```

the lecture identifies the demonstration machine as having:

```text
1 CPU
```

Therefore, configuring:

```nginx
worker_processes 4;
```

is not aligned with the lecture's one-worker-per-core recommendation.

---

# 11. Configure `worker_processes auto`

The hard-coded value is replaced with:

```nginx
worker_processes auto;
```

After saving and reloading NGINX, the process tree is checked again.

On the one-core demonstration machine, NGINX starts one worker process.

```text
NGINX master
    │
    └── Worker
```

The benefit of `auto` is that the same configuration can automatically adapt when deployed on machines with different
CPU counts.

For example:

```text
1-core machine  → automatically configured workers
2-core machine  → automatically configured workers
4-core machine  → automatically configured workers
8-core machine  → automatically configured workers
```

---

# 12. The `worker_connections` Directive

The second performance-related directive is:

```nginx
worker_connections <number>;
```

Unlike `worker_processes`, this directive belongs inside the **`events` context**.

Example:

```nginx
events {
    worker_connections 1024;
}
```

The lecture describes `worker_connections` as controlling how many connections each worker process can handle.

---

# 13. Relationship Between Workers and Connections

Suppose:

```nginx
worker_processes 2;
```

and:

```nginx
events {
    worker_connections 600;
}
```

The lecture calculates the total configured connection capacity as:

```text
2 workers × 600 connections
= 1,200 connections
```

Conceptually:

```text
Worker 1 → 600 connections
Worker 2 → 600 connections
----------------------------
Total    → 1,200 connections
```

Similarly, if there are two workers and each has 1,000 worker connections:

```text
2 × 1,000 = 2,000
```

The lecture uses this relationship to explain how worker processes and worker connections work together.

---

# 14. What `worker_connections` Controls

The directive tells each worker how many connections it can handle simultaneously.

For example:

```nginx
events {
    worker_connections 1000;
}
```

means each configured worker has a connection limit of 1,000 according to the lecture's model.

If there are two workers:

```text
Worker 1 → 1,000
Worker 2 → 1,000
```

giving:

```text
Total configured connections = 2,000
```

The lecture describes this as the number of connections that can be handled by the worker processes.

---

# 15. `worker_processes` vs. `worker_connections`

These directives control different dimensions of NGINX capacity.

| Directive            | Controls                   | Context  |
|----------------------|----------------------------|----------|
| `worker_processes`   | Number of worker processes | Global   |
| `worker_connections` | Connections per worker     | `events` |

A useful mental model is:

```text
CPU resources
     ↓
worker_processes
     ↓
Number of NGINX workers
     ↓
worker_connections
     ↓
Connections available to each worker
```

---

# 16. The `events` Context

The lecture specifically distinguishes the contexts of the two directives.

### `worker_processes`

Belongs to the global context:

```nginx
worker_processes auto;
```

### `worker_connections`

Belongs to the `events` context:

```nginx
events {
    worker_connections 1024;
}
```

This follows the NGINX configuration hierarchy discussed in the earlier lectures.

---

# 17. Checking the Operating-System Limit

Before configuring `worker_connections`, the lecture checks the operating-system limit with:

```bash
ulimit -n
```

In the demonstration environment, the result is:

```text
1024
```

The lecture uses this value as an important reference when configuring NGINX's worker connections.

The idea is that the operating system places limits on the resources available to processes, so NGINX's connection
configuration should be considered together with the OS limits.



---

# 18. Configuring Worker Connections

The lab then adds the directive inside the `events` block:

```nginx
events {
    worker_connections 1024;
}
```

The configuration is tested:

```bash
nginx -t
```

If the configuration is valid, NGINX is reloaded:

```bash
nginx -s reload
```

The lecture then treats the configured worker-connection value as the number of connections available to the worker
under the demonstrated model.

---

# 19. Example: Combining Both Settings

A basic performance-oriented configuration from the lab is:

```nginx
worker_processes auto;

events {
    worker_connections 1024;
}
```

The configuration means:

```text
worker_processes auto
        ↓
Determine worker count from CPU resources
        ↓
Each worker
        ↓
Up to 1024 configured connections
```

If the machine has four CPUs, the lecture's model would give:

```text
4 workers × 1024 connections
= 4096 configured connections
```

The exact practical capacity can still depend on operating-system and application constraints; the lecture's main focus
is the relationship between these two NGINX directives.

---

# 20. Why These Settings Matter

The lecture emphasizes that these are important configuration settings for:

- Web servers
- Load balancers
- High-traffic applications

Incorrect tuning can prevent a machine from making effective use of its available resources.

For example, a machine may have substantial CPU resources but an NGINX configuration that starts too few workers.

Likewise, the connection configuration can limit the number of simultaneous connections a worker can handle.

The overall goal is to align NGINX's configuration with the capabilities of the machine.



---

# 22. Common Mistakes and Warnings

### 1. Configuring too many workers for the available CPU resources

For example:

```nginx
worker_processes 4;
```

on a one-core machine creates more workers than the lecture's recommended one-worker-per-core model.

### 2. Configuring too few workers

A multi-core machine with only one worker may leave CPU capacity unused by NGINX.

### 3. Hard-coding worker counts unnecessarily

Instead of:

```nginx
worker_processes 4;
```

the lecture recommends:

```nginx
worker_processes auto;
```

when the configuration needs to work across machines with different CPU sizes.

### 4. Putting `worker_connections` in the wrong context

It belongs inside:

```nginx
events {
    ...
}
```

not in the global context.

### 5. Ignoring the operating-system limit

The lecture checks:

```bash
ulimit -n
```

before configuring worker connections.

### 6. Forgetting to validate configuration

Use:

```bash
nginx -t
```

before reloading NGINX.

# 23. Key Takeaways

- NGINX has a **master process** and one or more **worker processes**.
- The master process manages workers.
- Worker processes handle client requests.
- `worker_processes` controls how many worker processes NGINX starts.
- `worker_processes` belongs to the global context.
- The lecture recommends approximately one worker process per CPU core.
- `worker_processes auto;` allows NGINX to determine the worker count automatically.
- `worker_connections` controls the number of connections available to each worker.
- `worker_connections` belongs inside the `events` context.
- The lecture models total configured connection capacity as:

```text
worker_processes × worker_connections
```

- `ulimit -n` is used in the lab to inspect the operating-system limit.
- `lscpu` and `nproc` can be used to identify CPU resources.
- `ps -aux --forest | grep nginx` can be used to inspect the master/worker process hierarchy.
- These settings are particularly important when configuring NGINX as a web server or load balancer.

## Performance Model

```text
                 NGINX
                   │
             Master Process
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
       Worker 1  Worker 2  Worker N
          │        │        │
       Connections Connections Connections
          │        │        │
          └────────┴────────┘
                   │
          Available CPU / OS resources
```

The central idea of this lab is that **`worker_processes` determines how many NGINX workers participate in handling
traffic, while `worker_connections` determines how many connections each worker can handle according to the configured
limits**. Properly aligning these settings with CPU and operating-system resources is an important part of NGINX
performance configuration.
