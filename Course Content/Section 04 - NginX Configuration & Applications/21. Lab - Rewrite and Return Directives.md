# 21. Lab — Rewrite and Return Directives

## Overview

The **`return`** and **`rewrite`** directives in NGINX are used to control how requests are handled and redirected.

They are useful in two broad situations:

1. **Redirecting users when a website URL changes**
   - For example, redirecting `www.mywebsite.com` to `www.mywebsite.org`.

2. **Controlling request flow within NGINX**
   - For example, mapping a user-friendly URI to another resource or dynamically determining which location should
     handle a request.

Although both directives can be used for redirection and request control, they behave differently. The `return`
directive has simpler logic and lower resource consumption, while `rewrite` provides more granular URL manipulation.



---

## Key Concepts

| Concept            | Description                                                                  |
|--------------------|------------------------------------------------------------------------------|
| `return`           | Simple directive used to immediately return a status code and/or response    |
| `rewrite`          | More flexible directive used to transform a URI using regular expressions    |
| `301`              | Permanent redirect status                                                    |
| `307`              | Temporary redirect status that preserves the request method                  |
| Regular expression | Pattern used by `rewrite` to match parts of a URI                            |
| Capture value      | A portion of a matched URI that can be reused, such as `$1`                  |
| `server` context   | A context where `return` and `rewrite` can be defined                        |
| `location` context | A context where request-specific `return` and `rewrite` rules can be defined |

---

# 1. The `return` Directive

The `return` directive is the simpler of the two mechanisms.

According to the lecture, its logical flow is simpler and its resource consumption is lower than `rewrite`.

A `return` directive can be placed inside a **`server`** or **`location`** block.

### Basic concept

```nginx
return <status-code> <URL-or-response>;
```

For example:

```nginx
return 301 http://www.newwebsite.com$request_uri;
```

This can be used when an old website needs to redirect users to a new website.

### Example: Domain Change

Suppose the old website is:

```text
www.oldwebsite.com
```

and the website has moved to:

```text
www.newwebsite.com
```

A server block can perform a permanent redirect:

```nginx
server {
    listen 80;
    server_name www.oldwebsite.com;

    return 301 http://www.newwebsite.com$request_uri;
}
```

The user requests the old domain, and NGINX returns a redirect response pointing to the new domain.

---

## Why Use `return`?

The lecture emphasizes that `return` is useful when the destination is already known.

For example:

```nginx
return 301 /some/path;
```

or:

```nginx
return 307 /some/path;
```

The directive can therefore provide a straightforward response without requiring the more complex URI processing
associated with `rewrite`.

---

# 2. The `rewrite` Directive

The `rewrite` directive provides more granular control than `return`.

It can be used to:

- Match URLs using regular expressions.
- Capture parts of the original URI.
- Modify or add elements to a path.
- Construct dynamic URIs.
- Use captured values when determining the next URI.
- Perform more complicated URL transformations.

The lecture describes this as the main distinction between the two directives: `rewrite` can perform more complicated
URL manipulation than `return`.



---

## Basic Syntax

The lecture gives the following general structure:

```nginx
rewrite <regex> <replacement> [flag];
```

Where:

- **`regex`** — regular expression used to match the requested URI.
- **`replacement`** — URI that should be generated from the match.
- **`flag`** — optional flag controlling how NGINX handles the rewrite.

Example structure:

```nginx
rewrite ^/guest/(.*)$ /welcome;
```

The exact regular expression depends on the URL pattern that needs to be handled.

---

# 3. Return vs. Rewrite

The primary difference demonstrated in the lecture is how much URI processing each directive performs.

### `return`

The flow is straightforward:

```text
Request
   ↓
return directive
   ↓
Response / Redirect
```

### `rewrite`

The flow can involve URI transformation and additional location processing:

```text
Request
   ↓
rewrite rule
   ↓
New URI
   ↓
Location matching
   ↓
Matching location
   ↓
Response
```

The lecture explains that when a rewritten URL matches another applicable directive/location, NGINX can process that URI
again. This additional processing is why `rewrite` is described as more resource-consuming than `return`.

# 5. Lab: Using `return` to Redirect to an Image

Initially, the image can be accessed through its complete resource URI.

For example:

```text
/assets/images/about/welcome-banner.jpg
```

The lecture demonstrates that exposing the complete path may not be desirable.

A new location is therefore created:

```nginx
location /welcome {
    return 301 /assets/images/about/welcome-banner.jpg;
}
```

After saving the configuration, reload NGINX.

```bash
nginx -s reload
```

Now the user can request:

```text
http://SERVER_IP:8081/welcome
```

NGINX returns a redirect to the actual image path.

---

## Observing the Redirect

The NGINX access log shows the redirect response.

For example:

```text
/welcome
```

produces a **301** response.

The browser subsequently requests the actual resource:

```text
/assets/images/about/welcome-banner.jpg
```

### Important Observation

Although `/welcome` provides a shorter URL, the browser ultimately exposes the complete resource URI because
`return 301` tells the client to redirect.

This is the drawback demonstrated in the lecture: the underlying URI remains visible to the client.



---

# 6. Using `rewrite` to Hide the Resource Path

To avoid exposing the underlying image path, the lecture introduces `rewrite`.

The goal is:

```text
/welcome
```

should serve the same resource without redirecting the browser to:

```text
/assets/images/about/welcome-banner.jpg
```

This is where `rewrite` provides more control.

The lecture demonstrates matching a URI pattern containing `guest` and rewriting it to `welcome`.

Conceptually:

```text
/guest/<name>
        ↓
     rewrite
        ↓
     /welcome
```

For example:

```text
/guest/Tom
```

can be rewritten internally to:

```text
/welcome
```

The browser continues using the original request URI while NGINX processes the rewritten URI internally.



---

# 7. Capturing Values with Rewrite

A major advantage of `rewrite` is that a regular expression can capture part of the original URI.

For example, a pattern can capture a username:

```text
/guest/<username>
```

The captured value can then be referenced using:

```nginx
$1
```

The lecture demonstrates the concept of passing the captured value into another URI.

Conceptually:

```text
/guest/Anshul
       │
       └── captured value
                ↓
           $1 = Anshul
                ↓
        /welcome/Anshul
```

This makes it possible to construct dynamic URIs from the original request.

---

# 8. Passing Captured Values to Another Location

The lecture then expands the example by using the captured username as part of the rewritten URI.

The conceptual flow is:

```text
/guest/<username>
        ↓
Capture <username>
        ↓
/welcome/<username>
        ↓
Location matching
        ↓
Response based on username
```

For example:

```text
/guest/Anshul
```

can become:

```text
/welcome/Anshul
```

The resulting URI can then be handled by another `location` block.

This demonstrates how `rewrite` can dynamically influence which location processes a request.

---

# 9. Example: Conditional Handling of a Captured Username

The lecture demonstrates a second rewrite pattern using a `user` URI.

Conceptually, the configuration:

1. Matches `/user/<username>`.
2. Captures the username.
3. Creates a new URI using the captured value.
4. Passes the generated URI through location matching.
5. Handles a specific username differently.

For example:

```text
/user/Anshul
```

can be transformed into:

```text
/welcome/Anshul
```

A corresponding location can then return a custom response for `Anshul`.

The demonstrated result is conceptually:

```text
/user/Anshul
        ↓
rewrite
        ↓
/welcome/Anshul
        ↓
matching location
        ↓
"Hello Anshul welcome"
```

The lecture contrasts this with another username such as `Maria`, where the request follows the general rewrite flow
rather than the special response.


```nginx
rewrite ^/guest/\+w /welcome;
rewrite ^/user/{\+w} /welcome/$1;

location = /welcome/arafat {
    return 200 "Hello Arafat after rewrite";
}
```

# 10. Practical Testing Workflow

When modifying NGINX rewrite/return rules, the lab follows this general workflow.

### Step 1: Open the configuration

```bash
vi /etc/nginx/nginx.conf
```

### Step 2: Add or modify the required `location`

For example:

```nginx
location /welcome {
    ...
}
```

### Step 3: Add the `return` or `rewrite` directive

Example:

```nginx
return 301 /assets/images/about/welcome-banner.jpg;
```

or a rewrite rule:

```nginx
rewrite <pattern> <replacement>;
```

### Step 4: Save the configuration

Exit the editor after making the changes.

### Step 5: Reload NGINX

```bash
nginx -s reload
```

### Step 6: Test from the browser

Use the configured port:

```text
http://SERVER_IP:8081/welcome
```

or:

```text
http://SERVER_IP:8081/guest/Tom
```

### Step 7: Inspect the logs

The lecture keeps the NGINX logs open in another terminal so the effect of each request can be observed.

# 11. `return` vs. `rewrite` — Lab Perspective

| Feature                                  | `return`                        | `rewrite`                                     |
|------------------------------------------|---------------------------------|-----------------------------------------------|
| Complexity                               | Simpler                         | More complex                                  |
| Resource consumption                     | Lower, according to the lecture | Higher, according to the lecture              |
| Direct redirect                          | Yes                             | Can be used for more involved transformations |
| Regular expressions                      | Not the focus                   | Core capability                               |
| Capture URI components                   | No                              | Yes                                           |
| Dynamic URI construction                 | Limited                         | Yes                                           |
| URI transformation                       | Simple                          | Granular                                      |
| Location processing after transformation | Not the demonstrated behavior   | Central to the demonstrated workflow          |

The lecture's main takeaway is that **`return` is preferable for simple, direct responses or redirects**, while **
`rewrite` is intended for more complicated URI transformations and dynamic request flows**.
