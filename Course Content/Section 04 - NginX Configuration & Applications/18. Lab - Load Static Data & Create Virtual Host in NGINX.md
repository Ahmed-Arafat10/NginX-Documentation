# 18. Lab — Load Static Data & Create a Virtual Host in NGINX

## Overview

In this lab, we configure NGINX to:

1. Upload a static HTML website to an NGINX server.
2. Create a virtual host using the `server` context.
3. Configure NGINX to listen on a specific port.
4. Configure the `server_name`.
5. Configure the filesystem location from which NGINX serves the website.
6. Safely modify the NGINX configuration.
7. Validate the configuration before reloading NGINX.
8. Understand the difference between `reload` and `restart`.
9. Diagnose static-file MIME type problems.
10. Use the `mime.types` file with the `include` directive.
11. Configure different ports on the same NGINX server.

The lab demonstrates the complete process of taking a static website from a local machine, uploading it to a remote
NGINX server, and configuring NGINX to serve it.

---

# 1. Verify That NGINX Is Running

The lab starts with an Ubuntu server where NGINX is already installed and running.

The NGINX processes can be checked with:

```bash
ps -ef | grep nginx
```

The expected result shows the NGINX:

- Master process
- Worker process (es)

The server's IP address can then be accessed from a browser on port `80`:

```text
http://SERVER_IP
```

Initially, the default NGINX web page is displayed.

This confirms that NGINX is running and responding to HTTP requests.

# 3. Upload the Website to the NGINX Server

The instructor uploads the entire `blogging template` directory from the local machine to the remote server.

The tool used for this is **SCP** (`Secure Copy Protocol`).

Because an entire directory is being uploaded rather than a single file, the recursive option `-R` is required:

```bash
scp -r /local/path/blogging-template username@SERVER_IP:/root/
```

The exact local path depends on where the website is stored on the local machine.

The general structure is:

```text
scp -r <local-directory> <username>@<server-ip>:<remote-path>
```

For example:

```bash
scp -r ~/Downloads/blogging-template root@104.131.80.130:/root/
```

The instructor emphasizes that the server IP should be provided without:

```text
http://
```

or other protocols.

After executing the command, SCP requests the remote server password and begins copying the directory.

---

# 4. Why Upload to the Root Location?

The instructor recommends uploading the website to the root location used in the lab.

The reason given is permissions.

NGINX may not have permission to access files in certain directories, which can result in:

```text
403 Forbidden
```

Therefore, following the same directory structure used in the lab helps avoid permission-related problems during the
exercise.

After uploading, verify the directory:

```bash
ls
```

Then:

```bash
cd /root/blogging-template
ls
```

You should see:

```text
index.html
assets/
```

Verify the assets:

```bash
cd assets
ls
```

Expected directories include:

```text
css
fonts
images
js
logo
```

This confirms that the complete website has been uploaded.

# 6. Simplify the Configuration for the Lab

For the purpose of the demonstration, the instructor removes the existing configuration contents and creates a minimal
configuration.

The resulting structure contains three main areas:

```nginx
events {
}

http {
    server {
    }
}
```

The:

- `events` context is empty for this demonstration.
- `http` context contains the `server` context.
- `server` context is initially empty.

This creates a clean starting point for building the virtual host.

---

# 7. Create the Virtual Host

Inside the `server` context, the first directive is:

```nginx
listen 80;
```

This tells NGINX to listen for requests on port `80`.

A basic server configuration begins as:

```nginx
server {
    listen 80;
}
```

Port `80` is the standard HTTP port used in the demonstration.

Another port can be used if required.

---

# 8. Configure `server_name`

Next, configure the `server_name`:

```nginx
server {
    listen 80;
    server_name 104.131.80.130;
}
```

In this lab, the instructor does not have a domain name, so the server IP address is used.

If you have a fully qualified domain name (FQDN), you can use the domain instead:

```nginx
server_name example.com;
```

Do not add:

```text
http://
```

or another protocol to the `server_name`.

The directive should contain the hostname or IP address itself.

---

# 9. Configure the Document Root

Next, NGINX needs to know where the website files are located.

This is configured with the `root` directive.

For the lab, the website was uploaded to:

```text
/root/blogging-template
```

The configuration therefore uses:

```nginx
root /root/blogging-template;
```

The complete initial virtual host becomes:

```nginx
server {
    listen 80;
    server_name 104.131.80.130;

    root /root/blogging-template;
}
```

The important directives are:

| Directive     | Purpose                                                  |
|---------------|----------------------------------------------------------|
| `listen`      | Specifies the port on which the server listens           |
| `server_name` | Specifies which hostname/IP the server block handles     |
| `root`        | Specifies the filesystem location containing the website |

---

# 10. Understand What the Virtual Host Does

The configuration tells NGINX:

```text
Request arrives on port 80
        ↓
Match server_name
        ↓
Use this server block
        ↓
Look for website files under:
 /root/blogging-template
```

The `index.html` file is located inside that directory:

```text
/root/blogging-template/index.html
```

Therefore, NGINX can use that directory as the document root for the website.

---

# 11. Reload Instead of Restarting NGINX

After modifying the configuration, the instructor emphasizes an important operational practice:

> **Do not immediately restart NGINX after configuration changes.**

Instead, reload the configuration.

For example:

```bash
systemctl reload nginx
```

A reload causes NGINX to reload its configuration while the service remains running.

---

# 12. Why Reload Is Preferred to Restart

A restart generally involves:

```text
Stop NGINX
     ↓
Start NGINX
```

If the new configuration contains an error, NGINX may fail to start.

That can cause an outage on a running server.

A reload is safer because the running NGINX process can load the new configuration without performing the same full
stop/start operation.

The lab therefore recommends:

```text
Configuration change
        ↓
Test configuration
        ↓
Reload NGINX
```

rather than:

```text
Configuration change
        ↓
Restart NGINX
```

---

# 13. Test the Configuration Before Reloading

Before reloading, NGINX provides a configuration-testing command:

```bash
nginx -t
```

A successful test reports that the configuration syntax is valid and that the test is successful.

For example:

```text
syntax is ok
test is successful
```

The exact output can vary by NGINX version.

The recommended workflow is:

```bash
nginx -t
systemctl reload nginx
```

---

# 14. Example of a Configuration Error

The instructor demonstrates what happens when a configuration syntax error is introduced.

For example, if a required semicolon is removed:

```nginx
root /root/blogging-template
```

instead of:

```nginx
root /root/blogging-template;
```

then:

```bash
nginx -t
```

reports a configuration error and identifies the relevant line.

The example demonstrates why testing the configuration is important.

If an invalid configuration is used with a restart, NGINX may stop and then fail to start again.

That can cause downtime.

---

# 15. Correct Configuration Workflow

The lab establishes this workflow:

```text
1. Modify nginx.conf
        ↓
2. nginx -t
        ↓
3. If the test succeeds
        ↓
4. Reload NGINX
```

Commands:

```bash
nginx -t
systemctl reload nginx
```

or use an NGINX reload signal where appropriate.

The key principle is:

> **Test first, reload second.**

# 17. First Website Result: HTML Loads, but CSS/JavaScript Does Not

After configuring the virtual host, the browser displays the uploaded HTML page.

However, an important problem appears:

- HTML loads.
- CSS does not apply.
- JavaScript does not behave correctly.

The instructor checks the NGINX logs and observes that requests for the CSS and JavaScript files are receiving HTTP
`200` responses.

For example:

```text
CSS request → 200
JavaScript request → 200
```

This means NGINX is successfully finding and returning the files.

However, the browser is not interpreting them as CSS or JavaScript.

---

# 18. Diagnose the MIME Type Problem

To investigate, the instructor uses `curl` with the `-I` option.

For example:

```bash
curl -I http://SERVER_IP/path/to/file.css
```

The response includes headers such as:

```text
HTTP/1.1 200 OK
Server: nginx
Content-Type: text/plain
```

The important problem is:

```text
Content-Type: text/plain
```

The requested file is CSS, but NGINX is identifying it as plain text.

The same issue occurs with JavaScript.

The JavaScript file is returned successfully, but its content type is also treated as plain text.

Therefore, the problem is not that NGINX cannot find the files.

The problem is that NGINX does not currently have the appropriate MIME type mappings configured.

---

# 19. MIME Types

A MIME type tells the client what type of content is being returned.

For example:

```text
HTML → text/html
CSS  → text/css
JavaScript → appropriate JavaScript MIME type
```

In the lab, the instructor initially defines types manually inside the `http` context:

```nginx
http {

    types {
        text/html html htm;
        text/css css;
    }

    server {
        ...
    }
}
```

The exact mapping can contain multiple extensions.

For example:

```nginx
types {
    text/html html htm;
    text/css css;
}
```

After changing the configuration, reload NGINX:

```bash
nginx -s reload
```

or:

```bash
systemctl reload nginx
```

After the reload, CSS is correctly identified as CSS rather than plain text.

---

# 20. Why We Should Not Manually Define Every MIME Type

The instructor then points out that manually defining every file type would not be practical.

NGINX already provides a MIME type configuration file:

```text
/etc/nginx/mime.types
```

This file contains many predefined MIME type mappings.

It includes mappings for file types such as:

- HTML
- CSS
- XML
- GIF
- JPEG/JPG
- JavaScript
- Atom
- RSS
- Various application types
- Video formats
- Audio formats
- Other common content types

Therefore, instead of manually defining every MIME type in `nginx.conf`, we can include the existing MIME type
configuration.

---

# 21. The `include` Directive

NGINX supports the `include` directive for loading configuration from another file.

The instructor changes the configuration from manually defining the `types` context to including the existing MIME type
file.

Inside the `http` context:

```nginx
http {

    include mime.types;

    server {
        ...
    }
}
```

Because `mime.types` is located in the same NGINX configuration directory in the lab, only the filename is used.

If the file were located somewhere else, the appropriate path would need to be provided.

For example:

```nginx
include /path/to/mime.types;
```

The important syntax is:

```nginx
include mime.types;
```

Note that the directive is `include`, not `includes`.

---

# 22. Why `include` Is Useful

The `include` directive allows configuration to be separated into multiple files.

Instead of putting everything into:

```text
nginx.conf
```

you can keep specialized configuration in separate files and include them.

The lecture describes this as a way to create a subdirectory/file structure that can contain different configuration
sections, such as:

- HTML/type configuration.
- Global configuration.
- Server configuration.
- Nested location configuration.

This makes configuration easier to organize and reuse.

# 24. Browser Cache

The instructor notes that the browser may cache previous responses.

Therefore, if changes do not immediately appear, testing through an **incognito/private browsing window** can help
ensure that the browser is requesting fresh resources. or just use `ctrl + shift + R` for hard reload

For example:

```text
Normal browser
      ↓
Possibly cached content

Incognito browser
      ↓
Fresh request
```

This is particularly useful when debugging static assets such as CSS and JavaScript.

# 25. Changing the Listening Port

The lab then demonstrates that the same NGINX server can listen on another port.

Initially:

```nginx
listen 80;
```

The configuration can be changed to:

```nginx
listen 8081;
```

After changing the configuration:

```bash
nginx -t
```

Then reload:

```bash
nginx -s reload
```

or:

```bash
systemctl reload nginx
```

The website can then be accessed using the new port:

```text
http://SERVER_IP:8081
```

If you attempt to access it through port `80` after NGINX has been configured to listen on `8081`, the expected behavior
is that port `80` no longer serves this particular server block.

---

# 26. Multiple Ports on the Same NGINX Server

The lab highlights an important real-world concept: one NGINX server can have multiple server configurations listening
on different ports.

For example:

```text
Port 80
    ↓
Main application

Port 8080
    ↓
Another application

Port 8081
    ↓
Child/support application

Port 9090
    ↓
Health-check endpoint/application
```

The exact arrangement depends on the application's architecture.

The instructor notes that production systems may use different ports for purposes such as:

- Real application traffic.
- Health checks.
- Support applications.
- Other services/applications.

NGINX can therefore provide different mappings for different ports on the same server.

# 29. Common Mistakes and Warnings

## Mistake 1 — Forgetting `-R` with SCP

When uploading a directory:

```bash
scp -r ...
```

is required.

Without recursive copying, the directory and its contents will not be transferred as intended.

---

## Mistake 2 — Using `http://` in `server_name`

Incorrect:

```nginx
server_name http://104.131.80.130;
```

Correct:

```nginx
server_name 104.131.80.130;
```

---

## Mistake 3 — Incorrect Filesystem Path

The `root` directive must point to the actual directory containing the website.

For this lab:

```nginx
root /root/blogging-template;
```

---

## Mistake 4 — NGINX Permission Problems

If NGINX cannot access the configured filesystem location, the request can result in:

```text
403 Forbidden
```

The instructor therefore recommends following the demonstrated directory placement for the lab.

---

## Mistake 5 — Restarting NGINX Without Testing

Avoid:

```bash
systemctl restart nginx
```

immediately after changing the configuration.

Instead:

```bash
nginx -t
systemctl reload nginx
```

A syntax error can prevent NGINX from starting after a restart.

---

## Mistake 6 — Forgetting Semicolons

NGINX directives normally end with semicolons:

```nginx
root /root/blogging-template;
```

not:

```nginx
root /root/blogging-template
```

A missing semicolon can produce a configuration syntax error.

---

## Mistake 7 — Forgetting MIME Types

If HTML loads but CSS/JavaScript does not behave correctly, inspect the response headers.

For example:

```bash
curl -I http://SERVER_IP/path/to/file.css
```

If a CSS file is being returned as:

```text
Content-Type: text/plain
```

the MIME type configuration needs to be investigated.

---

## Mistake 8 — Forgetting the Browser Cache

If the configuration has been corrected but the browser still displays old content, test using a private/incognito
browser window.

---

# 30. Key Takeaways

This lab introduces several important NGINX administration concepts:

1. Static websites can be uploaded to an NGINX server using SCP.
2. A `server` block can be used to create a virtual host.
3. `listen` specifies the port on which the server block listens.
4. `server_name` identifies the hostname/IP handled by the server block.
5. `root` specifies the filesystem location containing the website.
6. `nginx -t` validates NGINX configuration syntax.
7. Configuration should be tested before being applied.
8. `reload` is preferred for applying configuration changes without unnecessarily stopping NGINX.
9. `nginx.conf` should be backed up before major modifications.
10. MIME types determine how returned files are identified to the client.
11. The `mime.types` file contains predefined MIME mappings.
12. The `include` directive allows existing configuration to be incorporated into `nginx.conf`.
13. Multiple ports can be configured on the same NGINX server.
14. Logs and `curl -I` are useful tools for diagnosing static-content problems.

The most important operational workflow from this lab is:

```text
Modify configuration
        ↓
nginx -t
        ↓
Configuration OK?
    ↙          ↘
  NO            YES
  ↓              ↓
Fix error      Reload NGINX
                  ↓
             Test application
                  ↓
             Check logs if needed
```

This lab establishes the foundation for the next NGINX configuration exercises: **serve content, create server blocks,
safely change configuration, validate it, and diagnose the behavior through logs and HTTP response headers.**
