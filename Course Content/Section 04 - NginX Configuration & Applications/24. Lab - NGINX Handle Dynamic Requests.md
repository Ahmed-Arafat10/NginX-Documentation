# 24. Lab — NGINX Handle Dynamic Requests

## Overview

So far, the NGINX configuration has primarily served **static content**, such as:

- HTML files
- PNG/JPG images
- CSS files
- JavaScript files
- Static strings

This lab introduces handling **dynamic PHP requests** with NGINX.

The lecture demonstrates the request flow between NGINX and **PHP-FPM**:

```text
Client
   ↓
NGINX
   ↓
PHP-FPM
   ↓
Dynamic PHP processing
   ↓
NGINX
   ↓
Client
```

NGINX itself does not directly execute the PHP application. Instead, NGINX forwards PHP requests to PHP-FPM, which
processes the PHP code and returns the result to NGINX.



---

# 1. Static vs. Dynamic Requests

Before this lab, the server was handling resources such as:

```text
index.html
image.png
style.css
script.js
```

These are static resources because NGINX can directly read and serve them.

PHP is different.

For a PHP request such as:

```text
/index.php
```

the PHP code must be processed before a response can be returned to the client.

The lecture therefore introduces **PHP-FPM** as the process responsible for handling the dynamic PHP request.

---

# 2. NGINX and PHP-FPM Request Flow

The lecture describes NGINX as the main process that receives the client request.

For a dynamic PHP request:

```text
Client
  │
  │ HTTP request
  ▼
NGINX
  │
  │ forward PHP request
  ▼
PHP-FPM
  │
  │ execute PHP
  ▼
PHP-FPM
  │
  │ return processed result
  ▼
NGINX
  │
  │ HTTP response
  ▼
Client
```

This is also why the lecture describes NGINX as working as a **reverse proxy** in this scenario.

The PHP-FPM process handles the dynamic request, while NGINX remains responsible for communicating with the client.

---

# 3. Installing PHP-FPM

Before NGINX can process PHP requests through PHP-FPM, PHP-FPM needs to be installed.

First update the package information:

```bash
apt-get update
```

Then install PHP-FPM:

```bash
apt-get install php-fpm
```

The package installation creates the PHP-FPM service.

The lecture's environment creates a service corresponding to the installed PHP version, demonstrated as:

```text
php7.2-fpm
```

The version is environment-dependent; the lab uses the version available on the instructor's machine.



---

# 4. Verify PHP-FPM

After installation, verify the PHP-FPM service.

The lecture checks the service with:

```bash
systemctl status php7.2-fpm
```

The output shows the PHP-FPM master process and worker processes.

The lecture also verifies the running PHP processes with:

```bash
ps -aux | grep php
```

Conceptually:

```text
PHP-FPM
├── Master process
├── Worker process
└── Worker process
```

The master process runs as `root`, while the worker processes run under the PHP worker user demonstrated in the lab.

---

# 5. Configure the Index Files

The next step is to configure which file NGINX should use as the default index.

The lecture defines:

```nginx
index index.php index.html;
```

This establishes the preference:

1. `index.php`
2. `index.html`

Therefore, when a request is made for the root of the website, NGINX first looks for:

```text
index.php
```

If that file does not exist, it falls back to:

```text
index.html
```

This allows the same document root to contain both dynamic and static index files.

---

# 6. Initial Behavior Without `index.php`

At this point in the lab, the website contains:

```text
index.html
```

but does not contain:

```text
index.php
```

Therefore, with:

```nginx
index index.php index.html;
```

a request to the base URL first checks for `index.php`.

Because it does not exist, NGINX falls back to:

```text
index.html
```

The existing static website is therefore displayed.

This demonstrates the importance of index-file ordering.

---

# 7. Configure the Root Location with `try_files`

The lecture then adds a root location using `try_files`.

The conceptual configuration is:

```nginx
location / {
    try_files $uri $uri/ =404;
}
```

The purpose is to check the requested URI and then check the corresponding resource path before returning a `404` when
no matching resource exists.

The processing can be represented as:

```text
Request
   ↓
$uri
   ↓
Resource exists?
 ├── Yes → Serve resource
 └── No
      ↓
    $uri/
      ↓
  Resource exists?
 ├── Yes → Serve resource
 └── No
      ↓
    404
```

This builds on the `try_files` behavior covered in the previous lab.

# 8. Configure PHP Location Handling

To process PHP files, NGINX needs a dedicated location that matches PHP filenames.

The lecture creates a location using a regular expression for the `.php` extension.

Conceptually:

```nginx
location ~ \.php$ {
    ...
}
```

This means PHP files are handled by this location.

For example:

```text

/info.php
/test.php
```

can match the PHP location.

# 9. FastCGI

PHP-FPM communicates with NGINX through **FastCGI**.

The lecture describes FastCGI as a protocol used for dynamic processing, similar conceptually to HTTP but intended for
communication between the web server and dynamic application processes.

NGINX therefore needs to know:

1. Which FastCGI configuration to use.
2. Where the PHP-FPM process is listening.

---

# 10. Include the FastCGI Configuration

NGINX provides a FastCGI configuration file.

The lecture finds it under the NGINX configuration directory:

```text
/etc/nginx/
```

and refers to:

```text
fastcgi.conf
```

The PHP location includes the FastCGI configuration:

```nginx
include fastcgi.conf;
```

This supplies the configuration parameters required for the FastCGI request.



---

# 11. Configure `fastcgi_pass`

NGINX also needs to know how to communicate with PHP-FPM.

The lecture uses:

```nginx
fastcgi_pass unix:/run/php/php7.2-fpm.sock;
```

The important part is the PHP-FPM Unix socket:

```text
/run/php/php7.2-fpm.sock
```

The exact socket path depends on the installed PHP-FPM version and system configuration.

Conceptually:

```text
NGINX
   │
   │ Unix socket
   ▼
/run/php/php7.2-fpm.sock
   │
   ▼
PHP-FPM
```

---

# 12. Finding the PHP-FPM Socket

If the PHP-FPM socket location is unknown, the lecture searches the filesystem.

The demonstrated approach uses:

```bash

```

The result identifies the socket used by PHP-FPM.

For the lecture's environment, the result is:

```text
/run/php/php7.2-fpm.sock
```

That path is then supplied to `fastcgi_pass`.

# 17. Troubleshooting a `502 Bad Gateway`

During the lab, the first request to `info.php` produces:

```text
502 Bad Gateway
```

The lecture emphasizes that this is different from a `404`.

A `404` would indicate that the requested resource could not be found.

Here, `info.php` exists, but NGINX cannot communicate correctly with PHP-FPM.

The likely communication path is:

```text
Browser
   ↓
NGINX
   ↓
PHP-FPM socket
   X
Permission denied
```

The error is investigated through the NGINX error log.

---

# 18. Inspect the NGINX Error Log

The lecture uses the NGINX error log to investigate the `502` response.

For example:

```bash
tail -10 /var/log/nginx/error.log
```

The resulting message indicates a connection problem with the PHP-FPM Unix socket and includes:

```text
permission denied
```

This indicates that NGINX and PHP-FPM are not able to communicate through the configured socket with the current process
users/permissions.



---

# 19. Identify the NGINX Worker User

The lecture then checks the NGINX processes:

```bash
ps -aux | grep nginx
```

The output shows:

```text
NGINX master process → root
NGINX worker process → nobody
```

The PHP processes are then inspected:

```bash
ps -aux | grep php
```

The lecture observes:

```text
PHP-FPM master process → root
PHP-FPM worker process → www-data
```

This reveals the mismatch demonstrated in the lab:

```text
NGINX worker → nobody
PHP-FPM worker → www-data
```

The lecture identifies this user mismatch as the reason for the permission problem with the PHP-FPM socket.

---

# 20. Configure the NGINX Worker User

The lecture resolves the problem by changing the NGINX worker user to `www-data`.

At the global configuration level:

```nginx
user www-data;
```

This is a **global/main-context directive**.

Conceptually:

```text
NGINX master process
        │
        ├── Worker → www-data
        └── Worker → www-data

PHP-FPM
        │
        ├── Worker → www-data
        └── Worker → www-data
```

The lab then reloads NGINX and verifies the processes again.

The NGINX worker process is now running as:

```text
www-data
```

# 24. What Happens if `index.php` Is Missing?

The configuration provides a useful fallback.

If:

```text
index.php
```

does not exist, NGINX proceeds to:

```text
index.html
```

Therefore:

```text
index index.php index.html;
```

provides two levels of preference:

```text
Base URL
   ↓
Does index.php exist?
 ├── Yes → Process PHP
 └── No
      ↓
Does index.html exist?
 ├── Yes → Serve HTML
 └── No → Continue according to location configuration
```

This allows the same root path to support both dynamic and static content.

# 25. Complete Configuration Concept

The main concepts demonstrated in the lab can be combined into a configuration similar to:

```nginx
user www-data;

http {
    index index.php index.html;

    server {
        listen 80;
        server_name SERVER_IP;

        root /root/blogging-template;

        location / {
            try_files $uri $uri/ =404;
        }

        location ~ \.php$ {
            include fastcgi.conf;
            fastcgi_pass unix:/run/php/php7.2-fpm.sock;
        }
    }
}
```

The exact PHP-FPM socket path and document-root path depend on the environment used.

The important components are:

```text
user www-data
        ↓
NGINX worker permissions

index index.php index.html
        ↓
Index-file preference

location /
        ↓
Static resource handling

location ~ \.php$
        ↓
PHP request handling

include fastcgi.conf
        ↓
FastCGI parameters

fastcgi_pass
        ↓
PHP-FPM communication
```

# 26. Troubleshooting Checklist

When PHP requests fail, check the following in order.

### 1. Is PHP-FPM installed?

```bash
apt-get install php-fpm
```

### 2. Is PHP-FPM running?

```bash
systemctl status php7.2-fpm
```

Use the PHP-FPM version actually installed on the system.

### 3. Is the PHP file present?

```bash
ls
```

For example:

```text
info.php
index.php
```

### 4. Does NGINX have a PHP location?

```nginx
location ~ \.php$ {
    ...
}
```

### 5. Is FastCGI configuration included?

```nginx
include fastcgi.conf;
```

### 6. Is `fastcgi_pass` pointing to the correct socket?

```nginx
fastcgi_pass unix:/run/php/php7.2-fpm.sock;
```

### 7. Does the socket exist?

```bash
find / -name "*fpm.sock"
```

### 8. Are NGINX and PHP-FPM worker users compatible with the socket permissions?

Check NGINX:

```bash
ps -aux | grep nginx
```

Check PHP:

```bash
ps -aux | grep php
```

### 9. Check the NGINX error log

```bash
tail -10 /var/log/nginx/error.log
```

### 10. Validate and reload NGINX

```bash
nginx -t
nginx -s reload
```

# 27. Common Mistakes and Warnings

### 1. Expecting NGINX to execute PHP directly

The lab's architecture uses PHP-FPM for dynamic PHP processing.

```text
NGINX → PHP-FPM → NGINX → Client
```

### 2. Incorrect PHP-FPM socket

If `fastcgi_pass` points to a socket that does not exist or cannot be accessed, PHP requests can result in
`502 Bad Gateway`.

### 3. Ignoring the error log

When PHP returns `502`, the NGINX error log can provide the specific communication error.

### 4. Worker-user permission mismatch

The lab demonstrates a mismatch between:

```text
NGINX worker → nobody
PHP-FPM worker → www-data
```

and resolves it by configuring:

```nginx
user www-data;
```

### 5. Forgetting `nginx -t`

Always validate configuration changes before reloading:

```bash
nginx -t
```

### 6. Incorrect index ordering

If the intention is to prioritize PHP, the configuration must place:

```nginx
index.php
```

before:

```nginx
index.html
```

---

# 28. Key Takeaways

- NGINX can serve static resources directly, but PHP requires a separate dynamic-processing component.
- **PHP-FPM** handles PHP requests in this lab.
- NGINX communicates with PHP-FPM through a **FastCGI** interface.
- `fastcgi_pass` specifies the PHP-FPM communication endpoint.
- The lab uses a Unix socket for this communication.
- `location ~ \.php$` is used to identify PHP requests.
- `include fastcgi.conf;` supplies the FastCGI configuration.
- `index index.php index.html;` gives PHP index files priority over HTML index files.
- `try_files` continues to provide resource existence/fallback handling for the root location.
- A `502 Bad Gateway` in this lab indicates that the PHP resource exists but NGINX cannot successfully communicate with
  PHP-FPM.
- NGINX worker-process permissions can affect communication with the PHP-FPM socket.
- The lab resolves the demonstrated permission problem by running NGINX workers as `www-data`.
- `phpinfo()` is useful in the lab for confirming that PHP processing is working.
- Once `index.php` exists, a request to the base URL uses the PHP index before `index.html`.

## Overall Request Flow

```text
                    Client
                      │
                      ▼
                    NGINX
                      │
             ┌────────┴────────┐
             │                 │
        Static request     PHP request
             │                 │
             ▼                 ▼
       Static resource     FastCGI
                               │
                               ▼
                           PHP-FPM
                               │
                               ▼
                         Process PHP
                               │
                               ▼
                            NGINX
                               │
                               ▼
                            Client
```

The central idea of this lab is that **NGINX remains the web-facing server while PHP-FPM handles the dynamic PHP
processing**. Correct index configuration, PHP location matching, FastCGI configuration, socket configuration, and
process permissions allow NGINX to serve both static and dynamic content from the same website.
