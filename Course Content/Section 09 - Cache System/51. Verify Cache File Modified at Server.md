# Section 09 — NginX Caching

# Lecture 51: Verify Whether a Cached File Has Been Modified on the Server

## 1. Overview

When a browser or middleware caching server stores a local copy of a static resource, it can serve that copy directly to the user without downloading the file again from the backend application server.

However, the backend file may change after the cached copy has been stored. If the cache continues serving the old version, the user may receive **stale content**.

HTTP provides the `If-Modified-Since` request header to help determine whether a cached resource has changed since it was last retrieved.

This lecture explains:

- How the `If-Modified-Since` HTTP header works.
- How the `Last-Modified` response header identifies when a resource was last changed.
- How HTTP status codes `200 OK` and `304 Not Modified` are used during cache validation.
- How to verify cache behavior using Firefox Developer Tools.
- How to modify a static file on the backend server and verify that the browser retrieves the updated version.

## 2. Key Concepts

| Concept | Description |
|---|---|
| Browser cache | A local copy of a resource stored by the browser. |
| Middleware cache | A cache located between the client and the backend application server. |
| `If-Modified-Since` | An HTTP request header that asks whether a resource has changed since a specified date and time. |
| `Last-Modified` | An HTTP response header that indicates when the resource was last modified. |
| `200 OK` | Indicates a successful response, typically including the requested resource when it has been retrieved or updated. |
| `304 Not Modified` | Indicates that a cached representation can be reused because the resource has not changed since the supplied validation date. |
| Stale cache | A cached copy that no longer represents the current version of the resource. |
| Cache validation | Checking whether a stored resource remains valid before reusing it. |
| `no-store` | A cache directive that instructs compliant caches not to store the response. |

## 3. The Problem: A Cached File Becomes Outdated

Consider a website with a user, a caching server, and a backend web application server.

The user requests a static resource, such as a JPG image.

If the caching server already has a local copy, it may return that copy without contacting the backend server. This reduces network traffic and improves response time.

However, suppose the image is updated on the backend server after the cache has stored it.

Without appropriate cache validation or expiration, the client could continue receiving an outdated image.

The challenge is to determine whether the cached resource is still valid without downloading the entire file unnecessarily.

## 4. How `If-Modified-Since` Works

The `If-Modified-Since` header allows a client to ask the server whether a resource has changed since a particular date and time.

The header is included in an HTTP **request**. It is not an NginX configuration directive that must be manually added to the server configuration for every client.

### 4.1 Initial request

When the browser requests a resource for the first time, it may receive a response such as:

```http
HTTP/1.1 200 OK
Last-Modified: Wed, 12 Aug 2020 15:26:28 GMT
Content-Type: image/jpeg
```

The `Last-Modified` header tells the client when the server reports that the resource was last modified.

The browser can store the resource and its associated metadata in its cache.

### 4.2 Subsequent request

When the browser needs to validate its cached copy, it can send a conditional request:

```http
GET /assets/images/p1.jpg HTTP/1.1
Host: app.example.com
If-Modified-Since: Wed, 12 Aug 2020 15:26:28 GMT
```

The date in `If-Modified-Since` represents the last-modified time associated with the cached resource.

The server compares that date with the resource's current modification time.

### 4.3 Resource has not changed

If the resource has not been modified since the supplied date, the server can respond:

```http
HTTP/1.1 304 Not Modified
```

The response indicates that the cached copy can be reused. The server does not need to transmit the resource body again.

The browser uses its local copy to display the resource.

### 4.4 Resource has changed

If the resource has been modified since the supplied date, the server returns the updated representation, typically with:

```http
HTTP/1.1 200 OK
Last-Modified: Sun, 20 Sep 2020 10:00:00 GMT
Content-Type: image/jpeg
```

The response includes the updated resource body. The browser can update its cache and use the latest version.

The date above is illustrative; the actual modification date depends on the resource and server.

### 4.5 Request and response flow

```text
Browser / Client
       |
       | 1. Request a static resource
       v
Caching Layer
       |
       | 2. Validate the cached copy
       |    using If-Modified-Since
       v
Backend Web Server
       |
       | 3. Compare the supplied date
       |    with the resource's current
       |    modification time
       |
       +-----------------------------+
       |                             |
       v                             v
 Resource unchanged           Resource modified
       |                             |
       v                             v
 304 Not Modified                200 OK
 No resource body                Updated resource body
       |                             |
       v                             v
 Reuse cached copy             Update cached copy
       |                             |
       +--------------+--------------+
                      |
                      v
                 Browser uses
                the valid resource
```

**Important:** A browser and a middleware cache are different caching layers. The demonstration in this lecture uses Firefox's browser cache. A reverse proxy or middleware cache may perform similar validation when configured to do so, but its behavior depends on its caching implementation and configuration.

## 5. Understanding the Relevant HTTP Headers

### 5.1 `If-Modified-Since`

This is a conditional request header.

Example:

```http
If-Modified-Since: Wed, 12 Aug 2020 15:26:28 GMT
```

It asks the server to return the resource only if it has been modified since the specified date.

If the resource has not changed, the server can return `304 Not Modified`.

### 5.2 `Last-Modified`

This is a response header that indicates the last modification date and time reported by the server.

Example:

```http
Last-Modified: Wed, 12 Aug 2020 15:26:28 GMT
```

The browser can use this metadata when validating its cached copy.

### 5.3 `200 OK` versus `304 Not Modified`

| Status code | Meaning | Resource body |
|---|---|---|
| `200 OK` | The request succeeded and the server returned the resource representation. | Normally included for a successful GET response. |
| `304 Not Modified` | The cached representation remains valid under the conditional request. | Not included. The client reuses its stored copy. |

A `304 Not Modified` response is not an error. It is part of normal HTTP cache validation.

### 5.4 How caching saves resources

Cache validation can reduce:

- Repeated transfers of unchanged files.
- Network bandwidth consumption.
- Unnecessary work for the backend server.
- Download time for clients.

The browser still needs to make a validation request when required. The benefit is that the full resource body does not need to be transferred if the cached copy remains valid.

## 6. Practical Lab: Verify Cache Validation in Firefox

The lecture demonstrates cache validation using a website called Brownie and a static JPG image named `p1.jpg`.

The lab involves three stages:

1. Clear the browser cache and request the image.
2. Request the same image again and observe the `304 Not Modified` response.
3. Modify the image's file metadata on the backend and verify that the browser receives the updated resource.

### 6.1 Step 1: Clear the browser cache

Open Firefox and clear the cached files.

Then:

1. Open the Brownie website.
2. Press **F12** to open Developer Tools.
3. Select the **Network** tab.
4. Refresh the page.
5. Locate a JPG image request.

The lecture notes that PNG files have a `no-store` cache directive configured in NginX. For that reason, use a JPG image for this demonstration.

### 6.2 Step 2: Inspect the first JPG request

Select a JPG request in the Network panel.

On the first request, the lecture observes a response status of:

```http
200 OK
```

Inspect the response headers and locate `Last-Modified`.

For example:

```http
HTTP/1.1 200 OK
Last-Modified: Wed, 12 Aug 2020 15:26:28 GMT
Content-Type: image/jpeg
```

The timestamp above represents the example date described in the lecture.

Because the browser cache was cleared, the browser does not have a previously cached copy available for reuse. The server returns the image, and the browser can cache it if the applicable caching rules permit.

### 6.3 Step 3: Confirm that the image is cached

Open Firefox's cache inspection view, as demonstrated in the lecture, and locate the image URL.

The example resource is:

```text
p1.jpg
```

Verify that the URL is present in the browser cache.

This confirms that the browser has a stored copy available for later use.

### 6.4 Step 4: Refresh the page again

Return to the Brownie website and refresh it.

Open the Network panel and locate the same `p1.jpg` request.

The lecture observes:

```http
HTTP/1.1 304 Not Modified
```

This indicates that the browser's cached representation can be reused.

The image is not downloaded again as a full response body.

Other JPG images may also show `304 Not Modified` when their cached representations remain valid.

The PNG images configured with `no-store` behave differently because that directive prevents compliant caches from storing those responses.

**Note:** The precise status codes visible in Developer Tools can depend on the browser's cache state, the request headers, the server's response headers, and whether the resource is served from a local cache or revalidated with the server.

## 7. Practical Lab: Modify the Resource on the Backend Server

Next, the lecture modifies the backend file to demonstrate that an existing cached copy can be refreshed when the resource changes.

### 7.1 Step 1: Navigate to the image directory

Connect to the backend server and navigate to the website's image directory.

The lecture uses the following directory structure:

```text
blogging-template/
└── assets/
    └── images/
        ├── clients/
        ├── about/
        └── portfolio/
            └── p1.jpg
```

The directory names are based on the demonstration and may differ in another installation.

Navigate to the portfolio directory:

```bash
cd /path/to/blogging-template/assets/images/portfolio
```

Replace the example path with the actual path on your server.

List the files:

```bash
ls -l
```

The lecture identifies `p1.jpg` in the portfolio directory.

### 7.2 Step 2: Inspect the original modification time

Run:

```bash
ls -lrt
```

This lists files in time order, showing the oldest entries first.

In the demonstration, `p1.jpg` has an earlier modification date, reported as August 12.

### 7.3 Step 3: Copy the image to a temporary filename

Create a copy named `p7.jpg`:

```bash
cp p1.jpg p7.jpg
```

List the files again:

```bash
ls -lrt
```

The newly created copy should have a newer filesystem modification time.

The lecture observes a date in September for the copied file.

### 7.4 Step 4: Remove the original file

Remove `p1.jpg`:

```bash
rm p1.jpg
```

Verify the directory contents:

```bash
ls -lrt
```

At this point, `p7.jpg` remains and `p1.jpg` is no longer present.

**Warning:** The `rm` command permanently removes the specified file unless recovery mechanisms are available. Confirm the directory and filename before executing it. For a production system, use a safer staging procedure rather than deleting a live application asset.

### 7.5 Step 5: Rename the copied file to the original name

Rename `p7.jpg` back to `p1.jpg`:

```bash
mv p7.jpg p1.jpg
```

Inspect the files again:

```bash
ls -lrt
```

The lecture observes that `p1.jpg` now has a newer modification time than the original file.

The filename remains the same, but the filesystem modification metadata has changed.

### 7.6 Step 6: Refresh the browser

Return to Firefox and refresh the Brownie website.

Open the Network panel and locate `p1.jpg`.

The lecture observes:

```http
HTTP/1.1 200 OK
```

The browser receives the resource again because the server reports that the resource has been modified since the cached version's validation date.

Inspect the response headers. The `Last-Modified` value should now reflect the newer modification time reported by the server.

Other unchanged JPG images may continue to return:

```http
HTTP/1.1 304 Not Modified
```

This demonstrates that cache validation is performed for individual resources rather than forcing every cached image to be downloaded again.

### 7.7 Step 7: Refresh once more

Refresh the page again and inspect `p1.jpg`.

The lecture observes:

```http
HTTP/1.1 304 Not Modified
```

After the browser has received and cached the updated representation, the resource can be reused on subsequent requests when it remains unchanged.

The expected sequence is:

| Stage | Resource state | Observed status |
|---|---|---|
| First request after clearing the cache | No cached copy available | `200 OK` |
| Second request | Cached copy is still valid | `304 Not Modified` |
| Backend file is replaced with a newer version | Cached copy is outdated | `200 OK` |
| Next request after the cache is updated | Cached copy is valid again | `304 Not Modified` |

These statuses reflect the lecture's demonstration. Actual results depend on the server and browser cache configuration.

## 8. Important Notes and Common Mistakes

### 8.1 Do not confuse the two headers

- `If-Modified-Since` is sent in a request.
- `Last-Modified` is returned in a response.

They work together to support conditional requests.

### 8.2 A `304` response does not mean the file is missing

`304 Not Modified` means the client can reuse a previously stored representation. It does not indicate that the server failed to locate the file.

### 8.3 `no-store` changes the caching behavior

The lecture's NginX configuration uses a `no-store` cache directive for PNG files.

A compliant cache should not store a response carrying `Cache-Control: no-store`. Consequently, PNG requests may behave differently from JPG requests in the demonstration.

### 8.4 File modification time matters

The demonstration changes the resource by copying and renaming a file, resulting in a newer filesystem modification time.

This is intended to make the server report a different `Last-Modified` value.

However, replacing a file does not guarantee that every server or storage system will report the expected timestamp. Filesystem timestamp precision, deployment tools, metadata handling, and server behavior can affect the result.

### 8.5 A cached file is not always validated on every request

The lecture demonstrates conditional validation, but HTTP caching can also use freshness lifetimes and other caching directives.

While a cached resource is considered fresh, the browser may reuse it without contacting the server. Once validation is needed, conditional requests can determine whether the cached representation remains valid.

### 8.6 Modification-time validation has limitations

`Last-Modified` validation relies on modification-time metadata. If a resource changes without a distinguishable modification timestamp, this mechanism may not detect the change as expected.

HTTP also supports entity tags through the `ETag` and `If-None-Match` headers, which provide another mechanism for validating cached resources.

## 9. Summary

The `If-Modified-Since` header allows a client to validate a cached resource without necessarily downloading it again.

The main takeaways are:

1. A browser or caching server may store static resources locally to reduce repeated downloads.
2. `If-Modified-Since` is a conditional request header containing the date associated with the cached representation.
3. `Last-Modified` is a response header that reports the resource's last modification time.
4. If the resource has not changed, the server can return `304 Not Modified`, allowing the client to reuse its cached copy.
5. If the resource has changed, the server typically returns `200 OK` with the updated resource.
6. Firefox Developer Tools can be used to inspect request status codes and response headers.
7. The lecture demonstrates this behavior by caching `p1.jpg`, modifying its backend file, and refreshing the browser.
8. Cache directives such as `no-store` affect whether resources can be stored and reused.
9. HTTP cache validation helps keep resources current while avoiding unnecessary transfer of unchanged files.

Understanding these headers is useful when troubleshooting browser caching, static resources, and NginX caching behavior.
