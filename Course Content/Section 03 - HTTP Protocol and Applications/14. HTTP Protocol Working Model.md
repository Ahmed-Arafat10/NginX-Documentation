# 14. HTTP Protocol Working Model

## Lecture Title

**HTTP Protocol Working Model**

## Overview

HTTP (**Hypertext Transfer Protocol**) is the protocol used for **web communication**. It defines how a web client
creates and sends requests to a web server and how the server processes those requests and returns responses.

The lecture focuses on:

- What HTTP is
- The HTTP client-server model
- How HTTP requests and responses work
- The connectionless nature of HTTP
- The media-independent nature of HTTP
- The stateless nature of HTTP
- How a web server processes a request
- The difference between static and dynamic web content
- A practical example using YouTube

---

# 1. What Is HTTP?

HTTP stands for **Hypertext Transfer Protocol**.

The lecture describes HTTP as an **application-level protocol used for web communication**.

A book-style definition given in the lecture describes HTTP as:

> An application-level protocol for a distributed, collaborative hypermedia information system.

This relates to the Web because web communication involves distributed systems where:

- A web client sends a request.
- A web server receives and processes the request.
- The web server sends a response back to the client.

The communication between the web client and web server takes place using HTTP.

---

# 2. HTTP and the TCP/IP Model

The lecture explains that HTTP is a **TCP/IP-based communication protocol** used to deliver different types of data over
the World Wide Web.

The data can include:

- HTML files
- Image files
- Query results
- Media files
- Other supported data

Conceptually:

```text
Web Client
    |
    | HTTP Request
    v
Web Server
    |
    | HTTP Response
    v
Web Client
```

HTTP operates as part of the broader TCP/IP networking architecture.

# 3. HTTP Client-Server Architecture

HTTP follows a **client-server architecture**.

The two main participants are:

### Client

The client is the system that initiates the request.

A common example is a:

- Web browser

Other tools can also act as HTTP clients.

### Server

The server receives the HTTP request, processes it, and sends an HTTP response.

For example:

```text
Browser
   |
   | HTTP Request
   v
Web Server
   |
   | HTTP Response
   v
Browser
```

---

# 4. HTTP Request

Whenever a web client wants information from a web server, it creates an **HTTP request**.

The request follows a defined format so that the server knows how to interpret it.

The lecture emphasizes that the request contains necessary information and follows a standard structure.

Conceptually:

```text
HTTP Request
├── Request information
├── URI
├── Parameters
└── Other request data
```

The server uses this information to understand what the client is requesting.

---

# 5. HTTP Response

After receiving the request, the web server processes it and sends a response back to the client.

The response also follows a defined format.

Conceptually:

```text
Client
  |
  | HTTP Request
  v
Server
  |
  | Process Request
  v
Server
  |
  | HTTP Response
  v
Client
```

The client can then interpret the response and display the resulting information to the user.

For example, when a browser requests a web page, the server sends a response containing the information required to
display that page.

---

# 6. Basic HTTP Working Model

The basic HTTP workflow described in the lecture is:

1. The web client creates an HTTP request.
2. The request is sent to the web server.
3. The web server accepts the request.
4. The server identifies the requested **URI** and parameters.
5. If server-side processing is required, the server executes the appropriate server-side script.
6. The server performs the required processing.
7. The server generates a response.
8. The response is sent back to the web client.
9. The client displays the resulting content to the user.

A simplified representation is:

```text
+-------------+
| Web Client  |
|  (Browser)  |
+------+------+
       |
       | HTTP Request
       v
+------+------+
| Web Server  |
+------+------+
       |
       | Identify URI / Parameters
       |
       | Execute server-side processing
       |
       | Retrieve required data
       |
       v
+------+------+
|  Response   |
+------+------+
       |
       | HTTP Response
       v
+-------------+
| Web Client  |
| Displays    |
| Content     |
+-------------+
```

# 7. HTTP Is Connectionless

One of the characteristics discussed in the lecture is that **HTTP is connectionless**.

The lecture explains this using a browser request.

Suppose you enter a website URL into a browser.

For example:

```text
https://example.com
```

The browser acts as the client.

The process is:

1. The browser sends a request.
2. The server receives the request.
3. The server processes the request.
4. The server sends the response.
5. The connection for that request is disconnected.

Conceptually:

```text
Client                    Server
  |                         |
  |------ Request --------->|
  |                         |
  |                         | Process
  |                         |
  |<------ Response --------|
  |                         |
  X  Connection ends        X
```

During the request/response interaction, the client and server communicate with each other.

Once the request has been processed and the response has been returned, the lecture describes the connection as being
disconnected.

### Browser example

When you enter a URL:

```text
https://example.com
```

the browser sends an HTTP request.

While waiting for the server's response, the browser may show a loading/progress indicator.

Once the server returns the response, the browser receives the result and displays the page.

---

# 8. HTTP Is Media Independent

Another characteristic discussed in the lecture is that HTTP is **media independent**.

This means HTTP can be used to transfer different types of data.

The lecture gives examples including:

- Text data
- HTML data
- JSON data
- Stream data
- Media data

Conceptually:

```text
HTTP
 |
 +-- Text
 +-- HTML
 +-- JSON
 +-- Streams
 +-- Media
```

The condition is that **both the client and server must know how to handle the particular type of data being
exchanged**.

Therefore, HTTP itself is not restricted to transferring only HTML pages.

---

# 9. HTTP Is Stateless

HTTP is also described as **stateless**.

This means that the server and client do not inherently retain information about previous requests.

The lecture explains it as follows:

> The server and client know each other during the current request only, and after that both forget about each other.

Therefore, each request is treated independently.

---

## 9.1 Multiple Requests

Suppose a browser makes ten requests to a web server.

According to the model explained in the lecture, each request is treated independently:

```text
Request 1 → Connection → Response 1
Request 2 → Connection → Response 2
Request 3 → Connection → Response 3
...
Request 10 → Connection → Response 10
```

The lecture uses this example to explain that one request does not inherently know about another request.

For example:

```text
Request 1
    |
    +--> Does not inherently know about Request 2

Request 2
    |
    +--> Does not inherently know about Request 1
```

Therefore, HTTP does not inherently maintain the state of requests across different interactions.

---

# 10. Connectionless vs. Stateless

The lecture discusses both concepts, and they describe different aspects of HTTP.

### Connectionless

Refers to the lifecycle of the communication described in the lecture:

```text
Request
   ↓
Processing
   ↓
Response
   ↓
Connection ends
```

### Stateless

Refers to the fact that one request does not inherently retain knowledge of previous requests:

```text
Request 1 → Response 1

Request 2 → Response 2

Request 3 → Response 3
```

Each request is treated independently.

# 11. HTTP Request Processing Architecture

When a request is sent from a web client, the web server performs several operations.

The lecture describes the following flow:

### Step 1 — Client sends a request

The request originates from a web client, such as:

- A web browser
- Another HTTP-capable tool

```text
Web Client
     |
     | HTTP Request
     v
Web Server
```

### Step 2 — Server accepts the request

The web server receives the HTTP request.

### Step 3 — Server identifies the URI and parameters

The server examines information in the request, including:

- URI
- Parameters

This allows the server to determine what resource or operation the client is requesting.

### Step 4 — Server-side processing

If the request requires server-side processing, the server executes the appropriate server-side script.

For example:

```text
Request
   |
   v
Identify URI
   |
   v
Execute server-side script
   |
   v
Process request
```

### Step 5 — Retrieve/process data

The application may perform additional processing, such as obtaining data from a database.

```text
Web Request
     |
     v
Server-side Script
     |
     v
Database
     |
     v
Data
```

### Step 6 — Generate the response

The server creates the response based on the processing.

### Step 7 — Return response to the client

The server sends the response back to the web client.

```text
Web Server
     |
     | HTTP Response
     v
Web Client
```

### Step 8 — Display the result

The browser processes the response and displays the resulting web page or content to the user.

# 12. Static vs. Dynamic Websites

The lecture uses static and dynamic websites to demonstrate how HTTP requests can result in different responses.

## 12.1 Static Website

A **static website** contains static web pages.

When a request is made, the web server returns the same page/content.

Conceptually:

```text
Request
   |
   v
Web Server
   |
   v
Static Page
   |
   v
Response
```

If the same request is made again, the server can return the same static content.

---

## 12.2 Dynamic Website

A **dynamic website** can generate different responses for the same request.

The lecture explains that the web server may:

1. Receive the request.
2. Execute server-side scripts.
3. Retrieve data.
4. Process the data.
5. Generate the response.
6. Return the response to the client.

Conceptually:

```text
Client Request
      |
      v
Web Server
      |
      v
Server-Side Script
      |
      v
Database / Data Source
      |
      v
Process Data
      |
      v
Generate Response
      |
      v
Client
```

Because the application is dynamic, the response can change between requests.

The instructor demonstrates the HTTP working model using **YouTube**.

The browser is used to access:

```text
https://youtube.com
```

The process can be represented as:

```text
Browser
   |
   | HTTPS Request
   v
YouTube Web Server
   |
   | Process Request
   | Execute application logic
   | Retrieve data
   v
HTTPS Response
   |
   v
Browser
   |
   v

```

The lecture points out that YouTube is a **dynamic website**.

When the page is refreshed, the content can change.

For example, different video links may appear after refreshing the page.

This demonstrates that although the browser can send what appears to be the same request, the web server/application can
produce a different response.

# 16. Complete HTTP Working Model

Putting the concepts together, the lecture's overall model can be represented as:

```text
                    HTTP / HTTPS
+-------------+   Request   +----------------+
|             | ----------> |                |
| Web Client  |              |   Web Server   |
|  (Browser)  | <---------- |                |
|             |   Response  |                |
+-------------+             +-------+--------+
                                     |
                                     |
                              Server-side logic
                                     |
                                     v
                               +-----------+
                               | Database  |
                               | / Data    |
                               +-----------+
```

For a dynamic application:

1. The client sends a request.
2. The server receives it.
3. The server identifies the URI and parameters.
4. Server-side logic executes when required.
5. The application may retrieve information from a database.
6. The server generates the response.
7. The response is returned to the client.
8. The client displays the resulting content.

# Practical Notes / Best Practices

- **HTTP is the fundamental web communication protocol** discussed in this lecture.
- HTTP uses a **client-server model**.
- A browser is a common example of an HTTP client.
- HTTP requests and responses follow defined formats so that both sides can understand the exchanged information.
- HTTP can transport different types of data, including HTML, JSON, text, streams, and media.
- HTTP is described in the lecture as **stateless**, meaning individual requests do not inherently retain knowledge of
  previous requests.
- Static websites generally return static content.
- Dynamic websites can generate different responses based on application processing and retrieved data.
- When troubleshooting Nginx web traffic, understanding the request → processing → response flow is fundamental.

## Lecture Takeaway

The core HTTP model is:

```text
Client
   |
   | Request
   v
Server
   |
   | Process
   v
Server-side logic / Data
   |
   | Response
   v
Client
```

In the context of Nginx, this model is particularly important because Nginx commonly sits in the path between clients
and web applications, receiving HTTP/HTTPS requests and participating in the delivery of the resulting responses.
