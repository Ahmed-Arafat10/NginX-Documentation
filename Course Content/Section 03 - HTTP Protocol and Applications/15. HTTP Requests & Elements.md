# 15. HTTP Requests & Elements

## Lecture Title

**HTTP Requests & Elements**

## Overview

An **HTTP request** is sent by a client to a server to request or exchange data. For the web server to understand and
process that request, the request follows a defined structure containing several components.

This lecture covers:

- The structure of an HTTP request message
- Request lines
- Request headers
- The optional request body
- HTTP request methods
- Request URI / resource path
- HTTP protocol version
- How to inspect requests using browser developer tools
- Practical examples using an Nginx server and YouTube

---

# 1. HTTP Request Message

When an HTTP client sends a request to a server, the request is sent in the form of a **request message**.

The lecture identifies four parts of the request message:

1. **Request line**
2. **Zero or more headers**
3. **An empty line**
4. **Optional message body**

Conceptually:

```text
HTTP Request Message
│
├── Request Line
│
├── Headers
│   ├── Header 1
│   ├── Header 2
│   └── ...
│
├── Empty Line
│
└── Optional Message Body
```

---

# 2. Request Line

The **request line** is the first part of an HTTP request.

It contains three main components:

1. **Method token**
2. **Request URI**
3. **Protocol version**

The general structure is:

```text
METHOD REQUEST_URI HTTP_VERSION
```

For example, conceptually:

```text
GET / HTTP/1.1
```

This can be broken down into:

```text
GET       → Method
/         → Request URI
HTTP/1.1  → Protocol Version
```

---

# 3. Method Token

The **method token** specifies what operation the client wants to perform.

The lecture introduces several HTTP methods:

- `GET`
- `POST`
- `PUT`
- `DELETE`
- `CONNECT`

Each method has a different purpose.

---

# 4. Request URI

The **Request URI** identifies the resource that the client is requesting.

The lecture describes it as the **resource path**.

For example:

```text
/
```

represents the root resource path.

A more specific URI might look like:

```text
/feed/trending
```

The resource URI is appended to the base/host URL.

For example:

```text
https://example.com/feed/trending
```

Here:

```text
https://example.com
```

is the base/host portion, while:

```text
/feed/trending
```

identifies the requested resource path.

---

# 5. HTTP Protocol Version

The third component of the request line is the **HTTP protocol version**.

For example:

```text
HTTP/1.1
```

The version tells the server which HTTP protocol version is being used for the request.

Therefore, the complete request line contains:

```text
METHOD + REQUEST URI + HTTP VERSION
```

---

# 6. Request Headers

After the request line, an HTTP request can contain **zero or more headers**.

Headers provide additional information about the request.

Conceptually:

```text
GET / HTTP/1.1
Host: example.com
Accept: text/html
Accept-Encoding: gzip
Accept-Language: en-US
Connection: keep-alive

```

The lecture's browser example shows headers such as:

- `Accept`
- `Accept-Encoding`
- `Accept-Language`
- `Connection`
- `Host`
- Other request-related parameters

For example, the browser may indicate that it accepts content such as:

```text
text/html
application/xml
image/webp
image/png
image/jpeg
```

It can also provide information about:

```text
Accept-Encoding: gzip
Accept-Language: en-US
Connection: keep-alive
Host: <host>
```

---

# 7. Empty Line

After the request headers, there is an **empty line**.

This empty line indicates that the header section has ended.

Conceptually:

```text
GET / HTTP/1.1
Host: example.com
Accept: text/html
Connection: keep-alive

<optional body>
```

The blank line separates the headers from the optional request body.

---

# 8. Request Body

The request can optionally contain a **message body**.

The lecture emphasizes that the body is **optional**.

Some HTTP requests use a body, while others do not.

Conceptually:

```text
Request Line
Headers

Optional Request Body
```

The lecture later gives `POST` as an example of a method that can carry data in the request body.

---

# 9. Complete HTTP Request Structure

Putting the components together:

```text
METHOD REQUEST_URI HTTP_VERSION
Header-1: value
Header-2: value
Header-3: value

Optional Request Body
```

For example:

```text
GET / HTTP/1.1
Host: example.com
Accept: text/html
Accept-Encoding: gzip
Accept-Language: en-US
Connection: keep-alive

```

The exact headers vary depending on the client and request.

# 14. HTTP Request Methods

The lecture introduces several HTTP request methods.

## 14.1 GET

The `GET` method is used to **retrieve data from the web server**.

According to the lecture, `GET` is used when:

- Retrieving data
- The request is not intended to change server data
- No request body is required

Example:

```text
GET / HTTP/1.1
```

Another example:

```text
GET /about HTTP/1.1
```

The important purpose is retrieving information from the server.

---

# 15. POST

The `POST` method is used to **send data to a server**.

The lecture associates `POST` with operations such as:

- Submitting data
- Modifying data
- Updating information
- Uploading files
- Sending other data to the server

A `POST` request can contain a **request body**.

Conceptually:

```text
POST /comments HTTP/1.1
Host: example.com
Content-Type: application/...

<comment data>
```

---

## 15.1 Facebook Comment Example

The lecture uses a Facebook comment as an example.

When a user submits a comment, data needs to be sent to the Facebook server.

The request can contain information such as:

- Who is sending the request
- Where the request originated
- Which post the comment belongs to
- The content of the comment

Conceptually:

```text
POST /some/resource HTTP/1.1
Host: example.com

Comment Data
```

The lecture explains that `POST` can also be used to:

- Update customer information
- Update other server-side data
- Upload files
- Submit data modifications

The server must support and understand the request format, and the client may need to be authenticated depending on the
application.

---

# 16. PUT

The `PUT` method is described as being similar to `POST` because both can be used to change data on the server.

The lecture specifically explains that `PUT` **replaces the current representation of the target resource with the
uploaded contents**.

Conceptually:

```text
PUT /resource HTTP/1.1
Host: example.com

Updated Resource
```

The lecture also remarks that developers often use `POST` instead of `PUT` in many situations.

---

# 17. DELETE

The `DELETE` method is used to **remove a resource/representation identified by the URI**.

The lecture explains that the client defines the resource path that should be deleted.

Conceptually:

```text
DELETE /resource HTTP/1.1
Host: example.com
```

The lecture states that `DELETE` does not accept a body and that the resource to remove is identified through the
resource path.

---

# 18. CONNECT

The `CONNECT` method is described in the lecture as being used to **establish a tunnel between the client and server for
the given URI**.

Conceptually:

```text
CONNECT target.example.com HTTP/1.1
```

The lecture associates `CONNECT` with establishing a connection/tunnel with the server from application code.

---

# 19. HTTP Methods Summary

| Method    | Purpose described in lecture                            |
|-----------|---------------------------------------------------------|
| `GET`     | Retrieve data from the server                           |
| `POST`    | Send/submit data and perform data modifications         |
| `PUT`     | Replace the current representation of a target resource |
| `DELETE`  | Remove the resource identified by the URI               |
| `CONNECT` | Establish a tunnel to the server for the given URI      |

The lecture focuses on these methods as the request methods being introduced.

# 20. Request URI in Practice

The instructor demonstrates the Request URI concept using **YouTube**.

When the root YouTube page is opened, the resource path can be:

```text
/
```

The request is therefore targeting the root resource.

When navigating to another section of the website, the URI changes.

For example, the lecture uses the YouTube trending section:

```text
/feed/trending
```

The browser is still using the `GET` method, but the **Request URI has changed**.

Conceptually:

```text
GET / HTTP/...
```

becomes:

```text
GET /feed/trending HTTP/...
```

The changed URI tells the web server which resource/section the client is requesting.

---

# 21. YouTube Subscription Example

The instructor then navigates to another section, such as subscriptions.

The resource URI changes again.

Conceptually:

```text
/feed/subscriptions
```

The important observation is:

```text
Same Method
    ↓
GET

Different Resource URI
    ↓
Different Requested Resource
```

Therefore, two requests can both use `GET` while requesting different resources.

---

# 22. Resource URI and Website Pages

The same concept applies to many websites.

A website may contain resources such as:

```text
/
```

```text
/about
```

```text
/contact
```

```text
/forgot
```

The lecture describes these paths as resource URIs for the website.

For example:

```text
https://example.com/about
```

can be understood as:

```text
Host:
example.com

Resource URI:
/about
```

Similarly:

```text
https://example.com/contact
```

contains:

```text
Resource URI:
/contact
```

These resource URIs can point to static pages or dynamically generated resources.

---

# 23. Static and Dynamic Pages

The resource URI concept applies to both:

- Static websites
- Dynamic websites

For a static page:

```text
GET /about HTTP/...
```

may retrieve a static resource.

For a dynamic application, a URI can identify a resource that causes server-side processing to occur.

The important point from the lecture is that the **URI identifies the resource being requested**, regardless of whether
the resulting content is static or dynamically generated.

The lecture's concepts can be combined into the following model:

+------------------------------------------------+

+------------------------------------------------+

The request line itself consists of:

```text
+---------+-------------------+----------------+
| Method  | Request URI       | HTTP Version   |

+---------+-------------------+----------------+
```

# Practical Notes / Best Practices

- The **request line** is the first part of an HTTP request.
- The request line contains the **method, request URI, and HTTP protocol version**.
- HTTP requests can contain **zero or more headers**.
- An **empty line** separates the headers from the optional body.
- The **request body is optional** and is commonly relevant when submitting data.
- `GET` is used to retrieve information.
- `POST` can submit data to the server.
- `PUT` is used for replacement of a target resource representation.
- `DELETE` identifies a resource to remove.
- `CONNECT` establishes a tunnel for the given URI.
- The **Request URI changes depending on the resource being requested**.
- Browser developer tools, particularly the **Network** tab, are useful for examining real HTTP requests.
- When troubleshooting Nginx, inspecting the request method, URI, headers, and response status can help determine
  exactly what the client is requesting.

# Common Mistakes / Warnings

### 1. Confusing the host with the Request URI

For:

```text
https://example.com/feed/trending
```

the host and resource path are different pieces:

```text
Host:
example.com

Resource URI:
/feed/trending
```

### 2. Assuming every request has a body

The request body is **optional**. Some requests do not contain a body.

### 3. Looking only at the HTTP method

The method alone does not identify the requested resource.

For example:

```text
GET /
```

and:

```text
GET /feed/trending
```

both use `GET`, but they request different resources.

### 4. Ignoring request headers

Headers provide important information to the server, including accepted content types, encoding, language, host
information, and other request properties.

# Lecture Takeaway

An HTTP request is a structured **request message** consisting of:

```text
Request Line
     ↓
Headers
     ↓
Empty Line
     ↓
Optional Body
```

The request line contains:

```text
METHOD + REQUEST URI + HTTP VERSION
```

The main methods introduced in this lecture are:

```text
GET
POST
PUT
DELETE
CONNECT
```

The **Request URI** identifies the resource being requested. For example:

```text
/
```

```text
/feed/trending
```

```text
/feed/subscriptions
```

Understanding these request components is fundamental when working with Nginx because it allows you to inspect exactly
**what the client is sending to the web server** and understand how Nginx receives and processes HTTP requests.
