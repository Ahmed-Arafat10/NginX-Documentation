# NGINX Upstream Configuration: `zone`, `state`, and Named Locations (`@`)

## 1. The `zone` Directive

### Overview

The `zone` directive allocates a shared memory zone for an NGINX upstream group. This allows worker processes to share
upstream runtime state instead of maintaining completely independent copies.

Shared upstream state can include information used for server selection, connection tracking, and peer health
management.

### Syntax

```nginx
zone <zone_name> <size>;
```

Example:

```nginx
upstream appservers {
    zone backend_zone 64k;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
}
```

In this example:

- `backend_zone` is the shared memory zone name.
- `64k` specifies the memory allocated to the zone.
- The zone allows NGINX worker processes to share relevant upstream state.

### Why Is `zone` Important?

Without a shared memory zone, upstream configuration and runtime state are generally maintained separately by worker
processes. Changes to shared upstream state may therefore require a shared zone to be visible consistently across
workers.

A shared zone is particularly important for features such as:

- Dynamic upstream server management through the NGINX Plus API.
- Sharing upstream peer state between workers.
- Runtime changes to server availability and configuration.
- Certain upstream health-checking and session-persistence features.

**Important:** The exact features requiring a shared zone depend on the NGINX edition and the specific module or
functionality being used.

## 2. The `state` Directive

### Overview

The `state` directive specifies a file where NGINX Plus can persist the configuration of dynamically managed upstream
servers.

It is useful when backend servers are added, removed, or modified at runtime through the NGINX Plus API.

Without a state file, runtime changes to dynamically managed upstream servers may not survive a restart.

### Syntax

```nginx
state <file_path>;
```

Example:

```nginx
upstream appservers {
    zone appservers 64k;

    state /var/lib/nginx/state/appservers.conf;

    server appserv1.example.com weight=5;
    server appserv2.example.com:8080;
}
```

In this example:

- `zone appservers 64k;` creates shared memory for upstream state.
- `state /var/lib/nginx/state/appservers.conf;` specifies the file used to persist dynamically managed upstream server
  configuration.

### How `state` Works

At a high level, the process is:

1. NGINX starts with the configured upstream group.
2. The upstream group uses a shared memory zone.
3. An administrator or automation system modifies the upstream server list through the NGINX Plus API.
4. NGINX applies the supported runtime changes.
5. The state file preserves the dynamically managed server configuration for recovery after a restart.

The `state` directive is not a general-purpose file into which NGINX continuously writes every runtime statistic. It is
intended to persist dynamically managed upstream server configuration.

### Important Considerations

- The `state` directive is an NGINX Plus feature.
- The state file's directory must exist and be writable by the NGINX master process as required by the deployment.
- The file should not be edited manually while NGINX is managing the upstream through the API.
- The state file is not a replacement for the main NGINX configuration.
- Runtime upstream management must be configured using the supported NGINX Plus API and upstream configuration.

## 3. Using `zone` and `state` Together

The two directives serve different purposes.

| Directive | Purpose                                                    | Scope         |
|-----------|------------------------------------------------------------|---------------|
| `zone`    | Shares upstream runtime state between worker processes     | Shared memory |
| `state`   | Persists dynamically managed upstream server configuration | File on disk  |

### Example Configuration

```nginx
http {
    upstream appservers {
        zone appservers 64k;

        state /var/lib/nginx/state/appservers.conf;

        server appserv1.example.com weight=5;
        server appserv2.example.com:8080 fail_timeout=5s;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://appservers;
        }
    }
}
```

This configuration defines an upstream group named `appservers`.

The shared zone allows worker processes to share upstream state, while the state file supports persistence of
dynamically managed server configuration.

**Remember:**

- `zone` provides shared runtime state.
- `state` provides persistence of dynamic upstream server configuration.
- Neither directive independently enables the NGINX Plus API; the API must be configured separately.

## 4. Named Locations in NGINX (`@`)

### Overview

In NGINX, the `@` symbol defines a **named location**.

Unlike ordinary locations, named locations are not selected through normal URI matching. They provide internal routing
targets that can be invoked by NGINX directives such as `try_files` and `error_page`.

A named location is useful when NGINX needs to transfer request processing to a specific configuration block without
performing an ordinary URI-based location lookup.

### Syntax

```nginx
location @name {
    # Configuration directives
}
```

Example:

```nginx
location @backend {
    proxy_pass http://appservers;
}
```

Here, `@backend` is the name of the internal routing target.

### Key Characteristics

- **Internal routing only:** A named location cannot be accessed directly by requesting its name in a browser URL.
- **No ordinary URI matching:** NGINX does not compare the request URI against a named location as it does with prefix
  or regular-expression locations.
- **Explicit invocation:** Named locations are reached through supported internal-routing mechanisms.
- **Reusable routing target:** They can centralize fallback, error-handling, or proxying behavior.

Named locations are not functions in the programming-language sense, but they can be understood as reusable internal
routing destinations.

## 5. Use Case 1: Fallback Proxying with `try_files`

A common use case is serving static files when they exist and forwarding requests to an application backend when they do
not.

This is useful for applications that combine static assets with dynamically generated responses.

### Example Configuration

```nginx
upstream my_upstream_pool {
    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
}

server {
    listen 80;

    location / {
        try_files $uri $uri/ @backend;
    }

    location @backend {
        proxy_pass http://my_upstream_pool;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### How It Works

1. A client requests a resource.
2. NGINX checks whether the requested path corresponds to an existing file using `$uri`.
3. NGINX checks whether the path corresponds to an existing directory using `$uri/`.
4. If neither check succeeds, NGINX transfers processing to `@backend`.
5. The named location forwards the request to the upstream application servers.

The `@backend` target provides a fallback without requiring NGINX to perform another ordinary URI-based location match.

**Note:** This pattern can be useful for certain applications, but single-page applications often need an explicit
fallback to `/index.html` instead. The appropriate `try_files` configuration depends on the application's routing
requirements.

## 6. Use Case 2: Custom Error Handling with `error_page`

Named locations can also handle specific HTTP errors.

For example, NGINX can route certain upstream failures to a maintenance page or a dedicated error-handling block.

### Example Configuration

```nginx
server {
    listen 80;

    root /var/www/html;

    error_page 500 502 503 504 @maintenance;

    location / {
        proxy_pass http://appservers;
    }

    location @maintenance {
        rewrite ^ /maintenance.html break;
    }
}
```

### How It Works

1. A request reaches the application through NGINX.
2. NGINX encounters an applicable error, such as `502 Bad Gateway` or `503 Service Unavailable`.
3. The `error_page` directive transfers processing to `@maintenance`.
4. The named location internally rewrites the URI to `/maintenance.html`.
5. NGINX processes the maintenance page using the applicable configuration.

The example assumes that `/var/www/html/maintenance.html` exists and is accessible.

**Important:** Named-location error handling and internal redirects affect how NGINX processes the response. Test the
configuration to ensure the intended status code and error-page behavior are preserved.

## 7. Named Locations vs. Ordinary Locations

| Feature                             | Ordinary Location            | Named Location                              |
|-------------------------------------|------------------------------|---------------------------------------------|
| Example                             | `location /api/`             | `location @backend`                         |
| Matches request URIs                | Yes                          | No                                          |
| Directly accessible by URL matching | Yes                          | No                                          |
| Used for internal routing           | Yes                          | Yes                                         |
| Common use cases                    | Static files, APIs, proxying | Fallbacks, error handling, internal routing |

An ordinary location is selected according to NGINX's URI location-matching rules.

A named location is selected when an internal-routing directive explicitly transfers processing to it.

---

## 8. Practical Notes and Best Practices

- Use `zone` when upstream state needs to be shared between worker processes or when required by a specific upstream
  feature.
- Use `state` when dynamically managed NGINX Plus upstream server configuration must persist across restarts.
- Keep the upstream state file in a directory with appropriate ownership and permissions.
- Use named locations to centralize fallback or error-handling logic.
- Remember that named locations are not directly matched against request URIs.
- Use `try_files` for filesystem-based fallback logic and `error_page` for applicable error-handling flows.
- Test internal redirects carefully, especially when serving custom error pages or proxying requests.
- Verify that directives are supported by your NGINX edition and version.

---

## 9. Summary

### `zone` and `state`

- `zone` allocates shared memory for upstream runtime state.
- `state` persists dynamically managed upstream server configuration in NGINX Plus.
- They complement each other but are not interchangeable.

### Named Locations (`@`)

- The `@` prefix defines an internal named location.
- Named locations are not selected through ordinary URI matching.
- They are commonly used with `try_files` and `error_page`.
- They help implement fallback proxying and custom error-handling behavior.
