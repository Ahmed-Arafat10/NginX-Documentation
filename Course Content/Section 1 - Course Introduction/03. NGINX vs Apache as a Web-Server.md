# Section 1 — Course Introduction

## Lecture 03: NGINX vs. Apache Web Server

## Overview

**Apache HTTP Server (HTTPD)** and **NGINX** are both web servers, but they use different architectural approaches and
therefore have different characteristics.

This lecture compares the two technologies across several areas:

- Architecture
- Simplicity
- Performance
- Static and dynamic content
- Operating-system support
- Configuration model
- Request processing
- Feature modules
- Resource consumption
- Flexibility
- Security
- Appropriate use cases
- Using NGINX and Apache together

The lecture's central architectural distinction is that Apache uses a **process-driven model**, while NGINX uses an
**event-driven architecture** designed to handle many requests efficiently.

---

# 1. NGINX and Apache

Apache is also commonly referred to as **HTTPD**.

Both technologies can be used as web servers, but they have different characteristics and are better suited to different
scenarios.

The choice between them depends on factors such as:

- The amount of traffic.
- The number of concurrent requests.
- Whether static or dynamic content is being served.
- Configuration requirements.
- Module requirements.
- Operating-system requirements.
- Resource availability.

---

# 2. Architectural Difference

The primary difference between Apache and NGINX is their **architecture**.

## Apache: Process-Driven Architecture

Apache uses a **process-driven approach**.

According to the lecture, Apache creates a separate process or thread to handle each request.

Conceptually:

```text
Request 1 ---> Apache Process 1
Request 2 ---> Apache Process 2
Request 3 ---> Apache Process 3
Request 4 ---> Apache Process 4
...
```

When configuring Apache, the number of processes that can handle concurrent requests must be considered.

The lecture explains the model as approximately:

```text
Concurrent requests ≈ Available request-handling processes
```

If the number of incoming requests exceeds what Apache can handle concurrently, additional requests may be dropped or
otherwise unable to be handled immediately.

Each Apache process handles its associated request from beginning to end.

---

## NGINX: Event-Driven Architecture

NGINX uses an **event-driven architecture**.

The lecture describes this as a **one-to-many model**, where a single process can handle a large number of requests.

Conceptually:

```text
                    +--> Request 1
                    |
                    +--> Request 2
                    |
NGINX Process ------+--> Request 3
                    |
                    +--> Request 4
                    |
                    +--> ...
```

The lecture emphasizes that the same NGINX process can handle a very large number of requests rather than creating a
separate process for every request.

> **Important:** The transcript describes NGINX as using a single process with separate threads for requests. More
> precisely, NGINX uses an event-driven worker architecture; the exact process/thread model depends on its configuration
> and operating environment. The key course concept is that NGINX does not use a one-process-per-request model.

This architectural difference is presented as the fundamental reason NGINX can provide strong performance when handling
a large number of concurrent requests.

---

# 3. Simplicity and Module Management

The two web servers differ significantly in how modules and application logic are integrated.

## Apache

Apache is described as simpler when it comes to integrating modules and dynamic content.

Because of its one-connection-per-process approach, modules can be inserted into different points of the web-server
processing logic.

This makes it relatively straightforward to:

- Add modules.
- Customize web-server logic.
- Integrate dynamic-content functionality.

The isolation provided by separate processes also means that a problem affecting one process primarily affects the
request being handled by that process.

---

## NGINX

NGINX has a different model because it uses a shared event-driven process architecture.

Therefore, module development and integration require more care.

The lecture highlights an important consideration:

> An error in a shared NGINX process can potentially affect the entire web server rather than only one request.

This is different from the process isolation model described for Apache.

As a result, the lecture characterizes **Apache as simpler than NGINX for dynamic-content modules**.

---

# 4. Performance

NGINX was designed with high performance and high concurrency in mind.

The lecture differentiates the performance characteristics based on traffic levels.

## Lower Traffic

Apache can perform well when a website experiences relatively low traffic.

For example, if an application receives a relatively small number of requests, Apache's process-driven architecture may
be sufficient.

---

## High Traffic and High Concurrency

NGINX is presented as being more suitable when a website receives a large number of simultaneous requests.

The fundamental reason is its event-driven architecture, which avoids creating a separate process for every incoming
request.

Conceptually:

```text
Low / Moderate Traffic
        |
        +--> Apache can perform well

High Concurrent Traffic
        |
        +--> NGINX is designed for this workload
```

---

# 5. Apache Performance and I/O Operations

The lecture identifies **I/O operations** as one reason for Apache's poorer performance under heavy workloads.

Apache uses a configuration file containing directory-based configuration for websites. this refers to **`.htaccess`**.

The lecture explains that Apache processes repeatedly read this configuration information.

For example, if 1,000 Apache processes are operating:

```text
1,000 Apache processes
        |
        +--> Read configuration
        |
        +--> Read configuration
        |
        +--> Read configuration
        |
       ...
```

With 10,000 processes, the number of simultaneous configuration-file reads can increase significantly.

This increases system I/O activity.

The lecture associates this with:

- Higher CPU utilization.
- Higher memory consumption.
- Reduced performance under high concurrency.

---

# 6. NGINX Caching

The lecture contrasts this with NGINX's use of caching.

When a URL has recently been requested, NGINX can keep the corresponding content in its cache.

If another request arrives for the same URL, NGINX can return the cached response rather than performing the complete
operation again.

Conceptually:

```text
First request
Client ---> NGINX ---> Resource
                    |
                    +--> Cache response

Subsequent request
Client ---> NGINX ---> Cache
                       |
                       v
                    Response
```

This caching behavior is presented as another factor contributing to NGINX's strong performance when handling large
numbers of requests.

---

# 7. Static Content vs. Dynamic Content

An important part of the comparison is the distinction between **static content** and **dynamic content**.

## Static Content

Static content is content that can be returned without dynamically generating the page for each request.

Examples include:

- HTML files
- PNG files
- Text files
- Other static assets

A request can map directly to a file, which the web server returns to the client.

---

## Dynamic Content

Dynamic content is generated when a request is received.

The page is constructed dynamically using a programming language or application process.

The lecture gives examples of websites such as:

- Google
- YouTube
- Facebook

as examples of services serving dynamically generated content.

The distinction can be summarized as:

```text
Static Content:
Request ---> Existing File ---> Response

Dynamic Content:
Request ---> Application Processing ---> Generated Response
```

---

# 8. NGINX Performance for Static Content

The lecture states that NGINX performs approximately **2.5 times faster than Apache for static content**.

The explanation given is based on the architectural difference.

### Apache

Each request creates or uses a separate process, which introduces additional processing overhead.

### NGINX

A static request can be handled directly by the NGINX worker architecture.

For example:

```text
Client
  |
  | GET /index.html
  v
NGINX
  |
  | URI mapping
  v
/index.html
  |
  v
Response
```

The lecture therefore presents NGINX as significantly more efficient for static-content delivery.

---

# 9. Dynamic Content Processing

The comparison changes when dealing with dynamic content.

## Apache Dynamic Content

Apache can process dynamic content **natively within its web-server environment**.

For example, when a PHP request is received, Apache can use a PHP-related process to execute the application logic.

Conceptually:

```text
Client
  |
  v
Apache
  |
  v
PHP Processing
  |
  v
Generated Content
  |
  v
Client
```

The lecture emphasizes that the dynamic request can be processed within the Apache server environment without requiring
the same reverse-proxy architecture used by NGINX.

---

# 10. NGINX Dynamic Content Processing

NGINX does **not natively execute dynamic application code** in the same way described for Apache.

Instead, NGINX can forward dynamic requests to an external application processor.

For example:

```text
Client
  |
  v
NGINX
  |
  | Dynamic request
  v
PHP-FPM
  |
  | Process PHP
  v
Response
  |
  v
NGINX
  |
  v
Client
```

The lecture uses **PHP-FPM** as an example of an external process that can handle dynamic PHP requests.

NGINX receives the request, forwards it to PHP-FPM, receives the generated response, and then returns that response to
the client.

This is described in the lecture as the **reverse proxy model**.

---

# 11. Example: Static and Dynamic Requests

The lecture provides an example involving three requests:

1. A PNG file — static content.
2. A PHP file — dynamic content.
3. A text file — static content.

The processing model is:

```text
                         NGINX
                           |
             +-------------+-------------+
             |             |             |
             v             v             v
          PNG file      PHP request    Text file
          (static)      (dynamic)      (static)
             |             |             |
             v             v             v
          NGINX        PHP-FPM         NGINX
             |             |             |
             |<------------+             |
             |                           |
             +-------------+-------------+
                           |
                           v
                         Client
```

### Static Requests

The PNG and text requests can be handled directly by NGINX based on the URI and its configuration.

### Dynamic Request

The PHP request is forwarded to a PHP-FPM process.

PHP-FPM processes the dynamic content and returns the result to NGINX.

NGINX then sends the result back to the client.

---

# 12. Static vs. Dynamic Performance

According to the lecture:

### Static Content

NGINX has a significant performance advantage for static content, with the lecture stating approximately **2.5× better
performance than Apache**.

### Dynamic Content

The lecture states that Apache and NGINX can provide approximately similar performance for dynamic content because NGINX
relies on external processors or libraries to provide the dynamic-content functionality.

The important architectural difference is:

```text
Apache:
Client -> Apache -> Dynamic Processing -> Client

NGINX:
Client -> NGINX -> External Processor -> NGINX -> Client
```

---

# 13. Operating-System Support

Another comparison criterion is operating-system support.

## Apache

According to the lecture, Apache supports:

- Unix
- Linux
- BSD
- Microsoft Windows

Apache is therefore described as having broad operating-system support, including full Windows support.

## NGINX

NGINX also runs on several modern Unix-like operating systems and has Windows support.

However, the lecture states that:

> NGINX performance on Windows is not as stable as its performance on Unix-based systems.

Therefore, for operating-system support, the lecture considers **Apache more favorable than NGINX**, particularly
because of its Windows support and behavior.

---

# 14. Configuration Model

Web servers need configuration that determines:

- Which requests should be processed.
- Which requests should be blocked.
- Which resources should be served.
- How requests should be handled.

Apache and NGINX approach this differently.

---

## Apache: Per-Directory Configuration

Apache supports additional configuration on a **per-directory basis** through `.htaccess`.

The lecture refers to `.htaccess`.

This allows configuration to be placed close to the directory or resource being controlled.

For example, directory-specific rules can define which requests are allowed or blocked.

---

## NGINX: Centralized Configuration

NGINX does not use Apache's `.htaccess` mechanism.

Instead, NGINX uses its own configuration files, commonly centered around:

```text
nginx.conf
```

The lecture describes this as a more centralized configuration model.

Therefore:

```text
Apache
   |
   +--> Main configuration
   |
   +--> Per-directory .htaccess configuration

NGINX
   |
   +--> Central NGINX configuration
```

---

# 15. Request Interpretation

The lecture also compares how each server interprets incoming requests.

## Apache

Apache processes the filesystem location associated with the request.

Its directory-based configuration determines how the requested URI and corresponding document should be handled.

---

## NGINX

NGINX uses the **URI** as an important part of request processing.

The URI can be mapped to an upstream server according to the NGINX configuration.

For example:

```text
Request URI
    |
    v
NGINX Configuration
    |
    +---- /static/  ------> Static content
    |
    +---- /api/     ------> Application upstream
    |
    +---- /php/     ------> PHP processing
```

The lecture considers NGINX's URI-based request handling faster and more efficient.

---

# 16. Feature Modules

Another major difference is module management.

## Apache Modules

The lecture states that Apache has approximately **60 official dynamically loadable modules**.

These modules can be enabled or disabled as required.

The instructor notes that although many modules are available, production environments may only commonly use around
**12–13** of them depending on requirements.

The dynamic module system makes Apache highly customizable.

---

## NGINX Modules

The lecture explains that the open-source version of NGINX does not provide the same type of dynamically loadable
core-module system.

Instead, NGINX has a large ecosystem of **third-party modules**.

According to the lecture, there are thousands of third-party modules.

However, these modules cannot simply be dynamically loaded in the same way as Apache modules.

If a third-party module needs to be included in NGINX, the module generally needs to be included when building the NGINX
binary.

Conceptually:

```text
NGINX Source
     +
Third-Party Module
     |
     v
Build NGINX
     |
     v
NGINX Binary
```

This is one reason the lecture describes Apache as more flexible for dynamic module loading.

---

# 17. Resource Consumption

One of NGINX's major characteristics is its lightweight architecture.

The lecture attributes this to the fact that NGINX does not create a separate process for every request.

As a result, its resource consumption can be significantly lower under high concurrency.

The lecture gives a hypothetical comparison:

```text
Machine
  |
  +-- Apache: 5,000 concurrent requests
  |
  +-- NGINX:  5,000 concurrent requests
```

Under the same machine configuration, the instructor states that NGINX could use approximately **15% of the resources
used by Apache** in this scenario.

This is presented as an illustrative comparison of resource consumption rather than a universal benchmark.

---

# 18. Flexibility

## Apache

Apache supports extensive customization through dynamic modules.

The lecture states that Apache's dynamic module system allows administrators to:

- Enable modules.
- Disable modules.
- Customize web-server functionality.
- Extend server behavior.

---

## NGINX

NGINX is less flexible regarding **dynamic module loading**, according to the lecture.

When additional functionality requires a module, the module generally needs to be incorporated into the NGINX build.

This provides a trade-off:

```text
Apache
More dynamic module flexibility
        |
        v
More customization options

NGINX
More static/lightweight architecture
        |
        v
High performance and low resource usage
```

---

# 19. Security

Both Apache and NGINX are presented as capable of providing strong security.

## Apache Security

The lecture states that Apache provides security mechanisms and configuration guidance for handling various attacks,
including:

- DoS attacks
- DDoS attacks
- Brute-force attacks

Apache also supports security-related modules and configuration mechanisms.

---

## NGINX Security

NGINX is also described as providing a strong security model.

The lecture highlights its **smaller code base** as an advantage.

The underlying argument is that a smaller and simpler code base can reduce the amount of software that needs to be
exposed and maintained.

The lecture therefore presents NGINX as having strong security characteristics while maintaining a lightweight
architecture.

---

# 20. When to Choose Apache

According to the lecture, Apache may be appropriate when the application requires:

### `.htaccess`

If per-directory configuration through `.htaccess` is important, Apache is the appropriate choice according to the
course.

### Per-Directory Overrides

Apache allows system-wide settings to be overridden on a per-directory basis.

### Standard Hosting Environments

The lecture states that Apache works well in standard hosting environments, particularly because of its `.htaccess`
support.

### Dynamic Module Configuration

If the application requires dynamically enabling or disabling modules, Apache provides this capability.

---

# 21. When to Choose NGINX

According to the lecture, NGINX is appropriate when the primary requirements include:

### High Concurrent Traffic

If the application needs to handle a large number of concurrent requests, NGINX's event-driven architecture is
advantageous.

### Static Content

If static-content processing is a major requirement, NGINX is presented as the preferred option because of its strong
static-content performance.

### High-Traffic Websites

NGINX is particularly suited to websites experiencing high traffic and many simultaneous connections.

---

# 22. Can NGINX and Apache Be Used Together?

Yes.

The lecture explicitly explains that **NGINX and Apache can be deployed together**.

A common architecture is to put NGINX in front of Apache.

NGINX can act as the:

- Front-end server
- Reverse proxy
- Load balancer

Apache can then handle dynamic content behind NGINX.

---

# 23. NGINX + Apache Architecture

The lecture provides an architecture in which NGINX is positioned in front of multiple backend services.

A simplified representation is:

```text
                    Client
                       |
                       v
               +---------------+
               |     NGINX     |
               | Front End /   |
               | Load Balancer |
               +---------------+
                    /       \
                   /         \
                  v           v
        +---------------+   +---------------+
        | Static Server |   |    Apache     |
        |               |   | Dynamic/PHP   |
        +---------------+   +---------------+
              |                    |
              v                    v
        Static Content        Dynamic Content
```

The roles are divided according to the type of request.

---

## Static Requests

NGINX can directly serve static content.

```text
Client
  |
  v
NGINX
  |
  v
Static Content
  |
  v
Client
```

This takes advantage of NGINX's strong static-content performance.

---

## Dynamic Requests

For dynamic requests, NGINX acts as a reverse proxy and forwards the request to Apache.

```text
Client
  |
  v
NGINX
  |
  | Reverse Proxy
  v
Apache
  |
  v
PHP / Dynamic Application
  |
  v
Apache
  |
  v
NGINX
  |
  v
Client
```

This allows Apache to perform dynamic-content processing while NGINX handles the front-end traffic.

---

# 24. Benefits of Using Both Servers

The combined architecture attempts to take advantage of the strengths of both technologies.

### NGINX Handles

- High concurrent connections.
- Static content.
- Front-end traffic.
- Reverse proxying.
- Load balancing.

### Apache Handles

- Dynamic content.
- PHP-related processing.
- Functionality that benefits from Apache's module architecture.
- `.htaccess`-based configuration where required.

The resulting architecture addresses multiple requirements simultaneously:

```text
                    NGINX
                      |
          +-----------+-----------+
          |                       |
          v                       v
    Static Content             Apache
                                  |
                                  v
                          Dynamic Content
```

The lecture describes this model as solving the problems associated with:

- Static-content performance.
- Dynamic-content processing.
- Large numbers of concurrent requests.
