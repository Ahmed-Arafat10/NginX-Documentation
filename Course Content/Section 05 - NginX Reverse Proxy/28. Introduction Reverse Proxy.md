# 28. Introduction to Reverse Proxy

## Overview

A **reverse proxy** is a server that sits between clients and application/web servers. It receives requests from clients, processes them according to its configuration, and forwards valid requests to the appropriate application server.

When the application server produces a response, the reverse proxy receives that response and forwards it back to the client.

In this section, **NGINX** is used as the reverse proxy.

A reverse proxy is typically implemented to improve:

- **Security**
- **Performance**
- **Reliability**
- **Load balancing**
- **Protection against attacks**
- **Caching**
- **SSL/TLS encryption handling**

---

## Key Concepts

The reverse proxy architecture contains three main entities:

1. **Web Client**
    - A web browser or another client/tool that sends requests.
2. **NGINX**
    - Acts as the reverse proxy between the client and the application server.
3. **Application Server**
    - Processes the client's request and generates the response.

The communication flow is:

```text
Web Client
    |
    | Request
    v
  NGINX
(Reverse Proxy)
    |
    | Forwarded Request
    v
Application Server
    |
    | Response
    v
  NGINX
    |
    | Forwarded Response
    v
Web Client
```

The client does **not** communicate directly with the application server. Instead, NGINX handles the communication on behalf of the application server.

---

# What Is a Reverse Proxy?

A **reverse proxy** is a server that sits in front of web/application servers and forwards client requests to those servers.

In a traditional setup:

```text
Client ---> Application Server
```

With a reverse proxy:

```text
Client ---> NGINX ---> Application Server
```

The reverse proxy therefore becomes an intermediary between the client and the application server.

### Request Flow

When a client accesses an application:

1. The client sends a request.
2. The request reaches NGINX.
3. NGINX accepts the request.
4. NGINX determines whether the request is valid according to its configuration.
5. If the request is valid, NGINX forwards it to the appropriate application server.
6. The application server processes the request.
7. The application server sends the response back to NGINX.
8. NGINX forwards the response to the web client.

Therefore, although the client ultimately needs information from the application server, the communication takes place through NGINX.

```text
Client
  |
  | Request
  v
NGINX
  |
  | Request
  v
Application Server
  |
  | Response
  v
NGINX
  |
  | Response
  v
Client
```

This complete communication and data-flow model is referred to as **reverse proxying**.

# Why Use a Reverse Proxy?

The lecture identifies several important benefits of using a reverse proxy.

## 1. Load Balancing

NGINX can also work as a **load balancer**.

Instead of having a single application server handle every incoming request, multiple servers can be configured to handle requests.

For example:

```text
                 +--> Application Server 1
                 |
Client ---> NGINX+--> Application Server 2
                 |
                 +--> Application Server 3
```

NGINX can define multiple upstream/backend application servers and distribute incoming requests among them.

The lecture also relates this concept to NGINX `location` configuration, where different locations can forward requests to specific servers.

### Why Is Load Balancing Needed?

Consider a popular website that receives millions of users every day.

A single origin server may not have enough capacity to handle all incoming traffic.

Instead, multiple frontend/application servers can be created with the same configuration:

```text
                    +--> Server 1
                    |
                    +--> Server 2
Client ---> NGINX --+
                    +--> Server 3
                    |
                    +--> Server 4
```

Incoming requests are distributed across these servers.

This is **load balancing**.

### Benefits of Load Balancing

Load balancing helps:

- Distribute incoming traffic across multiple servers.
- Prevent a single server from becoming overloaded.
- Improve application performance.
- Increase application availability.
- Provide failover when one server becomes unavailable.

For example, if one server goes down:

```text
                 +--> Server 1  (DOWN)
                 |
Client ---> NGINX+--> Server 2  (AVAILABLE)
                 |
                 +--> Server 3  (AVAILABLE)
```

NGINX can stop sending requests to the unavailable server and continue sending requests to the other servers.

Without load balancing, if the only production server goes down, the entire production site may become unavailable.

---

# 2. Protection Against Attacks

Another benefit of using a reverse proxy is protecting the application servers from attacks.

With a reverse proxy architecture, the application server's IP address does not need to be exposed directly to clients.

Instead:

```text
Client ---> NGINX ---> Application Server
```

The clients communicate with NGINX rather than directly with the application server.

Therefore, the IP address of the original/application server is hidden from the outside world.

This makes it more difficult for attackers to directly target the origin server with attacks such as:

- Denial-of-Service (DoS) attacks
- Other network-level attacks mentioned in the lecture

The reverse proxy acts as an additional entity between users and the application servers.

---

# 3. Caching

NGINX can also work as a **caching system**.

A reverse proxy can cache application content and serve subsequent requests directly from the cache instead of repeatedly requesting the same resource from the origin/application server.

This can significantly improve response time and overall performance.

## Example: Tokyo Application Server and London Users

Suppose:

- The application server is located in **Tokyo**.
- Users are located in **London**.

Without a nearby reverse proxy cache:

```text
London User
     |
     | Request
     v
   Tokyo
Application Server
     |
     | Response
     v
London User
```

The request must travel from London to Tokyo, and the response must travel from Tokyo back to London.

This introduces **network latency**.

### Adding an NGINX Reverse Proxy in London

Now suppose an NGINX reverse proxy server is also located in London:

```text
London User
     |
     v
 London NGINX
     |
     v
Tokyo Application Server
```

Assume the user requests:

```text
/index.html
```

The first user requests `/index.html`.

1. The request reaches the London NGINX server.
2. NGINX forwards the request to the application server in Tokyo.
3. The Tokyo application server returns `/index.html`.
4. NGINX receives the response.
5. NGINX caches the resource.

Now, when another user in the same location requests the same resource:

```text
London User 1 ----\
London User 2 -----+--> London NGINX Cache
London User 3 ----/
```

NGINX can serve the cached resource directly instead of contacting the Tokyo application server again.

Therefore:

```text
First request:

London ---> NGINX ---> Tokyo
                         |
                         v
                       Response
                         |
                         v
                      NGINX Cache


Subsequent requests:

London ---> NGINX Cache ---> London User
```

### Benefits of Caching

Caching can:

- Reduce requests sent to the origin/application server.
- Reduce network latency.
- Improve website performance.
- Improve the user experience.
- Allow users to receive frequently requested resources from a nearby reverse proxy.

# 4. SSL/TLS Encryption

Another important use of a reverse proxy is handling **SSL/TLS encryption and decryption** for HTTPS traffic.

When a client accesses an application over HTTPS, traffic is encrypted while traveling across the network.

The general flow is:

```text
Client
  |
  | Encrypted Request
  v
Server
  |
  | Decrypted Request
  v
Application
```

The response is then encrypted again before being sent back to the client.

If the application server performs all encryption and decryption itself, it has to spend computational resources processing SSL/TLS traffic.

For a very large number of requests, this can become computationally expensive.

---

## SSL/TLS Termination at the Reverse Proxy

A reverse proxy can be configured to handle the encryption and decryption instead of the application server.

For example:

```text
Client
  |
  | HTTPS / Encrypted
  v
NGINX
  |
  | Decrypts request
  |
  | HTTP/internal request
  v
Application Server
```

For the response:

```text
Application Server
  |
  | Response
  v
NGINX
  |
  | Encrypts response
  v
Client
```

In this architecture:

- NGINX decrypts incoming requests.
- NGINX forwards the request to the application server.
- The application server processes the request without having to perform the external SSL/TLS encryption/decryption work.
- NGINX encrypts the outgoing response.
- The encrypted response is sent back to the client.

### Why Is This Useful?

Consider an application receiving **one million requests**.

Without a reverse proxy handling SSL/TLS:

```text
Application Server
    |
    +--> Encrypt/decrypt request 1
    +--> Encrypt/decrypt request 2
    +--> Encrypt/decrypt request 3
    +--> ...
    +--> Encrypt/decrypt request 1,000,000
```

The application server must spend resources on both application processing and encryption/decryption.

With NGINX handling the encryption/decryption:

```text
                    +--> SSL/TLS processing
Client ---> NGINX --+
                    |
                    v
             Application Server
             (request processing)
```

NGINX handles the encryption/decryption on behalf of the application server.

This frees application-server resources so the application server can focus more effectively on processing application requests.

# Summary of Reverse Proxy Benefits

The lecture identifies the following major benefits of using NGINX as a reverse proxy:

| Benefit | Purpose |
|---|---|
| **Load Balancing** | Distributes traffic across multiple application servers |
| **Failover / Reliability** | Allows other servers to continue serving traffic when one server goes down |
| **Protection Against Attacks** | Hides the origin/application server from direct client access |
| **Caching** | Serves cached resources without repeatedly contacting the origin server |
| **Performance** | Reduces unnecessary processing and network latency |
| **SSL/TLS Handling** | Allows NGINX to perform encryption/decryption on behalf of the application server |

# Overall Reverse Proxy Architecture

The concepts discussed in this lecture can be combined into a single architecture:

```text
                         +--> Application Server 1
                         |
                         +--> Application Server 2
                         |
Client ---> NGINX -------+--> Application Server 3
           Reverse       |
           Proxy         +--> Application Server 4
              |
              +--> Cache
              |
              +--> SSL/TLS Handling
```

NGINX becomes the central entry point for client traffic and can provide multiple capabilities before requests reach the application servers.

The client communicates with NGINX, while NGINX communicates with the backend/application servers.

---

## Practical Notes / Best Practices

- A reverse proxy should be understood as an **intermediary layer** between clients and application servers.
- The application server does not need to be directly exposed to clients.
- Multiple backend servers can be placed behind NGINX to support load balancing.
- Caching is particularly useful for frequently requested resources.
- Placing a reverse proxy closer to users can reduce the effects of network latency.
- SSL/TLS processing can be moved to the reverse proxy to reduce the workload on application servers.
- If a backend server becomes unavailable in a load-balanced architecture, traffic can be handled by other available servers.

## Key Takeaway

The central idea of this lecture is:
