# 31. Lab — Use of X-Real-IP Directive

## Overview

When NGINX is configured as a **reverse proxy**, the backend/application server receives requests from the reverse proxy rather than directly from the original client.

This creates an important problem when the application needs to know the client's real IP address.

The request flow looks like this:

```text
Web Client
    |
    | Request
    v
NGINX Reverse Proxy
    |
    | Forwarded Request
    v
Application / Web Server
```

Suppose the machines have the following IP addresses:

```text
Web Client       → 192.0.0.1
NGINX Proxy      → 192.0.0.2
Web Server       → 192.0.0.3
```

The client sends a request from `192.0.0.1` to the reverse proxy.

The reverse proxy then sends the request to the application server.

From the application's perspective, the request appears to come from:

```text
192.0.0.2
```

rather than:

```text
192.0.0.1
```

This is because the application server is communicating directly with the reverse proxy.

---

# The Problem With Reverse Proxying

Consider 1,000 different clients sending requests:

```text
Client 1 ──┐
Client 2 ──┤
Client 3 ──┤
   ...     ├──> NGINX Reverse Proxy ──> Application Server
Client 1000┘
```

The reverse proxy forwards all of these requests to the application server.

Without forwarding the original client IP, the application server may see all requests as coming from the same IP:

```text
NGINX Reverse Proxy IP
```

The application therefore cannot distinguish the original clients based on their IP addresses.

This can cause problems for applications that use IP addresses for:

- IP-based binding
- IP-based application logic
- IP-based throttling
- Request limiting
- Other IP-related application behavior

For example, if an application needs to limit requests per client IP, it cannot correctly perform that operation if every request appears to originate from the reverse proxy.


This is the problem that the `X-Real-IP` mechanism is intended to address.

# 9. Add Client IP Headers to the Reverse Proxy

The next step is to modify the NGINX configuration on the **reverse proxy server**.

Go to the `location` block that forwards requests to the backend application.

Add the following directives:

```nginx
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

The configuration conceptually becomes:

```nginx
location / {
    proxy_pass http://<APPLICATION_SERVER_IP>;

    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

---

# Understanding the Directives

## `proxy_set_header`

The `proxy_set_header` directive allows NGINX to modify or add HTTP headers when forwarding a request to the backend server.

---

## `X-Real-IP`

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

This tells NGINX to send the original remote address to the backend in the:

```text
X-Real-IP
```

HTTP header.

The lecture identifies `$remote_addr` as the NGINX variable containing the remote/client IP address.

Therefore:

```text
Client IP
    |
    v
$remote_addr
    |
    v
X-Real-IP
```

---

## `X-Forwarded-For`

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

This forwards the client IP information using the:

```text
X-Forwarded-For
```

HTTP header.

The lecture explains that `$proxy_add_x_forwarded_for` is an NGINX variable used to add the forwarding information to the `X-Forwarded-For` header.

These two headers allow client IP information to be carried through the reverse proxy.

# 12. Configure a Custom Log Format on the Application Server

The NGINX configuration on the **application server** is edited:

```bash
vi /etc/nginx/nginx.conf
```

A custom log format is added.

The lecture calls the format:

```text
specialLog
```

The format is:

```nginx
log_format specialLog '$http_x_real_ip - $remote_user [$time_local] '
                      '"$request" $status $body_bytes_sent '
                      '"$http_referer" "$http_user_agent" $remote_addr';
```

This format contains both the forwarded client IP and the connection's remote address.

---

# 13. Understanding the Custom Log Format

The custom format contains several NGINX variables.

### `$http_x_real_ip`

```nginx
$http_x_real_ip
```

Reads the value of the:

```text
X-Real-IP
```

HTTP header.

This is the important value for obtaining the original client IP forwarded by the reverse proxy.

### `$remote_user`

```nginx
$remote_user
```

Records the authenticated remote user, if applicable.

### `$time_local`

```nginx
$time_local
```

Records the local timestamp.

### `$request`

```nginx
$request
```

Records the HTTP request.

### `$status`

```nginx
$status
```

Records the HTTP response status.

### `$body_bytes_sent`

```nginx
$body_bytes_sent
```

Records the number of response-body bytes sent.

### `$http_referer`

```nginx
$http_referer
```

Records the HTTP referrer.

### `$http_user_agent`

```nginx
$http_user_agent
```

Records the client's user-agent information.

### `$remote_addr`

```nginx
$remote_addr
```

Records the address of the machine directly connected to the application server.

In this reverse proxy architecture, this is still the **reverse proxy's IP**.

Therefore, the custom log deliberately includes both:

```text
$http_x_real_ip
```

and:

```text
$remote_addr
```

This allows the difference between the original client and the reverse proxy to be observed.

# 14. Configure the Custom Access Log

The instructor then creates a separate access log using the custom format:

```nginx
access_log /var/log/nginx/access-special.log specialLog;
```

The standard access log is also retained:

```nginx
access_log /var/log/nginx/access.log;
```

The error log remains configured:

```nginx
error_log /var/log/nginx/error.log;
```

The relevant configuration therefore looks like:

```nginx
log_format specialLog '$http_x_real_ip - $remote_user [$time_local] '
                      '"$request" $status $body_bytes_sent '
                      '"$http_referer" "$http_user_agent" $remote_addr';

access_log /var/log/nginx/access-special.log specialLog;
access_log /var/log/nginx/access.log;
error_log /var/log/nginx/error.log;
```

This gives the application server two access logs:

```text
/var/log/nginx/access.log
/var/log/nginx/access-special.log
```

The first uses the existing/default access-log format.

The second uses the new `specialLog` format.

# 20. Why Does `access.log` Still Show the Proxy IP?

The instructor explains an important detail.

The normal `access.log` continues to show the reverse proxy IP because the existing **log rotation policy/configuration** is already defined.

Therefore, seeing the reverse proxy IP in the standard log does not mean that the application is failing to receive the client's IP.

The custom log demonstrates that the application server is receiving the forwarded client IP.

The lecture's key conclusion is:

> If the application server is receiving the actual client IP through the forwarded header, it can process requests using that client IP even if the existing standard access-log format continues to display the reverse proxy IP.

# Complete Request Flow

After the configuration is implemented, the request flow becomes:

```text
                         X-Real-IP:
                         Client IP
                             |
                             v
Client ---> NGINX Reverse Proxy ---> Application Server
               |
               |
               +---- X-Forwarded-For
```

The reverse proxy receives:

```text
Client IP = $remote_addr
```

It then adds:

```http
X-Real-IP: <Client-IP>
```

and:

```http
X-Forwarded-For: <Client-IP>
```

The application server can read these headers.

The custom access log reads:

```nginx
$http_x_real_ip
```

and records the original client IP.

# Key Concepts

### `X-Real-IP`

Carries the original client IP from the reverse proxy to the backend application.

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

### `X-Forwarded-For`

Carries the forwarding chain/client IP information:

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

### `$remote_addr`

Represents the address of the remote peer directly connected to NGINX.

For the backend server behind a reverse proxy, this can be the reverse proxy's IP.

### `$http_x_real_ip`

Reads the `X-Real-IP` request header:

```nginx
$http_x_real_ip
```

This can be used in a custom access-log format to record the original client IP.

---

# Practical Notes / Best Practices

- A reverse proxy changes what the backend server sees as the source IP.
- Applications that depend on client IP information can therefore encounter problems after introducing a reverse proxy.
- IP-based throttling is one example of functionality that can be affected.
- The reverse proxy should explicitly forward the client IP using appropriate headers.
- The backend can use a custom log format to verify that the original IP is being forwarded.
- Always run `nginx -t` before reloading a modified configuration.
- Keep the standard access log while testing so that the difference between `$remote_addr` and `$http_x_real_ip` can be clearly observed.
- When rebuilding NGINX, preserve the configuration options from the existing `nginx -V` output and add the required module rather than arbitrarily replacing the original build configuration.
- The lecture specifically enables the **HTTP Real IP module** using `--with-http_realip_module`.

# Final Takeaway

When NGINX is used as a reverse proxy, the backend server normally sees the **reverse proxy's IP address**, not the original client's IP.

The solution demonstrated in this lab is to forward the original IP using:

```nginx
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

and then use the forwarded value in the application server's logging:

```nginx
$http_x_real_ip
```

The resulting architecture preserves the original client IP information across the reverse proxy:

```text
Client
  |
  | Real IP
  v
NGINX Reverse Proxy
  |
  | X-Real-IP: Real Client IP
  | X-Forwarded-For: Client IP
  v
Application Server
  |
  +--> Custom log records original client IP
```

This allows applications and logging systems to distinguish individual clients even when all traffic reaches the backend through a single NGINX reverse proxy.
