
# 29. Lab — Configure NGINX as Reverse Proxy

## Overview

In this lab, NGINX is configured as a **reverse proxy** in front of multiple application servers.

Three machines are used:

1. **Custom NGINX / Brownie machine**
    - Existing machine.
    - Runs the Brownie website.
    - Acts as one application server.

2. **NGINX Reverse Proxy machine**
    - Newly created machine.
    - Runs NGINX.
    - Acts as the reverse proxy.
    - Receives client requests and forwards them to the appropriate backend server.

3. **PHP Application machine**
    - Newly created machine.
    - Runs NGINX with PHP-FPM.
    - Acts as another application server.

The resulting architecture is:

```text
                    +----------------------+
                    |  Brownie Application |
                    |   NGINX Server       |
                    +----------^-----------+
                               |
                               |
Client ---> NGINX Reverse Proxy+
                               |
                               |
                    +----------v-----------+
                    | PHP Application     |
                    | NGINX + PHP-FPM     |
                    +----------------------+
```

The lab eventually configures the reverse proxy so that:

- Requests to **port 80** are forwarded to the Brownie application.
- Requests to **port 8080** are forwarded to the PHP application.
- Both applications are accessed through the same reverse proxy server.

# 10. Create the Reverse Proxy Server Block

Inside the `http` context, create a `server` block:

```nginx
http {
    server {
        listen 80;
        server_name <PROXY_SERVER_IP>;

        location / {
            proxy_pass http://<BROWNIE_SERVER_IP>;
        }
    }
}
```

Replace the placeholders with the actual IP addresses.

For example, conceptually:

```nginx
server {
    listen 80;
    server_name 206.189.132.205;

    location / {
        proxy_pass http://206.189.132.130;
    }
}
```

### What This Configuration Does

The configuration contains three important parts.

### `listen`

```nginx
listen 80;
```

NGINX listens for HTTP requests on port `80`.

### `server_name`

```nginx
server_name <PROXY_SERVER_IP>;
```

The server name identifies the server receiving the request.

### `location /`

```nginx
location / {
    proxy_pass http://<BROWNIE_SERVER_IP>;
}
```

The `/` location matches requests to the root of the server.

The `proxy_pass` directive tells NGINX where to forward those requests.

Therefore:

```text
Client
  |
  | HTTP request
  v
Proxy Server :80
  |
  | proxy_pass
  v
Brownie Server
```

# 14. Configure NGINX for PHP

The NGINX configuration is edited:

```bash
vi /etc/nginx/nginx.conf
```

The `http` block is simplified while retaining the error and access log definitions.

A server block is then created.

The configuration conceptually contains:

```nginx
http {
    server {
        listen 80;
        server_name <PHP_SERVER_IP>;

        index index.php index.html;

        location ~ \.php$ {
            include fastcgi.conf;
            fastcgi_pass <PHP-FPM_SOCKET>;
        }
    }
}
```

The instructor uses the PHP-FPM socket path required by the installed PHP version.

---

# 15. Find the PHP-FPM Socket

The PHP-FPM socket path must be identified before it can be used in `fastcgi_pass`.

The instructor searches for the socket using a `find` command.

The resulting socket is shown as being similar to:

```text

```

The exact path depends on the PHP version installed on the machine.

The socket path is then added to the NGINX configuration.

For example:

```nginx
location ~ \.php$ {
    include fastcgi.conf;
    fastcgi_pass unix:/run/php/php7.4-fpm.sock;
}
```

The configuration is tested:

```bash

```

```bash

```

# 17. Configure the Reverse Proxy for the PHP Application

The reverse proxy currently forwards root requests to the Brownie server.

The instructor now adds another `server` block to the reverse proxy configuration.

The purpose is to make a different URL path forward to the PHP server.

The configuration conceptually becomes:

```nginx
http {
    server {
        listen 80;
        server_name <PROXY_SERVER_IP>;

        location / {
            proxy_pass http://<BROWNIE_SERVER_IP>;
        }
    }

    server {
        listen 80;
        server_name <PROXY_SERVER_IP>;

        location /php {
            proxy_pass http://<PHP_SERVER_IP>;
        }
    }
}
```

The important point is that the reverse proxy can contain **multiple server blocks and routing rules**.

The `/php` location is configured to forward requests to the PHP application server.

# 23. Final Architecture

At the end of the lab, one NGINX reverse proxy is controlling access to multiple backend applications.

```text
                           +----------------------+
                           | Brownie Application  |
                           | NGINX                |
                           | Backend .130         |
                           +----------^-----------+
                                      |
                                      | Port 80
                                      |
Client ---> Reverse Proxy NGINX -------+
             Backend .205              |
                                      | Port 8080
                                      |
                           +----------v-----------+
                           | PHP Application      |
                           | NGINX + PHP-FPM      |
                           | Backend .80          |
                           +----------------------+
```

The same reverse proxy server can therefore provide access to multiple web servers.

### Request Routing

```text
Proxy :80
   |
   +----> Brownie application


Proxy :8080
   |
   +----> PHP application
```

This demonstrates an important capability of NGINX reverse proxying: **a single NGINX proxy can route requests to multiple backend servers according to the configured server blocks, ports, and locations.**

# Practical Notes / Best Practices

### Always Test the Configuration

Before reloading NGINX, use:

```bash
nginx -t
```

This verifies the configuration syntax.

### Reload Rather Than Reinstall

After changing the configuration, reload NGINX:

```bash
nginx -s reload
```

### Use Logs to Verify Traffic Flow

The access log is particularly useful when learning or troubleshooting reverse proxy configurations:

```bash
tail -f /var/log/nginx/access.log
```

The lab uses the logs to confirm which backend server actually received each request.

### Verify the Backend Independently

Before configuring the reverse proxy, verify that each application server works directly.

In this lab:

- The Brownie server is tested directly.
- The PHP server is tested directly.
- Only after the backends work independently are they placed behind the reverse proxy.

### Multiple Backends Can Be Behind One Proxy

A single NGINX reverse proxy does not have to forward every request to one backend.

Different server blocks or locations can route traffic to different application servers.

# Common Mistakes / Warnings

- Make sure the reverse proxy's `proxy_pass` points to the correct backend IP.
- Do not include unnecessary trailing configuration when constructing the simplified lab configuration.
- Always run `nginx -t` before reloading after configuration changes.
- Make sure the backend NGINX server is actually running before testing the proxy.
- When configuring PHP, use the correct PHP-FPM socket path for the installed PHP version.
- Remember that the backend server's logs can show the **reverse proxy's IP** as the source of the forwarded request.
- When using different ports, make sure NGINX is configured to listen on those ports.
- The instructor explicitly keeps the reverse proxy and the original custom NGINX machine running because the following lectures continue to use the proxy server.

# Lab Conclusion

This lab demonstrates the complete process of configuring NGINX as a reverse proxy.

The progression is:

```text
1. Create backend/proxy machines
          ↓
2. Install NGINX
          ↓
3. Verify backend applications
          ↓
4. Configure proxy_pass
          ↓
5. Test nginx -t
          ↓

          ↓

          ↓

          ↓
```

The key result is that clients communicate with the **reverse proxy**, while the reverse proxy communicates with the actual application servers.

A single NGINX reverse proxy can therefore act as the central entry point for multiple web applications and backend servers.
