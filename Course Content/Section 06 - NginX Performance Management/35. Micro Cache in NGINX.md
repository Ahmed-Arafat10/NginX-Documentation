# Lecture 35 — Micro Caching in NGINX

## Overview

The previous lecture covered **static client-side caching**. This lecture introduces **micro caching**, which allows NGINX to cache certain types of **dynamic content** for a very short period.

The key idea is:

> Dynamic content does not always have to be generated for every request.

If the same dynamic response can be safely shared by many users for a short period, NGINX can temporarily cache that response and serve subsequent requests directly from its cache instead of repeatedly invoking the backend application.

This can improve website performance and reduce load on the origin/application server. Pasted text

---

# 1. Types of Content

The lecture divides web content into three broad categories:

1. **Static content**
2. **Dynamic but non-personalized content**
3. **Personalized content**

Understanding the difference is important because each category has different caching characteristics.

---

# 2. Static Content

Static content is relatively straightforward to cache.

Examples include:

- Images
- JavaScript
- CSS
- Simple web pages

These resources generally do not change frequently and can often be cached for relatively long periods.

The previous lecture demonstrated how static resources can be cached on the client side.

For example:

```text
Browser
   |
   | Request CSS
   v
NGINX
   |
   v
CSS Resource
   |
   v
Browser Cache
```

Once cached, the browser can reuse the resource without repeatedly requesting it from NGINX.

---

# 3. Personalized Content

At the opposite end is **personalized content**.

Personalized content is specific to a particular user.

Examples include:

- Shopping cart information
- Account information
- User-specific data

This type of content generally cannot be shared between users because the response can be different for every user.

For example:

```text
User A → /account → Account A
User B → /account → Account B
User C → /account → Account C
```

Caching User A's response and returning it to User B would be incorrect.

Therefore, personalized content generally cannot be safely cached as a shared response.

---

# 4. Dynamic, Non-Personalized Content

Between static and personalized content is an important category:

> **Dynamic content that is not personalized.**

This content can change over time, but the same current response may be useful to many users.

For example:

```text
User A ─┐
User B ─┤
User C ─┼──> Same dynamic response
User D ─┤
User E ─┘
```

Although the content is generated dynamically, it is not necessarily unique to each user.

This is the primary target for **micro caching**.

---

# 5. Examples of Dynamic Content

The lecture provides several examples of dynamic content that may be shared among multiple users.

### News or Blog Front Page

A news website's front page may change whenever new articles are published.

For example:

```text
09:00 → Article A
09:01 → Article B
09:02 → Article C
```

The content changes dynamically, but the same page can be displayed to many users.

---

### RSS Feed

An RSS feed containing recent information is also dynamic.

It may change frequently, but the feed itself is generally the same for many visitors.

---

### CI Build Status Page

A Continuous Integration (CI) system may have a status page showing:

- Current builds
- Build status
- Success/failure information

The status changes dynamically, but it is typically common to users within the organization.

---

### Inventory Status

An inventory or availability status can also be dynamic.

The value changes over time, but many users may see the same current state.

---

### Fundraising Counter

A fundraising counter can change continuously:

```text
$100,000
   ↓
$100,500
   ↓
$101,000
```

It is dynamic, but there may be no need to generate a completely new backend response for every individual request.

---

### Lottery Results

Lottery results are another example of dynamic content.

The result changes when new results are published, but the result itself is shared by many users.

---

### Calendar Data

Calendar information can also be dynamic while remaining common to multiple users.

---

# 6. Personalized Dynamic Content Can Contain Shared Dynamic Content

The lecture gives an interesting example involving personalized messages.

Suppose an application displays:

```text
Hello Tom!

Are you happy with our service?
[Yes] [No]
```

The name:

```text
Tom
```

is personalized data.

However, the rest of the message:

```text
Are you happy with our service?
```

may be the same for every user.

Therefore, a response can contain both:

- Personalized data
- Shared dynamic data

This distinction is important when deciding what can and cannot be cached.

The lecture also mentions personalized content generated on the client device, such as advertising or messages that use cookie information.

---

# 7. What Is Micro Caching?

**Micro caching** is a caching technique where dynamic content is cached for a **very short period of time**.

The name comes from the short cache lifetime.

Static resources may be cached for:

```text
Months
Years
```

Micro-cached dynamic content may instead be cached for:

```text
Seconds
10 minutes
20 minutes
30 minutes
60 minutes
```

The exact lifetime depends on how frequently the underlying dynamic information changes.

The important principle is:

> **The cache lifetime should be short enough that the dynamic content remains reasonably fresh.**

---

# 8. Why Not Cache Dynamic Content for Years?

Suppose a news page changes every few seconds.

If the page were cached for two years:

```text
New article published
        ↓
Old cached page remains
        ↓
Users continue seeing stale information
```

That would defeat the purpose of dynamic content.

Therefore, micro caching deliberately uses a short lifetime.

For example:

```nginx
# Conceptual example
Cache lifetime: 30 seconds
```

The lecture emphasizes that dynamic content should generally not receive the long cache durations used for static resources.

---

# 9. NGINX Micro-Cache Architecture

The lecture describes the architecture as:

```text
Web Client
    |
    v
  NGINX
    |
    v
 PHP-FPM
    |
    v
Application / Database
```

The client sends a dynamic request to NGINX.

NGINX identifies the request as dynamic and communicates with PHP-FPM.

PHP-FPM processes the request and may:

- Execute application code.
- Process JavaScript or other application logic.
- Read data from a database.
- Generate the dynamic response.

The response then travels back:

```text
Database/Application
        |
        v
     PHP-FPM
        |
        v
      NGINX
        |
        v
      Client
```

---

# 10. What Happens Without Micro Caching?

Without micro caching, every request may result in another PHP-FPM processing operation.

For example:

```text
Request 1 → NGINX → PHP-FPM → Database → Response
Request 2 → NGINX → PHP-FPM → Database → Response
Request 3 → NGINX → PHP-FPM → Database → Response
Request 4 → NGINX → PHP-FPM → Database → Response
```

If hundreds or thousands of users request the same dynamic resource, the backend may repeatedly perform the same work.

This creates unnecessary load.

---

# 11. What Happens With Micro Caching?

With micro caching enabled:

```text
Request 1
   |
   v
NGINX → PHP-FPM → Response
   |
   v
NGINX Cache
```

A subsequent request for the same cacheable resource can be handled directly:

```text
Request 2
   |
   v
NGINX
   |
   | Cache HIT
   v
Cached Response
   |
   v
Client
```

The backend does not need to process the same request again during the cache lifetime.

---

# 12. Micro Caching Flow

The complete process can be represented as:

```text
                 First Request
Client ──────────────────────────> NGINX
                                     |
                                     | Cache MISS
                                     v
                                  PHP-FPM
                                     |
                                     v
                              Application/DB
                                     |
                                     v
                                  PHP-FPM
                                     |
                                     v
                                   NGINX
                                  /     \
                                 /       \
                         Store Cache     Client
                                         |
                                         v
                                      Response


                 Subsequent Request
Client ──────────────────────────> NGINX
                                     |
                                     | Cache HIT
                                     v
                                Cached Data
                                     |
                                     v
                                   Client
```

The key benefit is that NGINX can avoid invoking PHP-FPM when a valid cached response is available.

---

# 13. NGINX Cache Storage

The lecture explains that NGINX uses a **persistent disk-based cache** located in the local filesystem.

Conceptually:

```text
NGINX
  |
  v
Local File System
  |
  v
NGINX Cache
```

The cached dynamic responses are therefore stored locally according to the configured cache path.

The lecture also discusses a shared-memory zone for cache keys and metadata.

---

# 14. PHP-FPM and FastCGI

NGINX communicates with PHP-FPM using the **FastCGI protocol**.

FastCGI is described as a widely used protocol for interfacing interactive applications such as PHP with web servers such as NGINX.

One of its advantages is the ability to manage multiple CGI requests using a single process.

Conceptually:

```text
NGINX
   |
   | FastCGI
   v
PHP-FPM
   |
   +---- Request 1
   +---- Request 2
   +---- Request 3
   +---- Request 4
```

This allows the web server and application process manager to work together efficiently.

---

# 15. `fastcgi_cache_path`

The main directive introduced for FastCGI micro caching is:

```nginx
fastcgi_cache_path
```

This directive defines the location and configuration of the FastCGI cache.

It must be defined at the **HTTP context** level.

Conceptually:

```nginx
http {
    fastcgi_cache_path ...;

    server {
        ...
    }
}
```

The directive defines where NGINX stores cached FastCGI responses.

---

# 16. `fastcgi_cache_key`

The lecture also introduces:

```nginx
fastcgi_cache_key
```

This defines the identifier/key used by NGINX to determine which request corresponds to which cached response.

The basic idea is:

```text
Request
   |
   v
Cache Key
   |
   v
Cached Response
```

If the same request produces the same cache key, NGINX can locate and reuse the corresponding cached response.

---

# 17. Why the Cache Key Matters

Suppose the first request creates a cached response:

```text
Request A
   |
   v
Cache Key A
   |
   v
Cached Response A
```

A subsequent request must generate the same key to reuse that response:

```text
Request A
   |
   v
Cache Key A
   |
   v
Cache HIT
```

If the request changes in a way that affects the cache key:

```text
Request B
   |
   v
Cache Key B
   |
   v
Cache MISS
```

NGINX can then generate and store a separate cached response.

---

# 18. Parameters of `fastcgi_cache_path`

The lecture discusses several important parameters associated with `fastcgi_cache_path`.

They include:

1. Cache location
2. Levels
3. Key zone
4. Inactive
5. Maximum cache size

---

# 19. Cache Location

The first parameter specifies where NGINX stores its cache on the local filesystem.

The lecture uses a path similar to:

```text
/var/cache/nginx
```

Conceptually:

```nginx
fastcgi_cache_path /var/cache/nginx ...;
```

This is the directory in which NGINX maintains its cache data.

---

# 20. `levels`

The `levels` parameter defines the directory hierarchy used for storing cached objects.

The lecture explains that NGINX generates an **MD5-based key** for each cache entry.

If every cache object were stored directly in one directory, a very large number of files could accumulate in the same directory.

Instead, a directory hierarchy can be created.

For example:

```text
/var/cache/nginx/
├── 1/
│   └── cache-object
├── 2/
│   └── cache-object
└── 3/
    └── cache-object
```

The lecture describes a two-level hierarchy.

Conceptually:

```nginx
levels=1:2
```

This distributes cache objects across subdirectories.

---

# 21. Why Cache Levels Are Used

Without levels:

```text
/var/cache/nginx/
    ├── cache1
    ├── cache2
    ├── cache3
    ├── cache4
    ├── ...
```

A very large number of cache files could end up in the same directory.

With levels:

```text
/var/cache/nginx/
    ├── 1/
    │   ├── cache...
    │   └── cache...
    ├── 2/
    │   ├── cache...
    │   └── cache...
    └── 3/
        ├── cache...
        └── cache...
```

This provides a more organized cache filesystem structure.

The lecture notes that the practical lab will demonstrate this hierarchy in more detail.

---

# 22. `keys_zone`

The cache configuration also defines a shared memory zone.

Conceptually:

```nginx
keys_zone=<zone-name>:<size>
```

The zone stores information about:

- Active cache keys
- Cache metadata
- Information about cached data

For example, conceptually:

```nginx
keys_zone=my_cache:10m
```

The exact name and size depend on the deployment.

---

# 23. Why `keys_zone` Uses Memory

Keeping cache key information in memory makes cache lookup more efficient.

Instead of repeatedly examining the disk to determine whether a particular cache entry exists, NGINX can use the shared memory zone to determine whether a cache entry is available.

Conceptually:

```text
Request
   |
   v
Check cache key in memory
   |
   +---- HIT ----> Locate cached response
   |
   +---- MISS ---> Process request
```

This helps NGINX determine whether a request is a cache **hit** or **miss** efficiently.

---

# 24. Multiple Cache Zones

The lecture explains that multiple cache zones can be configured.

For example:

```text
Location 1 → Zone 1
Location 2 → Zone 2
Location 3 → Zone 3
```

This allows cache boundaries to be defined for different application areas.

Conceptually:

```text
NGINX
 |
 +-- Zone 1 → Location 1 cache
 |
 +-- Zone 2 → Location 2 cache
 |
 +-- Zone 3 → Location 3 cache
```

The key zone therefore acts as a boundary/parent structure for cache information.

---

# 25. `inactive`

The `inactive` parameter controls how long cached data can remain in the cache when it has not been accessed.

The lecture emphasizes that this is independent of whether the cached content is technically still fresh.

If the cached item has not been accessed for the configured inactive period, it can be removed.

Conceptually:

```text
Cache Entry
   |
   | No access for configured inactive period
   v
Removed from cache
```

This helps prevent unused cache entries from occupying disk space indefinitely.

---

# 26. `max_size`

The `max_size` parameter defines the maximum amount of storage that the cache can consume.

Conceptually:

```nginx
max_size=<size>
```

For example:

```text
Cache maximum size = configured limit
```

This parameter is optional according to the lecture.

It can be omitted if a maximum cache size is not required.

---

# 27. Complete Conceptual `fastcgi_cache_path`

Putting the discussed parameters together, the configuration has the following conceptual structure:

```nginx
fastcgi_cache_path /var/cache/nginx
    levels=1:2
    keys_zone=my_cache:10m
    inactive=30m
    max_size=1g;
```

This illustrates:

- `/var/cache/nginx` → cache location
- `levels=1:2` → directory hierarchy
- `keys_zone=my_cache:10m` → shared memory zone
- `inactive=30m` → remove unused entries after the configured period
- `max_size=1g` → maximum cache size

The lecture introduces these parameters; the exact values should be chosen according to the application's requirements.

---

# 28. `fastcgi_cache_key` Components

The lecture explains the components used to construct the FastCGI cache key.

The key includes:

1. `$scheme`
2. Request method
3. Host
4. Request URI

A conceptual key is:

```nginx
fastcgi_cache_key "$scheme$request_method$host$request_uri";
```

The exact formatting/separators can be adjusted, but the lecture's key components are important.

---

# 29. `$scheme`

The first component is:

```nginx
$scheme
```

This represents the request protocol.

Possible values include:

```text
http
https
```

This distinction is important.

For example:

```text
http://www.example.com/page
```

and:

```text
https://www.example.com/page
```

may represent the same apparent URL/path but use different schemes.

NGINX therefore maintains different cache keys for the two schemes.

```text
HTTP  → Cache Key A
HTTPS → Cache Key B
```

---

# 30. Request Method

The cache key also contains the request method.

Examples include:

```text
GET
POST
PUT
DELETE
```

Therefore, the method becomes part of the identity of the request.

For example:

```text
GET /page
```

and:

```text
POST /page
```

are not treated as the same request simply because they use the same URI.

---

# 31. Host

The cache key also includes the host.

For example:

```text
www.example.com
```

The host identifies the requested domain.

A request such as:

```text
GET http://www.example.com/page
```

contains:

```text
Scheme:        http
Method:        GET
Host:          www.example.com
```

The lecture describes the host as the complete domain name.

---

# 32. Request URI

The final major component is the **request URI**.

The request URI identifies the requested resource and its request-specific information.

For example, the lecture gives a request conceptually similar to:

```text
GET /?name=tom
```

The request URI contains the requested URI information, including the query portion.

Thus, changing the request URI can result in a different cache key.

---

# 33. Example Cache Key

Consider:

```text
GET http://www.example.com/?name=tom
```

The cache key components are:

```text
Scheme        → http
Method        → GET
Host          → www.example.com
Request URI   → /?name=tom
```

Conceptually:

```text
http + GET + www.example.com + /?name=tom
```

NGINX uses these request characteristics to calculate the cache key.

---

# 34. Same URI → Same Cache Entry

If the same request is received again:

```text
GET http://www.example.com/?name=tom
```

the same cache key can be generated.

NGINX can therefore locate the previously cached response:

```text
Request
   |
   v
Same Cache Key
   |
   v
Cached Response
   |
   v
Client
```

This is the **cache hit** scenario.

---

# 35. Different URI → Different Cache Key

If the request changes:

```text
GET http://www.example.com/?name=john
```

the request URI is different.

Therefore, a different cache key is generated:

```text
name=tom → Cache Key A
name=john → Cache Key B
```

NGINX can maintain separate cached responses for the different requests.

---

# 36. Micro Caching vs. Static Caching

| Characteristic | Static Caching | Micro Caching |
|---|---|---|
| Typical content | CSS, JS, images | Dynamic application responses |
| Content changes | Relatively infrequently | Can change frequently |
| Cache duration | Long | Very short |
| Backend processing | Usually unnecessary | Avoided during cache hits |
| Main benefit | Reduce repeated downloads | Reduce repeated dynamic processing |
| Typical storage | Browser/CDN/server cache | NGINX FastCGI cache |

The major distinction is **how frequently the content changes and how long it is safe to reuse**.

---

# 37. Performance Benefits

Micro caching can provide several benefits.

### Reduced PHP-FPM workload

Instead of processing every request:

```text
100 requests
    ↓
100 PHP-FPM operations
```

micro caching can turn many of those requests into cache hits:

```text
First request
    ↓
PHP-FPM
    ↓
Cache

Remaining requests
    ↓
NGINX Cache
```

---

### Reduced Database Load

If PHP-FPM normally queries a database to generate a response, a cache hit can avoid the database operation entirely.

```text
Without cache:

Request → NGINX → PHP-FPM → Database


With cache hit:

Request → NGINX → Cache
```

---

### Faster Responses

Serving an already-generated response from NGINX's local cache is generally faster than repeatedly executing the backend application.

---

### Better User Experience

The lecture emphasizes that micro caching can make the website faster and improve the user experience.

---

# 38. Important Limitation

Micro caching should not be used blindly for personalized responses.

For example:

```text
User A → Shopping Cart A
User B → Shopping Cart B
```

Caching User A's response and returning it to User B could expose incorrect or private information.

Therefore, the key question before enabling micro caching is:

> **Can this response safely be shared among multiple users for the configured cache period?**

If the response is user-specific, it should generally not be treated as a shared micro-cache response.
