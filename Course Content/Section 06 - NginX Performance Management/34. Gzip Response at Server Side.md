# Lecture 34 — Gzip Response at Server Side

## Overview

In this lecture, NGINX is configured to **compress HTTP responses at the server side before transmitting them to the
client**.

The primary goals are:

- Reduce the amount of data transferred over the network.
- Improve website loading performance.
- Reduce bandwidth consumption.
- Reduce bandwidth-related costs.
- Make better use of network resources.

The basic workflow is:

```text
Client
   |
   | HTTP Request
   v
NGINX
   |
   | Compress response with Gzip
   v
Compressed Response
   |
   v
Client Browser
   |
   | Decompresses automatically
   v
Original Resource
```

Modern web browsers can automatically decompress Gzip-compressed HTTP responses, so the application does not need to
manually decompress the response. Pasted text

---

# 1. Why Response Compression Is Required

Website loading speed is strongly affected by the amount of data that the browser has to download.

A typical website may contain many different resources:

- HTML files
- CSS files
- JavaScript files
- AJAX/XHR responses
- Images
- Other text-based resources

When the browser opens a website, it may need to download dozens or hundreds of individual resources.

Therefore:

> **The more data that needs to be transferred, the more work the browser and network need to perform before the page is
fully loaded.**

Reducing the size of those responses can therefore improve website performance.

# 3. Transferred Data vs. Resource Size

One important observation from the browser's Network panel is that **transferred data can be smaller than the total
resource size**.

For example:

```text
Resource size:       6.9 MB
Transferred:         2.2 MB
```

This can happen when the server uses compression.

The browser receives a compressed representation of the resource, while the resource itself may have a considerably
larger uncompressed size.

This distinction becomes important when evaluating the effectiveness of Gzip compression.

---

# 4. Benefits of Compression

Reducing the size of files transmitted between the server and client provides two major benefits.

### 4.1 Faster Website Loading

Smaller responses require less network bandwidth and can therefore be transferred faster.

Conceptually:

```text
Large File
   |
   | Compression
   v
Smaller File
   |
   | Network
   v
Browser
```

### 4.2 Lower Bandwidth Usage

Bandwidth usage can also affect hosting costs.

The lecture mentions hosting providers such as Bluehost and GoDaddy as examples of environments where bandwidth usage
can be a consideration.

If a server transmits a large amount of data:

```text
More data transferred
        ↓
More bandwidth consumed
        ↓
Potentially higher cost
```

Compressing responses reduces the amount of data transmitted over the network.

Therefore, compression can improve both:

- Performance
- Resource/cost efficiency

---

# 5. NGINX Gzip Compression

NGINX can compress responses **on the fly** using Gzip.

The basic concept is:

```text
Client requests resource
          |
          v
       NGINX
          |
          | Compress resource
          v
   Gzip-compressed response
          |
          v
        Client
```

Instead of sending the original uncompressed file, NGINX compresses the response before sending it.

The client browser then decompresses it automatically.

---

# 6. Browser Decompression

A common question is:

> If NGINX compresses the response, who decompresses it?

Modern web browsers support compressed HTTP responses and can decompress them automatically.

Therefore:

```text
NGINX
  |
  | Gzip
  v
Compressed Response
  |
  v
Browser
  |
  | Automatic decompression
  v
Original content
```

No special application-side decompression code is required for normal browser requests.

---

# 7. Compression Uses Server Resources

Compression has an important trade-off.

Although it reduces network traffic, **compression requires CPU/server resources**.

For every response that NGINX compresses, the server has to perform additional processing.

Therefore:

```text
Higher Compression
        ↓
Smaller Response
        ↓
Less Network Traffic

BUT

Higher Compression
        ↓
More CPU Processing
        ↓
More Server Resources
```

The goal is therefore not necessarily to select the maximum possible compression level.

Instead, a reasonable balance should be chosen.

---

## 8. Gzip Compression Level

The Gzip compression level is a value from **1 to 9**.

Higher compression levels generally produce smaller compressed output but require more CPU time.

| Level | Behavior                       |
|------:|--------------------------------|
|   `1` | Lowest compression, fastest    |
| `2–3` | Low compression                |
| `4–6` | Moderate/practical compression |
| `7–8` | High compression               |
|   `9` | Maximum compression, slowest   |

> **Important:** Gzip compression levels do **not** go up to `10`. The valid compression level range is **1–9**.

A higher compression level attempts to reduce the response size further, but requires more server resources.

The instructor recommends values around:

```text
3
4
5
```

The instructor's preferred value is:

```text
4
```

The reason is to achieve a useful reduction in response size without consuming excessive server resources.

# 11. Enabling Gzip in NGINX

The Gzip configuration is added inside the **HTTP block** of the NGINX configuration.

Conceptually:

```nginx
http {
    gzip on;
    gzip_comp_level 4;

    ...
}
```

Because the configuration is placed inside the `http` block, it applies to servers using that HTTP configuration.

The lecture also notes that these values can be modified at the `server` or `location` level where appropriate.

---

# 12. `gzip on`

The first important directive is:

```nginx
gzip on;
```

This enables Gzip compression in NGINX.

Without this directive:

```nginx
gzip off;
```

compression is not enabled.

With:

```nginx
gzip on;
```

NGINX can compress eligible responses.

---

# 13. `gzip_comp_level`

The compression level is configured with:

```nginx
gzip_comp_level 4;
```

The lecture recommends a middle value rather than using the maximum level.

The example configuration uses:

```nginx
gzip_comp_level 4;
```

This provides a reasonable compromise between:

- CPU usage
- Compression ratio
- Network transfer size

---

# 14. Selecting Which Files to Compress

NGINX should not blindly compress every type of resource.

The lecture configures Gzip for text-based resources such as:

```text
text/plain
text/css
application/json
application/x-javascript
application/javascript
application/xml
application/rss+xml
```

The exact MIME types should be configured according to the resources the application actually serves.

A representative configuration based on the lecture is:

```nginx
gzip on;
gzip_comp_level 4;

gzip_types
    text/plain
    text/css
    application/json
    application/x-javascript
    application/javascript
    application/xml
    application/rss+xml;
```

---

# 15. Why JPG and PNG Are Not Compressed

A particularly important point from the lecture is that the instructor **does not configure Gzip for JPG and PNG
images**.

The reason is that formats such as:

```text
.jpg
.jpeg
.png
```

are already compressed image formats.

Trying to Gzip them again generally provides little additional reduction.

Instead, it consumes server resources while producing little or no useful size reduction.

Conceptually:

```text
Already-compressed image
          |
          | Gzip again
          v
Very small additional benefit
          +
Additional CPU usage
```

The lecture therefore recommends avoiding unnecessary Gzip processing for these image formats.

---

# 16. Text Files Are Good Candidates for Gzip

Text-based resources are much better candidates for Gzip compression.

Examples include:

```text
CSS
JavaScript
JSON
XML
Plain text
RSS/XML data
```

Text can often be compressed substantially.

The lecture states that text resources can potentially be reduced by approximately **50% to 80%**, depending on the
content.

Therefore, Gzip provides significant value for these resources.

# 21. Testing Gzip with `curl`

The browser automatically sends headers indicating that it supports compression.

When testing manually with `curl`, however, the instructor demonstrates that the client must explicitly indicate its
support for compressed content.

A request without an appropriate `Accept-Encoding` header does not necessarily cause NGINX to return the compressed
representation.

Conceptually:

```bash
curl -i http://<server>/<resource>
```

may return the uncompressed response.

To request Gzip/deflate encoding explicitly:

```bash
curl -H "Accept-Encoding: gzip, deflate" -i \
    http://<server>/<resource>
```

The important header is:

```http
Accept-Encoding: gzip, deflate
```

This tells the server that the client can accept those content encodings.

# 28. Important Best Practices

### Use a reasonable compression level

A value such as:

```nginx
gzip_comp_level 4;
```

provides a practical balance between compression and CPU usage.

Avoid automatically choosing the maximum compression level simply because it produces the smallest response.

---

### Compress text-based resources

Good candidates include:

```text
CSS
JavaScript
JSON
XML
Plain text
```

These resources can often benefit significantly from Gzip.

---

### Avoid unnecessary compression of already-compressed formats

Do not blindly add:

```text
JPG
JPEG
PNG
```

to Gzip compression.

These formats are already compressed, so additional Gzip processing generally provides little benefit while consuming
server CPU.

---

### Verify the response headers

Look for:

```http
Content-Encoding: gzip
```

This confirms that the response is being delivered using Gzip encoding.

---

### Test with a client that advertises compression support

When using `curl`, explicitly send:

```http
Accept-Encoding: gzip, deflate
```

Otherwise, the server may return the uncompressed representation.

---

# 29. Common Troubleshooting Points

## Gzip is enabled but the response is not compressed

Check:

1. Whether the client sends `Accept-Encoding`.
2. Whether the resource's MIME type is included in `gzip_types`.
3. Whether NGINX was successfully reloaded.
4. Whether the response is already compressed.
5. Whether the requested resource is actually eligible for Gzip.
