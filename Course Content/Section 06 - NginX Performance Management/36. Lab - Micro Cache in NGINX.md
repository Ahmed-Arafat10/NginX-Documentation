# Lecture 36 — Lab: Micro Cache in NGINX

## Overview

This lab demonstrates how to configure **micro caching for dynamic content in NGINX** and how much performance improvement it can provide when the backend application requires significant processing time.

The lab uses:

- NGINX
- PHP-FPM
- FastCGI
- `fastcgi_cache_path`
- `fastcgi_cache_key`
- `fastcgi_cache`
- `fastcgi_cache_valid`
- Apache Bench (`ab`)
- NGINX cache-status headers

The practical objective is to compare a dynamic PHP application **with and without micro caching** under multiple concurrent requests. Pasted text

# 8. Configuring `fastcgi_cache_path`

The first micro-cache configuration is added inside the **HTTP context**.

The lecture defines a cache directory under `/tmp`.

A conceptual configuration is:

```nginx
fastcgi_cache_path /tmp/cache-nginx
    levels=1:2
    keys_zone=zone_one:100m
    inactive=60m;
```

The lab uses the following concepts:

| Parameter | Lab Purpose |
|---|---|
| Cache path | `/tmp/cache-nginx` |
| `levels` | `1:2` |
| Cache zone | `zone_one` |
| Zone size | `100 MB` |
| `inactive` | `60 minutes` |

---

# 9. Cache Directory

The cache location used in the lab is:

```text
/tmp/cache-nginx
```

This is where NGINX stores the cached FastCGI responses.

The instructor later inspects this directory to demonstrate how the cache hierarchy is physically created.

---

# 10. Cache Levels

The configuration uses:

```nginx
levels=1:2
```

This creates a two-level directory hierarchy.

The purpose is to prevent all cache objects from being stored in one huge directory.

Conceptually:

```text
/tmp/cache-nginx/
    └── 0/
        └── 9d/
            └── <MD5-cache-file>
```

The actual directory names and hashes are generated by NGINX.

---

# 11. Cache Zone

The cache zone is defined as:

```nginx
keys_zone=zone_one:100m
```

This defines:

```text
Zone name: zone_one
Zone size: 100 MB
```

The zone is used for cache keys and related metadata.

The same zone will later be assigned to the PHP location through:

```nginx
fastcgi_cache zone_one;
```

---

# 12. Inactive Cache Time

The lab configures:

```nginx
inactive=60m
```

This means cached content that is not accessed during the configured inactive period can be removed.

The lecture uses **60 minutes** for the demonstration.

This should not be confused with how frequently the underlying content changes; it controls the handling of cache entries that remain unused.

---

# 13. Configuring `fastcgi_cache_key`

The next important directive is:

```nginx
fastcgi_cache_key
```

The lab constructs the cache key from:

- Scheme
- Request method
- Host
- Request URI

Conceptually:

```nginx
fastcgi_cache_key "$scheme$request_method$host$request_uri";
```

This corresponds to the cache-key components discussed in the previous lecture.

---

# 14. Complete Global Cache Configuration

Putting the lab's major directives together:

```nginx
http {
    fastcgi_cache_path /tmp/cache-nginx
        levels=1:2
        keys_zone=zone_one:100m
        inactive=60m;

    fastcgi_cache_key "$scheme$request_method$host$request_uri";

    ...
}
```

The actual configuration can contain additional NGINX directives required by the application.

The important point is that `fastcgi_cache_path` and `fastcgi_cache_key` are defined at the appropriate global HTTP level.

---

# 15. Enabling the Cache for PHP

Defining `fastcgi_cache_path` alone does not automatically cache PHP responses.

The PHP location must explicitly use the configured cache zone.

Conceptually:

```nginx
location ~ \.php$ {
    include fastcgi_params;

    fastcgi_pass unix:/run/php/php7.2-fpm.sock;

    fastcgi_cache zone_one;
}
```

This associates PHP responses handled by this location with:

```text
zone_one
```

---

# 16. Multiple Cache Zones

The instructor explains that different locations can use different cache zones.

For example:

```text
Location 1 → Zone 1
Location 2 → Zone 2
Location 3 → Zone 3
```

Alternatively:

```text
Location 1 ─┐
Location 2 ─┼──> Same cache zone
Location 3 ─┘
```

Therefore, NGINX allows multiple locations to share a cache zone or use separate zones depending on the configuration requirements.

---

# 17. `fastcgi_cache_valid`

The next directive introduced is:

```nginx
fastcgi_cache_valid
```

This determines how long a response with a particular HTTP status code should remain valid in the FastCGI cache.

The lab configures successful `200` responses.

Conceptually:

```nginx
fastcgi_cache_valid 200 60m;
```

This means:

```text
HTTP 200 response
       ↓
Cache it
       ↓
Valid for 60 minutes
```

The lecture uses the same 60-minute period configured in the cache path.

---

# 18. Conceptual PHP Cache Configuration

The relevant portion can therefore be represented as:

```nginx
http {
    fastcgi_cache_path /tmp/cache-nginx
        levels=1:2
        keys_zone=zone_one:100m
        inactive=60m;

    fastcgi_cache_key "$scheme$request_method$host$request_uri";

    server {
        location ~ \.php$ {
            include fastcgi_params;
            fastcgi_pass unix:/run/php/php7.2-fpm.sock;

            fastcgi_cache zone_one;
            fastcgi_cache_valid 200 60m;
        }
    }
}
```

This represents the core micro-cache configuration demonstrated in the lab.


# 33. Cache Hit and Cache Miss

The next part of the lab demonstrates how to determine whether NGINX is serving a response from the cache.

A custom response header is added:

```nginx
add_header X-Cache $upstream_cache_status;
```

This exposes the NGINX cache status to the client.

---

# 34. `X-Cache` Header

After reloading NGINX, a request is made using `curl`.

The response contains:

```http
X-Cache: MISS
```

The first request is a **cache miss** because no cached response exists yet.

When the same request is sent again:

```http
X-Cache: HIT
```

This indicates that NGINX is now serving the response from its cache.

---

# 35. Understanding `MISS`

A cache miss means:

```text
Request
   |
   v
NGINX
   |
   | No cached response
   v
PHP-FPM
   |
   v
Response
   |
   v
Cache
```

The backend must process the request.

The generated response is then stored in the cache for future requests.

---

# 36. Understanding `HIT`

A cache hit means:

```text
Request
   |
   v
NGINX
   |
   | Cached response exists
   v
Cache
   |
   v
Client
```

PHP-FPM does not need to regenerate the response.

This is the central performance benefit of micro caching.

---

# 37. Example Cache Status

Repeated requests produce:

```http
X-Cache: MISS
```

on the first request and:

```http
X-Cache: HIT
```

on subsequent requests.

This provides a simple way to verify that the micro cache is actually working.

# 45. End-to-End Micro-Cache Flow

The complete process demonstrated in the lab can be summarized as:

```text
                 First Request
Client
  |
  v
NGINX
  |

  v
PHP-FPM
  |
  | Dynamic processing
  v
PHP Response
  |
  v
NGINX
  |
  +----> Store response in cache
  |
  v

```

```text

  |
  v
NGINX
  |

  v

  |
  v
Client
```

The expensive backend operation is therefore avoided for subsequent requests while the cached entry remains valid.

# 47. Performance Improvement Explained

Without micro caching:

```text
200 requests
     ↓
200 PHP-FPM processing operations
     ↓
Each operation waits ~1 second
```

With micro caching:

```text
First request
     ↓
PHP-FPM
     ↓
Cache response

Remaining requests
     ↓
NGINX cache
```

The backend is therefore protected from repeated identical processing.

This can dramatically reduce:

- PHP-FPM workload
- Application processing
- Database workload
- Origin server resource consumption

while improving response speed.

# 51. Important Warnings

### Do not cache personalized responses blindly

Micro caching is appropriate only when the response can safely be reused for subsequent requests.

Responses containing user-specific information require special care.

---

### Do not judge performance from a single request

A micro cache needs an initial request to populate the cache.

Therefore:

```text
First request → MISS
Second request → HIT
```

Testing only the first request can make the cache appear ineffective.

---

### Benchmark realistic workloads

Apache Bench is useful for demonstrating the concept, but benchmark results depend on:

- Server hardware
- Network conditions
- Application complexity
- PHP-FPM configuration
- Number of concurrent requests
- Cache configuration

The exact requests-per-second figures from the lab should therefore be treated as **lab measurements**, not universal NGINX performance numbers.
