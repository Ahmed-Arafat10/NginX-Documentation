# Lecture 33 — Lab: Client-Side Caching in NGINX

## Overview

Client-side caching is a mechanism where resources are stored in the user's browser so that subsequent requests can be served directly from the browser instead of repeatedly contacting the NGINX/web server.

This can improve application performance by:

- Reducing communication between the browser and server.
- Reducing data transfer.
- Reducing the number of requests reaching the web server.
- Improving performance for geographically distributed users.
- Reducing latency for static resources.

The lecture demonstrates how NGINX can **recommend caching behavior to browsers and intermediate proxies** using HTTP response headers.

> **Important:** NGINX does not have complete control over client-side caching because the cache belongs to the client/browser. The web server can send HTTP response headers that instruct the browser and intermediate caches how the resource may be cached.

---

# 1. What Is Client-Side Caching?

Client-side caching means storing resources on the **client side**, typically inside the user's web browser.

For example, a browser may cache:

- Images
- CSS files
- JavaScript files
- Other static resources

The browser can then reuse those resources instead of downloading them from the server every time.

### Example

Suppose a user requests the same JavaScript file 10 times within an hour.

Without appropriate caching:

```text
Browser
   |
   | Request JS
   v
NGINX/Web Server
   |
   | Response
   v
Browser

Browser
   |
   | Request JS again
   v
NGINX/Web Server
```

The server processes the request every time.

With client-side caching:

```text
Browser
   |
   | First request
   v
NGINX/Web Server
   |
   | JS file
   v
Browser Cache
   |
   | Subsequent requests
   v
Browser
```

The browser can use its locally cached copy instead of contacting the server.

This saves both **time and network communication**.

# 3. NGINX and Client-Side Caching

Web servers cannot completely control client-side caching because the cache is managed by the client.

However, the server can send **recommendations** to the client through HTTP response headers.

These response headers tell the browser and potentially intermediate proxy/cache servers how a resource should be handled.

The most important header discussed in this lecture is:

```http
Cache-Control
```

Other headers discussed include:

```http
Expires
Pragma
Vary
```

---

# 4. `Cache-Control` Header

`Cache-Control` is the primary HTTP response header used to control caching behavior.

For example:

```http
Cache-Control: public
```

If the `Cache-Control` header is not provided appropriately, the browser may request the resource again on subsequent requests rather than relying on a cached copy.

The lecture emphasizes `Cache-Control` as the most important header for effectively enabling browser-side caching.

---

# 5. `Cache-Control: public`

The `public` value indicates that the response can be cached not only by the end user's browser, but also by **intermediate proxy/cache servers**.

Example:

```http
Cache-Control: public
```

Consider this architecture:

```text
User in London
       |
       v
London Proxy
       |
       v
Application/Web Server in Tokyo
```

If the resource is public:

```text
                    +----------------+
                    | Web Server     |
                    | Tokyo          |
                    +----------------+
                            ^
                            |
                    +----------------+
                    | London Proxy   |
                    | Cached copy    |
                    +----------------+
                            ^
                            |
                    +----------------+
                    | User Browser   |
                    | Cached copy    |
                    +----------------+
```

There can be a cached copy at:

1. The user's browser.
2. The intermediate London proxy.

Other users passing through the same proxy can therefore receive the cached resource from the proxy instead of contacting the origin server in Tokyo.

This can significantly improve performance for geographically distributed users.

---

# 6. `Cache-Control: private`

The `private` value indicates that the response should only be cached by the **end client**.

Example:

```http
Cache-Control: private
```

Intermediate proxies should not cache the resource.

Conceptually:

```text
User Browser
     |
     | Cached copy
     |
London Proxy
     |
     | Request continues
     v
Tokyo Web Server
```

The browser can maintain its own cached copy, but intermediate proxies do not cache the resource for other users.

### Public vs. Private

| Value | Browser Cache | Intermediate Proxy |
|---|---|---|
| `public` | Yes | Yes |
| `private` | Yes | No |

The lecture notes that developers/DevOps engineers will generally use `public` for resources that are appropriate for shared caching.

---

# 7. `max-age`

`max-age` specifies how long a resource can remain cached before it is considered stale.

Example:

```http
Cache-Control: public, max-age=172800
```

The value is specified in **seconds**.

For example:

```text
max-age=172800
```

means the resource can be cached for 172,800 seconds.

The general syntax is:

```http
Cache-Control: public, max-age=<seconds>
```

It can also be combined with `private`:

```http
Cache-Control: private, max-age=<seconds>
```

The important point is that `max-age` defines the caching duration using a **time span in seconds**.

---

# 8. `Expires` Header

The lecture also discusses the `Expires` header.

Unlike `max-age`, which specifies a duration in seconds, `Expires` specifies an **absolute date/time** after which the cached resource should no longer be considered valid.

Conceptually:

```http
Expires: <date>
```

Until the expiration date is reached, the browser can use its locally cached copy.

After the expiration date, the browser should request a fresh copy from the web server.

For example, a resource could be configured to remain cached for several months or even years.

If the user does not manually clear the browser cache, the cached resource can remain available until its configured expiration.

---

# 9. `max-age` vs. `Expires`

Both mechanisms can define caching validity, but they express the validity differently.

### `max-age`

Uses a duration:

```http
Cache-Control: public, max-age=172800
```

The value is measured in seconds.

### `Expires`

Uses an absolute date:

```http
Expires: <specific-date>
```

The lecture explains that when both `max-age` and `Expires` are present, **`max-age` takes precedence**.

Therefore, if the two headers specify different expiration times, the `max-age` value is used for determining the caching lifetime.

# 14. `Pragma`

The lecture introduces:

```http
Pragma: public
```

`Pragma` is described as an older/legacy counterpart to `Cache-Control`.

The recommendation in the lecture is to define it as well:

```nginx
add_header Pragma "public";
```

The reasoning is compatibility with older protocols, systems, or browsers that may still use the legacy header.

It does not harm the configuration and can provide additional compatibility.

---

# 15. NGINX `expires` Directive

NGINX provides the `expires` directive to configure expiration information.

For example:

```nginx
expires 2M;
```

This configures an expiration period of two months.

The instructor initially demonstrates a six-month value and then changes it to:

```nginx
expires 2M;
```

Other values can be used, such as:

```nginx
expires 4M;
```

or a year-based value using `Y`.

The resulting HTTP response contains an `Expires` header representing the calculated expiration date.

---

# 16. Automatically Generated `max-age`

An important observation in the lab is that even though the instructor does not explicitly configure `max-age`, the response can still contain it.

For example, after configuring the NGINX expiration period, the response contains an automatically calculated cache duration.

Conceptually:

```http
Expires: <calculated-date>
Cache-Control: max-age=<calculated-seconds>
```

The `max-age` value is calculated from the configured expiration period.

This allows NGINX to provide cache-control information based on the `expires` configuration.

---

# 17. Example Response Headers

After the configuration is applied, the response contains headers similar to:

```http
Expires: <expiration-date>
Cache-Control: public, max-age=<seconds>
Pragma: public
Vary: Accept-Encoding
```

The exact date and calculated `max-age` depend on when the request is made and the configured expiration period.

The important result is that the browser receives instructions telling it that the resource can be cached.

# 18. Making the Configuration Generic

Initially, the cache configuration applies to a specific test location:

```nginx
location = /port.jpg {
    ...
}
```

The instructor then makes the configuration more useful by applying it to **file extensions**.

The goal is to cache static resources such as:

- CSS
- JavaScript
- JPG
- JPEG
- PNG

A regular-expression location can be used:

```nginx
location ~* \.(css|js|jpg|jpeg|png)$ {
    expires 2M;
}
```

The exact configuration can include the other headers demonstrated in the lab.

The important concept is the regular expression:

```regex
\.(css|js|jpg|jpeg|png)$
```

This matches requests ending with the specified file extensions.

# 21. Which Resources Are Cached?

With a configuration such as:

```nginx
location ~* \.(css|js|jpg|jpeg|png)$ {
    expires 2M;
}
```

the following resources receive the configured caching behavior:

```text
.css
.js
.jpg
.jpeg
.png
```

The lecture's configuration therefore causes these resources to be cached at the client side for the configured period.

---

# 22. HTML Is Not Automatically Included

An important detail from the lab is that HTML is **not** included in the regular expression.

For example:

```nginx
location ~* \.(css|js|jpg|jpeg|png)$ {
    expires 2M;
}
```

does not match:

```text
.html
```

Therefore, an HTML page does not receive the same caching configuration.

If HTML should also be cached, it can be added:

```nginx
location ~* \.(css|js|jpg|jpeg|png|html)$ {
    expires 2M;
}
```

Then HTML resources will also receive the corresponding caching headers.

# 23. Practical Architecture

The overall optimization can be understood as:

```text
                    First Request
Browser --------------------------------> NGINX
   ^                                      |
   |                                      |
   +------------- Resource ---------------+

                    Subsequent Request

Browser
   |
   | Resource available locally?
   |
   +---- YES ----> Browser Cache
   |
   +---- NO -----> NGINX
```

For publicly cacheable resources and environments with intermediate proxies:

```text
                    +------------------+
                    | Origin NGINX     |
                    | Web Server       |
                    +------------------+
                              ^
                              |
                    +------------------+
                    | Intermediate     |
                    | Proxy Cache      |
                    +------------------+
                              ^
                              |
                    +------------------+
                    | Client Browser   |
                    | Cache            |
                    +------------------+
```

This architecture can reduce requests reaching the origin server and improve response times for users.

# 24. Production Considerations

The lecture highlights the usefulness of these configurations for:

- Production websites.
- High-traffic websites.
- Websites with geographically distributed users.
- Applications serving many static resources.

Caching static resources can reduce unnecessary server communication and data transfer.

This becomes particularly useful when users are geographically far away from the origin server because intermediate caches can serve resources closer to the users.

---

# 25. Recommended Configuration Pattern

A practical pattern based directly on the lab is to target static file extensions rather than applying long-lived caching indiscriminately to every response.

For example:

```nginx
location ~* \.(css|js|jpg|jpeg|png)$ {
    expires 2M;
}
```

The lecture also demonstrates explicitly setting:

```nginx
add_header Cache-Control "public";
add_header Pragma "public";
```

The appropriate combination depends on the desired caching behavior and the resource being served.

# 26. Key Takeaways

1. **Client-side caching stores resources in the user's browser.**
2. Browser caching can reduce repeated communication with the NGINX server.
3. NGINX cannot completely control client-side caching.
4. NGINX communicates caching recommendations through HTTP response headers.
5. `Cache-Control` is the primary caching header.
6. `Cache-Control: public` allows caching by browsers and intermediate proxies.
7. `Cache-Control: private` limits caching to the end client and prevents intermediate proxy caching.
8. `max-age` specifies cache lifetime in **seconds**.
9. `Expires` specifies an absolute expiration date.
10. When both `max-age` and `Expires` are present, **`max-age` takes precedence**.
11. `Pragma` is a legacy caching-related header and can be retained for compatibility.
12. NGINX's `expires` directive can generate expiration information automatically.
13. Regular-expression locations can apply caching rules to groups of static file extensions.
14. The lab applies caching to CSS, JavaScript, JPG, JPEG, and PNG resources.
15. HTML is not cached by that rule unless `.html` is explicitly included.
16. Client-side caching is especially valuable for **high-traffic and geographically distributed production websites**.
