## 2. Passive vs. Active Health Checks

NginX supports two approaches to handling backend health.

Passive Health Checks

NginX observes failures while processing ordinary client requests. If a backend repeatedly fails, it can temporarily be marked unavailable according to the upstream failure parameters.

Open Source and Plus

Active Health Checks

NginX Plus periodically sends dedicated health-check requests to upstream servers and evaluates their responses independently of ordinary client traffic.

NginX Plus

### 2.1 Passive health checks

With passive health checks:

1. A client sends a request to NginX.
2. NginX forwards the request to a selected upstream server.
3. If the connection fails, NginX may retry the request against another eligible server.
4. NginX records qualifying failures.
5. The server can temporarily be marked unavailable after the configured failure threshold is reached.

Passive checks depend on actual traffic or connection attempts to reveal failures.

### 2.2 Active health checks

With active health checks, NginX Plus periodically sends a dedicated request to each server in the configured upstream group.

The process is:

1. NginX Plus sends a health-check request to an upstream server.
2. The server returns an HTTP response, or the connection fails.
3. NginX Plus evaluates the response against the configured health-check criteria.
4. If the response satisfies the criteria, the health check passes.
5. If the response fails the criteria, the health check fails.
6. The server can be marked unhealthy after the configured number of failed checks.
7. An unhealthy server is excluded from normal traffic until it satisfies the recovery criteria.

The important advantage is that active health checks can detect certain failures even when no users are accessing the application.

Product limitation: The built-in upstream `health_check` and `match` features described in this lecture are NginX Plus capabilities. They are not available as built-in upstream health-check directives in standard NginX Open Source.

## 3. The `health_check` Directive

The `health_check` directive enables active health checking for an upstream server group.

The instructor introduces it inside a `location` block that also proxies requests to an upstream group.

### 3.1 Basic configuration

```
http {
    upstream backend {
        server 192.0.2.10:8080;
        server 192.0.2.11:8080;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend;
            health_check;
        }
    }
}
```

In this example:

- `upstream backend` defines the backend server group.
- Each `server` directive identifies a backend address and port.
- `proxy_pass http://backend` forwards client requests to the upstream group.
- `health_check` enables active health checking for that upstream group from the applicable location.

### 3.2 Default health-check behavior

According to the lecture, the basic `health_check` directive uses these defaults:

- Health-check interval: five seconds.
- Request URI: `/`.
- Accepted HTTP status codes: the range from 200 through 399.
- Unsuccessful communication or an invalid response: the check fails.

For example, if an upstream server returns an HTTP status code outside the accepted range, the health check can fail and the server can be marked unhealthy after the applicable failure threshold is reached.

The instructor emphasizes that NginX Plus does not need to wait for a client request to discover a problem when active health checks are configured.

Practical note: A successful health-check response indicates that the server satisfies the configured checks. It does not guarantee that every application feature is functioning correctly.

## 4. Configuring Active Health-Check Parameters

The lecture introduces four main parameters for controlling active health checks: `port`, `interval`, `fails`, and `passes`. It also explains how to customize the request URI and validate the response using a `match` block.

### 4.1 The `interval` parameter

The `interval` parameter controls how frequently NginX Plus sends health-check requests.

The lecture identifies the default interval as five seconds.

Example:

```
location / {
    proxy_pass http://backend;
    health_check interval=10s;
}
```

With `interval=10s`, health checks are scheduled at a ten-second interval.

Other examples include:

```
health_check interval=3s;
health_check interval=30s;
```

Choose the interval according to how quickly the application needs to detect failures and how much additional monitoring traffic is acceptable.

### 4.2 The `fails` parameter

The `fails` parameter specifies how many consecutive unsuccessful health checks are required before a server is considered unhealthy.

The instructor identifies the default as one failed check.

Example:

```
location / {
    proxy_pass http://backend;
    health_check fails=3;
}
```

With `fails=3`, the server must fail three consecutive health checks before it is considered unhealthy.

This helps prevent a single transient failure from immediately taking a backend out of service.

### 4.3 The `passes` parameter

The `passes` parameter specifies how many consecutive successful health checks are required before a previously unhealthy server is considered healthy again.

The instructor uses two consecutive successful checks as an example.

```
location / {
    proxy_pass http://backend;
    health_check passes=2;
}
```

With `passes=2`, a server must pass two consecutive checks before it can return to normal service.

This can reduce the risk of sending traffic to a backend that is only recovering temporarily or inconsistently.

### 4.4 Combining the parameters

The following example combines the three timing and threshold parameters:

```
location / {
    proxy_pass http://backend;

    health_check interval=10s fails=3 passes=2;
}
```

This configuration means:

- Send health checks every ten seconds.
- Mark a server unhealthy after three consecutive failed checks.
- Require two consecutive successful checks before restoring an unhealthy server.

The exact detection and recovery time depends on when the failures occur relative to the checking schedule.

### 4.5 The `port` parameter

The `port` parameter allows health checks to use a port different from the port normally used for proxied client traffic.

For example:

```
location / {
    proxy_pass http://backend;
    health_check port=8080;
}
```

In this example, NginX Plus sends the health-check request to port `8080` on each upstream server.

This is useful when the application exposes a dedicated health-check listener on a separate port.

The backend servers must actually listen on that port, and the load balancer must be able to reach it.

### 4.6 The `uri` parameter

By default, the health-check request targets the root URI `/`. The `uri` parameter allows you to specify another endpoint.

For example:

```
location / {
    proxy_pass http://backend;

    health_check uri=/health;
}
```

The health-check request will target `/health` on each backend server.

For example, if an upstream server is configured as:

```
server 192.0.2.10:8080;
```

The health-check request targets the `/health` path on that server's configured address and health-check port.

The lecture also describes using an application-specific URI such as `/some/path`.

A dedicated endpoint is often preferable because it can be designed to verify the application's readiness rather than merely confirming that the web server responds.

Important: The health-check endpoint must return a response that satisfies the configured status, header, and body conditions.

## 5. Custom Health-Check Conditions with `match`

The lecture explains that NginX Plus allows custom conditions to determine whether an HTTP response represents a healthy backend.

These conditions are defined using the `match` block inside the `http` context.

A health check can validate:

- HTTP status codes.
- HTTP response headers.
- Response-body content.

This provides more control than accepting a response based only on its status code.

### 5.1 Define a custom match condition

Consider the following example:

```
http {
    match server_ok {
        status 200-399;
        body !~ "maintenance mode";
    }

    upstream backend {
        server 192.0.2.10:8080;
        server 192.0.2.11:8080;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend;
            health_check uri=/health match=server_ok;
        }
    }
}
```

This example illustrates the concepts explained in the lecture.

The `match` block defines a condition named `server_ok`.

The condition requires:

1. An HTTP status code between 200 and 399.
2. A response body that does not match the regular expression `maintenance mode`.

The health check references the condition using:

```
health_check uri=/health match=server_ok;
```

If the response fails either condition, the health check fails.

### 5.2 Understanding the `status` condition

The `status` condition specifies the acceptable HTTP response status code or range.

Example:

```
match server_ok {
    status 200-399;
}
```

This accepts status codes in the range from 200 through 399.

Responses outside this range fail the status condition.

### 5.3 Understanding the `body` condition

The `body` condition evaluates the response body using a regular expression.

For example:

```
match server_ok {
    status 200-399;
    body !~ "maintenance mode";
}
```

The expression `!~` means that the response body must not match the specified regular expression.

In this case, a response containing text matching `maintenance mode` fails the body condition.

This can be useful when a server returns HTTP 200 but serves a maintenance page instead of its normal application response.

### 5.4 Validating response headers

The `match` block can also validate response headers.

For example:

```
match server_ok {
    status 200-399;
    header Content-Type = text/html;
    body !~ "maintenance mode";
}
```

This adds a condition requiring the `Content-Type` response header to match `text/html`.

The lecture explains that a `match` block can contain:

- One status condition.
- One body condition.
- Multiple header conditions.

All specified conditions must be satisfied for the response to pass the health check.

Important: The examples in this section demonstrate NginX Plus functionality. The `match` directive is not a built-in upstream health-check feature in standard NginX Open Source.

## 6. Understanding the Sample NginX Plus Configuration

In the final part of the lecture, the instructor presents a larger configuration file named `activehelp.conf`.

The instructor does not run the configuration in a practical lab because NginX Plus is a commercial product and requires an appropriate subscription and installation setup. Instead, the configuration is used to demonstrate how the concepts fit together.

The sample includes:

- Worker-process and event settings.
- Detailed access logging.
- Two upstream groups.
- Shared upstream memory zones.
- Upstream state files.
- Reverse-proxy configuration.
- Separate routing for PHP requests.
- Active health checks for both upstream groups.
- Custom error pages for server errors.

### 6.1 Worker-process and event configuration

The instructor begins with the standard NginX configuration structure.

```
user nginx;
worker_processes auto;

error_log /var/log/nginx/error.log;

events {
    worker_connections 1024;
}
```

The directives configure the NginX worker user, worker-process count, error-log location, and maximum connections per worker.

The exact worker user and file paths must match the operating system and installation.

### 6.2 MIME types and detailed access logging

The sample includes MIME types and defines a custom access-log format.

The instructor's log format includes information such as:

- Client IP address.
- Remote username.
- Local timestamp.
- Request and HTTP status.
- Response-body bytes sent.
- HTTP referrer.
- HTTP user agent.
- Forwarded client IP information.
- Upstream connection time.
- Upstream header-response time.
- Upstream response time.
- Request URI.

An illustrative configuration is:

```
http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    log_format main
        '$remote_addr - $remote_user [$time_local] '
        '"$request" $status $body_bytes_sent '
        '"$http_referer" "$http_user_agent" '
        '"$http_x_forwarded_for" '
        'connect=$upstream_connect_time '
        'header=$upstream_header_time '
        'response=$upstream_response_time '
        'uri="$request_uri"';

    access_log /var/log/nginx/access.log main;
}
```

This is an illustrative reconstruction of the log format described in the lecture, not an exact copy of the instructor's original configuration.

The upstream timing variables help diagnose backend performance:

| Variable                  | Meaning                                                          |
| ------------------------- | ---------------------------------------------------------------- |
| `$upstream_connect_time`  | Time required to establish a connection with an upstream server. |
| `$upstream_header_time`   | Time until the upstream response headers are received.           |
| `$upstream_response_time` | Time spent receiving the upstream response.                      |

These values can help distinguish connection problems from slow application responses.

### 6.3 Define two upstream groups

The instructor defines two upstream groups:

- `cluster_fnt`
- `cluster_back`

Each group includes a shared memory zone and a state-file reference.

Conceptually, the configuration follows this structure:

```
upstream cluster_fnt {
    zone cluster_fnt 64k;
    state /var/lib/nginx/state/cluster_fnt.state;
}

upstream cluster_back {
    zone cluster_back 64k;
    state /var/lib/nginx/state/cluster_back.state;
}
```

These snippets illustrate the structure described in the lecture. They require the appropriate NginX Plus functionality and valid state files.

Shared memory zone: The `zone` directive allocates shared memory for upstream configuration and state. In this example, each zone has a size of 64 KB.

State file: The `state` directive specifies a file used to preserve dynamically managed upstream server configuration. In the instructor's example, the state files contain backend server information, including server addresses and failure-related parameters.

The instructor uses separate state files for the frontend and backend groups.

This approach is useful when upstream servers are managed dynamically rather than being listed directly in the static configuration.

The state-file paths must be accessible to NginX, and the relevant files and directories must be configured correctly for the deployment.

### 6.4 Configure reverse-proxy routing

The instructor then configures a server block to forward ordinary requests to the frontend upstream group.

The basic structure is:

```
server {
    listen 80;

    location / {
        proxy_set_header Host $host;
        proxy_pass http://cluster_fnt;
    }
}
```

The `proxy_set_header` directive forwards the original hostname to the backend, while `proxy_pass` directs requests to the configured frontend upstream.

The instructor also defines a separate location for PHP files that forwards matching requests to the backend upstream group.

A simplified illustrative example is:

```
location ~ \.php$ {
    proxy_set_header Host $host;
    proxy_pass http://cluster_back;
}
```

This example demonstrates routing requests matching the PHP-file pattern to a different upstream group.

It does not execute PHP locally; it proxies matching requests to the configured backend servers. Actual PHP application routing depends on the application architecture and the backend server configuration.

### 6.5 Add active health checks to each upstream location

The instructor configures active health checks separately for the frontend and backend upstream groups.

The structure follows this pattern:

```
location @fnt {
    proxy_set_header Host $host;
    proxy_pass http://cluster_fnt;

    health_check uri=/health;
}
```

A corresponding location is configured for the backend upstream:

```
location @back {
    proxy_set_header Host $host;
    proxy_pass http://cluster_back;

    health_check uri=/health;
}
```

These are illustrative examples of the described configuration pattern, not a complete reconstruction of the original file.

The key idea is that each upstream group has its own proxy configuration and health-check settings.

The URI can be customized to match the health endpoint exposed by the relevant application.

For example, the frontend and backend applications could use different endpoints if their health requirements differ.

### 6.6 Configure custom error pages

The instructor also defines a custom error page for server-side errors, including HTTP status codes 500, 502, 503, and 504.

An illustrative configuration is:

```
server {
    listen 80;

    error_page 500 502 503 504 /50x.html;

    location = /50x.html {
        root /etc/nginx;
    }
}
```

This configuration directs those error responses to `/50x.html`, served from the specified directory.

The custom HTML file must exist at the corresponding path.

These error pages can provide a consistent response when an application server fails or the load balancer cannot successfully complete a request.

## 7. Practical Notes and Best Practices

### 7.1 Use an application-specific health endpoint

A dedicated health endpoint such as `/health` is generally more useful than checking only `/`.

The endpoint should reflect the condition you want to monitor. For example, it might verify that the application can serve requests and that critical dependencies are available.

Avoid making the endpoint unnecessarily expensive to execute.

### 7.2 Choose appropriate health-check thresholds

The `interval`, `fails`, and `passes` parameters control how quickly NginX Plus detects failures and restores recovered servers.

- Shorter intervals can detect failures sooner but generate more health-check traffic.
- Higher failure thresholds tolerate transient errors but can delay failure detection.
- Higher recovery thresholds help prevent a server from returning to service after only one successful check.

The right values depend on the application's recovery behavior and availability requirements.

### 7.3 Treat health checks and application monitoring as complementary

A successful health check does not guarantee that every application operation is working correctly.

For example, a server might respond successfully to `/health` while a critical database-dependent operation is failing.

Design health endpoints to reflect the level of readiness that matters for your application.

### 7.4 Keep logs useful for troubleshooting

Detailed upstream timing information can help you identify:

- Connection failures.
- Slow backend response headers.
- Slow application responses.
- Differences in performance between upstream servers.

Use log formats that provide sufficient diagnostic information without unnecessarily increasing storage consumption or exposing sensitive data.

### 7.5 Validate the configuration before deployment

After modifying NginX configuration, run:

```
sudo nginx -t
```

For a production NginX Plus installation, also verify that the active health-check directives, upstream state files, and any dynamic configuration mechanisms are supported and configured correctly.

## 8. Common Mistakes and Warnings

| Mistake                                                  | Explanation                                                                                  |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Using `health_check` in standard NginX Open Source       | The built-in upstream active health-check feature described here requires NginX Plus.        |
| Using an incorrect health-check URI                      | The endpoint must exist and return a response satisfying the configured conditions.          |
| Setting an inappropriate interval                        | Very frequent checks can increase monitoring traffic; long intervals delay detection.        |
| Returning HTTP 200 for an unhealthy application          | A status-only check may incorrectly consider the application healthy.                        |
| Forgetting that all `match` conditions must pass         | A failed status, header, or body condition causes the health check to fail.                  |
| Using invalid state-file paths                           | The state file must be available and configured appropriately for the NginX Plus deployment. |
| Assuming active checks guarantee application correctness | Health checks only evaluate the conditions they are configured to test.                      |
