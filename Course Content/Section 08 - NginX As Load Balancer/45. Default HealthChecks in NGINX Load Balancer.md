## 2. What Is a Health Check?

A health check is a mechanism used to assess whether a backend server is available and able to handle requests.

In a load-balancing environment, multiple application servers are configured inside an upstream group. The load balancer needs to determine which servers can successfully receive and process traffic.

The lecture describes a health check as a scheduled rule that sends the same request to each member of a server group and evaluates the responses.

Conceptually, the process is:

1. A health-check mechanism attempts to communicate with a backend server.
2. The server's connection or response is evaluated.
3. The result helps determine whether the server is considered healthy or unavailable.
4. Traffic is directed to eligible servers according to the load-balancing configuration.

A successful health check indicates that the server satisfies the configured health criteria. A failed check indicates that the server may be unavailable or unable to respond correctly.

The exact criteria depend on the health-check mechanism being used.

### 2.1 TCP health checks

A TCP health check evaluates whether a TCP connection can be established with the backend server.

For example, if a backend NginX server listens on port 80, a TCP connection check can help determine whether that port is accepting connections.

A successful TCP connection does not necessarily mean that the application is functioning correctly. It only establishes that the TCP connection succeeded.

### 2.2 HTTP health checks

An HTTP health check evaluates the backend through an HTTP request and response.

The lecture mentions HTTP `GET` and `POST` methods as possible health-check request methods.

For example, an HTTP check might request:

```
GET /health HTTP/1.1
Host: app.example.com
```

The response can then be evaluated to determine whether the application satisfies the health criteria.

The `/health` endpoint in this example is illustrative; the lecture does not configure such an endpoint.

HTTP health checks can provide more application-level information than TCP checks because they can evaluate an HTTP response rather than merely checking whether a connection can be established.

Important distinction: The instructor describes HTTP as the general health-check type when TCP checking is not explicitly configured. In standard NginX Open Source, however, the default upstream failure handling is passive; it does not automatically issue periodic HTTP `GET` or `POST` health-check requests to every backend.

## 3. Types of Health Checks in NginX

The lecture identifies two types of health checks:

- Passive health checks.
- Active health checks.

Passive Health Checks

NginX observes failures during normal attempts to communicate with a backend server and uses the configured failure criteria to determine whether the server should temporarily be avoided.

NginX Open Source

Active Health Checks

A health-check mechanism actively sends periodic checks to backend servers to evaluate their health independently of ordinary client requests.

NginX Plus

### 3.1 Passive health checks

Passive health checking is available in NginX Open Source.

With passive health checks, NginX observes failures that occur while processing actual client requests. It can temporarily mark a backend as unavailable according to parameters such as `max_fails` and `fail_timeout`.

For example, if a backend repeatedly fails to respond, NginX can temporarily avoid sending additional requests to it.

The instructor emphasizes that passive health checking does not require a separate active-check configuration in the load balancer.

### 3.2 Active health checks

Active health checks periodically send dedicated requests to backend servers to determine whether they are healthy.

The checks can run independently of normal client traffic, allowing a load balancer to detect certain failures before a client request encounters them.

According to the lecture, active health checks require NginX Plus, the commercial version of NginX.

For standard NginX Open Source, active upstream health checks are not available as a built-in feature. Additional modules or external monitoring systems may be used when active checking is required.

### 3.3 Comparison

| Characteristic                 | Passive health checks                                                                                     | Active health checks                                                        |
| ------------------------------ | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| How failures are detected      | Through normal traffic and connection attempts                                                            | Through dedicated health-check requests                                     |
| Requires client traffic        | Yes, failures are observed during real requests                                                           | Not necessarily                                                             |
| Available in NginX Open Source | Yes                                                                                                       | Not as a built-in upstream feature                                          |
| Available in NginX Plus        | Yes                                                                                                       | Yes                                                                         |
| Recovery handling              | Backend can become eligible again after the applicable failure period and a successful subsequent attempt | Dedicated checks can identify recovery before normal traffic is routed back |

## 4. Default Health-Check Behavior in NginX

One of the most important points in this lecture is that NginX can respond to backend failures even when no explicit health-check configuration has been added.

The instructor's existing upstream configuration contains two application servers but no additional health-check directives.

A simplified version is:

```
http {
    upstream app_server {
        server BACKEND_IP_1;
        server BACKEND_IP_2;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://app_server;
        }
    }
}
```

This configuration defines a backend server group and forwards requests to it.

### 4.1 What happens when a backend fails?

Suppose the two backends are:

- Server A: Brownie website.
- Server B: Default NginX welcome page.

Initially, both servers are running, so NginX distributes requests between them.

If Server A stops, requests directed to it may fail. NginX's passive failure-handling mechanism can temporarily avoid that server after the applicable failure conditions are met.

Subsequent requests can then be served by Server B.

### 4.2 Default failure-handling parameters

NginX upstream servers support parameters such as:

```
upstream app_server {
    server BACKEND_IP_1 max_fails=1 fail_timeout=10s;
    server BACKEND_IP_2;
}
```

Here:

- `max_fails=1` sets the number of unsuccessful attempts that triggers the failure condition within the applicable period.
- `fail_timeout=10s` specifies the period used for failure counting and how long the server is considered unavailable after the relevant failures.

These values are an illustrative configuration, not the configuration used in the lecture.

For standard upstream servers, the defaults are generally `max_fails=1` and `fail_timeout=10s`, subject to special cases such as a single-server upstream group.

Important: Passive health checking is not equivalent to continuously probing all backends. NginX needs actual traffic or connection attempts to observe failures. A server may have recovered without NginX knowing until another attempt is made.

The instructor observes that NginX is no longer successfully serving requests through the stopped Brownie backend and that the other backend continues to respond.

The exact timing and sequence depend on the failure parameters, the request pattern, and whether the backend has become reachable again.

## 6. Important Clarification: How Passive Health Checks Actually Work

The instructor makes an important distinction during the demonstration: although NginX is often described as avoiding failed servers automatically, its behavior should not be interpreted as an unconditional guarantee that every request to an unavailable server will be prevented.

With the default Round Robin configuration and default passive failure handling:

1. NginX selects an upstream server for a request.
2. It attempts to connect to that server and proxy the request.
3. If the connection fails, NginX may try another eligible upstream server, depending on the failure and retry configuration.
4. After the applicable failure criteria are met, NginX can temporarily avoid the failed server.
5. After the failure timeout, the server can become eligible for selection again.
6. A subsequent attempt determines whether it is reachable.

This explains why a server may be selected again after some time, even if it previously failed.

It also explains the instructor's observation that NginX can take some time to resume sending requests to a recovered server.

### 6.1 Why might a request still fail?

A passive health check cannot guarantee that every client request will succeed.

A request may fail when:

- NginX selects a backend that is currently unavailable.
- The failure has not yet met the configured threshold.
- NginX cannot retry the request against another backend under the applicable conditions.
- The remaining backends are also unavailable.
- The backend is reachable at the TCP level but its application is returning errors.

Retry behavior also depends on `proxy_next_upstream` and the type of request. Retrying a request that may already have been processed can be unsafe for some non-idempotent operations, such as certain payment or transaction requests.

## 7. Where Health-Check Configuration Is Applied

The instructor emphasizes that any load-balancer health-check configuration discussed in this section is applied on the load-balancer machine, not directly on the application servers.

For example, a passive health-check configuration belongs in the load balancer's upstream block:

```
http {
    upstream app_server {
        server BACKEND_IP_1 max_fails=2 fail_timeout=15s;
        server BACKEND_IP_2 max_fails=2 fail_timeout=15s;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://app_server;
        }
    }
}
```

In this illustrative example:

- `max_fails=2` specifies the failure threshold.
- `fail_timeout=15s` specifies the failure-counting period and the temporary unavailability period.

No corresponding health-check configuration is required in the backend NginX configuration simply to enable these passive upstream failure parameters.

The backend application still needs to run correctly and accept requests on the configured addresses and ports.

## 8. Common Mistakes and Warnings

### Mistake 1: Assuming default behavior means continuous active checking

Default passive failure handling does not mean that NginX continuously sends dedicated health-check requests to every backend.

NginX Open Source generally learns about failures while processing normal traffic.

### Mistake 2: Assuming a recovered server immediately receives traffic

After a backend recovers, NginX may not use it immediately. The failure timeout and the timing of subsequent requests can affect when the server is tried again.

### Mistake 3: Confusing a TCP connection with application health

A server can accept TCP connections while its application is malfunctioning. An HTTP-level check can evaluate application responses more directly, provided the check is designed appropriately.

### Mistake 4: Expecting passive health checks to eliminate all errors

A request can still encounter a failure before NginX recognizes that a backend is unavailable. Failover depends on upstream configuration, retry eligibility, and the availability of other servers.

### Mistake 5: Configuring health checks on the wrong machine

The load-balancer configuration controls upstream selection and failure handling. For this lab, the relevant configuration is on the Ubuntu Load Balancer machine.

## 9. Summary

This lecture explains the default health-check and failure-handling behavior of NginX when acting as a load balancer.

The key takeaways are:

1. Health checks help determine whether backend servers are available to handle traffic.
2. TCP checks evaluate connection availability, while HTTP checks can evaluate application-level responses.
3. Passive health checking is available in NginX Open Source and observes failures during normal traffic.
4. Active upstream health checks are available as a built-in feature in NginX Plus, rather than standard NginX Open Source.
5. NginX can temporarily avoid failed backend servers through its default passive failure-handling behavior.
6. When a backend recovers, it can become eligible for traffic again after the applicable failure period and a subsequent successful attempt.
7. The lab demonstrates this behavior by stopping and restarting the NginX service on the Brownie application server.
8. Health-check and upstream failure-handling settings are configured on the load balancer, while the backend servers must remain reachable and operational.

Main takeaway: NginX Open Source provides basic passive upstream failure handling by default. Understanding how that mechanism works is essential before configuring more advanced health-check behavior in later lectures.
