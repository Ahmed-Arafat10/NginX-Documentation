# Section 08 — NginX as Load Balancer

## Lecture 46: Passive Health Checks in NginX

Technical documentation based on the lecture transcript

## 1. Overview

In the previous lecture, we explored the default health-check behavior of NginX when a backend application server becomes unavailable and later recovers.

In this lecture, we examine passive health checks in greater detail, focusing on the two upstream server parameters that control failure handling:

- `max_fails`
- `fail_timeout`

Passive health checks allow NginX to observe failures during normal client requests and temporarily avoid backend servers that repeatedly fail.

The lecture continues using the same three-machine lab:

- Application Server 1: Hosts the Brownie website.
- Application Server 2: Hosts the default NginX welcome page.
- Load Balancer: Distributes incoming requests between the two application servers.

The instructor demonstrates how to customize failure thresholds, stop a backend server, observe traffic distribution, and restore the server.

## 2. Key Concepts

| Concept              | Description                                                                                                                      |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Passive health check | Detects backend failures while processing normal client requests.                                                                |
| `max_fails`          | Specifies the number of unsuccessful attempts required to mark a server unavailable within the configured failure period.        |
| `fail_timeout`       | Defines the failure-counting period and the duration for which the server is considered unavailable after the relevant failures. |
| Unhealthy server     | A backend that NginX temporarily avoids because it has met the configured failure criteria.                                      |
| Server recovery      | The process by which a previously unavailable backend becomes eligible for traffic again.                                        |
| Upstream group       | A named group of backend servers configured in the NginX `http` context.                                                         |

## 3. How Passive Health Checks Work

Passive health checks monitor backend servers as NginX processes client requests.

Unlike active health checks, passive checks do not require NginX to send separate, periodic health-check requests. Instead, NginX observes whether its attempts to communicate with a backend succeed or fail.

The general process is:

1. NginX selects a backend server from the upstream group.
2. NginX attempts to forward the client request to that server.
3. If the request encounters a qualifying failure, NginX may retry it against another eligible backend, depending on the retry configuration.
4. NginX counts qualifying failures according to the configured parameters.
5. Once the failure threshold is reached within the applicable period, NginX can temporarily mark the backend unavailable.
6. After the failure timeout expires, the backend can become eligible for selection again.
7. A subsequent connection attempt determines whether the recovered server can successfully handle traffic.

The exact behavior depends on the upstream configuration, the type of failure, and the request's retry eligibility.

## 4. Understanding the Failure Scenario

Suppose the upstream group contains two application servers:

- Application Server 1: Brownie website.
- Application Server 2: Default NginX HTML page.

Initially, both servers are running, and NginX distributes incoming requests between them.

Now suppose the Brownie server goes offline.

The instructor explains the following sequence:

1. Request A is directed to the Brownie server.
2. The request fails because the server is unavailable.
3. NginX may retry the request against Application Server 2.
4. If the retry succeeds, the client receives the response from Application Server 2.
5. Another request may initially be directed to the Brownie server again.
6. Once enough qualifying failures occur, NginX temporarily avoids the Brownie server.
7. Requests can then be served by the remaining available backend.

The important distinction is that a failed request does not necessarily mean NginX immediately stops using that server. The behavior depends on the configured failure threshold and timeout.

## 5. Passive Health-Check Parameters

The lecture focuses on two parameters that can be configured directly on the `server` directives inside an upstream group.

### 5.1 The `fail_timeout` parameter

The `fail_timeout` parameter has two related purposes:

1. It defines the period during which failed attempts are counted when evaluating the server's failure threshold.
2. It defines how long the server is considered unavailable after the relevant failure condition is reached.

The instructor uses a default value of 10 seconds and demonstrates how to configure a longer period.

For example:

```
upstream app_server {
    server 192.0.2.130 fail_timeout=30s;
    server 192.0.2.192;
}
```

Here, the first server has a `fail_timeout` of 30 seconds.

Other valid time-unit examples include:

```
fail_timeout=60s;
fail_timeout=5m;
```

These illustrate 60 seconds and five minutes, respectively, when used as parameter values in a `server` directive. In actual configuration, the parameters must be attached to the appropriate upstream server entry rather than written as standalone directives.

#### What does `fail_timeout=30s` mean?

Suppose the first backend fails repeatedly and the failure threshold is reached.

NginX can temporarily avoid that server for the configured failure timeout. After that period, the server can become eligible for another connection attempt.

If the backend has recovered, a subsequent request may succeed and traffic can resume.

Important clarification: NginX does not necessarily send requests continuously to a failed backend for the entire 30-second period before marking it unavailable. The failure threshold is controlled by `max_fails`, while `fail_timeout` defines the relevant counting and unavailability periods.

### 5.2 The `max_fails` parameter

The `max_fails` parameter specifies how many unsuccessful attempts must occur within the `fail_timeout` period before NginX considers the server unavailable.

The instructor identifies the default as one failure and demonstrates increasing the threshold to five.

Example:

```
upstream app_server {
    server 192.0.2.130 max_fails=5;
    server 192.0.2.192;
}
```

With `max_fails=5`, five qualifying unsuccessful attempts within the applicable failure period can cause the first server to be marked unavailable temporarily.

A higher threshold means that more failures must occur before NginX avoids the backend.

A lower threshold allows NginX to react more quickly to repeated failures but may also make it more sensitive to intermittent problems.

#### Combining `max_fails` and `fail_timeout`

The instructor demonstrates configuring both parameters together.

```
upstream app_server {
    server 192.0.2.130 max_fails=5 fail_timeout=30s;
    server 192.0.2.192;
}
```

In this configuration:

- `max_fails=5` specifies the failure threshold.
- `fail_timeout=30s` defines the failure-counting period and the period of temporary unavailability after the threshold is reached.

If the first backend experiences five qualifying failures within the applicable 30-second period, NginX can temporarily mark it unavailable.

The second backend remains available to receive requests, assuming it is healthy and reachable.

### 5.3 Default values

The lecture identifies the following default values for ordinary upstream servers:

| Parameter      | Default | Purpose                                                              |
| -------------- | ------- | -------------------------------------------------------------------- |
| `max_fails`    | `1`     | Number of qualifying failures required to mark a server unavailable. |
| `fail_timeout` | `10s`   | Failure-counting period and temporary unavailability duration.       |

These defaults apply to ordinary upstream servers subject to NginX's documented exceptions. For example, when an upstream group contains only one server, the `max_fails` and `fail_timeout` failure-counting behavior is ignored.

This single-server exception is important: a one-server upstream group does not provide another backend to which NginX can fail over.

## 6. Step-by-Step Lab: Configure Passive Health Checks

### Step 1: Open the load-balancer configuration

Connect to the Ubuntu Load Balancer machine and open the main NginX configuration:

```
sudo vi /etc/nginx/nginx.conf
```

Locate the upstream group used by the load balancer.

The instructor's group contains two application servers, with the Brownie server listed first.

### Step 2: Add the passive health-check parameters

Update the upstream configuration:

```
upstream app_server {
    server BROWNIE_SERVER_IP max_fails=5 fail_timeout=30s;
    server SECOND_APP_SERVER_IP;
}
```

Replace the placeholders with the actual backend IP addresses.

This configuration applies the custom failure threshold and timeout to the Brownie server. The second server retains its default parameters.

### Step 3: Validate the configuration

Before applying the changes, run:

```
sudo nginx -t
```

Confirm that the syntax test succeeds.

If the configuration is invalid, NginX reports the relevant error. Correct the issue before restarting or reloading the service.

### Step 4: Restart NginX on the load balancer

The instructor restarts the service to apply the updated configuration:

```
sudo systemctl restart nginx
```

Alternatively, reload NginX after validating the configuration:

```
sudo systemctl reload nginx
```

A reload is generally preferable for routine configuration changes when you want to minimize disruption to existing connections.

### Step 5: Verify both backends are working

Send requests to the load balancer:

```
curl http://LOAD_BALANCER_IP
curl http://LOAD_BALANCER_IP
```

The instructor observes that one request returns the Brownie website and the other returns the default NginX page.

This confirms that both backends are available and receiving traffic.

### Step 6: Stop NginX on the Brownie server

Connect to the first application server and stop its NginX service:

```
sudo systemctl stop nginx
```

Verify that the service has stopped:

```
sudo systemctl status nginx
```

The Brownie server should now be unavailable through its NginX service.

### Step 7: Observe passive failure handling

Return to the load balancer and issue several requests:

```
curl http://LOAD_BALANCER_IP
curl http://LOAD_BALANCER_IP
curl http://LOAD_BALANCER_IP
curl http://LOAD_BALANCER_IP
```

The instructor observes responses from the second application server after the Brownie backend becomes unavailable.

This demonstrates the load balancer's handling of a failed backend.

With the configured `max_fails=5`, the server is not supposed to be marked unavailable simply because one qualifying attempt fails. The threshold must be reached within the applicable `fail_timeout` period.

The exact number of client-visible failures can differ from the failure count because NginX may retry an eligible request against another backend.

### Step 8: Restart the Brownie server

Reconnect to the first application server and start NginX:

```
sudo systemctl start nginx
```

Confirm that it is running:

```
sudo systemctl status nginx
```

### Step 9: Test recovery

After the configured timeout has elapsed, send requests to the load balancer again:

```
curl http://LOAD_BALANCER_IP
curl http://LOAD_BALANCER_IP
curl http://LOAD_BALANCER_IP
curl http://LOAD_BALANCER_IP
```

The instructor observes that requests eventually return content from both servers again.

This illustrates that the previously failed backend can become eligible for traffic after its temporary unavailability period ends.

The exact recovery timing depends on the timeout, the request pattern, and whether the backend can successfully accept connections when NginX tries it again.

## 7. Important Notes and Best Practices

### 7.1 Configure the parameters on the load balancer

The `max_fails` and `fail_timeout` parameters belong on the upstream server definitions in the load balancer's configuration.

For this lab, there is no need to add these parameters to the application servers' own NginX configurations.

### 7.2 Choose failure thresholds carefully

A low `max_fails` value allows NginX to react quickly to backend failures, but intermittent connection problems can temporarily remove a server from rotation.

A higher value tolerates more failures before the backend is marked unavailable, but it may allow additional failed requests before the threshold is reached.

Choose values based on the application's availability requirements and the behavior of its backend servers.

### 7.3 Understand the effect of `fail_timeout`

Increasing `fail_timeout` changes both the window for counting failures and the period of temporary unavailability after the threshold is reached.

It does not directly control how often NginX probes the backend, because passive health checking does not use a dedicated periodic probe.

### 7.4 Understand the single-server exception

When an upstream group contains only one server, NginX does not apply the ordinary `max_fails` and `fail_timeout` failure-counting mechanism to mark that server unavailable.

A multi-server upstream group is therefore important when failover to another backend is required.

### 7.5 Do not confuse passive checks with active monitoring

Passive checks depend on failures observed during normal traffic. They do not guarantee that NginX will detect every application problem before a user encounters it.

If an application needs dedicated periodic checks against a health endpoint, evaluate whether NginX Plus or another monitoring solution is appropriate.

## 8. Common Mistakes and Warnings

| Mistake                                                               | Explanation                                                                                   |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Setting `max_fails` without understanding the timeout                 | The threshold is evaluated within the applicable `fail_timeout` period.                       |
| Assuming `fail_timeout` is a health-check interval                    | It controls failure counting and temporary unavailability, not periodic probing.              |
| Expecting the server to return to rotation immediately after recovery | The failure timeout and a subsequent connection attempt affect recovery behavior.             |
| Testing with only one upstream server                                 | The ordinary passive failure-counting behavior is ignored for a single-server upstream group. |
| Assuming every failed request reaches the client                      | NginX may retry an eligible request against another backend.                                  |
| Applying the configuration without testing it                         | Always validate the configuration using `nginx -t` before applying changes.                   |
