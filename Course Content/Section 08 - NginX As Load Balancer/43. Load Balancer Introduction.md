# Section 08 — NginX as Load Balancer

## Lecture 43: Load Balancer Introduction

Technical documentation based on the lecture transcript

## 1. Overview

Load balancing is a technique used to distribute incoming client requests across multiple backend servers instead of allowing a single server to handle all traffic.

Modern web applications may receive hundreds of thousands of concurrent requests from users. A single server can become overloaded, resulting in slow responses, failed requests, or application crashes.

A load balancer sits in front of a group of servers and distributes incoming traffic among them. This improves application availability, reliability, performance, and capacity utilization.

In this lecture, we explore:

- The definition and primary functions of load balancing.
- How load balancing distributes traffic across multiple servers.
- Common load-balancing algorithms.
- Session persistence and dynamic server-group configuration.
- Hardware versus software load balancers.
- How NginX works as a load balancer and reverse proxy.

## 3. How Load Balancing Works

The process works as follows:

1. A client sends a request to the application.
2. The request reaches the load balancer.
3. The load balancer selects an appropriate backend server using its configured algorithm.
4. The selected server processes the request.
5. The response is returned to the client through the load balancer.

These operations happen quickly and allow multiple servers to serve the same application.

Important: The backend servers are expected to run compatible versions of the application and have the resources needed to fulfill the requests routed to them.

## 4. Primary Functions of a Load Balancer

### 4.1 Distribute traffic efficiently

The primary responsibility of a load balancer is to distribute client requests or network traffic across multiple servers.

A server pool can contain two, 20, 200, or more servers. The required number depends on:

- Business requirements.
- Incoming traffic volume.
- Application resource requirements.
- The capacity of each server.

The goal is to prevent a single server from becoming an unnecessary bottleneck.

### 4.2 Ensure high availability and reliability

A load balancer should avoid sending traffic to servers that are unavailable.

For example, suppose five application servers are configured behind a load balancer. If one server goes offline, the load balancer can direct new requests to the remaining healthy servers.

This helps the application continue serving users without requiring every individual server to remain operational.

The mechanism used to determine whether a server is online or offline depends on the load balancer and its configuration. The instructor identifies this as a topic to explore later when configuring NginX.

### 4.3 Support failover

Failover is the process of redirecting traffic when a server becomes unavailable.

For example:

- Server 1, Server 2, Server 3, Server 4, and Server 5 initially receive traffic.
- Server 3 becomes unavailable.
- The load balancer stops directing new requests to Server 3 when its failure is detected.
- The remaining available servers continue handling requests.

Failover reduces the impact of individual server failures, although it does not guarantee uninterrupted service if the remaining servers lack sufficient capacity or the load balancer itself fails.

### 4.4 Support auto scaling and auto descaling

Application traffic changes throughout the day. A business may require 20 servers during peak hours but only two to five servers during quiet periods.

Keeping all 20 servers running during low-demand periods can waste computing resources and money.

Dynamic scaling addresses this problem:

- Scale up: Add application servers when traffic increases.
- Scale down: Remove application servers when traffic decreases.

The instructor emphasizes that scaling applies to the application servers behind the load balancer, not necessarily to the load balancer itself.

This behavior requires additional engineering and configuration. A load balancer does not automatically create or remove backend servers merely because it distributes traffic.

Dynamic server management should also preserve existing connections where possible and avoid removing servers before their active requests or sessions have been handled.

## 5. Load-Balancing Algorithms

A load-balancing algorithm determines which backend server receives an incoming request. Different algorithms use different criteria, such as request order, active connections, response time, bandwidth, or a hash key.

### 5.1 Round Robin

Round Robin distributes requests across servers sequentially.

Suppose the load balancer has three application servers:

```
Request 1  ──> Server A
Request 2  ──> Server B
Request 3  ──> Server C
Request 4  ──> Server A
Request 5  ──> Server B
Request 6  ──> Server C
```

The sequence repeats as new requests arrive.

Advantages

- Simple to understand and implement.
- Distributes requests sequentially across the configured servers.
- Works well when servers have similar capacities and requests have relatively similar processing requirements.

Limitations

Round Robin does not consider how busy a server already is. If Server B is processing several expensive requests, the algorithm may still send it another request simply because it is next in the sequence.

This can result in uneven resource utilization when request processing times or server capacities differ.

DNS Round Robin

The instructor also discusses DNS load balancing. A DNS configuration can associate a hostname with multiple IP addresses, allowing clients to receive different server addresses.

For example, a DNS zone might contain multiple A records:

```
app.example.com.  300  IN  A  192.0.2.10
app.example.com.  300  IN  A  192.0.2.11
app.example.com.  300  IN  A  192.0.2.12
```

These addresses represent three application servers.

DNS-based distribution differs from a reverse-proxy load balancer: DNS returns address information to clients, while a proxy such as NginX receives the application request and forwards it to a selected backend.

Clarification: Round Robin remains a widely used software load-balancing algorithm. It is also the default upstream load-balancing method in standard NginX Open Source. The lecture's suggestion that modern load balancers do not use it should not be interpreted as a universal rule.

### 5.2 Least Connections

The Least Connections algorithm sends a new request to the server with the fewest active connections.

For example:

| Server   | Active connections |
| -------- | ------------------ |
| Server A | 12                 |
| Server B | 4                  |
| Server C | 8                  |

Server B would be selected because it has the fewest active connections.

This method considers the current connection count, unlike basic Round Robin.

Advantages

- Can distribute work more effectively when requests take different amounts of time.
- Helps avoid sending additional connections to servers that already have many active connections.

Limitations

- Connection count is not a perfect measure of server load. A single connection can consume more resources than many other connections.
- The algorithm does not inherently measure CPU usage or application response time.

NginX Open Source supports Least Connections using the `least_conn` directive.

```
upstream backend_servers {
    least_conn;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}
```

This defines an upstream server group and instructs NginX to prefer the server with the fewest active connections.

### 5.3 Least Response Time

The Least Response Time method considers response speed together with the number of active connections.

The objective is to select a server that can respond quickly while also accounting for its current connection load.

Conceptually, this method considers two factors:

1. How quickly the server responds.
2. How many active connections the server currently handles.

The instructor describes this as a more sophisticated approach than Least Connections and associates it with NginX Plus.

NginX Plus note: NginX Plus provides additional load-balancing capabilities, including the `least_time` directive. The precise selection criteria depend on the configured parameters, such as response time and connection count.

Example:

```
upstream backend_servers {
    least_time header;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}
```

Here, `least_time header` is a NginX Plus feature that considers the time to receive the response header, alongside connection count, when selecting a server.

This directive is not available in NginX Open Source.

### 5.4 Least Bandwidth

The Least Bandwidth method selects the server currently handling the lowest amount of network traffic, measured in megabytes per second in the lecture's explanation.

For example:

| Server   | Current traffic |
| -------- | --------------- |
| Server A | 18 MB/s         |
| Server B | 5 MB/s          |
| Server C | 12 MB/s         |

Under this approach, Server B would be preferred because it is serving the least traffic.

This method is useful conceptually when bandwidth utilization is an important indicator of load.

Important implementation note: Least Bandwidth is not a standard built-in upstream selection directive in NginX Open Source. Implementing bandwidth-aware routing may require an external load balancer, specialized functionality, or custom monitoring and routing logic.

### 5.5 Hashing

Hashing selects a backend server based on a defined key. The key can include information such as:

- Client IP address.
- Request URL.
- Other request attributes supported by the load-balancing implementation.

The key is processed to determine the server selection.

For example, requests associated with the same client IP address can be directed consistently to the same backend under an appropriate hashing configuration.

NginX Open Source supports IP-based hashing through `ip_hash`:

```
upstream backend_servers {
    ip_hash;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}
```

This method is useful when requests from the same client should tend to reach the same server.

Clarification: A hashing algorithm does not necessarily guarantee that every request reaches a particular server under all conditions. Server availability, membership changes, and the chosen hashing mechanism can affect the result.

### 5.6 Algorithm comparison

| Algorithm           | Selection criterion                  | Availability in NginX                         |
| ------------------- | ------------------------------------ | --------------------------------------------- |
| Round Robin         | Sequential distribution              | Open Source and Plus                          |
| Least Connections   | Fewest active connections            | Open Source and Plus                          |
| Least Response Time | Response-time and connection metrics | Plus; uses `least_time`                       |
| Least Bandwidth     | Lowest current bandwidth usage       | Not a standard Open Source upstream directive |
| Hashing             | A defined key, such as client IP     | Open Source and Plus; includes `ip_hash`      |

The algorithms above represent different ways of distributing traffic. No single method is optimal for every workload.

## 6. Related Load-Balancing Fundamentals

### 6.1 Session Persistence

Session persistence ensures that requests belonging to a particular user session continue to reach the same backend server for the required duration.

For example:

1. A user sends an initial request.
2. The load balancer routes the request to Server A.
3. The user sends another request.
4. The load balancer routes the subsequent request to Server A again.

The objective is to maintain continuity between the user and the server handling the session.

#### Why session persistence matters

Consider an online shopping application.

A user adds several products to a shopping cart and continues browsing. If the application stores session information locally on Server A, sending the user's next request to Server B may cause problems if Server B does not have access to that session information.

Potential consequences include:

- Missing shopping-cart items.
- Lost session state.
- Unexpected application behavior.
- Failed or interrupted transactions.

For applications that maintain session data locally on a particular server, directing requests consistently to that server can be essential.

#### Session persistence in NginX

The instructor identifies NginX upstream configuration as the area where session persistence will be discussed in more detail.

An IP-based hashing example is:

```
upstream backend_servers {
    ip_hash;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
}
```

This configuration attempts to keep requests from the same client IP address associated with the same backend server.

However, `ip_hash` is not identical to full session persistence in every situation. Users behind the same NAT gateway may share an IP address, and a server failure or upstream membership change can affect routing.

Where possible, applications should use shared session storage or stateless authentication so that any healthy backend can handle a request. This reduces dependence on sticky routing.

### 6.2 Dynamic Configuration of Server Groups

Dynamic server-group configuration refers to adding or removing backend servers as application demand changes. This is closely related to auto scaling and auto descaling.

The lecture highlights cloud environments such as:

- Amazon Web Services (AWS) Elastic Compute Cloud (EC2).
- Google Cloud servers.
- Google Cloud Load Balancing.

These environments allow organizations to adjust computing capacity based on actual requirements.

For example:

- During peak traffic, additional application servers are brought online.
- During low traffic, unnecessary servers are removed.
- The load balancer directs new requests to the appropriate available servers.

The instructor emphasizes that the load balancer should ideally support changes to the server group without unnecessarily interrupting existing connections.

Dynamic scaling requires integration with infrastructure provisioning, monitoring, orchestration, or cloud-management mechanisms. The load balancer alone does not necessarily perform the entire scaling process.

### 6.3 Hardware vs. Software Load Balancing

Load balancers generally fall into two categories: hardware-based and software-based.

Hardware Load Balancers

Hardware vendors provide dedicated appliances with proprietary software, sometimes using specialized processors to handle high traffic volumes.

To increase capacity, an organization may need to purchase a larger appliance or additional machines from the vendor.

Software Load Balancers

Software load balancers run on general-purpose servers or supported cloud infrastructure.

Organizations can select the machine size, configure resources, and deploy software such as NginX rather than relying exclusively on a dedicated vendor appliance.

#### Hardware load balancers

The lecture describes these characteristics:

- Vendor-supplied machines.
- Proprietary software.
- Potential use of specialized processing hardware.
- Capacity expansion through larger or additional appliances.

#### Software load balancers

The lecture highlights the following advantages:

- Generally more cost-effective.
- Greater flexibility in choosing server specifications.
- Less dependence on a dedicated hardware appliance vendor.
- Ability to run on infrastructure selected by the organization.

NginX is one example of a software-based load balancer. Cloud-provided load-balancing services are another option, although their underlying implementation may be managed by the cloud provider.

Practical consideration: Hardware and software load balancers both have operational costs and capacity limits. The appropriate choice depends on throughput, reliability requirements, support, security, and the organization's infrastructure.

## 7. NginX as a Load Balancer

NginX can operate as a reverse proxy, a load balancer, and a caching server.

When configured as a load balancer, NginX accepts incoming client connections and forwards requests to application servers in an upstream server group.

The general architecture is:

```
                   Clients
                      |
                      v
              +---------------+
              |     NginX     |
              | Load Balancer |
              +---------------+
                 /     |     \
                v      v      v
           +--------+ +--------+ +--------+
           | Server | | Server | | Server |
           |   A    | |   B    | |   C    |
           +--------+ +--------+ +--------+
                \      |      /
                 \     |     /
                      v
               Application responses
                      |
                      v
                   Clients
```

### 7.1 Why NginX can act as a load balancer

NginX supports reverse-proxy functionality, allowing it to receive requests on behalf of backend application servers.

The request flow is:

1. The client connects to NginX.
2. NginX accepts the incoming connection.
3. NginX selects an application server.
4. NginX forwards the request to that server.
5. The application server processes the request.
6. The server returns a response to NginX.
7. NginX forwards the response to the client.

This allows backend servers to remain behind a common entry point rather than requiring clients to connect directly to each application server.

### 7.2 Basic NginX load-balancing configuration

The following example illustrates the core configuration concepts introduced in this lecture.

```
http {
    upstream backend_servers {
        server 192.0.2.10:8080;
        server 192.0.2.11:8080;
        server 192.0.2.12:8080;
    }

    server {
        listen 80;
        server_name app.example.com;

        location / {
            proxy_pass http://backend_servers;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}
```

In this example:

- `upstream backend_servers` defines the group of backend application servers.
- Each `server` directive inside the upstream group identifies a backend address and port.
- `listen 80` configures NginX to accept HTTP connections on port 80.
- `server_name` specifies the hostname handled by this virtual server.
- `location /` matches requests under the root URI path.
- `proxy_pass http://backend_servers` forwards matching requests to the upstream group.
- `proxy_set_header` directives preserve useful information about the original client request.

Default behavior: Because no alternative algorithm is specified, NginX Open Source uses Round Robin for this upstream group.

The IP addresses in this example use the documentation-only IPv4 range `192.0.2.0/24`. Replace them with the actual addresses of your backend servers before deploying the configuration.

### 7.3 Validate and reload the configuration

After updating the NginX configuration, validate it before applying the changes:

```
sudo nginx -t
```

If the configuration test succeeds, reload NginX:

```
sudo systemctl reload nginx
```

The first command checks the configuration for syntax errors and other detectable problems. The second asks the NginX service to reload its configuration.

A successful configuration test does not guarantee that the backend application servers are reachable or healthy. Those conditions should also be tested.

## 8. Summary

This lecture introduces the fundamental concepts required to understand NginX load balancing.

The main takeaways are:

1. Load balancing distributes incoming traffic across multiple application servers to improve capacity utilization and application availability.
2. Failover helps maintain service when an individual backend server becomes unavailable.
3. Auto scaling and auto descaling adjust the number of application servers according to demand, but require additional configuration and infrastructure support.
4. Load-balancing algorithms include Round Robin, Least Connections, Least Response Time, Least Bandwidth, and Hashing.
5. Session persistence helps keep related requests associated with the same backend when an application requires it.
6. Hardware and software load balancers provide different approaches to capacity, flexibility, cost, and infrastructure management.
7. NginX acts as a reverse proxy and load balancer, receiving client requests and forwarding them to configured upstream servers.
8. NginX Open Source supports Round Robin, Least Connections, and IP-based hashing, while some additional algorithms and capabilities are specific to NginX Plus or require other implementations.

The next lectures will build on these concepts by exploring how to configure NginX as a load balancer in practice.
