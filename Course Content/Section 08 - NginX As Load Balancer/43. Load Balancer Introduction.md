# Section 08 — NginX as Load Balancer

## Lecture 43: Load Balancer Introduction

Technical documentation based on the lecture transcript

## 1. Overview

Load balancing is a technique used to distribute incoming client requests across multiple backend servers instead of
allowing a single server to handle all traffic.

Modern web applications may receive hundreds of thousands of concurrent requests from users. A single server can become
overloaded, resulting in slow responses, failed requests, or application crashes.

A load balancer sits in front of a group of servers and distributes incoming traffic among them. This improves
application availability, reliability, performance, and capacity utilization.

In this lecture, we explore:

- The definition and primary functions of load balancing.
- How load balancing distributes traffic across multiple servers.
- Common load-balancing algorithms.
- Session persistence and dynamic server-group configuration.
- Hardware versus software load balancers.
- How NginX works as a load balancer and reverse proxy.

## 2. Key Concepts

| Concept                      | Description                                                                         |
|------------------------------|-------------------------------------------------------------------------------------|
| Load balancing               | Distributing incoming traffic across multiple servers.                              |
| Backend server / server pool | A group of servers capable of handling application requests.                        |
| High availability            | Keeping an application accessible when individual servers fail.                     |
| Failover                     | Redirecting traffic away from an unavailable server.                                |
| Auto scaling                 | Increasing the number of application servers when demand increases.                 |
| Auto descaling               | Reducing the number of application servers when demand decreases.                   |
| Load-balancing algorithm     | The method used to select a server for an incoming request.                         |
| Session persistence          | Directing requests belonging to the same session to the same server.                |
| Reverse proxy                | An intermediary that receives client requests and forwards them to backend servers. |

## 3. How Load Balancing Works

Consider a web application running on five frontend application servers.

Without a load balancer, a single server might receive all incoming requests and become overloaded. With a load
balancer, incoming requests are distributed across the five servers.

The process works as follows:

1. A client sends a request to the application.
2. The request reaches the load balancer.
3. The load balancer selects an appropriate backend server using its configured algorithm.
4. The selected server processes the request.
5. The response is returned to the client through the load balancer.

These operations happen quickly and allow multiple servers to serve the same application.

Important: The backend servers are expected to run compatible versions of the application and have the resources needed
to fulfill the requests routed to them.

## 4. Primary Functions of a Load Balancer

### 4.1 Distribute traffic efficiently

The primary responsibility of a load balancer is to distribute client requests or network traffic across multiple
servers.

A server pool can contain two, 20, 200, or more servers. The required number depends on:

- Business requirements.
- Incoming traffic volume.
- Application resource requirements.
- The capacity of each server.

The goal is to prevent a single server from becoming an unnecessary bottleneck.

### 4.2 Ensure high availability and reliability

A load balancer should avoid sending traffic to servers that are unavailable.

For example, suppose five application servers are configured behind a load balancer. If one server goes offline, the
load balancer can direct new requests to the remaining healthy servers.

This helps the application continue serving users without requiring every individual server to remain operational.

The mechanism used to determine whether a server is online or offline depends on the load balancer and its
configuration. The instructor identifies this as a topic to explore later when configuring NginX.

### 4.3 Support failover

Failover is the process of redirecting traffic when a server becomes unavailable.

For example:

- Server 1, Server 2, Server 3, Server 4, and Server 5 initially receive traffic.
- Server 3 becomes unavailable.
- The load balancer stops directing new requests to Server 3 when its failure is detected.
- The remaining available servers continue handling requests.

Failover reduces the impact of individual server failures, although it does not guarantee uninterrupted service if the
remaining servers lack sufficient capacity or the load balancer itself fails.

### 4.4 Support auto scaling and auto descaling

Application traffic changes throughout the day. A business may require 20 servers during peak hours but only two to five
servers during quiet periods.

Keeping all 20 servers running during low-demand periods can waste computing resources and money.

Dynamic scaling addresses this problem:

- Scale up: Add application servers when traffic increases.
- Scale down: Remove application servers when traffic decreases.

The instructor emphasizes that scaling applies to the application servers behind the load balancer, not necessarily to
the load balancer itself.

This behavior requires additional engineering and configuration. A load balancer does not automatically create or remove
backend servers merely because it distributes traffic.

Dynamic server management should also preserve existing connections where possible and avoid removing servers before
their active requests or sessions have been handled.

## 5. Load-Balancing Algorithms

A load-balancing algorithm determines which backend server receives an incoming request. Different algorithms use
different criteria, such as request order, active connections, response time, bandwidth, or a hash key.

### 5.1 Round Robin

Round Robin distributes requests across servers sequentially.

Suppose the load balancer has three application servers:

```
Request 1  ──> Server A
Request 2  ──> Server B
Request 3  ──> Server C
Request 4  ──> Server A
Request 5  ──> Server B
Request 6  ──> Server C
```

The sequence repeats as new requests arrive.

Advantages

- Simple to understand and implement.
- Distributes requests sequentially across the configured servers.
- Works well when servers have similar capacities and requests have relatively similar processing requirements.

Limitations

Round Robin does not consider how busy a server already is. If Server B is processing several expensive requests, the
algorithm may still send it another request simply because it is next in the sequence.

This can result in uneven resource utilization when request processing times or server capacities differ.

DNS Round Robin

The instructor also discusses DNS load balancing. A DNS configuration can associate a hostname with multiple IP
addresses, allowing clients to receive different server addresses.

For example, a DNS zone might contain multiple A records:

```
app.example.com.  300  IN  A  192.0.2.10
app.example.com.  300  IN  A  192.0.2.11
app.example.com.  300  IN  A  192.0.2.12
```

These addresses represent three application servers.

DNS-based distribution differs from a reverse-proxy load balancer: DNS returns address information to clients, while a
proxy such as NginX receives the application request and forwards it to a selected backend.

Clarification: Round Robin remains a widely used software load-balancing algorithm. It is also the default upstream
load-balancing method in standard NginX Open Source. The lecture's suggestion that modern load balancers do not use it
should not be interpreted as a universal rule.

### 5.2 Least Connections

The **Least Connections** algorithm sends a new request to the backend server with the fewest active connections. Unlike
basic Round Robin, which distributes requests sequentially, Least Connections considers the current connection count of
each backend server when making a selection.

This algorithm is particularly useful when requests take different amounts of time to complete. A server processing
several long-running requests may have more active connections than a server handling short requests.

#### Example

Consider the following upstream servers:

| Server   | Active Connections |
|----------|-------------------:|
| Server A |                 12 |
| Server B |                  4 |
| Server C |                  8 |

When a new request arrives, NginX selects **Server B** because it has the fewest active connections.

#### Advantages

- Distributes work more effectively when requests have different processing times.
- Helps avoid sending additional connections to servers that already have many active connections.
- Adapts to changing connection counts instead of distributing requests solely according to a fixed sequence.
- Supports weighted backend servers, allowing servers with different capacities to participate in load balancing.

#### Limitations

- Connection count is not a perfect measure of server load. A single connection can consume more resources than many
  other connections.
- The algorithm does not directly measure CPU utilization, memory consumption, application response time, or backend
  queue length.
- A server with fewer active connections may still be slower because of CPU saturation, database contention, or other
  bottlenecks.
- Persistent and long-lived connections require careful interpretation because an open connection does not necessarily
  mean that the backend is actively processing a request.

#### Configuration

NginX Open Source and NginX Plus support Least Connections through the `least_conn` directive.

```nginx
http {
    upstream backend_servers {
        least_conn;

        server 192.0.2.10:8080;
        server 192.0.2.11:8080;
        server 192.0.2.12:8080;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend_servers;
        }
    }
}
```

The `upstream` block defines the backend server group, while `least_conn` instructs NginX to select a server based on
the number of active connections, taking configured server weights into account.

---

#### How Connection Tracking Works Internally

NginX maintains internal state for the backend servers in an upstream group. The Least Connections algorithm uses this
state to compare eligible servers and determine which one should receive the next request.

##### 1. Upstream Peer Structures

NginX maintains internal peer data structures representing the backend servers defined in an upstream group.

These structures contain information used during server selection, including connection counts, weights, and other state
needed by the load-balancing algorithm.

##### 2. Active Connection Counters

The upstream peer state includes an internal connection counter, commonly represented by the `conns` field in NginX's
upstream implementation.

This counter tracks active upstream connections associated with the peer. It is not a measurement of the backend's CPU
usage, memory consumption, or total application workload.

##### 3. Incrementing and Decrementing Connection Counts

At a high level, connection tracking follows this lifecycle:

1. NginX selects an eligible backend server.
2. The upstream connection is established or assigned for the request.
3. The selected peer's active connection count is updated.
4. The connection remains accounted for while it is active.
5. When the upstream connection is released, the corresponding connection count is decremented.

The exact lifecycle depends on the upstream connection handling and implementation details. For example, an idle
upstream keepalive connection is not necessarily counted as an active connection simply because its TCP connection
remains open.

##### 4. Shared State and Worker Processes

NginX uses worker processes to handle connections concurrently. Upstream peer state and synchronization mechanisms allow
the load-balancing implementation to maintain and access connection information safely.

When an upstream group is configured with shared state, such as through the `zone` directive, relevant peer state can be
shared between worker processes. Without shared upstream state, some peer information may be maintained separately by
workers.

This distinction matters when interpreting connection counts across workers and when configuring upstream groups for
monitoring or load balancing.

---

#### The Selection Process (`least_conn`)

When a new request needs to be assigned to an upstream server, NginX performs the following high-level steps.

##### Step 1: Identify Eligible Servers

NginX evaluates the upstream peers and excludes servers that are unavailable or otherwise ineligible for selection.

Eligibility can depend on factors such as server failure state, configured backup status, and other upstream selection
rules.

##### Step 2: Compare Active Connection Counts

NginX compares the active connection counts of eligible peers to identify the server with the lowest effective
connection load.

##### Step 3: Account for Server Weights

Server weights influence how Least Connections distributes traffic when backend servers have different configured
capacities.

For example:

```nginx
upstream backend_servers {
    least_conn;

    server 192.0.2.10:8080 weight=3;
    server 192.0.2.11:8080 weight=2;
    server 192.0.2.12:8080 weight=1;
}
```

In NginX's implementation, the comparison accounts for the relationship between active connection counts and configured
weights. Conceptually, the effective load can be understood as:

`active_connections / weight`

This is a useful mental model for understanding why a higher-weight server can accept a proportionally greater number of
active connections. The actual implementation compares weighted values using its internal selection logic.

##### Step 4: Resolve Ties

If multiple eligible servers have equivalent effective connection loads, NginX uses additional selection logic to choose
between them. The implementation incorporates its existing upstream selection state and tie-breaking rules, so it is
more precise to describe this as weighted Least Connections with internal tie-breaking rather than assume that every tie
is resolved by a separate, simple Round Robin pass.

##### Step 5: Assign the Request

NginX selects the winning peer and forwards the request to that backend server.

As upstream connections are established and released, the connection counts change. These updated counts influence
subsequent selection decisions.

---

#### Key Nuances in Real-World Behavior

##### Active Connections vs. CPU and Memory

Least Connections measures active upstream connections rather than the actual resource utilization of a backend
application.

For example, consider two backend servers:

- **Server A:** 4 active connections, but each request performs expensive database queries.
- **Server B:** 12 active connections, but each request performs lightweight operations.

Least Connections may prefer Server A because it has fewer active connections, even though Server A could be under
greater CPU or database pressure.

If application response latency is the primary concern, NginX Plus provides additional load-balancing capabilities,
including Least Response Time.

##### Keepalive Connections

NginX can reuse upstream connections through HTTP keepalive.

An idle connection retained in the upstream keepalive pool is not equivalent to an actively processing upstream
connection. Therefore, the presence of open TCP connections does not automatically mean that all those connections
contribute to the active connection count used by Least Connections.

For example, this configuration enables upstream HTTP keepalive:

```nginx
upstream backend_servers {
    least_conn;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;

    keepalive 32;
}

server {
    listen 80;

    location / {
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        proxy_pass http://backend_servers;
    }
}
```

The `keepalive 32` directive configures a cache of up to 32 idle upstream connections per worker process for this
upstream group. It does not limit the total number of upstream connections.

The `Connection` header configuration allows upstream HTTP/1.1 connections to remain reusable instead of explicitly
requesting that the connection close after each response.

##### HTTP/2 and WebSockets

Different protocols and connection patterns can affect how connection counts should be interpreted.

- **HTTP/1.1:** Multiple sequential requests can reuse an upstream connection when keepalive is configured.
- **HTTP/2:** Multiple concurrent streams can share a single client-side connection. The relationship between client
  connections and upstream connections depends on NginX's proxying and connection handling.
- **WebSockets:** A WebSocket connection can remain open for a long time, so active connection counts may reflect
  persistent sessions rather than short-lived request processing.

For these workloads, Least Connections should be evaluated against the actual upstream connection behavior instead of
assuming that one client connection always corresponds to one active request.

### 5.3 Least Response Time

The **Least Response Time** algorithm selects backend servers based on their response performance and, depending on the
configured method, their active connection load.

NginX Plus provides this functionality through the `least_time` directive. It is designed to prefer servers that respond
quickly while accounting for current workload, rather than relying only on connection counts.

Unlike Least Connections, which primarily evaluates active upstream connections, Least Response Time considers measured
response latency.

#### Configuration

The following example configures Least Response Time using the time required to receive the upstream response header:

```nginx
upstream backend_servers {
    zone backend_shared 64k;

    least_time header;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend_servers;
    }
}
```

Here:

- `least_time header` instructs NginX Plus to use response-header timing for server selection.
- `zone backend_shared 64k` allocates shared memory for upstream state, allowing worker processes to share relevant peer
  information.
- The `server` directives define the backend servers available for load balancing.

**Important:** The `least_time` directive is an NginX Plus feature. It is not available in standard NginX Open Source.
Open-source NginX supports alternatives such as `least_conn` and `random two least_conn`.

---

#### 1. How NginX Measures Response Time

NginX operates as an event-driven reverse proxy. It tracks upstream request timing to measure how long backend servers
take to respond.

For Least Response Time, the selected timing method determines which measurement is used.

##### 1.1 Header Response Time (`header`)

Header response time measures how long it takes NginX to receive the response headers from the upstream server.

The corresponding HTTP logging variable is:

```nginx
$upstream_header_time
```

This measurement is useful when the priority is how quickly the backend begins responding.

For example, a backend might take 25 ms to return its headers, while another takes 150 ms. Based on the configured
method and other selection criteria, the faster backend may be preferred.

However, header timing does not measure the complete response-body transfer time. It also includes upstream
connection-establishment time in the overall interval, where applicable.

##### 1.2 Last-Byte Response Time (`last_byte`)

Last-byte response time measures the time required to receive the complete upstream response, including its body.

The corresponding HTTP logging variable is:

```nginx
$upstream_response_time
```

This measurement is useful when the total time required to deliver a response from the backend is important.

For example:

- Server A returns a complete response in 80 ms.
- Server B returns a complete response in 300 ms.

If the configured selection method uses last-byte timing, Server A may be preferred based on its better measured
response performance.

The measurement can be influenced by application processing time, response size, network transfer time, and other
factors affecting completion.

##### 1.3 Connection Time (`connect`)

The connection-time measurement represents the time required to establish a connection to an upstream server.

The corresponding HTTP logging variable is:

```nginx
$upstream_connect_time
```

This is useful for diagnosing connection-establishment delays.

However, `connect` is not one of the standard timing choices for the HTTP `least_time` directive. In the NginX Stream
module, connection-related timing and Least Response Time configuration are handled in the TCP/UDP proxying context.

##### Timing Metrics Summary

| Metric      | Meaning                                               | HTTP Logging Variable     |
|-------------|-------------------------------------------------------|---------------------------|
| `connect`   | Time to establish an upstream connection              | `$upstream_connect_time`  |
| `header`    | Time until the upstream response headers are received | `$upstream_header_time`   |
| `last_byte` | Time until the complete upstream response is received | `$upstream_response_time` |

These timing measurements are useful for understanding backend behavior and selecting an appropriate response-time
method.

---

#### 2. How the Selection Algorithm Works Internally

Least Response Time combines measured response performance with additional upstream selection information.

At a high level, the process works as follows:

1. A client sends a request to NginX.
2. NginX identifies the configured upstream group.
3. NginX identifies eligible backend servers.
4. The configured Least Response Time method determines which response-time metric is relevant.
5. NginX evaluates the available response-time and connection information according to the configured selection method.
6. NginX selects an eligible backend and forwards the request.
7. When the upstream response reaches the relevant measurement checkpoint, NginX records the timing information.
8. The updated measurements contribute to subsequent load-balancing decisions.

This allows routing decisions to adapt as backend performance changes.

##### Response Time and Active Connections

Response time and active connection count provide different information.

- **Response time** indicates how quickly a backend has been responding.
- **Active connections** indicate how many upstream connections are currently active.

A server may have more active connections but still respond faster than another server. Conversely, a server with fewer
connections may be experiencing slow database queries or resource contention.

The `least_time` directive supports different selection methods, so the exact comparison depends on the configured
parameters.

##### Understanding the Scoring Concept

Conceptually, response-time-based load balancing can be understood as preferring servers with better measured response
performance while accounting for workload.

A simplified explanatory model is:

```text
Selection preference = measured response performance + workload considerations
```

This is a conceptual description, not the literal NginX implementation formula.

Do not assume that every `least_time` method uses the same mathematical formula or that NginX simply multiplies the
active connection count by a historical latency average. The precise selection behavior depends on the configured method
and NginX Plus implementation.

---

#### 3. Response-Time History and Changing Performance

Least Response Time uses response-time information to inform subsequent server-selection decisions.

Consider this example:

| Server   | Initial Response Time |
|----------|----------------------:|
| Server A |                 20 ms |
| Server B |                 60 ms |
| Server C |                100 ms |

Initially, Server A has the lowest measured response time.

Now suppose Server A experiences a database slowdown and its response time increases substantially.

As new timing measurements become available, the load balancer can adapt its selection decisions to the changed
performance characteristics.

This is one of the main benefits of response-time-aware load balancing: backend selection can respond to changing
performance rather than relying exclusively on connection counts.

**Implementation note:** Do not assume that NginX Plus implements `least_time` using a generic exponentially weighted
moving average (EWMA) with a particular decay factor. The precise internal statistical calculations should not be
inferred from the directive's name or from the behavior of other load balancers.

---

#### 4. The `inflight` Parameter

NginX Plus supports the `inflight` parameter in `least_time` configurations.

An inflight request is an upstream request that has been sent but has not yet completed.

Consider a backend server that has historically responded quickly. If many new requests arrive before the existing
requests finish, relying only on previously observed response times may not fully reflect its current workload.

Considering inflight requests helps the selection process account for work that is still in progress.

##### Configuration

```nginx
upstream backend_servers {
    zone backend_shared 64k;

    least_time header inflight;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}
```

The `inflight` parameter is supported in NginX Plus R15 and later.

The available combinations include:

| Configuration                   | Selection Metric                                           |
|---------------------------------|------------------------------------------------------------|
| `least_time header`             | Response-header timing                                     |
| `least_time last_byte`          | Complete-response timing                                   |
| `least_time header inflight`    | Response-header timing with inflight requests considered   |
| `least_time last_byte inflight` | Complete-response timing with inflight requests considered |

The exact selection behavior depends on the configured method.

##### Why Inflight Requests Matter

Suppose Server A has historically responded in 20 ms, while Server B has responded in 40 ms.

A burst of requests arrives, and Server A receives several requests that are still processing.

Without accounting for current work, Server A's historical performance alone may not adequately represent its current
situation.

The `inflight` option helps account for these outstanding requests during server selection, reducing the risk of
concentrating new traffic on a backend that is already handling a burst.

---

#### 5. Shared Memory and Worker Processes

NginX uses multiple worker processes to handle connections concurrently.

Because worker processes are separate processes, shared upstream state can be important when selection decisions need to
use information across workers.

The `zone` directive allocates shared memory for an upstream group.

##### Example

```nginx
upstream backend_pool {
    zone backend_shared 64k;

    least_time header;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
}
```

##### How the Shared Zone Helps

1. NginX allocates shared memory for the upstream group.
2. The shared zone holds relevant upstream peer state.
3. Worker processes can access shared peer information.
4. Updates to shared state can be observed by other workers.
5. Subsequent selection decisions can use the available shared information.

This helps maintain more consistent upstream state across worker processes.

The shared zone is not itself the Least Response Time algorithm. It provides shared storage for upstream state used by
the load-balancing implementation.

**Important clarification:** The exact timing-data structures, update operations, synchronization mechanisms, and
statistical calculations are implementation details. It is safer to describe the zone as shared upstream state than to
assume that every timing update follows a specific atomic EWMA-update procedure.

---

#### 6. Least Connections vs. Least Response Time

| Feature                    | Least Connections                            | Least Response Time                    |
|----------------------------|----------------------------------------------|----------------------------------------|
| Directive                  | `least_conn`                                 | `least_time`                           |
| NginX Open Source          | Supported                                    | Not supported                          |
| NginX Plus                 | Supported                                    | Supported                              |
| Main consideration         | Active upstream connections                  | Measured upstream response performance |
| Response-time measurements | Not required for selection                   | Used for selection                     |
| Inflight consideration     | Connection counts reflect active connections | Optional `inflight` parameter          |
| Direct CPU measurement     | No                                           | No                                     |
| Direct memory measurement  | No                                           | No                                     |

Use **Least Connections** when active connection counts provide a useful approximation of backend workload.

Use **Least Response Time** when measured response performance is important to server selection and NginX Plus is
available.

Neither algorithm directly measures CPU utilization, memory consumption, or every aspect of application health.

---

#### 7. Practical Notes and Best Practices

- Choose `header` when the time to receive upstream response headers is important.
- Choose `last_byte` when the time to receive the complete upstream response is more relevant.
- Consider `inflight` when outstanding requests should influence server selection.
- Use the `zone` directive when shared upstream state across worker processes is required.
- Monitor `$upstream_connect_time`, `$upstream_header_time`, and `$upstream_response_time` when diagnosing backend
  performance.
- Remember that response-time measurements can be affected by network conditions, connection setup, application
  processing, and response size.
- Do not interpret low response time as proof that a server has spare CPU or memory capacity.
- Verify NginX Plus availability and version compatibility before deploying `least_time`.
- Treat conceptual scoring formulas as explanatory models unless the exact implementation formula has been verified for
  the NginX version in use.

---

#### Summary

Least Response Time (`least_time`) is an NginX Plus load-balancing feature that uses upstream response-time measurements
to guide server selection.

Its principal timing methods are:

- `header` — time until upstream response headers arrive.
- `last_byte` — time until the complete upstream response arrives.

The optional `inflight` parameter allows outstanding requests to be considered during selection. The `zone` directive
provides shared upstream state across worker processes.

Together, these capabilities allow NginX Plus to make response-performance-aware routing decisions rather than relying
exclusively on the number of active connections.

### 5.4 Least Bandwidth

The Least Bandwidth method selects the server currently handling the lowest amount of network traffic, measured in
megabytes per second in the lecture's explanation.

For example:

| Server   | Current traffic |
|----------|-----------------|
| Server A | 18 MB/s         |
| Server B | 5 MB/s          |
| Server C | 12 MB/s         |

Under this approach, Server B would be preferred because it is serving the least traffic.

This method is useful conceptually when bandwidth utilization is an important indicator of load.

Important implementation note: Least Bandwidth is not a standard built-in upstream selection directive in NginX Open
Source. Implementing bandwidth-aware routing may require an external load balancer, specialized functionality, or custom
monitoring and routing logic.

### 5.5 Hashing

Hashing is a load-balancing technique that selects a backend server based on a key derived from client or request
information.

The key can include information such as:

- Client IP address.
- Request URI.
- A specific request parameter.
- Other NginX variables or strings supported by the hashing configuration.

NginX processes the key using a hashing algorithm and maps the result to a backend server.

Hashing is particularly useful when requests associated with the same key should consistently reach the same backend
server. This behavior can help maintain application session affinity or improve cache locality.

NginX supports two main hashing methods:

- **`ip_hash`** — selects a backend using the client's IP address.
- **`hash`** — selects a backend using a custom key defined by the administrator.

---

#### 1. The `ip_hash` Method

The `ip_hash` directive distributes requests according to the client's IP address. It provides a basic form of session
persistence without requiring cookies.

Requests associated with the same client IP generally reach the same backend server as long as the upstream server
configuration and available servers remain compatible with that mapping.

##### Configuration

```nginx
upstream backend_servers {
    ip_hash;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend_servers;
    }
}
```

The `ip_hash` directive instructs NginX to use client IP-based hashing when selecting a backend from the upstream group.

This method is supported by both NginX Open Source and NginX Plus.

##### How `ip_hash` Works Internally

**Step 1: Obtain the Client IP Address**

NginX obtains the client's IP address for the request.

When NginX operates behind another proxy or load balancer, the address it sees may belong to that intermediary rather
than the original client. The effective client address therefore depends on the network configuration and any correctly
configured real-IP handling.

**Step 2: Process the IP Address**

NginX uses the client IP address to calculate a hash value.

The handling differs by address family:

- **IPv4:** NginX uses the first three octets of the IPv4 address for hashing.
- **IPv6:** NginX uses the full IPv6 address.

For example, these IPv4 addresses share the same first three octets:

```text
192.168.1.10
192.168.1.25
192.168.1.100
```

They therefore produce the same IP-based hashing input under `ip_hash`.

As a result, clients behind the same IPv4 `/24` subnet may be directed to the same backend. This can cause multiple
users behind a shared office or network gateway to concentrate on one server.

**Step 3: Map the Hash to a Backend**

NginX uses its IP-hashing selection logic to map the calculated value to an eligible upstream server.

The exact mapping depends on the upstream server configuration and availability. It should not be assumed that NginX
simply performs a basic modulo operation against the number of servers.

**Step 4: Reuse the Mapping for Subsequent Requests**

As long as the relevant mapping remains stable, requests from the same client IP tend to reach the same backend.

This is useful when an application stores session state locally on a backend server, although IP hashing alone does not
guarantee session persistence under every failure or configuration change.

##### Advantages

- Provides basic client IP-based session affinity.
- Does not require session cookies to make the routing decision.
- Can improve cache locality when requests from the same client reach the same backend.
- Is available in NginX Open Source and NginX Plus.

##### Limitations

- Multiple users sharing a public IP address may be mapped to the same backend.
- A client's IP address can change, causing requests to map to a different server.
- Server failures and upstream membership changes can alter the mapping.
- It does not measure backend CPU utilization, memory usage, or response time.
- It does not guarantee application session persistence in every situation.

---

#### 2. The Generic `hash` Method

The generic `hash` directive allows administrators to define a custom key for backend selection.

Unlike `ip_hash`, which uses client IP-based hashing, the generic `hash` method can use NginX variables, text strings,
or a combination of values.

Examples of possible keys include:

- `$remote_addr` — client IP address.
- `$request_uri` — request URI, including the query string.
- `$arg_userid` — the value of the `userid` query-string parameter.
- `$remote_addr$request_uri` — a combination of the client IP address and request URI.

The appropriate key depends on the routing behavior you want to achieve.

##### Configuration

```nginx
upstream dynamic_cache {
    hash $request_uri consistent;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://dynamic_cache;
    }
}
```

In this example:

- `hash $request_uri consistent;` defines the request URI as the hashing key.
- Requests with the same URI generally map to the same backend while the upstream configuration remains stable.
- The `consistent` parameter enables consistent hashing.
- The `server` directives define the available backend servers.

##### How Generic Hashing Works Internally

**Step 1: Construct the Key**

NginX evaluates the configured key for the request.

For example, with:

```nginx
hash $arg_userid consistent;
```

a request such as:

```text
https://example.com/profile?userid=123
```

uses `123` as the key value.

**Step 2: Calculate the Hash**

NginX processes the key using the hashing mechanism associated with the upstream hash directive.

The resulting hash value provides the basis for selecting a backend.

**Step 3: Map the Hash to a Server**

NginX maps the hash to a server according to the configured hashing mode.

With ordinary hashing, the mapping is sensitive to the upstream server set. With consistent hashing, the mapping is
designed to minimize unnecessary reassignment when the server set changes.

**Step 4: Route the Request**

NginX forwards the request to the selected backend.

Requests with identical keys generally reach the same backend as long as the relevant mapping remains stable and the
selected server remains eligible.

##### Choosing an Appropriate Hash Key

The key determines which requests share the same backend mapping.

For example:

```nginx
upstream backend_by_client {
    hash $remote_addr consistent;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
}
```

This configuration uses the client IP address as the key.

Alternatively:

```nginx
upstream backend_by_user {
    hash $arg_userid consistent;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
}
```

This configuration uses the `userid` query parameter.

If several requests contain the same `userid`, they generally map to the same backend while the server mapping remains
stable.

**Important:** Hashing a user-controlled parameter does not authenticate the user or provide access control. The
application must still validate identity and permissions independently.

---

#### 3. Consistent Hashing (`consistent`)

Consistent hashing is an optional modifier for the generic `hash` directive.

Without `consistent`, NginX uses its ordinary hash-based server-selection method. Changes to the upstream server set can
cause many keys to map to different servers.

With `consistent`, NginX uses a consistent-hashing mechanism based on the Ketama approach.

##### Why Consistent Hashing Matters

Suppose an upstream group contains three servers:

```text
Server A
Server B
Server C
```

Requests are distributed according to their hash keys.

Now suppose Server D is added.

With ordinary hashing, changing the number of servers can change the mapping for many keys. This can result in requests
reaching different backends and can reduce cache effectiveness.

With consistent hashing, the mapping is designed to preserve most existing assignments when a server is added or
removed.

Only a subset of keys generally needs to be reassigned.

##### Configuration Example

```nginx
upstream cache_servers {
    hash $request_uri consistent;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
    server 192.0.2.12:8080;
}
```

##### How Consistent Hashing Works Conceptually

1. NginX calculates a hash for the request key.
2. The consistent-hashing mechanism maps the key to a position in a logical hash space.
3. Backend servers are represented in that space.
4. The selection logic determines which server is responsible for the key.
5. When a server is added or removed, only the affected portion of the mapping generally changes.

This reduces unnecessary reassignment compared with ordinary hashing.

##### Advantages

- Minimizes cache disruption when upstream membership changes.
- Reduces the number of keys reassigned when servers are added or removed.
- Helps preserve stable request-to-backend mappings.
- Is useful for distributed caches and applications that benefit from consistent routing.

##### Important Clarification

Consistent hashing does not guarantee that all sessions remain uninterrupted when a backend fails. Requests previously
assigned to an unavailable server must be handled according to the available upstream selection and failure-handling
behavior.

Consistent hashing minimizes remapping; it does not eliminate it.

---

#### 4. Handling Backend Failures and Recovery

Hash-based routing must account for servers becoming unavailable and later returning to service.

##### When a Backend Fails

Suppose a client or request key maps to Server A, but Server A becomes unavailable.

NginX can select another eligible backend according to its upstream failure-handling and selection rules.

The request may therefore reach a different server than the one normally associated with its key.

For example:

```nginx
upstream backend_servers {
    hash $request_uri consistent;

    server 192.0.2.10:8080 max_fails=3 fail_timeout=30s;
    server 192.0.2.11:8080 max_fails=3 fail_timeout=30s;
    server 192.0.2.12:8080 max_fails=3 fail_timeout=30s;
}
```

Here:

- `max_fails=3` configures the number of unsuccessful attempts considered during the failure window.
- `fail_timeout=30s` defines the interval used for failure tracking and the period for which the server is considered
  unavailable after reaching the configured failure threshold.

The actual behavior depends on the configured upstream settings and the type of failure. These parameters do not
guarantee that every failure will be detected or handled identically.

##### When a Backend Recovers

When the failed backend becomes eligible again, hashing may direct some keys back to it.

With consistent hashing, the mapping is designed to minimize unnecessary changes, but the return of a server can still
change assignments for a subset of keys.

If application sessions or cached data exist only on a particular backend, a change in routing may affect session
continuity or cache hit rates.

For this reason, hashing should not be treated as a replacement for shared session storage, replicated application
state, or a resilient cache architecture.

---

#### 5. Comparing `ip_hash`, `hash`, and `hash ... consistent`

| Feature                   | `ip_hash`                                  | `hash $key`                                          | `hash $key consistent`                         |
|---------------------------|--------------------------------------------|------------------------------------------------------|------------------------------------------------|
| Routing key               | Client IP address                          | Configured key                                       | Configured key                                 |
| Custom key support        | No                                         | Yes                                                  | Yes                                            |
| Session affinity          | Basic IP-based affinity                    | Depends on the chosen key                            | Depends on the chosen key                      |
| Mapping stability         | Depends on the IP and server configuration | Can change significantly when the server set changes | Designed to minimize remapping                 |
| Useful for cache locality | Yes                                        | Yes                                                  | Yes, especially when server membership changes |
| NginX Open Source         | Supported                                  | Supported                                            | Supported                                      |
| NginX Plus                | Supported                                  | Supported                                            | Supported                                      |

### 5.6 Algorithm comparison

| Algorithm           | Selection criterion                  | Availability in NginX                         |
|---------------------|--------------------------------------|-----------------------------------------------|
| Round Robin         | Sequential distribution              | Open Source and Plus                          |
| Least Connections   | Fewest active connections            | Open Source and Plus                          |
| Least Response Time | Response-time and connection metrics | Plus; uses `least_time`                       |
| Least Bandwidth     | Lowest current bandwidth usage       | Not a standard Open Source upstream directive |
| Hashing             | A defined key, such as client IP     | Open Source and Plus; includes `ip_hash`      |

The algorithms above represent different ways of distributing traffic. No single method is optimal for every workload.

## 6. Related Load-Balancing Fundamentals

### 6.1 Session Persistence

Session persistence ensures that requests belonging to a particular user session continue to reach the same backend
server for the required duration.

For example:

1. A user sends an initial request.
2. The load balancer routes the request to Server A.
3. The user sends another request.
4. The load balancer routes the subsequent request to Server A again.

The objective is to maintain continuity between the user and the server handling the session.

#### Why session persistence matters

Consider an online shopping application.

A user adds several products to a shopping cart and continues browsing. If the application stores session information
locally on Server A, sending the user's next request to Server B may cause problems if Server B does not have access to
that session information.

Potential consequences include:

- Missing shopping-cart items.
- Lost session state.
- Unexpected application behavior.
- Failed or interrupted transactions.

For applications that maintain session data locally on a particular server, directing requests consistently to that
server can be essential.

#### Session persistence in NginX

The instructor identifies NginX upstream configuration as the area where session persistence will be discussed in more
detail.

An IP-based hashing example is:

```
upstream backend_servers {
    ip_hash;

    server 192.0.2.10:8080;
    server 192.0.2.11:8080;
}
```

This configuration attempts to keep requests from the same client IP address associated with the same backend server.

However, `ip_hash` is not identical to full session persistence in every situation. Users behind the same NAT gateway
may share an IP address, and a server failure or upstream membership change can affect routing.

Where possible, applications should use shared session storage or stateless authentication so that any healthy backend
can handle a request. This reduces dependence on sticky routing.

### 6.2 Dynamic Configuration of Server Groups

Dynamic server-group configuration refers to adding or removing backend servers as application demand changes. This is
closely related to auto scaling and auto descaling.

The lecture highlights cloud environments such as:

- Amazon Web Services (AWS) Elastic Compute Cloud (EC2).
- Google Cloud servers.
- Google Cloud Load Balancing.

These environments allow organizations to adjust computing capacity based on actual requirements.

For example:

- During peak traffic, additional application servers are brought online.
- During low traffic, unnecessary servers are removed.
- The load balancer directs new requests to the appropriate available servers.

The instructor emphasizes that the load balancer should ideally support changes to the server group without
unnecessarily interrupting existing connections.

Dynamic scaling requires integration with infrastructure provisioning, monitoring, orchestration, or cloud-management
mechanisms. The load balancer alone does not necessarily perform the entire scaling process.

### 6.3 Hardware vs. Software Load Balancing

Load balancers generally fall into two categories: hardware-based and software-based.

Hardware Load Balancers

Hardware vendors provide dedicated appliances with proprietary software, sometimes using specialized processors to
handle high traffic volumes.

To increase capacity, an organization may need to purchase a larger appliance or additional machines from the vendor.

Software Load Balancers

Software load balancers run on general-purpose servers or supported cloud infrastructure.

Organizations can select the machine size, configure resources, and deploy software such as NginX rather than relying
exclusively on a dedicated vendor appliance.

#### Hardware load balancers

The lecture describes these characteristics:

- Vendor-supplied machines.
- Proprietary software.
- Potential use of specialized processing hardware.
- Capacity expansion through larger or additional appliances.

#### Software load balancers

The lecture highlights the following advantages:

- Generally more cost-effective.
- Greater flexibility in choosing server specifications.
- Less dependence on a dedicated hardware appliance vendor.
- Ability to run on infrastructure selected by the organization.

NginX is one example of a software-based load balancer. Cloud-provided load-balancing services are another option,
although their underlying implementation may be managed by the cloud provider.

Practical consideration: Hardware and software load balancers both have operational costs and capacity limits. The
appropriate choice depends on throughput, reliability requirements, support, security, and the organization's
infrastructure.

## 7. NginX as a Load Balancer

NginX can operate as a reverse proxy, a load balancer, and a caching server.

When configured as a load balancer, NginX accepts incoming client connections and forwards requests to application
servers in an upstream server group.

The general architecture is:

```
                   Clients
                      |
                      v
              +---------------+
              |     NginX     |
              | Load Balancer |
              +---------------+
                 /     |     \
                v      v      v
           +--------+ +--------+ +--------+
           | Server | | Server | | Server |
           |   A    | |   B    | |   C    |
           +--------+ +--------+ +--------+
                \      |      /
                 \     |     /
                      v
               Application responses
                      |
                      v
                   Clients
```

### 7.1 Why NginX can act as a load balancer

NginX supports reverse-proxy functionality, allowing it to receive requests on behalf of backend application servers.

The request flow is:

1. The client connects to NginX.
2. NginX accepts the incoming connection.
3. NginX selects an application server.
4. NginX forwards the request to that server.
5. The application server processes the request.
6. The server returns a response to NginX.
7. NginX forwards the response to the client.

This allows backend servers to remain behind a common entry point rather than requiring clients to connect directly to
each application server.

### 7.2 Basic NginX load-balancing configuration

The following example illustrates the core configuration concepts introduced in this lecture.

```
http {
    upstream backend_servers {
        server 192.0.2.10:8080;
        server 192.0.2.11:8080;
        server 192.0.2.12:8080;
    }

    server {
        listen 80;
        server_name app.example.com;

        location / {
            proxy_pass http://backend_servers;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}
```

In this example:

- `upstream backend_servers` defines the group of backend application servers.
- Each `server` directive inside the upstream group identifies a backend address and port.
- `listen 80` configures NginX to accept HTTP connections on port 80.
- `server_name` specifies the hostname handled by this virtual server.
- `location /` matches requests under the root URI path.
- `proxy_pass http://backend_servers` forwards matching requests to the upstream group.
- `proxy_set_header` directives preserve useful information about the original client request.

Default behavior: Because no alternative algorithm is specified, NginX Open Source uses Round Robin for this upstream
group.

The IP addresses in this example use the documentation-only IPv4 range `192.0.2.0/24`. Replace them with the actual
addresses of your backend servers before deploying the configuration.

### 7.3 Validate and reload the configuration

After updating the NginX configuration, validate it before applying the changes:

```
sudo nginx -t
```

If the configuration test succeeds, reload NginX:

```
sudo systemctl reload nginx
```

The first command checks the configuration for syntax errors and other detectable problems. The second asks the NginX
service to reload its configuration.

A successful configuration test does not guarantee that the backend application servers are reachable or healthy. Those
conditions should also be tested.
