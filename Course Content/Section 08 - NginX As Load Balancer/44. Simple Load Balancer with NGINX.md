# Section 08 — NginX as Load Balancer

## Lecture 44: Simple Load Balancer with NginX

Technical documentation based on the lecture transcript

## 1. Overview

This lecture demonstrates how to configure NginX as a basic load balancer using three Ubuntu virtual machines hosted on DigitalOcean.

The goal is to configure one NginX server to receive client requests and distribute them across two application servers. One application server hosts a Brownie website, while the other serves the default NginX welcome page.

The configuration uses an `upstream` block to define the backend servers and `proxy_pass` to forward client requests to that group.

By default, NginX distributes requests using the Round Robin algorithm when no alternative load-balancing method is specified.

### Learning objectives

By the end of this lecture, you should understand how to:

- Set up a basic load-balancing environment with three virtual machines.
- Install NginX on the application servers and the load-balancer server.
- Configure the `upstream` context inside the `http` context.
- Define backend application servers using the `server` directive.
- Forward incoming requests to an upstream group using `proxy_pass`.
- Test load balancing using `curl`.
- Observe how requests appear in the backend access logs.

- `sudo` privileges on each machine.

### Step 5: Configure NginX as a load balancer

Now configure the third machine, Ubuntu Load Balancer, to distribute requests across the two application servers.

Open the main NginX configuration file:

```
sudo vi /etc/nginx/nginx.conf
```

The instructor removes unnecessary default configuration and retains the essential directives, including:

- User and worker-process settings.
- PID file configuration.
- Module and MIME-type includes.
- The `events` context.
- The `http` context.
- Access and error log definitions.

The instructor then adds two important configuration components inside the `http` context:

1. An `upstream` block defining the backend application servers.
2. A `server` block that accepts client requests and forwards them to the upstream group.

#### 5.1 Define the upstream server group

The `upstream` block identifies the group of application servers that NginX can use to process incoming requests.

Example:

```
upstream app_server {
    server 192.0.2.130;
    server 192.0.2.192;
}
```

Explanation:

- `upstream` declares a backend server group.
- `app_server` is the group name chosen by the instructor. You can choose another valid name.
- Each `server` directive specifies the address of a backend application server.
- The first backend hosts the Brownie website.
- The second backend serves the default NginX welcome page.

The upstream group is defined inside `http`, not inside an individual `server` or `location` block.

Because the example does not specify ports, NginX uses port 80 for these backend addresses.

#### 5.2 Define the load-balancer server block

Next, create a `server` block alongside the upstream definition, within the same `http` context.

```
server {
    listen 80;

    location / {
        proxy_pass http://app_server;
    }
}
```

Explanation:

- `listen 80;` makes NginX accept HTTP connections on port 80.
- `location /` matches requests under the root URI path.
- `proxy_pass http://app_server;` forwards matching requests to the upstream group named `app_server`.

The `proxy_pass` directive references the upstream group by name rather than specifying a single backend IP address.

This allows NginX to select a backend according to the configured load-balancing algorithm.

#### 5.3 Complete load-balancer configuration

The following example combines the upstream and server blocks in a complete minimal configuration suitable for the lab.

```
user www-data;
worker_processes auto;
pid /run/nginx.pid;

include /etc/nginx/modules-enabled/*.conf;

events {
    worker_connections 768;
}

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    access_log /var/log/nginx/access.log;
    error_log /var/log/nginx/error.log;

    upstream app_server {
        server 192.0.2.130;
        server 192.0.2.192;
    }

    server {
        listen 80;
        server_name _;

        location / {
            proxy_pass http://app_server;
        }
    }
}
```

Replace the example backend IP addresses with the actual addresses of your application servers.

This example preserves the main structural elements demonstrated in the lecture. If your existing NginX installation uses additional required settings, retain them rather than replacing the entire configuration blindly.

The `upstream` and `server` blocks are siblings within `http`. The `location` block is nested inside the load-balancer `server` block.

### Step 6: Validate the configuration

Before restarting or reloading NginX, test the configuration:

```
sudo nginx -t
```

If the configuration is valid, NginX reports successful syntax and configuration tests.

If errors appear, review:

- Missing semicolons.
- Incorrect braces.
- Invalid IP addresses or server definitions.
- A misspelled upstream group name.
- Incorrect placement of configuration blocks.

The upstream name in `proxy_pass` must match the name declared in the `upstream` block.

### Step 7: Restart NginX

The instructor restarts NginX to apply the new configuration:

```
sudo service nginx restart
```

The lecture initially states the command in the wrong order, then corrects it. The command above is the corrected version.

You can also use the systemd equivalent:

```
sudo systemctl restart nginx
```

A restart applies the configuration but can interrupt existing connections. In production, a validated reload is often preferable when appropriate:

```
sudo systemctl reload nginx
```

### Step 8: Identify the load balancer's IP address

On the load-balancer machine, identify its IP address:

```

```

```

```

Use the address reachable from your client or browser. If the backend servers are on a private network, make sure the load balancer can also reach their private addresses.

## 5. Testing the Load Balancer

### 5.1 Send requests using curl

Once NginX has restarted successfully, send an HTTP request to the load balancer.

```
curl http://192.0.2.226
```

Replace `192.0.2.226` with your load balancer's actual IP address.

The instructor receives the content of one backend application. Running the same command again returns content from the other application server.

For example:

```
curl http://192.0.2.226
# Response from the first backend: Brownie website HTML

curl http://192.0.2.226
# Response from the second backend: default NginX HTML

curl http://192.0.2.226
# Response from the first backend: Brownie website HTML

curl http://192.0.2.226
# Response from the second backend: default NginX HTML
```

These comments illustrate the observed behavior; the actual HTML output depends on your backend applications.

### 5.2 Why does the response alternate?

The upstream group does not specify an alternative load-balancing algorithm. NginX therefore uses its default Round Robin behavior.

With two available backend servers, successive requests are distributed in sequence:

Round Robin request sequence

### 1

Brownie server

### 2

Default NginX server

### 3

Brownie server

### 4

Default NginX server

### 5

Brownie server

### 6

Default NginX server

This is the basic load-balancing behavior demonstrated in the lecture.

Important: The sequence assumes both backends remain eligible for selection and that requests are processed under the same conditions. The example demonstrates Round Robin request distribution, not a guarantee that every client connection will alternate between servers in all circumstances.

### 5.3 Test repeatedly from the command line

To observe the behavior without manually entering the command repeatedly, use a loop:

```
for i in {1..6}; do
    curl -s http://192.0.2.226
    echo
done
```

This sends six HTTP requests to the load balancer and prints each response.

If both backends return distinguishable HTML, you should be able to identify which server handled each request.

For easier testing, you can temporarily place a different marker in each backend's response, provided you do not overwrite application files or configurations that you need to preserve.

## 6. Verify Requests in the Access Logs

The instructor also verifies that requests reach the backend servers by examining their NginX access logs.

On Ubuntu, the default access log is typically located at:

```
/var/log/nginx/access.log
```

On the first application server, run:

```
sudo tail -f /var/log/nginx/access.log
```

Repeat the command on the second application server in another terminal.

Now send requests to the load balancer:

```
curl http://192.0.2.226
curl http://192.0.2.226
curl http://192.0.2.226
curl http://192.0.2.226
```

The instructor observes that:

- A request served by the default NginX backend appears in that backend's access log.
- A request served by the Brownie backend appears in the Brownie server's access log.
- The client IP recorded in the backend logs corresponds to the load balancer's IP address in the demonstrated setup.

This provides evidence that NginX is forwarding requests to the backend servers rather than serving both pages directly from the load-balancer machine.

The exact client IP shown in logs depends on the network topology and proxy configuration. In the instructor's example, the backend sees the load balancer as the immediate client.

If you need the original client IP to be recorded or used by the backend application, configure the appropriate forwarded headers and ensure the backend application trusts them only from authorized proxies.

## 7. Practical Notes and Best Practices

### 7.1 Keep backend applications distinguishable during testing

Using different backend responses makes it easier to verify that load balancing is working.

For example:

- Backend 1 returns the Brownie website.
- Backend 2 returns the default NginX welcome page.

Once the load-balancing behavior has been verified, both servers can serve the same application version in a production architecture.

### 7.2 Verify network connectivity

The load balancer must be able to reach both backend servers on the configured ports.

Check that:

- NginX is running on each backend.
- The backend HTTP ports are listening.
- Firewall rules permit traffic from the load balancer.
- The configured IP addresses are correct.

If the load balancer returns a gateway error, check the backend availability and the NginX error log.

```
sudo tail -f /var/log/nginx/error.log
```

### 7.3 Understand the difference between proxying and load balancing

The following directive forwards requests to the upstream group:

```
proxy_pass http://app_server;
```

However, the actual load balancing depends on how `app_server` is defined and which backend servers are available.

Defining an upstream group alone does not make a server accept external client requests. The load-balancer server block and its `location` configuration must also be configured correctly.

### 7.4 Understand the limitations of this basic configuration

This lab demonstrates a simple load balancer, not a complete production deployment.

The configuration does not explicitly add:

- Custom health-check configuration.
- Session persistence.
- Advanced load-balancing algorithms.
- TLS termination.
- Dedicated monitoring or automatic scaling.
- Redundancy for the load balancer itself.

These features may be needed depending on application requirements. Standard NginX Open Source also does not provide all the advanced health-check and load-balancing features available in NginX Plus.

## 8. Common Mistakes and Troubleshooting

| Problem                                                  | Likely cause                                                                               | Recommended action                                                                  |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Brownie website does not load directly                   | Incorrect backend NginX configuration or document root                                     | Check the site configuration and application files.                                 |
| Default NginX page does not load on the second server    | NginX is stopped or port 80 is unavailable                                                 | Check the service, listening ports, and firewall.                                   |
| NginX configuration test fails                           | Syntax errors or misplaced directives                                                      | Run `sudo nginx -t` and fix the reported errors.                                    |
| Load balancer shows an error instead of the backend page | Backend unavailable, wrong IP, wrong port, or network restrictions                         | Inspect the load-balancer error log and test backend connectivity.                  |
| Only one backend's content appears                       | The other server may be unreachable, incorrectly configured, or returning the same content | Inspect both backend servers and their logs.                                        |
| Backend logs show the load balancer's IP                 | Expected behavior when the load balancer is the immediate proxy client                     | Configure and process forwarded headers if original-client information is required. |
