# Section 08 — NginX as Load Balancer

## Lecture 44: Simple Load Balancer with NginX

## 1. Overview

This lecture demonstrates how to configure NginX as a basic load balancer using three Ubuntu virtual machines hosted on
DigitalOcean.

The goal is to configure one NginX server to receive client requests and distribute them across two application servers.
One application server hosts a Brownie website, while the other serves the default NginX welcome page.

The configuration uses an `upstream` block to define the backend servers and `proxy_pass` to forward client requests to
that group.

By default, NginX distributes requests using the Round Robin algorithm when no alternative load-balancing method is
specified.

### Learning objectives

By the end of this lecture, you should understand how to:

- Set up a basic load-balancing environment with three virtual machines.
- Install NginX on the application servers and the load-balancer server.
- Configure the `upstream` context inside the `http` context.
- Define backend application servers using the `server` directive.
- Forward incoming requests to an upstream group using `proxy_pass`.
- Test load balancing using `curl`.
- Observe how requests appear in the backend access logs.

Before beginning the lab, ensure that you have:

- `sudo` privileges on each machine.
- NginX installed on the application servers and the load balancer.

- The IP addresses of all three machines.

The backend servers must be reachable on the ports specified in the upstream configuration. The demonstration uses HTTP,

### Step 5: Configure NginX as a load balancer

Now configure the third machine, Ubuntu Load Balancer, to distribute requests across the two application servers.

Open the main NginX configuration file:

```
sudo vi /etc/nginx/nginx.conf
```

The instructor removes unnecessary default configuration and retains the essential directives, including:

- User and worker-process settings.
- PID file configuration.
- Module and MIME-type includes.
- The `events` context.
- The `http` context.
- Access and error log definitions.

The instructor then adds two important configuration components inside the `http` context:

1. An `upstream` block defining the backend application servers.
2. A `server` block that accepts client requests and forwards them to the upstream group.

#### 5.1 Define the upstream server group

The `upstream` block identifies the group of application servers that NginX can use to process incoming requests.

Example:

```
upstream app_server {
    server 192.0.2.130;
    server 192.0.2.192;
}
```

Explanation:

- `upstream` declares a backend server group.
- `app_server` is the group name chosen by the instructor. You can choose another valid name.
- Each `server` directive specifies the address of a backend application server.
- The first backend hosts the Brownie website.
- The second backend serves the default NginX welcome page.

The upstream group is defined inside `http`, not inside an individual `server` or `location` block.

Because the example does not specify ports, NginX uses port 80 for these backend addresses.

#### 5.2 Define the load-balancer server block

Next, create a `server` block alongside the upstream definition, within the same `http` context.

```
server {
    listen 80;

    location / {
        proxy_pass http://app_server;
    }
}
```

Explanation:

- `listen 80;` makes NginX accept HTTP connections on port 80.
- `location /` matches requests under the root URI path.
- `proxy_pass http://app_server;` forwards matching requests to the upstream group named `app_server`.

The `proxy_pass` directive references the upstream group by name rather than specifying a single backend IP address.

This allows NginX to select a backend according to the configured load-balancing algorithm.

#### 5.3 Complete load-balancer configuration

The following example combines the upstream and server blocks in a complete minimal configuration suitable for the lab.

```
user www-data;
worker_processes auto;
pid /run/nginx.pid;

include /etc/nginx/modules-enabled/*.conf;

events {
    worker_connections 768;
}

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    access_log /var/log/nginx/access.log;
    error_log /var/log/nginx/error.log;

    upstream app_server {
        server 192.0.2.130;
        server 192.0.2.192;
    }

    server {
        listen 80;
        server_name _;

        location / {
            proxy_pass http://app_server;
        }
    }
}
```

Replace the example backend IP addresses with the actual addresses of your application servers.

This example preserves the main structural elements demonstrated in the lecture. If your existing NginX installation
uses additional required settings, retain them rather than replacing the entire configuration blindly.

The `upstream` and `server` blocks are siblings within `http`. The `location` block is nested inside the load-balancer
`server` block.

### Step 6: Validate the configuration

Before restarting or reloading NginX, test the configuration:

```
sudo nginx -t
```

If the configuration is valid, NginX reports successful syntax and configuration tests.

If errors appear, review:

- Missing semicolons.
- Incorrect braces.
- Invalid IP addresses or server definitions.
- A misspelled upstream group name.
- Incorrect placement of configuration blocks.

The upstream name in `proxy_pass` must match the name declared in the `upstream` block.

## 5. Testing the Load Balancer

### 5.1 Send requests using curl

Once NginX has restarted successfully, send an HTTP request to the load balancer.

```
curl http://192.0.2.226
```

Replace `192.0.2.226` with your load balancer's actual IP address.

The instructor receives the content of one backend application. Running the same command again returns content from the
other application server.

For example:

```
curl http://192.0.2.226
# Response from the first backend: Brownie website HTML

curl http://192.0.2.226
# Response from the second backend: default NginX HTML

curl http://192.0.2.226
# Response from the first backend: Brownie website HTML

curl http://192.0.2.226
# Response from the second backend: default NginX HTML
```

These comments illustrate the observed behavior; the actual HTML output depends on your backend applications.

### 5.2 Why does the response alternate?

The upstream group does not specify an alternative load-balancing algorithm. NginX therefore uses its default Round
Robin behavior.

With two available backend servers, successive requests are distributed in sequence

This is the basic load-balancing behavior demonstrated in the lecture.

Important: The sequence assumes both backends remain eligible for selection and that requests are processed under the
same conditions. The example demonstrates Round Robin request distribution, not a guarantee that every client connection
will alternate between servers in all circumstances.

### 5.3 Test repeatedly from the command line

To observe the behavior without manually entering the command repeatedly, use a loop:

```
for i in {1..6}; do
    curl -s http://192.0.2.226
    echo
done
```

This sends six HTTP requests to the load balancer and prints each response.

If both backends return distinguishable HTML, you should be able to identify which server handled each request.

For easier testing, you can temporarily place a different marker in each backend's response, provided you do not
overwrite application files or configurations that you need to preserve.

# NGINX Load Balancing: SSL Termination vs. End-to-End Encryption

## 1. Overview

When using NGINX as an HTTPS load balancer, **the upstream application servers do not necessarily need SSL/TLS
configured**. Whether they require HTTPS depends on how NGINX forwards requests to them.

There are two common architectures:

1. **SSL Termination:** NGINX decrypts incoming HTTPS traffic and forwards requests to backend servers using HTTP.
2. **End-to-End Encryption:** NGINX decrypts incoming HTTPS traffic, then encrypts it again before forwarding requests
   to backend servers using HTTPS.

The appropriate architecture depends on your security requirements, network environment, performance considerations, and
compliance obligations.

## 2. Comparing the Two Architectures

| Configuration         | NGINX Upstream Protocol | Backend SSL/TLS Required? | Typical Use Case                                                                               |
|-----------------------|-------------------------|---------------------------|------------------------------------------------------------------------------------------------|
| SSL Termination       | `http://`               | No                        | Applications behind a load balancer on a trusted private network                               |
| End-to-End Encryption | `https://`              | Yes                       | Sensitive workloads, untrusted networks, and environments requiring encrypted internal traffic |

**Important:** HTTPS between the client and NGINX does not automatically encrypt traffic between NGINX and the upstream
servers. That depends on the upstream protocol configured in `proxy_pass`.

---

## 3. SSL Termination

### 3.1 How It Works

SSL termination means that NGINX handles the TLS connection with the client.

The process works as follows:

1. A client establishes an HTTPS connection to NGINX.
2. NGINX uses its TLS certificate and private key to establish the secure connection.
3. NGINX decrypts the incoming HTTP request.
4. NGINX forwards the request to an upstream application server using ordinary HTTP.
5. The application server processes the request and returns its response.
6. NGINX sends the response back to the client over HTTPS.

The traffic between NGINX and the upstream servers is unencrypted HTTP.

### 3.2 Architecture

```text
Client
  |
  | HTTPS (port 443)
  v
NGINX Load Balancer
  |
  | TLS termination and decryption
  |
  | HTTP (port 80)
  v
Upstream Application Servers
```

### 3.3 Configuration Example

```nginx
http {
    upstream my_backend_servers {
        server 10.0.0.1:80;
        server 10.0.0.2:80;
    }

    server {
        listen 443 ssl;
        server_name example.com;

        ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

        location / {
            proxy_pass http://my_backend_servers;

            # Preserve the original hostname
            proxy_set_header Host $host;

            # Forward the client's IP address
            proxy_set_header X-Real-IP $remote_addr;

            # Preserve the proxy forwarding chain
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

            # Inform the application that the original request used HTTPS
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}
```

### 3.4 Explanation

- `listen 443 ssl;` configures NGINX to accept HTTPS connections.
- `ssl_certificate` specifies the certificate presented to clients.
- `ssl_certificate_key` specifies the corresponding private key.
- `upstream my_backend_servers` defines the backend server group.
- `proxy_pass http://my_backend_servers;` forwards requests using HTTP rather than HTTPS.
- `proxy_set_header Host $host;` forwards the original hostname.
- `proxy_set_header X-Real-IP $remote_addr;` passes the client IP address observed by NGINX.
- `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` maintains the forwarded client-IP chain.
- `proxy_set_header X-Forwarded-Proto $scheme;` tells the application which protocol the client used to connect to
  NGINX.

Because the upstream connection uses HTTP, the backend servers do not need TLS certificates for this connection. They
can listen on port 80 or another configured HTTP port.

### 3.5 Advantages

- TLS certificate management is centralized at NGINX.
- Backend servers do not need to handle TLS for connections from NGINX.
- Reduces TLS processing overhead on backend application servers.
- Simplifies the configuration of internal application services.
- Works well when the NGINX-to-backend network is appropriately secured and trusted.

### 3.6 Limitations

- Traffic between NGINX and the upstream servers is not encrypted.
- Anyone who can observe that network traffic may be able to inspect its contents.
- A private network does not automatically eliminate the risk of interception or unauthorized access.

**Best practice:** Use SSL termination when the internal network and security requirements permit unencrypted upstream
traffic. Restrict access to backend servers so that clients cannot bypass NGINX and connect directly when that is not
intended.

## 4. End-to-End Encryption

### 4.1 How It Works

With end-to-end encryption in this architecture, the client-to-NGINX connection uses HTTPS, and the NGINX-to-backend
connection also uses HTTPS.

NGINX terminates the client's TLS connection, processes the HTTP request, and establishes a separate TLS connection to
the selected upstream server.

The two TLS connections are independent. NGINX decrypts the incoming request and encrypts it again when forwarding it
upstream.

### 4.2 Architecture

```text
Client
  |
  | HTTPS (port 443)
  v
NGINX Load Balancer
  |
  | TLS termination
  | Request processing
  | New TLS connection
  |
  | HTTPS (port 443)
  v
Upstream Application Servers
```

This protects traffic on both network segments, provided that TLS is configured correctly and certificate verification
is appropriately enforced.

### 4.3 Upstream Requirements

When `proxy_pass` uses HTTPS, the upstream servers must support TLS.

Typically, each backend server:

- Listens on an HTTPS port, commonly port 443.
- Presents a TLS certificate.
- Has a corresponding private key.
- Presents a certificate that NGINX can validate when upstream certificate verification is enabled.

A certificate can be issued by a public certificate authority or an internal certificate authority. Self-signed
certificates are also possible, but NGINX must be configured to trust the appropriate certificate or authority if
verification is enabled.

### 4.4 Configuration Example

```nginx
http {
    upstream my_backend_servers {
        server 10.0.0.1:443;
        server 10.0.0.2:443;
    }

    server {
        listen 443 ssl;
        server_name example.com;

        # Certificate presented to clients
        ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

        location / {
            # Forward requests using HTTPS
            proxy_pass https://my_backend_servers;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            # Verify upstream TLS certificates
            proxy_ssl_verify on;
            proxy_ssl_trusted_certificate /etc/nginx/ssl/backend_ca.crt;

            # Verify the expected upstream certificate name
            proxy_ssl_server_name on;
            proxy_ssl_name backend.example.internal;
        }
    }
}
```

### 4.5 Explanation

- `proxy_pass https://my_backend_servers;` tells NGINX to establish HTTPS connections to the upstream servers.
- `proxy_ssl_verify on;` enables verification of the upstream server's certificate.
- `proxy_ssl_trusted_certificate` specifies the trusted CA certificates used to validate the upstream certificate chain.
- `proxy_ssl_server_name on;` enables SNI (Server Name Indication) for the upstream TLS connection.
- `proxy_ssl_name backend.example.internal;` specifies the name used for upstream certificate verification and SNI.

**Important:** The example assumes that both upstream servers can present certificates valid for
`backend.example.internal`. If the backend servers use different certificate names, configure the upstream TLS naming
appropriately for your architecture.

By default, upstream certificate verification is disabled in NGINX. Enabling it and configuring the trusted CA is
important when the upstream connection must be authenticated, not merely encrypted.

### 4.6 Advantages

- Encrypts traffic between NGINX and backend servers.
- Helps protect sensitive information transmitted across internal or untrusted networks.
- Supports security architectures that require encrypted service-to-service communication.
- Allows upstream server identities to be verified through TLS certificate validation.

### 4.7 Limitations

- Requires TLS configuration and certificate management on backend servers.
- Adds TLS processing overhead to NGINX and upstream servers.
- Requires appropriate trust configuration and certificate renewal procedures.
- Incorrect certificate verification settings can leave upstream connections vulnerable to impersonation.

**Best practice:** For sensitive workloads, enable upstream certificate verification and use certificates issued by a
trusted internal or public CA. Encryption without proper certificate verification does not provide the same protection
against impersonation.

---

## 5. Important Distinction: Two Separate TLS Connections

Even with HTTPS on both sides, NGINX is normally a TLS termination point rather than a transparent TLS tunnel.

The connections are:

1. Client to NGINX: TLS session using the certificate configured on NGINX.
2. NGINX to upstream: Separate TLS session using the certificate presented by the backend server.

This is often called TLS re-encryption or TLS termination with encrypted upstream connections.

If you need to forward the original TLS connection without decrypting its contents, that is a different architecture and
typically involves TCP-level proxying with the NGINX Stream module rather than ordinary HTTP reverse proxying.

---

## 6. Comparison: SSL Termination vs. End-to-End Encryption

| Feature                                  | SSL Termination                       | End-to-End Encryption                           |
|------------------------------------------|---------------------------------------|-------------------------------------------------|
| Client-to-NGINX traffic                  | HTTPS                                 | HTTPS                                           |
| NGINX-to-backend traffic                 | HTTP                                  | HTTPS                                           |
| Backend TLS configuration                | Not required                          | Required                                        |
| Backend TLS certificates                 | Not required for this connection      | Required                                        |
| Internal traffic encrypted               | No                                    | Yes                                             |
| TLS configuration complexity             | Lower                                 | Higher                                          |
| TLS processing on backends               | Not required                          | Required                                        |
| Upstream certificate verification        | Not applicable to HTTP                | Recommended and important for authenticated TLS |
| Suitable for untrusted internal networks | No, not without additional protection | Yes, when correctly configured                  |

---

## 7. Choosing the Right Architecture

### Choose SSL Termination When

- Your backend servers are on a suitably protected private network.
- Internal HTTP traffic is permitted by your security requirements.
- You want to centralize public-facing TLS configuration.
- You want to reduce TLS configuration and processing on application servers.

### Choose End-to-End Encryption When

- Traffic between NGINX and the backend must also remain encrypted.
- Backend servers communicate across an untrusted network.
- Your security policy requires TLS for internal service-to-service communication.
- You need upstream certificate verification to authenticate backend servers.

Neither approach is universally better. The correct choice depends on the threat model, internal network protections,
and applicable security requirements.
